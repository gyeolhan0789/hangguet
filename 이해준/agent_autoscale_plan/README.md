## 1. 목적 · 범위

지금은 서버 한 대(4 vCPU)에 앱 · 미디어 · AI가 모두 있다. 부하 테스트(S5)에서 CPU를 가장 많이 쓴 것은 **AI 면접관(에이전트, `a301-prod-ai-agent`)**이었고, 지속 가능 한계(서버 CPU 평균 40%)는 동시 화상 면접 **약 5건**이었다.

- **[결정]** 에이전트를 메인 서버에서 떼어 EC2 Auto Scaling Group(ASG)으로 띄운다. 메인 서버의 CPU는 BE · FE · 녹화(Egress · 합치기)가 쓴다
  - 왜: 에이전트는 면접 수에 비례해 CPU를 쓰는 유일한 AI 구성 요소이고(2장), 면접마다 독립이라 여러 대로 나누기 쉽다. LiveKit이 같은 이름의 에이전트 여러 대에 면접을 나눠 배정한다
- **[제안]** 먼저 **테스트 환경(EC2 테스트 서버)**에서 만들고 검증한 뒤 운영 반영을 정한다
  - 왜: 테스트 서버는 이미 EC2(VPC)라 ASG와 같은 망에 둘 수 있다. 운영은 Lightsail이라 VPC 피어링 같은 연결 작업이 더 필요하다(5.4)
- **[미정]** AI 작업자(ai-plan · ai-analysis) 동시 처리 늘리기. 하면 이 문서와 따로 한다
- 범위 밖: 미디어 서버(LiveKit · Egress) 분리. 동시 면접이 약 20건을 넘으면 필요하다(2장)

## 2. 근거(부하 테스트 실측)

| 항목 | 값 | 출처 |
|---|---|---|
| 에이전트 CPU | 면접 1건당 **약 0.12~0.16코어**(동시 10건 1.19~1.64코어) | [S5 보고서](../../loadtest/report/s5-2026-11-02.md) 3 · 9장 |
| 에이전트 메모리 | 기본 약 450MB + 1건당 약 45~50MB | S5 3 · 9장, [S0 보고서](../../loadtest/report/s0-2026-11-02.md) 7장 |
| 에이전트를 뺀 메인 서버 몫 | 기본 약 0.36코어 + 1건당 약 0.12코어(Egress · LiveKit · 합치기 · BE · FE) | S5 재측정 10건: 서버 68% − 에이전트 |
| 새 면접 거절 기준 | 머신 CPU 70%(livekit-agents 1.8.8 `load_threshold` 운영 기본값) | 테스트 서버 컨테이너에서 확인 |
| 면접 1건 길이 | 가짜 답변으로 약 2분(실제 약 10분 예상) | S5 |

에이전트를 떼면 메인 서버(4 vCPU)는 `0.36 + 0.12 × 동시 면접`코어가 된다. 지속 가능(40%) 약 10건, 몰림(70%) 약 20건이다. 그 위는 미디어 서버 분리가 필요하다.

### 2.1 수요 가정 **[제안]**

운영 사용량 데이터가 아직 적어 수요는 **가정**으로 둔다. 숫자를 바꾸면 아래 대수 · 비용이 같이 바뀐다.

| 구간 | 하루 중 | 동시 접속 | 그중 화상 면접 중 | 에이전트 필요 대수(대당 목표 5건) |
|---|---|---|---|---|
| 한산 | 0~9시(9시간) | 0~10명 | 0~2건 | 1(최소) |
| 평소 | 9~19시(10시간) | 30명 | 약 6건(20%) | 2 |
| 저녁 몰림 | 19~23시(4시간) | 100명 | **약 20건**(20%) | 4 |
| 이벤트(발표 · 채용 시즌 직후) | 월 4번, 1시간 | 100명 | 약 20건이 몇 분 안에 시작 | 4(예약 확장으로 미리) |

- 왜 20%: 동시 접속자 대부분은 기록 · 결과 · 마이페이지를 본다고 본다(S1의 화면 부하 쪽). 면접은 1건 약 10분이라 접속 시간 중 일부다
- 왜 동시 면접 최대 20건: 에이전트를 뗀 뒤 메인 서버가 버티는 몰림 한계가 약 20건이다(2장). 이 단계에서는 그 이상을 받지 않는다. 동시 100건은 미디어 서버 분리 뒤 같은 ASG의 최대 대수(12대)로 받는다

### 2.2 고정 대수와 비교 **[제안]**

| 방식 | 계산(월 730시간, `t3.medium` 대당 시간당 약 $0.061 = 인스턴스 $0.052 + IP · 디스크) | 월 비용 |
|---|---|---|
| 몰릴 때 기준 고정 4대 | 4대 × 730시간 × $0.061 + 바쁠 때 초과 요금 | 약 $180 + α |
| **ASG(2.1 가정)** | 한산 1대 × 9시간 + 평소 2대 × 10시간 + 저녁 4대 × 4시간 = 하루 45대 · 시간 → 월 약 1,370대 · 시간 × $0.061 + 이벤트 몇 대 · 시간 | **약 $85 + α** |
| (참고) 메인 서버 안에 두기(지금) | 추가 비용 없음 | 동시 면접 지속 약 5건이 한계(S5) |

- α(unlimited 초과 요금)는 두 방식이 비슷하다. 면접 수가 같으면 쓰는 CPU가 같기 때문이다
- 하루 중 수요 차이가 4배(1대 ~ 4대)라 ASG가 고정 대수의 약 절반이다. 수요가 하루 종일 일정하다면 고정 대수가 더 단순하다. 이 판단은 가정에 기대므로, 운영 데이터가 쌓이면 다시 계산한다

## 3. 구조

```
                         ┌──────────── 메인 서버(테스트: EC2 t3.xlarge) ─────────────┐
 사용자 ── Cloudflare ── │ nginx · FE · BE · Postgres · Redis · AI 작업자 · 모니터링   │
   │                     │ LiveKit(시그널링 7880 · 미디어 UDP 7882 · TURN 443) · Egress │
   │  WebRTC(UDP 7882)   └──────▲────────────────────────▲──────────────────────────┘
   └────────────────────────────┘                        │ 사설망: LiveKit 7880 · Redis 6379
                                              ┌──────────┴───────────────┐
                                              │ 에이전트 ASG(1~N대)        │
                                              │  a301-ai-agent 컨테이너 1개 │
                                              └──────────────────────────┘
```

- 에이전트는 LiveKit에 "작업자"로 등록하고(이름 `a301-interviewer`), BE가 면접방을 만들 때 그 이름으로 배정을 요청한다. LiveKit은 부하가 기준(70%) 아래인 작업자에게 면접을 준다
- 에이전트는 면접 중 Redis(`ai:results`)에 질문 · 답변 결과를 넣는다(`ResultPublisher`). 그래서 LiveKit과 Redis 둘 다 닿아야 한다
- 메인 서버의 `a301-prod-ai-agent`는 끈다(테스트는 compose 덮어쓰기로 0개). 모든 면접이 ASG로 간다

## 4. 에이전트 인스턴스

| 항목 | 값 | 상태 |
|---|---|---|
| 인스턴스 종류 | `t3.medium`(2 vCPU · 4GB, x86), **크레딧 모드 unlimited**(시작 템플릿에 명시) | **[결정]** |
| 대당 면접 | 약 **9건**에서 새 면접 거절(2 × 0.7 ÷ 0.16 ≈ 8.8). 평소 목표 **5건**(6.2) | **[결정]** |
| 메모리 | 9건이면 약 0.9GB. 컨테이너 상한 3g(운영 4g에서 인스턴스 메모리에 맞춰 줄임) | **[제안]** |
| 디스크 | gp3 30GB(이미지 · 로그) | **[제안]** |
| AMI | Amazon Linux 2023 + Docker. 처음에는 user data로 설치, 시작 시간이 길면 Docker · 이미지를 넣은 AMI로 바꾼다 | **[제안]** |
| 컨테이너 | 운영과 같은 AI 이미지 `hanggeut/a301:ai-<태그>`, 명령 `python -m app.agent.main start` | **[제안]** |

- 왜 `t3.medium`: 에이전트는 대부분 시간 면접이 거의 없고 몰릴 때만 CPU를 쓴다. 놀 때(최소 1대 상시) 시간당 약 $0.052로 `c7i.xlarge`(약 $0.20)의 약 1/4이고, 꽉 찰 때도 면접 1건 · 1시간당 비용이 비슷하다(약 $0.011 대 $0.012, 11장)
- 왜 unlimited: T3 기준치는 vCPU당 20%(대당 0.4코어)라 standard면 면접 2~3건을 넘는 순간 크레딧이 바닥나 0.4코어로 묶인다. unlimited는 기준치를 넘는 만큼 초과 요금(vCPU · 시간당 $0.05)을 내고 계속 쓴다
- 왜 `t4g`(ARM)가 아닌가: AI 이미지는 x86(amd64) 전용으로 빌드한다. arm64 빌드(CI `buildx`)와 네이티브 패키지 확인이 먼저 필요하다. 요금 차이(약 20%)보다 일이 크다
- 작은 인스턴스의 장단: 한 대가 죽어도 끊기는 면접이 최대 약 9건으로 적다. 대신 같은 면접 수에 대수가 많고(100건 약 12대), 면접마다 새 프로세스를 띄우는 구조(`num_idle_processes=0`)라 여러 면접이 동시에 시작하면 2 vCPU에서 첫 질문이 늦어질 수 있다(9장에서 확인)

## 5. 네트워크 · 연결

### 5.1 에이전트 → LiveKit **[제안]**

- 시그널링: 메인 서버 사설 IP의 7880(`ws://<사설 IP>:7880`). 메인 서버 compose에서 7880을 사설 IP에만 열고, 보안 그룹은 에이전트 보안 그룹에서 오는 것만 허용한다
  - 왜: 지금 공개 경로(`wss://rtc-lt…`, Cloudflare Tunnel)로도 붙지만, 사설망이 지연이 적고 Cloudflare를 거치지 않는다
- 미디어: 에이전트도 사용자처럼 LiveKit이 알려 주는 주소(공인 IP의 UDP 7882)로 붙는다. **같은 VPC 안이라도 공인 IP를 거치면 전송 요금이 붙을 수 있다**(11장 확인 필요). 사설 IP 후보를 알리게 하는 LiveKit 설정을 확인한다

### 5.2 에이전트 → Redis **[제안]**

- 지금 Redis는 비밀번호가 없고 내부 Docker 망에만 있다. AI 코드(`ai/app/common/redis.py`)에도 비밀번호 설정이 없다
- 테스트 환경: 메인 서버 compose에서 6379를 **사설 IP에만** 열고 보안 그룹으로 에이전트만 허용한다
- 운영 반영 전: Redis 비밀번호(`requirepass`)를 켠다. BE(`spring.data.redis.password`) · LiveKit · Egress(`redis.password`)는 설정만, AI는 `REDIS_PASSWORD`를 읽도록 코드 수정이 필요하다
  - 왜: Redis에는 리프레시 토큰 · 작업 큐가 있다. 망을 열면 보안 그룹 하나에만 기대게 된다

### 5.3 에이전트 → 외부 API

- Soniox(STT) · ElevenLabs(TTS) · Jev(리액션)를 인터넷으로 부른다. 퍼블릭 서브넷 + 퍼블릭 IP(또는 NAT)가 필요하다 **[제안: 퍼블릭 서브넷]**
  - 왜: NAT 게이트웨이는 시간당 요금이 있다. 에이전트는 받는 포트가 없어 보안 그룹으로 들어오는 것을 모두 막으면 된다

### 5.4 운영(Lightsail)일 때 **[미정]**

- Lightsail과 같은 리전 VPC를 피어링하면 사설 IP로 서로 닿는다. 보안 그룹 · Lightsail 방화벽을 서로의 대역으로 연다
- 또는 운영 메인 서버를 EC2로 옮긴다. 이건 배포 계획 결정이 필요하다

## 6. 확장 · 축소

### 6.1 ASG **[제안]**

| 항목 | 값 | 왜 |
|---|---|---|
| 최소 · 원하는 · 최대 | 1 · 1 · 12 | 최소 1대는 늘 받을 수 있게. 이 단계의 수요 가정(2.1)으로는 최대 4대면 된다. 최대 12대 ≈ 동시 100건(대당 약 9건)은 미디어 서버 분리 뒤를 위한 값 |
| 예약 확장 | 매일 19시 원하는 대수 4, 23시 1. 이벤트는 시작 10분 전 4 | 저녁 몰림 · 이벤트는 시간을 안다(2.1). 확장 지연(3~4분) 동안 거절을 막는다 |
| 서브넷 | 테스트 서버와 같은 VPC의 퍼블릭 서브넷 2개(가용 영역 둘) | 한 영역 장애 대비 |
| 상태 확인 | EC2 상태 확인 + 컨테이너 헬스체크(8081)는 user data의 감시 스크립트가 보고 | 컨테이너가 죽으면 인스턴스를 바꾼다 |
| 인스턴스 준비 시간(warmup) | 180초(실측 후 조정) | 이미지 받기 · 등록까지 |

### 6.2 확장 지표 **[제안]**

- **대당 진행 중 면접 수**(`a301_agent_active_interviews`, 에이전트가 이미 9464 포트로 낸다)를 CloudWatch 사용자 지표로 1분마다 보낸다
- **목표 추적: 대당 평균 5건.** 넘으면 늘리고 한참 밑이면 줄인다
  - 왜 5: 거절 기준(약 9건)까지 4건 여유가 있다. 한 대가 새로 뜨는 3~4분 동안 들어오는 면접을 기존 대가 받아야 한다. 최소 1대일 때 3~4분 안에 5건 넘게 몰리면 예약 확장으로 미리 늘린다
  - 왜 CPU가 아닌가: CPU는 면접이 끝난 뒤의 결과 생성 등과 섞이고, 거절 기준이 CPU라 목표를 그 근처에 두면 늘리기 전에 거절이 먼저 난다. 면접 수는 사용자 수와 바로 맞물린다
- **예약 확장**: 발표 · 시연처럼 시간을 아는 몰림은 미리 원하는 대수를 올려 둔다
- 안전장치: CPU 평균 60% 경보 → 1대 추가(단계 확장)

### 6.3 줄일 때 진행 중 면접 보호 **[제안]**

ASG가 인스턴스를 줄이면 그 인스턴스의 면접이 끊긴다. 그래서 종료를 늦추고 면접이 끝날 때까지 기다린다.

1. ASG **수명 주기 훅**(`autoscaling:EC2_INSTANCE_TERMINATING`, 하트비트 1800초)으로 종료를 대기 상태에 둔다
2. 인스턴스의 감시 스크립트가 IMDS(`/latest/meta-data/autoscaling/target-lifecycle-state`)에서 `Terminated`를 보면 `docker stop --time 1800 a301-ai-agent`
3. 에이전트(livekit-agents)는 SIGTERM을 받으면 **새 면접을 받지 않고(drain) 진행 중인 면접이 끝날 때까지 기다린다**. `drain_timeout` 기본 3600초를 1800초로 맞춘다
4. 컨테이너가 끝나면 `aws autoscaling complete-lifecycle-action`으로 종료를 진행한다

- 왜 1800초: 실제 면접은 약 10분, 결과 생성은 BE · AI 작업자가 하므로 에이전트는 면접방이 끝나면 놓인다. 여유를 두 배 이상 뒀다
- 축소 보호: 진행 중인 면접이 있는 인스턴스에 축소 보호(scale-in protection)를 켜는 방법도 있다. 수명 주기 훅만으로 되는지 먼저 본다

### 6.4 늘어나는 동안

- 새 인스턴스가 준비되기 전에 모든 대가 거절 기준을 넘으면, LiveKit이 면접을 배정하지 못해 **면접관이 들어오지 않는다**(부하 테스트 H6, 첫 질문 2분 초과로 실패). 6.2의 여유(대당 5건 목표)와 예약 확장으로 막는다
- BE에 배정 실패를 다시 시도하거나 "잠시 후" 안내를 주는지 확인한다(11장)

## 7. 배포 · 버전

- **[제안]** 이미지 태그와 비밀값은 **SSM Parameter Store**에 둔다(`/a301/loadtest/ai-image-tag`, `/a301/loadtest/agent/*`, 보안 문자열)
  - user data가 인스턴스 역할로 읽어 `docker run`에 넘긴다. 비밀값을 시작 템플릿에 적지 않는다
- **[제안]** 새 버전 배포: 태그 매개변수를 바꾸고 ASG **인스턴스 새로 고침**(최소 정상 비율 100%, 6.3의 drain을 거침)
  - 왜: 에이전트와 BE가 같은 명세 버전이어야 한다. 메인 서버 배포(`deploy/prod/deploy.sh`) 뒤에 새로 고침을 이어서 한다
- **[제안]** 이미지 받기: 처음에는 Docker Hub 읽기 토큰(SSM)을 쓴다. 시작 시간이 길거나 토큰 관리가 번거로우면 ECR로 옮긴다
- 운영 CI/CD 연결은 운영 반영을 정한 뒤에 한다

## 8. 모니터링

- **[제안]** 메인 Prometheus가 에이전트 지표(9464)를 EC2 서비스 탐색(`ec2_sd_configs`, 태그 `a301-role=agent`)으로 찾아 수집한다. Grafana에 "에이전트 대수 · 대당 면접 · CPU" 줄을 더한다
- CloudWatch: ASG 원하는 · 실행 중 대수, 6.2 사용자 지표, 수명 주기 대기 시간, **`CPUSurplusCreditsCharged`**(unlimited 초과 요금), CPU steal
  - 왜: T3는 기준치를 넘는 만큼 요금이 붙고, 같은 호스트의 다른 인스턴스 영향(steal)을 받을 수 있다. 부하 테스트 서버(t3.xlarge)에서 steal이 최대 4.8%까지 보였다
- 로그: 처음에는 인스턴스 로컬(docker logs). 필요하면 Alloy로 메인 Loki에 보낸다
