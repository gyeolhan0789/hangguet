## 1. 목적 · 범위

지금은 서버 한 대(4 vCPU)에 앱 · 미디어 · AI가 모두 있다. 이 문서에서 **메인 서버**는 이 서버를 말한다. 운영 메인 서버는 **SSAFY 계정의 EC2 `t3.xlarge`**다(11/03 인스턴스 정보로 확인, 팀에서는 "Lightsail"이라고 불러 왔다). 테스트 메인 서버는 우리 계정 EC2 `t3.xlarge`다. 부하 테스트(S5)에서 CPU를 가장 많이 쓴 것은 **AI 면접관(에이전트, `a301-prod-ai-agent`)**이었고, 지속 가능 한계(서버 CPU 평균 40%)는 동시 화상 면접 **약 5건**이었다.

- **[결정]** 에이전트를 메인 서버에서 떼어 EC2 Auto Scaling Group(ASG)으로 띄운다. 메인 서버의 CPU는 BE · FE · LiveKit · 녹화 합치기가 쓴다(Egress도 떼기로 함, 아래)
  - 왜: 에이전트는 면접 수에 비례해 CPU를 쓰는 유일한 AI 구성 요소이고(2장), 면접마다 독립이라 여러 대로 나누기 쉽다. LiveKit이 같은 이름의 에이전트 여러 대에 면접을 나눠 배정한다
- **[결정] 방식: EC2 ASG + 인스턴스 안 감시 스크립트**(지표 보내기 · 축소 보호 · 수명 주기 처리 · 서비스 준비 확인, 6장)
  - 비교한 대안
    - 관리형 에이전트 호스팅(LiveKit Cloud 에이전트 배포 등): 미디어 서버를 셀프 호스팅하기로 했고, 구조를 직접 다루지 않게 된다
    - ECS(EC2 기반): 작업 축소 보호 · 관리형 종료 보호 · 서비스 오토스케일링으로 감시 스크립트 대부분이 필요 없다. 비용은 A와 같다(ECS 자체 무료, 같은 EC2). 대신 클러스터 · 작업 정의 · 용량 공급자를 새로 만들고 Tailscale 연결을 다시 설계해야 한다
    - ECS(Fargate): 놀 때 비용이 약 4배(2 vCPU · 4GB 시간당 약 $0.11 대 `t3.small` 약 $0.026)이고 종료 대기가 최대 120초다
    - Kubernetes: 1~5대 규모에 운영 부담이 크다
  - 왜 A: 비용은 ECS(EC2)와 같고, 11/03에 테스트한 구성(user data · SSM · ASG)을 그대로 이어 간다. 남은 기간에 새 오케스트레이터를 익히고 다시 검증하는 것보다 감시 스크립트를 만드는 일이 작다. 축소 보호 · drain을 직접 구현해 동작을 설명할 수 있다
- **[결정]** 먼저 **테스트 환경(EC2 테스트 서버)**에서 만들고 검증한 뒤 운영에 반영한다
  - 왜: 테스트 서버는 우리 계정 EC2라 ASG와 같은 VPC에 둘 수 있다. 운영 메인 서버는 SSAFY 계정이라 연결 방법이 다르다(5.4)
  - 11/03 테스트 환경 1 · 2단계 완료(같은 5건에서 메인 서버 CPU 44% → 24%, [scale out 보고서](../../loadtest/report/scaleout-2026-11-03.md))
- **[결정] 운영 구성**: 에이전트는 **전부 ASG**(메인 서버 안에 남기지 않음), 메인 서버는 **LiveKit + 웹(BE · FE · DB) + AI 작업자**를 맡는다. 녹화(Egress)도 메인 서버에서 떼어 **에이전트와 다른 ASG**로 띄운다(아래, 11/05)
  - 왜: 예산이 제약이 아니어서(11장 비용) 메인 서버 CPU를 가장 많이 비우는 쪽을 골랐다. 메인 서버 안에 일부를 남기는 안(하이브리드)은 놀 때 비용이 0이지만, 동시 10건에서 메인 서버 CPU가 약 35% → 45%로 올라 지속 가능 기준(40%)을 넘는다
- **[결정] Egress도 ASG로 뗀다(11/05). 에이전트와 같은 인스턴스에 두지 않고 ASG를 따로 둔다**(4.2 · 5.5 · 6.5)
  - 왜 떼나: 에이전트를 뗀 뒤 메인 서버에서 가장 큰 몫이 Egress다(10건 0.45코어 · 743MB **[실측]**, 2.3). Egress도 면접 수에 비례해 CPU · 메모리를 쓰고 면접마다 독립이라 여러 대로 나눌 수 있다. 메인 서버에 두면 상한을 3g로 올려도 면접 수와 함께 계속 커진다. 떼면 메인 서버는 면접 수에 덜 묶이는 LiveKit · 웹만 남는다
  - 왜 따로(같은 인스턴스에 두지 않나): **두 서비스의 거절 판정이 서로의 CPU를 보지 않는다.** livekit-agents는 cgroup v2에서 자기 컨테이너 CPU만 재고(`livekit/agents/utils/hw/cpu.py`), Egress도 자기 녹화 CPU만 센다(S5 보고서 7장). 같은 대에 두면 에이전트가 70%(약 9건)까지 받는 동안 Egress 몫이 더해져 서버가 90%를 넘고, 두 판정 모두 이를 막지 못한다. 막으려면 `load_threshold`를 낮추거나 컨테이너 `cpus`를 나눠야 해 대당 약 4건(목표) · 7건(한계)로 준다 **[추정]**. 또 LiveKit이 면접의 에이전트와 녹화를 서로 다른 대에 배정해 축소 보호 조건이 얽힌다. 따로 두면 각 ASG의 CPU가 곧 자기 부하라 거절 · 확장 기준이 맞는다
  - 손해: 상시 최소 대수가 1 → 2대가 되어 월 약 $45가 는다(11장 비용). 시작 템플릿 · 역할 · 감시 스크립트가 두 벌이지만 구조는 같다
- **[결정] AI 작업자는 메인 서버에 남긴다.** `ai-plan` · `ai-analysis`는 2개씩으로 늘릴 계획이지만 **에이전트 전환과 따로, 실측한 뒤 적용한다**: `ai-plan` 2 · `ai-analysis` 2 · `ai-recording` 1 · `ai`(상태 확인 HTTP) 1. compose에서는 `container_name`을 쓰므로 서비스를 `-1` · `-2`로 나눈다
  - 왜 남기나: 작업자는 면접마다 생기지 않고 종류별 1개가 큐를 한 줄로 처리한다. CPU를 거의 쓰지 않아(GMS 응답 대기) 빼도 메인 서버가 가벼워지지 않고, 늘리는 기준(큐 길이)도 에이전트(진행 중 면접 수)와 달라 같은 ASG에 넣지 않는다
  - 왜 2개: 문제는 자원이 아니라 한 줄 대기였다 **[실측]**(S4 질문 준비 최대 182초, 2단계 10건 결과 대기 평균 230초). 2개면 대기가 대략 절반 **[추정]**이지만 GMS 처리량 · 재시도에 따라 달라 실측으로 확인한다. 합치기는 ffmpeg가 순간 최대 1코어씩이라 늘리지 않는다(다시보기 대기 최대 3초 **[실측]**)
  - 왜 따로: 에이전트 전환과 같이 바꾸면 결과가 나빠졌을 때 원인을 가르기 어렵다
  - 같은 큐에 2개면, 하나만 재시작될 때 다른 작업자가 처리 중이던 작업까지 되돌려 한 번 더 처리한다(`ai/app/worker/queue.py`). 데이터는 깨지지 않는다: EVALUATE는 BE가 작업을 넣는 시점의 채점값을 메시지에 담아 가고(없으면 직접 채점), BE가 중복 결과를 한 번만 저장한다(AI 명세 1.3 · 4장). 손해는 GMS 호출 · 비용 · 요청 한도다. 작업자별 처리 중 목록은 AI 개선으로 따로 요청한다
  - 확인: GMS 동시 요청 한도(동시 호출이 2배가 된다). 에이전트도 면접 중 꼬리질문으로 GMS를 부르므로(5.3) 한도를 같이 나눠 쓴다
- 작업 안 GMS 병렬 호출은 이 문서와 따로 한다(전환 조건 아님)
- 범위 밖
  - LiveKit(SFU) 분리. 메인 서버가 다음 한계(2.3)에 닿으면 필요하다
  - **메인 서버는 여전히 단일 장애점이다.** 에이전트 · Egress가 여러 대여도 LiveKit · Redis · BE가 한 서버에 있어, 그 서버가 죽으면 면접 전체가 멈춘다. 분리 전과 같고 이 문서가 바꾸지 않는다

## 2. 근거(부하 테스트 실측)

| 항목 | 값 | 출처 |
|---|---|---|
| 에이전트 CPU | 면접 1건당 **약 0.12~0.16코어**(동시 10건 1.19~1.64코어) | [S5 보고서](../../loadtest/report/s5-2026-11-02.md) 3 · 9장 |
| 에이전트 메모리 | 기본 약 450MB + 1건당 약 45~50MB | S5 3 · 9장, [S0 보고서](../../loadtest/report/s0-2026-11-02.md) 7장 |
| 에이전트를 뺀 메인 서버 몫 | 기본 약 0.36코어 + 1건당 약 0.12코어(Egress · LiveKit · 합치기 · BE · FE) | S5 재측정 10건: 서버 68% − 에이전트 |
| 새 면접 거절 기준 | 머신 CPU 70%(livekit-agents 1.8.8 `load_threshold` 운영 기본값) | 테스트 서버 컨테이너에서 확인 |
| 면접 1건 길이 | 가짜 답변으로 약 2분(실제 약 10분 예상) | S5 |

분리 전 S5로 계산했을 때는 에이전트를 떼면 메인 서버(4 vCPU)가 `0.36 + 0.12 × 동시 면접`코어가 되어, 지속 가능(40%) 약 10건 · 몰림(70%) 약 20건이었다 **[추정]**. 분리 뒤 실측으로 아래처럼 고쳤다.

- 11/03 분리 실측(2단계): 동시 5 · 8 · 10건에 메인 서버 CPU 24 · 32 · 35% **[실측]**. 이 기울기(1건 약 2%p)를 늘려 보면 지속 가능 **약 12~13건**, 몰림 **약 25건**이다 **[추정]**. 10건 위는 재지 않았고, 면접 몫만 본 값이라 로그인이 몰리면(BE 비밀번호 해시, S2 · S6) 더 낮아진다. 12~15건(지속 가능)과 20~25건(몰림 · 실패 동작)을 따로 잰다(9장)
- 분리 뒤 Egress는 기본 약 165MB + 1건당 약 58MB(10건 743MB) **[실측]**를 쓴다. 상한 3g면 약 50건 **[추정, 선형]**이라 CPU보다 먼저 막히지 않을 것으로 봤다. 11/05 Egress도 떼기로 해 대당 환산은 2.3에 따로 적는다

**에이전트 인스턴스(`t3.small`, 2 vCPU) 1대의 CPU** — 1대에 몰아 직접 잰 값은 아직 없다(9장 3단계). 아래로 환산한다. `t3.small`과 `t3.medium`은 vCPU(2개) · 기준치(vCPU당 20%)가 같고 메모리만 다르므로, `t3.medium`으로 잰 2단계 값도 그대로 쓴다.

| 기록 | 동시 면접 | 에이전트 CPU | 2 vCPU 환산 |
|---|---|---|---|
| S5 재측정(모든 브라우저가 면접방에 있는 2분 평균, 메인 서버 안) | 5 · 8 · 10건 | 0.73 · 1.02 · 1.19코어 | 약 37 · 51 · 60% |
| 대조군(메인 서버 안, 8분 평균) | 5건 | 0.51코어(최대 0.78) | 약 26%(최대 39%) |
| 원격 2대, 2단계 CloudWatch 5분 평균(11/03 13:00~13:40) | 대당 실제 진행 약 2~3건(반복 중 결과 대기 · 다시보기 시간이 섞임) | – | 대당 최대 약 21% |

- 면접 1건당 약 0.15코어(S5 재측정)가 가장 깨끗한 값이다. 메인 서버와 같은 T3 계열이라 코어 수로 나눠 환산했다. 2단계 원격 실측도 이와 어긋나지 않는다
- 환산 **[추정]**: 대당 5건 약 37%, CPU 40%(확장 목표, 6.2)는 약 5건, 새 면접 거절(70%)은 약 9~10건
- **위 값은 음성 조각이 10ms이던 이미지(`e9874c74`) 기준이다.** 100ms로 바꾼 develop 이미지를 개발 서버에서 재 보니 1건 약 0.18코어(N100)였고, 같은 서버의 변경 전후 차이로 환산하면 `t3`에서 1건 **약 0.1코어**다 **[추정]**([에이전트 CPU 보고서](../../loadtest/report/agent-cpu-dev-2026-11-05.md)). 그러면 대당 확장 목표(40%)는 약 7건, 거절(70%)은 약 13건이다. 대당 목표 5건 **[설정]**은 3단계를 develop 이미지로 잰 뒤 바꾼다
- **약 9~10건은 평균으로 본 값이다.** 면접을 받을 때마다 프로세스를 새로 띄워 CPU가 몇 초 튄다(새 인스턴스 첫 면접 0.97 **[실측]**). LiveKit은 5초 평균으로 거절하므로, 이미 여러 건이 진행 중인 대에 새 면접이 겹쳐 들어오면 평균상 여유가 있어도 잠깐 거절될 수 있다. 그래서 순간적으로 받을 수 있는 건수는 이보다 낮을 수 있다. 반대로 1건당 0.15코어는 2분짜리 가짜 면접에 기동 비용이 섞인 값이라, 실제 10분 면접에서는 평균이 더 낮을 수 있다. 두 효과를 3단계에서 "3초 간격 시작"과 "한꺼번에 시작"으로 나눠 잰다
- 기동 튐은 `num_idle_processes` 1 이상(`AGENT_IDLE_PROCESSES`, 반영됨)으로 줄인다. 새 인스턴스는 대기 프로세스가 준비된 뒤에 LiveKit에 등록해 첫 면접의 0.97이 없어지고(livekit-agents 1.8.8 코드로 확인), 이후에는 면접을 받는 순간이 아니라 그 직후에 다음 대기 프로세스를 띄운다
- 대당 처리량은 CPU만으로 정하지 않는다. 3단계에서 **첫 질문 시간**(원격은 이미 9~14초 **[실측]**), 새 면접 거절, 5초 단위 CPU 최대치를 같이 보고 확정한다. CPU 70% 전에 첫 질문이 너무 늦어지면 그 건수가 한계다
- 위 값은 2분 이상 평균이다. LiveKit은 5초 평균으로 거절을 판단하고, 새 인스턴스가 첫 면접을 받는 순간 0.97이 된 적이 있어 순간 거절은 이 표로 알 수 없다

### 2.1 수요 가정 **[제안]**

운영 사용량 데이터가 아직 적어 수요는 **가정**으로 둔다. 숫자를 바꾸면 아래 대수 · 비용이 같이 바뀐다.

| 구간 | 하루 중 | 동시 접속 | 그중 화상 면접 중 | 에이전트 필요 대수(대당 목표 5건) |
|---|---|---|---|---|
| 한산 | 0~9시(9시간) | 0~10명 | 0~2건 | 1(최소) |
| 평소 | 9~19시(10시간) | 30명 | 약 6건(20%) | 2 |
| 저녁 몰림 | 19~23시(4시간) | 100명 | **약 20건**(20%) | 4 |
| 이벤트(발표 · 채용 시즌 직후) | 월 4번, 1시간 | 100명 | 약 20건이 몇 분 안에 시작 | 4(예약 확장으로 미리) |

- 왜 20%: 동시 접속자 대부분은 기록 · 결과 · 마이페이지를 본다고 본다(S1의 화면 부하 쪽). 면접은 1건 약 10분이라 접속 시간 중 일부다
- 왜 동시 면접 최대 20건: 에이전트를 뗀 뒤 메인 서버가 버티는 몰림 한계(약 25건 **[추정]**, 2장)보다 낮게 잡았다. 이 단계에서는 그 이상을 받지 않는다. 동시 100건은 미디어 서버 분리 뒤 같은 ASG의 최대 대수(12대)로 받는다

### 2.2 고정 대수와 비교 **[제안]**

| 방식 | 계산(월 730시간, `t3.small` 대당 시간당 약 $0.036 = 인스턴스 $0.026 + IP · 디스크) | 월 비용 |
|---|---|---|
| 몰릴 때 기준 고정 4대 | 4대 × 730시간 × $0.036 + 바쁠 때 초과 요금 | 약 $105 + α |
| **ASG(2.1 가정)** | 한산 1대 × 9시간 + 평소 2대 × 10시간 + 저녁 4대 × 4시간 = 하루 45대 · 시간 → 월 약 1,370대 · 시간 × $0.036 + 이벤트 몇 대 · 시간 | **약 $50 + α** |
| (참고) 메인 서버 안에 두기(지금) | 추가 비용 없음 | 동시 면접 지속 약 5건이 한계(S5) |

- α(unlimited 초과 요금)는 두 방식이 비슷하다. 면접 수가 같으면 쓰는 CPU가 같기 때문이다
- 하루 중 수요 차이가 4배(1대 ~ 4대)라 ASG가 고정 대수의 약 절반이다. 수요가 하루 종일 일정하다면 고정 대수가 더 단순하다. 이 판단은 가정에 기대므로, 운영 데이터가 쌓이면 다시 계산한다

### 2.3 Egress(녹화) 근거 · 대당 환산 **[제안]**(11/05)

| 항목 | 값 | 출처 |
|---|---|---|
| 면접 1건의 녹화 | 트랙 3개(지원자 영상 · 음성, 면접관 음성). 녹화 수 = 면접 × 3 | S5 9.2 **[실측]** |
| Egress CPU | 8분 평균 5 · 8 · 10건에 0.25 · 0.35 · 0.45코어 → 1건 약 **0.04코어** + 기본 약 0.05. 시작이 몰린 2분 평균은 0.63 · 0.81 · 0.67코어(1건 최대 약 0.13) | scale out 5장 · S5 9.2 **[실측]** |
| Egress 메모리 | 기본 약 165MB + 1건 약 **58MB**(녹화 1개 약 21MB) | scale out 5장 · S5 9.2 **[실측]** |
| 녹화 1개 처리 | 요청마다 `egress run-handler` 자식 프로세스 하나 | Egress v1.15.0 `pkg/server/server_rpc.go` |
| 수락 판정 | `CPU 수 × 0.8 − 예약 − 녹화들의 실제 CPU ≥ 요청 비용`이면 받고, 비용을 15초 예약한다. `cpu_cost.max_memory`를 주면 메모리도 본다(`사용량 + 예약 + 요청 비용 + 1.0GB ≥ max_memory`면 거절, 1.0GB는 고정 여유) | S5 7장 · Egress v1.15.0 `pkg/stats/monitor.go` |

**Egress 인스턴스(`t3.medium`, 2 vCPU · 4GB) 1대** **[추정]**

| 기준 | 계산 | 건수 |
|---|---|---|
| 확장 목표(ASG 평균 CPU 40%, 0.8코어) | 8분 평균 기준 (0.8 − 0.05) ÷ 0.04~0.05, 시작이 몰린 구간 기준 ÷ 0.08 | 약 **10~15건** |
| 15초 안에 새로 받는 면접(빈 대) | 2 × 0.8 = 1.6 ÷ (트랙 3 × `track_cpu_cost` 0.1 = 0.3) | 약 **5건**(0.05로 낮추면 약 10건) |
| 15초 안에 새로 받는 면접(10건 녹화 중) | (1.6 − 0.45) ÷ 0.3 | 약 3건(0.05면 약 7건) |
| 메모리(컨테이너 3g) | (3GB − 165MB) ÷ 58MB | 약 48건. `max_memory` 3이면 1.0GB 여유 때문에 약 30건에서 거절 |

- CPU가 먼저 막는다. 메모리는 여유가 크다
- **15초 안에 몰려 시작할 때가 가장 먼저 막힌다.** 메인 서버(4코어)는 같은 계산으로 15초에 약 9~10건을 받았는데, 2코어 한 대는 절반이다. 거절되면 녹화가 조용히 빠진다(`no response from servers`, S5 요약 · 6장). 그래서 `track_cpu_cost`를 실제(녹화 1개 약 0.02~0.03코어)에 더 가깝게 0.05로 낮추고 **[제안]**, BE 녹화 누락 감지를 필수로 둔다(10.1)
- Egress만 `t3.medium`(에이전트는 `t3.small`)인 이유는 4.2

**Egress를 뗀 뒤 메인 서버** **[추정]**: 분리 2단계 실측(5 · 10건에 메인 서버 0.96 · 1.40코어)에서 Egress 몫(0.25 · 0.45)을 빼면 기본 약 0.47코어 + 1건 약 0.05코어다. 계산으로는 지속 가능(40%, 1.6코어) 약 23건, 몰림(70%) 약 48건이고, 여유를 두어 **지속 가능 약 20건**으로 본다. 10건 위는 재지 않았고, 합치기(ffmpeg 순간 최대 1코어) · 로그인 몰림(BE 비밀번호 해시)이 섞이면 더 낮아진다. 에이전트 ASG 최대 5대(대당 5건 = 25건, 6.1)는 그대로 두고 9장 결과를 보고 다시 정한다. 11/06부터는 웹 TLS도 Cloudflare가 아니라 메인 서버 Nginx가 풀어 CPU를 조금 더 쓴다. 이 몫은 분리 실측에 없으므로 9장 운영 경로 검증에서 함께 본다

## 3. 구조

테스트 서버(11/03, Cloudflare Tunnel을 쓰던 구성):

```
                         ┌──────────── 메인 서버(테스트: EC2 t3.xlarge) ─────────────┐
 사용자 ── Cloudflare ── │ nginx · FE · BE · Postgres · Redis · AI 작업자 · 모니터링   │
   │                     │ LiveKit(시그널링 7880 · 미디어 UDP 7882 · TURN 443) · Egress │
   │  WebRTC(UDP 7882)   └──────▲────────────────────────▲──────────────────────────┘
   └────────────────────────────┘                        │ 사설망: LiveKit 7880 · Redis 6379
                                              ┌──────────┴───────────────┐
                                              │ 에이전트 ASG(1~N대)        │
                                              │  a301-ai-agent 컨테이너 1개 │
                                              └──────────────────────────┘
```

- 에이전트는 LiveKit에 "작업자"로 등록하고(이름 `a301-interviewer`), BE가 면접방을 만들 때 그 이름으로 배정을 요청한다. LiveKit은 부하가 기준(70%) 아래인 작업자에게 면접을 준다
- 에이전트는 면접 중 Redis(`ai:results`)에 질문 · 답변 결과를 넣는다(`ResultPublisher`). 그래서 LiveKit과 Redis 둘 다 닿아야 한다
- 메인 서버의 `a301-prod-ai-agent`는 끈다(테스트는 compose 덮어쓰기로 0개). 모든 면접이 ASG로 간다

**운영 구조 [결정]**: 메인 서버가 SSAFY 계정이라 우리 계정 VPC와 사설망으로 이을 수 없다. 에이전트 · Egress와 메인 서버를 **Tailscale**(WireGuard) 사설망으로 잇고, 미디어만 공인 IP로 간다(5.4 · 5.5).

```
                    ┌──── 메인 서버(SSAFY 계정 EC2 t3.xlarge, 4 vCPU · 16GB) ───┐
 사용자 ─ TCP 443 ─▶ │ Nginx(SNI로 나눔): 웹 · rtc · grafana / TURN/TLS → LiveKit │
   │                 │ FE · BE · Postgres · Redis · AI 작업자 · 모니터링          │
   │                 │ LiveKit(SFU · TURN)                                    │
   │ UDP 7882 · TURN └──▲──────────────────────▲──────────────────────────────┘
   └────────────────────┘                      │ Tailscale: LiveKit 7880 · Redis 6379
                         UDP 7882(공인 IP) ─┐  │ (지표 · 로그는 8장)
                    ┌───────────────────────┴──┴─────────────────────────────┐
                    │ 우리 AWS 계정(기본 VPC, 서울 2a · 2b)                     │
                    │  에이전트 ASG: t3.small 1~5대                             │
                    │  Egress ASG:   t3.medium 1~2대 ──▶ S3 recordings/raw/    │
                    └────────────────────────────────────────────────────────┘
```

- 사용자 웹은 서버 443을 Nginx가 직접 받는다(11/06 Cloudflare 프록시 제거, Cloudflare는 DNS만, [배포 계획](../deploy_plan/README.md) 5.1). Nginx가 TLS를 풀지 않고 도메인 이름(SNI)만 보고 나눠, `hangguet.co.kr` · `rtc.` · `grafana.`는 Nginx HTTPS로 받고 그 밖(`turn.`)은 LiveKit TURN/TLS로 넘긴다. 에이전트 · Egress는 이 길을 쓰지 않는다(Tailscale로 7880 · 6379에 바로 붙는다)
- Egress는 에이전트와 같은 길로 붙는다: 시그널링(7880)과 LiveKit 사이 요청(Redis 6379)은 Tailscale, 녹화할 트랙(미디어)은 공인 IP의 UDP 7882로 받는다. 녹화 파일은 BE가 요청에 담아 보낸 S3 키로 바로 올린다(배포 계획 4.3, 지금과 같음)
- 녹화 합치기(`ai-recording`)는 메인 서버에 남는다. S3에서 원본을 받아 합치므로 Egress가 어디 있든 같다

## 4. 인스턴스

### 4.1 에이전트

| 항목 | 값 | 상태 |
|---|---|---|
| 인스턴스 종류 | **`t3.small`**(2 vCPU · 2GB, x86), **크레딧 모드 unlimited**(시작 템플릿에 명시) | **[결정]**(11/05, 처음 안 `t3.medium`) |
| 대당 면접 | 약 **9~10건**에서 새 면접 거절 **[추정]**(2장 환산, 100ms 이미지면 약 13건, 3단계에서 확정). 평소 목표 **5건 [설정]**(6.2) | 목표만 **[결정]** |
| 메모리 | 13건이면 약 1.0GB **[추정]**(대기 프로세스 2개일 때 기본 약 400MB + 1건 약 45~50MB). 컨테이너 상한 **1536m**. 나머지 약 0.5GB를 OS · Docker · Tailscale · Alloy · SSM 에이전트가 쓴다 | **[제안]**, 3단계에서 확인 |
| 디스크 | gp3 30GB(이미지 · 로그) | **[제안]** |
| AMI | Amazon Linux 2023 + Docker. 처음에는 user data로 설치, 시작 시간이 길면 Docker · 이미지를 넣은 AMI로 바꾼다 | **[제안]** |
| 컨테이너 | 운영과 같은 AI 이미지 `hanggeut/a301:ai-<태그>`, 명령 `python -m app.agent.main start` | **[제안]** |

- 왜 T3: 에이전트는 대부분 시간 면접이 거의 없고 몰릴 때만 CPU를 쓴다. 버스트형이라 놀 때 싸고, 꽉 찰 때도 초과 요금을 내고 계속 쓴다(11장)
- **왜 `t3.small`(`t3.medium`이 아니라)**: 두 종류는 vCPU(2개) · 기준치(vCPU당 20%) · 초과 요금이 같고 메모리만 2GB · 4GB로 다르다. 에이전트는 CPU가 먼저 막히고(거절 직전 약 13건에서도 메모리 약 1.0GB), `t3.medium`의 남는 2GB를 쓰지 않는다. 그래서 대당 처리량은 같고 요금은 절반(시간당 약 $0.026 대 $0.052)이다. 2.1 가정으로 월 약 $35가 준다(2.2 · 11장)
  - 손해: 메모리 여유가 작다. 대기 프로세스 수(`AGENT_IDLE_PROCESSES`, 기본값은 CPU 수 = 2)와 상한 1536m가 맞는지 3단계에서 메모리 최대치로 확인한다. 넘치면 상한을 지키는 쪽으로 대기 프로세스를 1개로 줄인다
  - Egress는 메모리 거절 판정 때문에 `t3.medium`에 둔다(4.2)
- 왜 unlimited: T3 기준치는 vCPU당 20%(대당 0.4코어)라 standard면 면접 2~3건을 넘는 순간 크레딧이 바닥나 0.4코어로 묶인다. unlimited는 기준치를 넘는 만큼 초과 요금(vCPU · 시간당 $0.05)을 내고 계속 쓴다
- 왜 `t4g`(ARM)가 아닌가: AI 이미지는 x86(amd64) 전용으로 빌드한다. arm64 빌드(CI `buildx`)와 네이티브 패키지 확인이 먼저 필요하다. 요금 차이(약 20%)보다 일이 크다
- 작은 인스턴스의 장단: 한 대가 죽어도 끊기는 면접이 최대 약 9~10건으로 적다. 대신 같은 면접 수에 대수가 많고(100건 약 12대), 면접마다 새 프로세스를 띄우는 구조(`num_idle_processes=0`)라 여러 면접이 동시에 시작하면 2 vCPU에서 첫 질문이 늦어질 수 있다(9장에서 확인)

| AMI | 에이전트와 같은 Amazon Linux 2023 + Docker, user data로 설치 | **[제안]** |
| 컨테이너 | 공식 이미지 `livekit/egress:v1.15.0`(버전 고정, 운영 LiveKit `v1.13.10`과 지금 짝). 설정은 지금처럼 `EGRESS_CONFIG_BODY`로 넣되 값은 SSM에서 읽는다(7장) | **[제안]** |

- 왜 `t3.medium`(`t3.small` 2GB가 아니라): 녹화는 CPU를 적게 써 `t3.small`로도 CPU는 비슷하게 받지만(같은 2 vCPU), 메모리 2GB에서는 `max_memory`의 고정 여유 1.0GB 때문에 메모리 거절을 쓸 수 없다. 그러면 몰릴 때 거절 대신 메모리가 넘쳐, 그 대의 녹화가 한꺼번에 잘릴 수 있다. 상시 1대 기준 월 약 $20 차이다. 에이전트(`t3.small`)와 종류만 다른 같은 T3 계열이라 시작 템플릿 · 감시 스크립트를 거의 그대로 쓴다
- 왜 unlimited: 기준치(대당 0.4코어)를 넘는 건수(약 8건 위)에서 standard면 크레딧이 바닥나 묶인다. 에이전트와 같은 이유다(4.1)
- 녹화 파일: 트랙 녹화가 S3에 올리기 전까지 로컬 임시 폴더에 쓰는지는 **[확인 필요]**(9장). 쓴다면 10분 녹화 1건이 수십~수백 MB라 30GB로 충분하다 **[추정]**
- 대당 건수가 에이전트(목표 5건)보다 많아, 같은 면접 수에 Egress 대수가 더 적다(25건이면 에이전트 5대 · Egress 2대)

## 5. 네트워크 · 연결

### 5.1 에이전트 → LiveKit **[제안]**

- 시그널링: 메인 서버 사설 IP의 7880(`ws://<사설 IP>:7880`). 메인 서버 compose에서 7880을 사설 IP에만 열고, 보안 그룹은 에이전트 보안 그룹에서 오는 것만 허용한다
  - 왜: 지금 공개 경로(`wss://rtc-lt…`, Cloudflare Tunnel)로도 붙지만, 사설망이 지연이 적고 Cloudflare를 거치지 않는다
- 미디어: 에이전트도 사용자처럼 LiveKit이 알려 주는 주소(공인 IP의 UDP 7882)로 붙는다. **같은 VPC 안이라도 공인 IP를 거치면 전송 요금이 붙을 수 있다**(11장 확인 필요). 사설 IP 후보를 알리게 하는 LiveKit 설정을 확인한다

### 5.2 에이전트 → Redis **[제안]**

- 지금 Redis는 비밀번호가 없고 내부 Docker 망에만 있다. AI 코드(`ai/app/common/redis.py`)에도 비밀번호 설정이 없다
- 테스트 환경: 메인 서버 compose에서 6379를 **사설 IP에만** 열고 보안 그룹으로 에이전트만 허용한다
- **[결정] 운영 반영 전 필수**: Redis 비밀번호(`requirepass`)를 켠다. BE(`spring.data.redis.password`) · LiveKit · Egress(`redis.password`)는 설정만, AI는 `REDIS_PASSWORD`를 읽도록 코드 수정이 필요하다
  - 왜: Redis에는 리프레시 토큰 · 작업 큐가 있다. 망을 열면 보안 그룹 하나에만 기대게 된다

### 5.3 에이전트 → 외부 API

- Soniox(STT) · ElevenLabs(TTS) · Jev(리액션) · **GMS(꼬리질문)**를 인터넷으로 부른다.
  - 꼬리질문(AI 명세 2.2, develop `0acb308`)은 에이전트가 면접 중 1 · 3번 답변 뒤 GMS로 만든다. 4초 안에 못 만들면 미리 만든 질문을 낸다. 에이전트 안에서 도는 일이라 ASG로 같이 옮겨 가고 구조는 바뀌지 않는다
  - GMS는 호출 IP를 제한하지 않는다(11/03 확인). 우리 계정 인스턴스의 공인 IP에서 그대로 부를 수 있다 퍼블릭 서브넷 + 퍼블릭 IP(또는 NAT)가 필요하다 **[제안: 퍼블릭 서브넷]**
  - 왜: NAT 게이트웨이는 시간당 요금이 있다. 에이전트는 받는 포트가 없어 보안 그룹으로 들어오는 것을 모두 막으면 된다

### 5.4 운영 메인 서버와 잇기 **[결정: Tailscale]**

운영 메인 서버는 **우리 계정이 아니다**(11/03 확인: 운영 서버 인스턴스 정보 문서의 계정 번호 ≠ 우리 계정 `A301` 번호). 인스턴스 정보로는 Lightsail이 아니라 SSAFY 계정의 EC2(`t3.xlarge`, 사설 IP `172.26.x.x`)다. 계정이 다른 VPC끼리도 피어링 자체는 되지만, SSAFY 계정에서 수락 · 라우팅 · 보안 그룹을 바꿔야 하고 우리는 그 계정 콘솔 권한이 없다. 그래서 우리 계정 ASG와 사설망으로 이을 수 없다(Lightsail이라도 피어링은 같은 계정 기본 VPC와만 되어 마찬가지다).

| 경로 | 방법 | 왜 |
|---|---|---|
| 시그널링(7880) | Tailscale. LiveKit 7880을 메인 서버의 **Tailscale IP에만** 연다(`LIVEKIT_URL=ws://<Tailscale IP>:7880`) | Redis(6379) 때문에 어차피 Tailscale이 필요해 같은 길을 쓴다. 11/06 Cloudflare 프록시를 걷어내 공개 주소(`wss://rtc.hangguet.co.kr`, Nginx 443)로도 붙을 수 있지만, 메인 서버에서 TLS · Nginx를 한 번 더 거친다 |
| Redis(6379) | Tailscale IP에만 연다 + 비밀번호(5.2) | 리프레시 토큰 · 작업 큐가 있는 Redis를 인터넷에 열지 않는다. ASG IP는 매번 바뀌어 IP 제한도 걸 수 없다 |
| 에이전트 지표 · 로그 | Tailscale(8장) | 같은 망을 다시 쓴다 |
| 미디어(UDP 7882) | 지금처럼 공인 IP | 브라우저와 같은 길이다. 테스트에서도 이 경로였다(사설 IP 미디어 실험은 TURN 브라우저가 깨져 원복) |

- 다른 방법을 뺀 이유: Redis를 공인으로 열기(TLS · 비밀번호)는 IP 제한을 못 걸어 보안 그룹 하나 없이 비밀번호에만 기댄다. 결과를 Redis 대신 BE HTTP로 보내기는 AI · BE 코드를 고치고 "AI ↔ BE는 Redis 큐로만" 결정([배포 계획](../deploy_plan/README.md) 1.1)을 뒤집는다
- 지연: Tailscale로 가는 것은 입장 때의 제어 메시지와 결과 큐 쓰기뿐이고, 음성 · 영상 · 리액션 · 상태 알림(데이터 채널)은 미디어 경로로 간다. 둘 다 서울 리전이라 직접 연결되면 1ms 안팎이 는다
- **[결정] 계정**: 팀 공용 계정으로 tailnet을 만든다(무료 Personal 플랜, 기기는 메인 1 + 에이전트 최대 5). 어떤 계정(팀 Google 계정 등)으로 할지는 **[미정]**. Personal 플랜은 개인 · 비상업 용도이고 1회용 기기 관련 조건이 있을 수 있어, 가입 전에 약관을 확인한다 **[확인 필요]**
  - 왜: 한 사람 계정에 묶이면 그 사람에게 문제가 생기거나 프로젝트가 끝난 뒤 운영 연결을 넘기기 어렵다
- **[결정] 에이전트 가입**: 가입 키 대신 **OAuth 클라이언트 비밀값**(SSM 보안 문자열 `/a301/prod/agent/tailscale-auth-key`)으로 부팅 때 가입한다. 태그 `tag:a301-agent` · 1회용(ephemeral) · 미리 승인으로 가입해, 인스턴스가 꺼지면 tailnet에서 자동으로 빠진다
  - 왜: 일반 가입 키는 만료가 최대 90일이라 바꾸는 것을 놓치면 새 인스턴스가 가입하지 못해 확장이 멈춘다. OAuth 클라이언트 비밀값은 만료가 없고 태그 없이는 가입되지 않는다
- **[결정] 메인 서버 가입**: Tailscale을 호스트에 설치하고 `tag:a301-main`으로 한 번 가입한다(태그 기기는 키가 만료되지 않는다). 에이전트가 쓸 주소는 메인 서버의 **Tailscale IP**를 SSM(`livekit-url`, `redis-host`)에 그대로 적는다
  - 왜: Tailscale IP는 기기마다 고정이다. 이름(MagicDNS)은 에이전트 컨테이너 안에서 이름 풀이가 되는지 따로 확인해야 한다
- **[결정] 접근 규칙(ACL)**: 아래만 열고 나머지는 막는다. 팀원 기기는 tailnet에 넣지 않는다(운영 서버 접속은 지금처럼 SSH)

| 출발 | 도착 | 포트 | 용도 |
|---|---|---|---|
| `tag:a301-agent` | `tag:a301-main` | 7880 · 6379 | 시그널링 · 결과 큐 |
| `tag:a301-agent` | `tag:a301-main` | 9090 · 3100 | 에이전트 지표(원격 쓰기) · 로그(Loki)를 보냄(8장) |
| `tag:a301-egress` | `tag:a301-main` | 7880 · 6379 | 시그널링 · LiveKit과 Egress 사이 요청(5.5) |
| `tag:a301-egress` | `tag:a301-main` | 9090 · 3100 | Egress 지표 · 로그를 보냄(8장) |

- 메인 서버에서 에이전트 · Egress로 들어가는 규칙은 없다. 지표 · 로그를 그쪽에서 보내므로(8장) 받는 포트가 없다
- Egress는 에이전트와 다른 태그(`tag:a301-egress`)로 가입한다. 왜: 지금 열어 줄 포트는 같지만, 한쪽만 막거나 바꿀 일이 생겼을 때 다른 쪽을 건드리지 않는다. 기기 수는 메인 1 + 에이전트 최대 5 + Egress 최대 2

- **확인할 것(테스트 서버에서 먼저)**
  - 직접 연결: `tailscale status`에 `direct`로 나오는지, `tailscale ping` 지연. 릴레이(DERP)로 가면 수십 ms가 늘 수 있다
  - 재부팅 순서: Docker가 Tailscale IP(`100.x`)에 포트를 묶으려면 그 IP가 먼저 있어야 한다. Docker를 `tailscaled` 뒤에 시작하게 하거나(systemd `After=`) `net.ipv4.ip_nonlocal_bind=1`을 켠다
  - Docker가 연 포트는 ufw를 거치지 않으므로, 바깥 주소(`0.0.0.0`)에 7880 · 6379가 열리지 않았는지 `ss -tulpn`으로 본다
  - **Tailscale이 끊길 때**: 진행 중 면접이 어떻게 되는지, 다시 연결되면 에이전트가 LiveKit에 자동으로 다시 등록되는지, 지표가 끊긴 동안 ASG가 어떻게 움직이는지 본다. Tailscale은 새 단일 의존이다

### 5.5 Egress 연결 **[제안]**(11/05)

| 경로 | 방법 | 왜 |
|---|---|---|
| 시그널링(7880) | Tailscale. Egress 설정 `ws_url: ws://<메인 서버 Tailscale IP>:7880` | 녹화할 방에 참가자로 들어간다. 에이전트와 같은 길이다(5.4) |
| LiveKit ↔ Egress 요청(6379) | Tailscale. Egress 설정 `redis.address`를 메인 서버 Tailscale IP로, `redis.password`(5.2) | LiveKit은 녹화 요청을 Redis(psrpc)로 Egress에 보낸다. 받지 못하면 녹화가 시작되지 않는다 |
| 미디어(UDP 7882) | 공인 IP. 에이전트와 같다 | 사설 IP 미디어는 TURN 브라우저가 깨진다(11장) |
| S3 업로드 | 키는 BE가 녹화 요청에 담아 보낸다(지금과 같음). 길은 **S3 게이트웨이 VPC 엔드포인트**(기본 VPC 라우팅 테이블에 붙임) **[제안]** | 지금과 같다(배포 계획 4.3). Egress 인스턴스에는 S3 키 · 권한을 두지 않는다. 엔드포인트는 아래 IP 조건 때문이다 |

- **배포 계획 6.2의 버킷 IP 조건과 부딪힌다.** 아직 넣지 않은 그 조건은 녹화 키(`a301-prod-egress`)를 메인 서버 공인 IP에서만 쓰게 하는데, ASG 인스턴스의 공인 IP는 뜰 때마다 바뀌어 조건을 넣으면 녹화 업로드가 모두 막힌다. 그래서 녹화 키 조건은 IP 대신 `aws:SourceVpc`(우리 기본 VPC)로 건다 **[제안]**. S3 게이트웨이 엔드포인트를 붙이면 같은 리전 S3로 가는 요청이 엔드포인트를 거쳐 이 조건을 쓸 수 있고, 요금이 없다. 앱 키(`a301-prod-app`)는 메인 서버에 남으므로 IP 조건 그대로다
  - 다른 안: Egress 인스턴스 역할로 올리기(BE가 키를 빼고 Egress 설정에 버킷만). 키가 없어져 더 낫지만, 개발(LiveKit Cloud)은 요청에 키가 있어야 해 BE가 환경마다 다르게 동작하게 된다. "코드는 같고 주소 · 키만 다르게"(배포 계획 4.0)를 지키려고 뺐다
- **에이전트와 다른 점: 영상을 받는다.** 에이전트는 지원자 음성만 받지만 Egress는 지원자 영상까지 받으므로, 메인 서버 → Egress 공인 IP 전송이 면접 1건에 영상 비트레이트만큼(약 1~2Mbps **[추정]**, 9장에서 실측) 생긴다. 10건이면 약 10~20Mbps로 서버 대역폭에는 작다. 보내는 쪽 전송 요금은 SSAFY 계정(메인 서버)에 붙고, 받는 쪽(우리 계정) · S3 업로드는 요금이 없다
- 녹화 시작 요청은 LiveKit 서버가 직접 Egress로 보낸다(BE가 방을 만들 때 건 자동 트랙 녹화, `LiveKitInterviewRoom`). 받을 Egress가 없으면 LiveKit 로그에만 `no response from servers`가 남고 BE는 모른다(S5 요약 · 6장). Egress가 다른 서버로 가면서 이 경우(ASG 0대 · Tailscale 끊김)가 늘어나므로 BE 녹화 누락 감지를 필수로 둔다(10.1)

| 상태 확인 | EC2 상태 확인 + **서비스 준비 확인**: 감시 스크립트가 ① Tailscale 연결 ② 메인 서버 7880 연결 ③ Redis 6379 인증 · 연결 ④ 컨테이너 헬스체크(8081)와 LiveKit 작업자 등록을 1분마다 보고, 일정 시간 계속 실패하면 `set-instance-health Unhealthy`로 알린다 **[결정]** | 컨테이너가 떠 있어도 Tailscale · Redis가 안 되면 면접을 못 받는다. EC2 상태 확인은 이걸 모른다. 8081이 LiveKit 등록까지 반영하는지는 확인 필요 |
| 인스턴스 준비 시간(warmup) | **180초 [결정]**, 9장 "늘리기"에서 실측해 조정 | 이미지 받기 · LiveKit 등록까지. 이 시간 동안 새 대의 CPU를 평균에서 뺀다(막 뜬 대의 기동 CPU · 놀고 있는 CPU가 평균을 흔들지 않게) |
| 최대 대수가 다 찼을 때 | 더 늘리지 않는다. BE 입장 시간 초과 처리(10.1 필수 수정)로 화면이 연결 실패를 안내한다 | 메인 서버 한계(약 25건) 근처라 대수를 늘려도 소용없다. 면접관 없이 방만 남지 않게 한다 |

### 6.2 확장 지표 **[결정: CPU]**(목표값은 3단계에서 확정)

- **[결정] 목표 추적: ASG 평균 CPU 40%** (`ASGAverageCPUUtilization`, AWS 기본 지표). 넘으면 늘리고 한참 밑이면 줄인다
  - 40%는 대당 약 5건 **[추정]**(1건 약 0.15코어, 2장 환산)이다. 새 면접 거절(70%, 약 9~10건)까지 30%p, 약 4건 여유가 있어 새 대가 뜨는 3~4분을 기존 대가 받는다
  - 3단계(1대에 몰기)에서 진행 중 면접 수와 CPU를 같이 보고 목표값을 확정한다(예: 1건이 실측으로 더 가벼우면 50%로 올린다)
- **[결정] EC2 세부 모니터링(1분)을 켠다.** 기본 모니터링은 5분 단위라 늘리는 판단이 늦다. 대당 월 약 $2
- 왜 면접 수가 아니라 CPU인가
  - 에이전트 인스턴스에는 에이전트만 돈다. 결과 생성 · 녹화 같은 다른 일이 섞이지 않아, CPU가 곧 면접 부하다
  - **LiveKit도 CPU로 배정 · 거절한다.** ASG도 CPU로 늘리면 두 기준이 같아진다. 면접 수로 늘리면 "평균 5건이라 안 늘리는데 한 대는 CPU 70%라 거절"하는 어긋남이 생긴다
  - 면접 1건의 무게가 바뀌어도(꼬리질문 · 코드 변경) 따로 고치지 않아도 된다. 면접 수 기준은 "1건 = 몇 %"가 바뀔 때마다 목표를 다시 맞춰야 한다
  - AWS 기본 지표라 지표를 보내는 스크립트 · 지표 수식이 필요 없다
- 약점과 대응
  - 면접을 받는 순간 프로세스 기동으로 CPU가 튄다(새 인스턴스 0.97). 목표 추적은 몇 분 연속으로 넘어야 움직여 순간 튐에는 반응하지 않는다. 튐 자체는 미리 띄우기(`AGENT_IDLE_PROCESSES`, 반영됨)로 줄인다
  - CPU는 면접이 시작된 뒤에 오른다. 면접이 약 10분이라 몇 분 늦게 반응해도 큰 문제는 아니지만, 몰림에는 약하다(아래)
  - T3 steal(같은 호스트 영향)이 CPU에 섞일 수 있다. CloudWatch로 본다(8장)
- 진행 중 면접 수(`a301_agent_active_interviews`)는 확장에 쓰지 않지만 계속 본다: 축소 보호(6.3)의 기준이고, Grafana에서 대당 면접 수를 본다(8장)
- **예약 확장**: 발표 · 시연처럼 시간을 아는 몰림은 미리 원하는 대수를 올려 둔다
- LiveKit 배정 쏠림: CPU 기준이면 LiveKit이 70% 아래인 대 중 하나로 보내므로, 한 대가 차도 다른 대가 받는다. 면접 수 기반 부하(`load_fnc`)는 순간 튐에 덜 흔들리게 하는 개선으로 두고, 확장 정책의 전제와 AI 요청에서는 뺀다
- 급격한 몰림에는 약하다: 1대에서 갑자기 15건이 들어오면 3대가 필요하지만 새 대는 3~4분 뒤에 준비된다. 운영 사용자가 적어 목표 추적으로 시작하고, 실제 유입 속도를 본 뒤 단계 확장(한 번에 여러 대)을 붙인다
- **[제안] 나중에 검토**: 규모가 커지면(수십 대) 대마다 같은 비율을 비워 두는 CPU 목표는 여유가 과해진다. 그때 게임 서버 오토스케일링(GameLift · Agones)처럼 **빈자리 수**(`대수 × 대당 상한 − 진행 중 면접 합계`)를 일정 이상 유지하는 기준으로 바꾼다. EC2 ASG **웜 풀**(미리 초기화해 둔 인스턴스로 준비 시간 단축)도 함께 본다

### 6.3 줄일 때 진행 중 면접 보호 **[결정]**(축소 보호 + 수명 주기 훅)

ASG가 인스턴스를 줄이면 그 인스턴스의 면접이 끊긴다. 두 단계로 막는다.

**① 바쁜 대를 고르지 않게: 축소 보호(scale-in protection)**

- 감시 스크립트가 1분마다 진행 중 면접 수를 보고, **1건 이상이면 축소 보호를 켜고 0건이면 끈다**(`autoscaling:SetInstanceProtection`, 바뀔 때만 호출)
- ASG는 보호가 꺼진 대(한가한 대)부터 줄인다. 모든 대가 보호 중이면 줄이지 않고 기다린다
- 왜: ASG는 줄일 대를 가용 영역 균형 · 오래된 순서로 고르고 면접 수는 보지 않는다. 훅만 있으면 면접이 끊기지는 않지만, 면접 8건인 대가 내려가며 drain하는 동안 0건인 대는 남는 비효율이 생긴다

**② 그래도 골라졌을 때: 수명 주기 훅(최종 안전장치)**

- 면접이 막 배정된 순간과 보호가 켜지는 순간(최대 1분) 사이, 인스턴스 새로 고침, 원하는 대수를 직접 낮출 때는 보호가 없는 대가 골라질 수 있다. 이때 훅이 drain을 기다린다

1. ASG **수명 주기 훅**(`autoscaling:EC2_INSTANCE_TERMINATING`, 하트비트 3900초)으로 종료를 대기 상태에 둔다
2. 인스턴스의 감시 스크립트가 IMDS(`/latest/meta-data/autoscaling/target-lifecycle-state`)에서 `Terminated`를 보면 `docker stop --time 3900 a301-ai-agent`
3. 에이전트(livekit-agents)는 SIGTERM을 받으면 **새 면접을 받지 않고(drain) 진행 중인 면접이 끝날 때까지 기다린다**. `drain_timeout` 기본 3600초를 1800초로 맞춘다
4. 컨테이너가 끝나면 `aws autoscaling complete-lifecycle-action`으로 종료를 진행한다

- 왜 3900초(65분, 11/06 1800초에서 바꿈): 개인 면접은 약 10분이지만 그룹 면접(docs/그룹면접-설계.md)은 약 60분이다. 상한이 그보다 짧으면 비정상 교체 · 강제로 내릴 때 그룹 면접이 중간에 끊긴다. **3900초는 상한이다**: 면접이 끝나면 바로, 면접이 없으면 즉시 내려간다. 무한정 보호하는 장치도 아니다(넘으면 종료가 진행된다). 훅 하트비트 최대값(7200초) 안이다
- 11/03 1단계에서 확인한 것은 **에이전트 자체의 drain**(면접 중 SIGTERM → 끝까지 진행 → 1초 뒤 종료)이다. ASG 축소 전체(보호 · 훅 · 완료 호출)는 9장 "줄이기"에서 검증한다
- 강제 종료 · 인스턴스 장애는 보호와 훅으로 막지 못한다(9장 "장애")

### 6.4 늘어나는 동안

- 새 인스턴스가 준비되기 전에 모든 대가 거절 기준을 넘으면, LiveKit이 면접을 배정하지 못해 **면접관이 들어오지 않는다**(부하 테스트 H6, 첫 질문 2분 초과로 실패). 6.2의 여유(대당 5건 목표)와 예약 확장으로 막는다
- BE는 정한 시간 안에 첫 질문이 시작되지 않으면 방을 닫고 `START_FAILED`로 바꾼다(10.1 필수 수정, [BE 요청](be-requests.md) 1). 화면이 "면접관을 연결하지 못했어요"를 띄우고 [다시 시작]이 방을 새로 열어 다시 배정하므로, 같은 방에 에이전트가 둘 들어가지 않는다

### 6.5 Egress ASG **[제안]**(11/05)

에이전트 ASG(6.1~6.4)와 같은 방식이다. 다른 값만 적는다.

| 항목 | 값 | 왜 |
|---|---|---|
| 최소 · 원하는 · 최대 | **운영 1 · 1 · 2** | 최소 1대는 늘 녹화를 받게. 최대 2 = 에이전트 최대(25건) ÷ 대당 목표(10~15건, 2.3). 에이전트가 더 늘지 않으므로 그 이상은 필요 없다 |
| 확장 지표 | **ASG 평균 CPU 40%**, 세부 모니터링(1분) | Egress 인스턴스에는 Egress만 돌아 CPU가 곧 녹화 부하다. Egress 수락 판정도 CPU라 에이전트(6.2)와 같은 이유로 기준이 맞는다. 메모리는 CPU보다 한참 뒤에 막혀(2.3) 지표로 쓰지 않는다 |
| 인스턴스 준비 시간(warmup) | 180초, 9장에서 실측 | Egress 이미지가 크다(GStreamer · Chrome 포함). 처음 받는 시간을 재서 맞춘다 |
| 상태 확인 | 에이전트와 같은 감시 스크립트 구성(6.1): ① Tailscale ② 7880 ③ Redis 인증 · 연결 ④ Egress 상태 포트(8080) 응답과 지표 `livekit_egress_can_accept_request` | Egress가 떠 있어도 Redis가 안 되면 녹화 요청을 못 받는다 |
| 서브넷 | 에이전트와 같은 기본 VPC `2a` · `2b` | |

- **몰려 시작할 때**: 확장은 몇 분 단위라, 15초 안에 대당 약 5건(2.3)을 넘게 몰리면 확장 전에 거절된다. `track_cpu_cost` 0.05(2.3)로 줄이고, 시연처럼 시간을 아는 몰림은 에이전트처럼 원하는 대수를 미리 올린다
- 에이전트 ASG와 대수를 묶지 않는다(각자 CPU로 늘고 준다). 면접 1건의 에이전트와 녹화가 서로 다른 ASG에 있으므로 한쪽이 늘 때 다른 쪽이 따라 늘 필요가 없다

**줄일 때 진행 중 녹화 보호 [제안]**: 에이전트의 축소 보호 + 수명 주기 훅(6.3)을 그대로 쓴다.

- 축소 보호 기준: 감시 스크립트가 1분마다 Egress 지표 `livekit_egress_requests`(종류별 진행 중 녹화 수, 9090)의 합을 보고 1 이상이면 보호를 켜고 0이면 끈다
- 수명 주기 훅: `Terminated`를 보면 `docker stop --time 3900 a301-egress`. Egress v1.15.0은 **SIGTERM을 받으면 새 녹화를 받지 않고 진행 중 녹화가 모두 끝날 때까지 기다린 뒤 종료한다**(`cmd/server/main.go` "finishing recording then shutting down", 자체 시간 상한 없음). **SIGINT는 진행 중 녹화를 바로 멈춘다**. 그래서 `docker stop`이 보내는 신호가 SIGTERM인지(이미지의 `StopSignal`) 확인해야 한다 **[확인 필요]**(9장)
- 녹화는 면접이 끝나 BE가 방을 닫으면(API 명세 5.8) 같이 끝난다. 그래서 3900초 상한의 근거는 에이전트와 같다(면접 약 10분)
- 메모리 넘침 · 인스턴스 장애로 Egress가 죽으면 그 대의 진행 중 녹화가 모두 잘린다. 합치기가 실패해(`TRACK_NOT_FOUND`) 다시보기가 "녹화를 불러오지 못했어요"가 된다. 면접 · 결과는 영향이 없다

## 7. 배포 · 버전

- **[결정]** 이미지 태그와 비밀값은 **SSM Parameter Store**에 둔다. 테스트 `/a301/loadtest/agent/*`, 운영 `/a301/prod/agent/*`(보안 문자열). 운영 값은 GitLab `prod/*` 변수와 같은 값을 넣고, Tailscale 가입 키(`tailscale-auth-key`)를 더한다. 인스턴스 역할 · 보안 그룹 · 시작 템플릿 · ASG도 운영용을 따로 만든다(`a301-prod-agent*`)
  - 왜: 테스트 리소스를 고치다 운영 에이전트가 바뀌지 않게 한다

**운영 리소스 [결정]**

| 리소스 | 이름 · 내용 |
|---|---|
| SSM 매개변수 | `/a301/prod/agent/*`(보안 문자열, 기본 KMS 키): 이미지 태그, Docker Hub 사용자 · 읽기 토큰, LiveKit 주소(메인 서버 Tailscale IP) · API 키 · 비밀값, Redis 주소(Tailscale IP) · 비밀번호, Soniox · ElevenLabs · Jev 키, **GMS(`LLM_CHAT_URL` · `LLM_MODEL` · `LLM_API_KEY`, 꼬리질문)**, Tailscale OAuth 클라이언트 비밀값 |
| IAM 역할 | `a301-prod-agent`: `/a301/prod/agent/*` 읽기, 이 ASG의 수명 주기 완료 · 축소 보호 켜고 끄기 · 상태 알리기(`CompleteLifecycleAction` · `SetInstanceProtection` · `SetInstanceHealth`) |
| 보안 그룹 | `a301-prod-agent`: 인바운드는 **UDP 41641(Tailscale)만**, 아웃바운드 전체 |
| 시작 템플릿 · ASG | `a301-prod-agent`, 태그 `a301-role=agent` · `a301-env=prod`, 기본 VPC `2a` · `2b` |
| Docker Hub | **에이전트 전용 읽기 토큰을 새로 만든다**(`a301-prod-agent-pull`) |

- 왜 UDP 41641: 에이전트는 받는 포트가 없다(지표 · 로그도 에이전트가 보낸다, 8장). 이 포트가 막혀도 대부분 직접 연결되지만 릴레이(DERP)로 빠질 수 있다. WireGuard는 키가 없는 패킷에 응답하지 않아 열어도 위험이 작다
- 왜 전용 토큰: 토큰이 새도 에이전트 토큰만 폐기하면 되고, 운영 서버 배포(`a301-prod-pull`)는 영향을 받지 않는다
- GMS 값은 빠뜨려도 에이전트가 오류 없이 꼬리질문만 빼고 미리 만든 질문으로 진행한다. 그래서 전환 뒤 첫 면접에서 `꼬리질문 생성 완료 ms=…` 로그로 확인한다(10.1)
  - user data가 인스턴스 역할로 읽어 `docker run`에 넘긴다. 비밀값을 시작 템플릿에 적지 않는다
- **[제안]** 새 버전 배포: 태그 매개변수를 바꾸고 ASG **인스턴스 새로 고침**(최소 정상 비율 100%, 6.3의 drain을 거침)
  - 왜: 에이전트와 BE가 같은 명세 버전이어야 한다. 메인 서버 배포(`deploy/prod/deploy.sh`) 뒤에 새로 고침을 이어서 한다
  - **[결정] 순서는 BE 먼저 → 에이전트 새로 고침.** 배정 메타데이터 형식이 바뀌면 새 BE가 보낸 면접을 옛 에이전트가 잠깐 받을 수 있으므로, 메타데이터를 바꿀 때는 에이전트가 옛 · 새 형식을 모두 읽게 먼저 배포한다
  - **[결정] 운영은 처음부터 CI로 자동화**(11/06, 7.1): 운영 배포(▶ `prod-deploy`)가 메인 서버 배포에 성공하면 같은 잡에서 SSM 태그를 바꾸고 새로 고침을 시작한다(`deploy/asg/ci-agent-refresh.sh`). 메인 서버 러너에는 `ssm:PutParameter`(태그 하나) · `autoscaling:StartInstanceRefresh`(이 ASG)만 준 IAM 사용자 키를 준다(메인 서버는 SSAFY 계정이라 우리 계정 역할을 못 씀). CI는 새로 고침을 시작만 하고 끝까지 기다리지 않는다
  - **[결정] 새로 고침 설정**: 최소 정상 비율 100% · 최대 200%(새 대를 먼저 띄우고 옛 대를 drain), 준비 시간 180초. 옛 대는 진행 중 면접이 끝날 때까지 최대 3900초 기다리고, 면접이 없으면 바로 내려간다
    - 지금 운영 사용자는 거의 없어 몇 분 안에 끝난다. 그래도 사용자 · 시연이 있을 때를 기준으로 둔다. 비용은 몇 분이고, "진행 중 면접을 끊지 않는 배포"가 이 구조의 핵심이다
  - 되돌리기: SSM 태그를 이전 값으로 바꾸고 새로 고침을 다시 한다. 급하면 10.1의 되돌리기(메인 서버 안 에이전트 + ASG 0)
- 최소 1대 상시(`t3.small` 월 약 $26)는 사용자가 거의 없어도 유지한다 **[결정]**. 왜: 최소 0이면 첫 면접이 인스턴스가 뜨는 3~4분을 기다린다. 예산($100 + 남은 크레딧)으로 12/1까지 충분하다
- **[제안]** 이미지 받기: 처음에는 Docker Hub 읽기 토큰(SSM)을 쓴다. 시작 시간이 길거나 토큰 관리가 번거로우면 ECR로 옮긴다
- **[결정] 운영 수칙: 에이전트 · Egress 인스턴스는 EC2 콘솔 · API로 직접 종료하지 않는다.** 대수를 줄이거나 한 대를 빼려면 ASG로 한다: 원하는 대수 낮추기, 인스턴스 새로 고침, `aws autoscaling terminate-instance-in-auto-scaling-group`(교체가 필요하면 `--no-should-decrement-desired-capacity`)
  - 왜: ASG로 내리면 수명 주기 훅 → 감시 스크립트 → drain을 거쳐 에이전트가 연결을 닫고 나간다. EC2에서 직접 끄면 연결을 닫지 못하고 사라져 LiveKit에 **유령 작업자**가 남고, 그동안 새 면접이 그쪽에 배정돼 면접관 없이 멈춘다(11장, [운영 경로 보고서](../../loadtest/report/asg-path-2026-11-06.md) 3장). 진행 중이던 면접도 잃는다
  - 유령은 하드웨어 장애처럼 피할 수 없는 경우에도 생긴다. 그래서 LiveKit 재전송 상한(`deploy/prod/compose.asg.yml`의 `tcp_retries2=8`, 약 2분)과 BE의 시작 실패 처리(`START_FAILED`)를 같이 둔다
- 운영 CI/CD 연결은 운영 반영을 정한 뒤에 한다

**Egress 운영 리소스 [제안]**(11/05)

| 리소스 | 이름 · 내용 |
|---|---|
| SSM 매개변수 | `/a301/prod/egress/*`(보안 문자열): Egress 이미지 버전, LiveKit 주소(메인 서버 Tailscale IP) · API 키 · 비밀값, Redis 주소(Tailscale IP) · 비밀번호, Tailscale OAuth 클라이언트 비밀값. S3 키는 두지 않는다(5.5) |
| IAM 역할 | `a301-prod-egress-node`: `/a301/prod/egress/*` 읽기, 이 ASG의 수명 주기 완료 · 축소 보호 · 상태 알리기 |
| 보안 그룹 · 시작 템플릿 · ASG | `a301-prod-egress-node`, 보안 그룹 인바운드는 UDP 41641(Tailscale)만, 태그 `a301-role=egress` · `a301-env=prod` |
| Docker Hub | 토큰 없음(공식 공개 이미지) |

- 왜 `-node`: `a301-prod-egress`는 이미 Egress가 S3에 올릴 때 쓰는 IAM **사용자** 이름이다(배포 계획 6.2). 역할 · ASG를 같은 이름으로 두면 콘솔과 정책에서 헷갈린다
- 왜 에이전트 매개변수와 나누나: Egress는 외부 API 키 · GMS 값이 필요 없다. 역할마다 필요한 값만 읽게 한다
- 버전: Egress는 우리 코드가 아니라 공식 이미지라 운영 배포(▶)마다 바꾸지 않는다. LiveKit 서버 버전을 올릴 때 짝이 맞는 Egress 버전으로 SSM 값을 바꾸고 인스턴스 새로 고침(에이전트와 같은 설정, drain을 거침)을 한다

### 7.1 master 배포를 ASG에 반영하는 방법 **[제안]**(11/05 기록)

> **다음 릴리즈에는 ASG를 넣지 않는다**(11/05). 다음 릴리즈의 에이전트 · Egress는 지금처럼 메인 서버 compose로 배포한다. 이 절은 운영 반영(10.1) 때 쓸 방법을 미리 적어 둔 것이다.

지금 CI의 운영 배포(`prod-deploy`, [배포 계획](../deploy_plan/README.md) 8.1)는 **메인 서버의 compose만** 다시 띄운다. ASG 인스턴스는 **부팅할 때 SSM의 이미지 태그를 읽어** 그 이미지로 뜨므로, master 배포가 ASG에 자동으로 반영되지 않는다. 태그를 바꾸고 인스턴스를 새로 띄워야 한다.

```
① develop → master 병합
② prod-build (자동)   be · fe · ai · admin 이미지 → Docker Hub hanggeut/a301:<서비스>-<SHA>
③ prod-deploy (▶)     메인 서버만: BE · FE · AI 작업자 · LiveKit … 새 이미지로 up -d
④ SSM 태그 변경        /a301/prod/agent/image-tag = <③과 같은 SHA>
⑤ 인스턴스 새로 고침    a301-prod-agent ASG(최소 정상 100% · 최대 200% · 준비 시간 180초)
     새 인스턴스: user data가 SSM에서 새 태그를 읽어 이미지를 받고 LiveKit에 등록
     옛 인스턴스: 수명 주기 훅 → SIGTERM → 새 면접은 받지 않고 진행 중 면접이 끝나면 종료(최대 3900초, 6.3)
```

| 항목 | 내용 | 왜 |
|---|---|---|
| 이미지 | 에이전트는 메인 서버 AI 작업자와 **같은 `ai-<SHA>` 이미지**다. ASG용으로 따로 빌드하지 않는다 | ②에서 이미 만들어진다. 같은 커밋의 이미지라 작업자 · 에이전트 버전이 맞는다 |
| 순서 | **③ 뒤에 ④ · ⑤**(BE 먼저, 에이전트 나중) | 그 사이 몇 분은 새 BE와 옛 에이전트가 같이 돈다. 배정 메타데이터 형식을 바꿀 때는 에이전트가 옛 · 새 형식을 모두 읽게 먼저 배포한다(7장 위) |
| ④만 하고 ⑤를 안 하면 | 기존 대는 옛 버전, 그 뒤 확장으로 뜬 대만 새 버전이 섞인다 | 새로 고침까지 해야 모든 대가 같은 버전이 된다 |
| ④를 잊으면 | 메인 서버만 새 버전이고 에이전트는 계속 옛 버전이다. 확장으로 새로 뜨는 대도 옛 태그를 읽는다 | **가장 놓치기 쉬운 곳**이다. 수동일 때는 운영 배포 체크리스트에 ④ · ⑤를 넣고, 안정되면 CI로 옮긴다(아래) |
| 되돌리기 | SSM 태그를 이전 SHA로 돌리고 ⑤를 다시 한다. 메인 서버 되돌리기([배포 계획](../deploy_plan/README.md) 8.3 Re-deploy)와 같은 커밋으로 맞춘다 | 메인 서버만 되돌리면 에이전트가 새 버전으로 남는다 |
| Egress | master 배포와 상관없다. LiveKit 서버 버전을 올릴 때만 `/a301/prod/egress/*`의 버전을 바꾸고 `a301-prod-egress-node` ASG를 같은 설정으로 새로 고친다 | 공식 이미지라 우리 코드와 함께 바뀌지 않는다 |
| 개발 서버 | ASG 없음. develop 배포는 지금처럼 미니PC compose가 반영한다 | 에이전트 ASG는 운영(과 테스트 환경)에만 둔다 |

**운영은 CI로 자동화 [결정]**(11/06): ④ · ⑤를 사람이 하지 않는다. `prod-deploy` 잡이 `deploy/prod/deploy.sh`(③) 성공 뒤 [`deploy/asg/ci-agent-refresh.sh`](../../deploy/asg/ci-agent-refresh.sh)를 이어서 부른다. ③이 실패하면 ④ · ⑤는 돌지 않는다.

- 켜기: GitLab CI/CD 변수 `AGENT_ASG_ENABLED=true`(범위 `prod/*`). 없으면 스크립트가 아무것도 하지 않고 끝나므로, ASG로 전환하기 전에 머지해도 운영 배포는 지금과 같다. 전환하는 날 켜고, 10.1 되돌리기(메인 서버 에이전트로 돌아감) 때는 끈다
- 권한: 메인 서버 러너는 SSAFY 계정이라 우리 계정 역할을 쓸 수 없다. **이 파라미터 하나에 `ssm:PutParameter`, 이 ASG에 `autoscaling:StartInstanceRefresh` · `DescribeInstanceRefreshes`만** 준 IAM 사용자 `a301-prod-agent-ci`(`deploy/asg/iam/ci-agent-refresh-policy.json`)의 키를 `AGENT_REFRESH_AWS_ACCESS_KEY_ID` · `AGENT_REFRESH_AWS_SECRET_ACCESS_KEY`(범위 `prod/*`, Protected · Masked)로 둔다. AWS CLI는 러너에 설치하지 않고 공식 이미지(`amazon/aws-cli`)로 돌린다
- 동작: 진행 중인 새로 고침이 있으면 태그도 바꾸지 않고 잡을 실패로 남긴다(섞인 상태를 만들지 않게). 없으면 `put-parameter --overwrite` → `start-instance-refresh`(최소 정상 100% · 최대 200% · 준비 180초 · **축소 보호가 켜진 대는 풀릴 때까지 기다림** `ScaleInProtectedInstances=Wait`)
  - 왜 `Wait`: 감시 스크립트가 면접 중인 대에 축소 보호를 건다. 기본값(`Ignore`)이면 그 대는 새로 고침에서 빠져 옛 버전으로 남는다 **[확인함]**(11/06, [운영 경로 보고서](../../loadtest/report/asg-path-2026-11-06.md) 2.3): 면접 중인 대가 있으면 새로 고침은 새 대를 띄우지도 않고 보호가 풀릴 때까지 기다린다. 면접이 끝나면 새 대를 먼저 띄우고 준비 시간(180초) 뒤 옛 대를 내린다. 진행 중 면접은 끊기지 않고, 반영은 면접이 끝난 뒤 약 4~5분 걸린다. 면접이 끊이지 않는 시간에는 배포가 그만큼 늦어진다
- 기다리지 않는다: 새로 고침은 진행 중 면접 때문에 최대 65분 걸릴 수 있어, 잡은 시작만 하고 끝난다. 끝났는지는 콘솔 · `describe-instance-refreshes`로 본다
- 실패해도 메인 서버 배포(③)는 되돌리지 않는다. 그 상태는 "④를 잊은 경우"와 같으므로 잡을 다시 돌리면(Retry) 된다
- 되돌리기: GitLab에서 이전 배포를 Re-deploy하면 ③과 함께 ④ · ⑤도 이전 SHA로 다시 돈다

## 8. 모니터링

**[결정] 운영: 에이전트가 메인 서버로 보낸다(push)**

| 대상 | 방법 |
|---|---|
| 지표 | 에이전트 인스턴스의 **Alloy**가 에이전트 지표(9464, 컨테이너 안, `job=a301-ai-agent`)와 인스턴스 CPU · 메모리 · 디스크(`prometheus.exporter.unix`, `job=a301-asg-node`)를 긁어 메인 Prometheus에 **원격 쓰기**(`remote_write`, Tailscale IP의 9090)로 보낸다. 메인 Prometheus는 원격 쓰기 받기(`--web.enable-remote-write-receiver`)를 켠다 |
| 로그 | 같은 Alloy가 에이전트 컨테이너 로그를 메인 **Loki**(Tailscale IP의 3100)로 보낸다 |
| 라벨 | 지표: `instance_id`(EC2 인스턴스 ID) · `az` · `env` · `role`. 로그: `instance_id` · `env` · `role` · `service=a301-prod-ai-agent`. `instance`는 모든 대가 `127.0.0.1:9464`로 같으므로 대를 나눌 때는 `instance_id`를 쓴다 |
| Grafana | 운영 대시보드 "AI 면접 에이전트" 줄에 **에이전트 인스턴스**(지표가 들어오는 대수) · **인스턴스별 진행 중 면접** · **인스턴스별 CPU**(40% 점선) · **인스턴스별 메모리**. 다른 에이전트 패널은 모든 대의 합계다. 로그 대시보드에 **에이전트 인스턴스** 선택 칸(전체 = 메인 서버 로그 포함) |
| Egress **[제안]** | 같은 방식. Egress 인스턴스의 Alloy가 Egress 지표(9090: `livekit_egress_requests` · `livekit_egress_can_accept_request` · `livekit_egress_handler_results_total`)를 원격 쓰기로, 컨테이너 로그를 Loki로 보낸다. 메인 Prometheus가 지금 직접 긁는 `a301-egress` 작업(`deploy/prod/prometheus.yml`)은 지우고, 원격 쓰기로 받는 지표에 같은 `job` 라벨을 붙여 기존 패널을 그대로 쓴다. 대시보드 LiveKit · 녹화 줄을 대별로 바꾸고, 녹화 결과 중 `completed`가 아닌 것(`killed_oom` 등)을 따로 보인다 |

- 왜 보내는 쪽(push): 메인 Prometheus가 가져가려면(pull) 늘고 주는 에이전트 목록을 알아야 한다. EC2 서비스 탐색(`ec2_sd_configs`)은 메인 서버가 우리 계정 EC2 API를 부를 역할이 없고, 받은 사설 IP도 Tailscale로는 닿지 않아 쓸 수 없다. Tailscale API로 목록을 만드는 방법은 갱신 스크립트와 API 키가 더 든다. 보내면 목록이 필요 없고 지표 · 로그를 Alloy 설정 한 곳에서 끝낸다
- 왜 로그를 메인 Loki로: 면접 하나의 BE · LiveKit · 에이전트 로그를 Grafana 한 곳에서 같이 봐야 원인을 찾을 수 있다(scale out 보고서 4장의 추적 방식)
- 원격 쓰기 받기 · Loki는 인증이 없다. Tailscale IP에만 열고 접근 규칙(5.4)으로 `tag:a301-agent`만 들어오게 한다
- Tailscale이 끊기면 Alloy가 잠시 쌓아 두었다가 다시 보낸다. 오래 끊기면 일부를 잃을 수 있지만, 그때는 면접도 진행되지 않는다(5.4)

**[결정] CloudWatch는 콘솔에서 따로 본다(우리 계정)**: ASG 원하는 · 서비스 중 대수, ASG 평균 CPU(6.2), 수명 주기 대기 시간, **`CPUSurplusCreditsCharged`**(unlimited 초과 요금), CPU steal

- 왜: T3는 기준치를 넘는 만큼 요금이 붙고, 같은 호스트의 다른 인스턴스 영향(steal)을 받을 수 있다. 부하 테스트 서버(t3.xlarge)에서 steal이 최대 4.8%까지 보였다
- Grafana에 붙이지 않는다: CloudWatch 데이터 소스를 쓰려면 메인 서버에 우리 계정 읽기 IAM 키를 둬야 한다. 필요해지면 그때 한다
