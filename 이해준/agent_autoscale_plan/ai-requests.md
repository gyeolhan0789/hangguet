# AI 파트 요청: 에이전트 분리 · 부하 테스트에서 나온 개선 사항

> 근거: [scale out 보고서](../../loadtest/report/scaleout-2026-11-03.md), [S5 보고서](../../loadtest/report/s5-2026-11-02.md), [S6 보고서](../../loadtest/report/s6-2026-11-03.md), [에이전트 오토스케일링 계획](README.md)
> 대상 코드: `ai/app/agent/`(livekit-agents 1.8.8). 우선순위 순서로 적었다.

## 1. 질문 음성 재생에 시간 상한 두기(면접 무한 멈춤 방지) — 높음

**증상**: 에이전트를 별도 인스턴스로 분리한 직후 면접 20건 중 5건이 질문 도중 멈췄다(11/03, 같은 시간대 비교에서는 재현되지 않아 원인이 분리라고 단정하지는 않는다). 에이전트 로그에는 `질문 상태 화면 전달 실패 speech=started code=timeout`만 남고, 그 면접은 10분 넘게 아무 기록 없이 멈춰 있다가 지원자가 나가며 끝났다. 화면은 "질문 0/5", "음성 인식에 연결하고 있어요" 그대로였다.

**원인(코드)**: `question.py` `QuestionSpeaker.ask()`
1. `_notify(STARTED)`: 화면에 상태 알림(RPC, 최대 3초, 실패해도 진행)
2. `_play(audio)`: `source.capture_frame()`로 프레임을 넣고 **`source.wait_for_playout()`을 시간 상한 없이 기다림**
3. `_notify(ENDED)` → 답변 듣기

송출 경로(에이전트 → LiveKit)가 그 순간 흐르지 않으면 프레임이 소비되지 않아 2번에서 끝없이 기다린다. 1번 알림이 시간 초과로 실패한 것도 같은 순간 송출이 막혔다는 신호로 본다. 송출이 막힌 원인은 조사 중이다(보고서 4장).

**요청**
- `_play()`에 시간 상한을 둔다. 예: `음성 길이 + 10초`. 넘기면 `clear_queue()` 후 `SpeechState.FAILED`를 알리고 다음 단계(답변 듣기)로 넘어간다. 화면은 질문 글을 보여 주고 있으므로 면접은 이어질 수 있다
- 면접 전체에 "진행 없음" 감시를 둔다. 예: 한 단계에서 N분 넘게 진척이 없으면 면접을 실패로 끝내고 BE에 알려, 사용자가 무한정 기다리지 않게 한다
- 같은 패턴인 발화 중단 안내(`say()`)에도 같은 상한을 둔다

**확인 방법**: 테스트에서 송출을 막기는 어렵다. 단위 테스트로 `capture_frame`이 끝나지 않는 가짜 `AudioSource`를 넣어, 상한 뒤 FAILED 알림과 답변 단계 진입을 확인한다.

## 2. 프로세스 미리 띄우기(`num_idle_processes`) — 중간

**증상**
- 막 켜진 에이전트 인스턴스가 첫 면접을 받는 순간 `no warmed process available for job, waiting for one to be created` 경고가 나고, 부하가 **0.97**로 "가득 참"이 됐다가 2초 뒤 풀렸다(11/03 새 인스턴스 시험)
- 원격 에이전트의 첫 질문이 9~14초로, 메인 서버 안(4~6초)보다 일정하게 느리다

**원인(코드)**: `main.py` `AgentServer(num_idle_processes=0)`. 면접마다 프로세스를 새로 띄운다(livekit-agents 운영 기본값은 4).

**요청**
- `num_idle_processes`를 1~2로(환경 변수로 바꿀 수 있게 하면 좋다). 대기 프로세스 1개 메모리(약 100~200MB 추정)를 실측해 대당 메모리 계획(`t3.medium` 4GB, 컨테이너 3g)에 반영한다
- 0으로 둔 이유(메모리 절약 등)가 있으면 알려 주면 계획에 반영한다

**확인 방법**: 같은 부하(동시 5건)로 첫 질문 시간과 새 인스턴스 첫 면접 때 부하를 다시 잰다(인프라가 측정).

## 3. 부하 판단을 진행 중 면접 수 기반으로(`load_fnc`) — 중간(오토스케일을 CPU 기준으로 정해 필수에서 뺐다)

**증상**: LiveKit이 작업자 하나에 면접을 몰아 준다(5건 8분 동안 13건 중 10건이 한 대로). 기본 부하 판단이 CPU 5초 평균이라, 몰리는 순간에는 모든 대가 한가해 보인다. 반대로 순간 CPU 튐(프로세스 기동)만으로 "가득 참"이 되기도 한다.

**요청**
- `AgentServer(load_fnc=..., load_threshold=...)`로 부하를 `진행 중 면접 수 ÷ 대당 상한`으로 보고한다. 대당 상한은 환경 변수(예: `AGENT_MAX_INTERVIEWS`, 기본 5)로 둔다
- 안전장치로 CPU도 같이 본다: `max(진행 중 면접 수 ÷ 상한, CPU 사용률)`
- 오토스케일 기준(대당 진행 중 면접 5건, 계획 6.2)과 같은 숫자를 쓰게 된다
- 오토스케일은 CPU 기준(ASG 평균 CPU 40%)으로 정해 LiveKit 배정(CPU)과 기준이 같아졌다. 그래서 필수는 아니다. 남는 이점: 면접을 받는 순간의 CPU 튐(프로세스 기동)에 배정이 덜 흔들리고, 대수가 고르게 찬다
- `min`이 아니라 `max`로 합친다(`min`이면 CPU가 높아도 부하가 낮게 나온다). `active_jobs`가 실제 진행 중 면접을 정확히 세는지 확인해 달라

**확인 방법**: 에이전트 2대에 동시 10건을 걸어 대당 5건 안팎으로 나뉘는지 본다(인프라가 측정).

## 4. 녹화 합치기: 같은 종류 파일 여러 개 이어 붙이기 — 높음

**증상**: 면접 608(11/03 13:09)에서 지원자 마이크 녹화가 13.8초 만에 끝나고(지원자 트랙이 내려감) 몇 초 뒤 다시 올라와 녹화가 새로 시작됐다. 지원자 음성 파일이 2개가 되자 합치기가 `MERGE_ERROR: 같은 종류의 트랙이 여러 개다: CANDIDATE_AUDIO`로 실패했고, 다시보기는 "녹화를 불러오지 못했어요"가 됐다. 실제 사용자도 네트워크가 잠깐 끊기거나 마이크를 다시 잡으면 같은 일이 생긴다.

**요청**
- `ai-recording` 합치기가 같은 종류(`CANDIDATE_AUDIO` · `CANDIDATE_VIDEO` · `INTERVIEWER_AUDIO`) 파일이 여러 개면 시작 시각 순서로 이어 붙이고, 사이 빈 구간은 무음 · 정지 화면으로 채운다(타임라인 동기 유지)
- 이어 붙일 수 없으면 그 트랙만 빼고 나머지로라도 다시보기를 만든다

**확인 방법**: 면접 중 지원자 마이크를 껐다 켜는 시나리오(또는 S3에 올린 파일 2개를 넣은 단위 테스트)로 다시보기가 만들어지는지 본다.

## 5. 마지막 답변 뒤 면접 종료를 화면에만 맡기지 않기 — 중간

**증상**: 면접 631(11/03 13:22)에서 에이전트는 질문 5개를 끝내고 "마지막 질문까지 진행했다"를 남겼고 답변 5개가 DB에 저장됐다. 그런데 화면이 질문 3에서 갱신되지 않아 "면접 종료"(5.8)를 보내지 못했고, 면접은 `IN_PROGRESS`로 남아 결과가 만들어지지 않았다.

**요청(AI · BE 같이)**
- 에이전트가 마지막 답변을 저장하면 결과 메시지로 "면접 끝"을 알리고, BE가 화면 요청이 없어도 일정 시간(예: 1분) 뒤 면접을 종료 · 분석 단계로 넘긴다
- 또는 BE가 `IN_PROGRESS`로 오래 남은 면접(답변 5개 저장 후 N분)을 정리하는 작업을 둔다

## 6. 채점 · 결과 병렬 처리 — 중간

**증상**: 동시 10건이 거의 같이 끝나자 결과 대기가 평균 230초, 최대 358초였다(11/03 2단계). 채점 · 결과 작업 1건이 GMS를 11번 **차례로** 불러 약 30초가 걸리고(`result/job.py` `for answer in job.answers`), 작업자 1개가 작업도 1건씩 처리한다. 면접 640은 큐에서 98초를 기다렸다.

**요청**
- 작업 안: 답변별 채점 GMS 호출을 동시에(`asyncio.gather` 등) 보낸다. 1건 약 30초 → 약 10초 예상. GMS 공용 동시 요청 한도 확인 필요
- 작업 사이: `ai-analysis` 작업자를 2~4개로(같은 큐를 나눠 받는다, CPU는 0.05코어 안팎). 이건 인프라가 compose에서 바로 할 수 있다. **운영은 `ai-plan` · `ai-analysis`를 2개씩 띄우기로 했다**([오토스케일링 계획](README.md) 1장)
- 같은 큐에 여러 개를 띄우면 하나만 재시작될 때 `recover`가 다른 작업자의 처리 중 작업까지 되돌린다(`worker/queue.py`). 작업자마다 처리 중 목록을 따로 두고(예: `ai:jobs:processing:<작업자 id>`), 죽은 작업자의 목록만 되돌리게 바꿔 달라

## 7. 참고: 다른 파트와 같이 볼 것

| 내용 | 파트 |
|---|---|
| 모든 에이전트가 가득 차면 LiveKit이 배정하지 않는데, BE는 배정 요청(`createDispatch`)만 하고 면접관 입장을 확인하지 않는다. 배정 요청 · 실제 입장 · 시간 초과 · 다시 배정 · 사용자 안내를 상태로 나눠 다루고, 다시 배정할 때 같은 방에 에이전트가 둘 들어가지 않게 한다. **운영 전환 전 필수**([오토스케일링 계획](README.md) 10.1) | BE |
| STT 연결이 처음부터 실패하면(DNS 오류 등) 다시 연결하지 않는다(`stt.py` "자동 재연결이 없으므로"). 화면은 "음성 인식이 끊겼어요"를 띄우지만, 인식된 글이 없으면 [답변 완료]가 꺼져 있어 진행할 수 없을 수 있다(S6 08:50) | AI · FE |
| 면접 화면이 에이전트 진행을 놓치고 질문 3에서 멈춤(631, 에이전트 쪽 RPC는 정상 응답). 면접 중 지원자 마이크 트랙을 내렸다 다시 올림(608) | FE |
