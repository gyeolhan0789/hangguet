## 1. 목적 · 범위

운영 서버는 Lightsail 한 대(4코어 · 15GB)에 모든 서비스가 있다. 배포 계획 3.2는 이 서버의 한계를 "동시 면접 약 20~30건(메모리 기준), CPU · Egress · AI 작업자가 먼저 막을 수 있음"으로 **추정**만 해 두었고, 13장에 동시 면접 수 · 에이전트 메모리 · Egress 메모리가 **[미정] 실측**으로 남아 있다.

이 테스트의 목적은 두 가지다.

1. **어디가 먼저 막히는지**, 어느 부하에서 막히는지 찾는다. 이 결과를 보고 스케일 아웃 등 대응을 정한다(대응은 이 문서 범위 밖)
2. 배포 계획 13장의 [미정] 값(동시 면접 수, 컨테이너별 메모리 상한)을 실측값으로 채운다

이 테스트로 답할 질문:

| # | 질문 | 왜 중요한가 |
|---|---|---|
| Q1 | 화상 면접을 **동시에 몇 건**까지 품질(음성 끊김 · 질문 지연)을 지키며 돌릴 수 있나 | 서비스 핵심 기능이고, 넘치면 진행 중인 면접이 모두 끊길 수 있다(에이전트 메모리 4g 공유) |
| Q2 | 면접 만들기가 몰릴 때 **질문 생성(PLAN) 3분 마감**을 몇 건까지 지키나 | PLAN 작업자는 1개이고 작업을 하나씩 처리한다. 사용자가 화면 앞에서 기다린다 |
| Q3 | 지원서 저장(자소서 검증, 최대 8초 대기)을 동시에 몇 건까지 받나 | 검증은 `ai-analysis` 안의 스레드 하나가 처리한다. 밀리면 지원서를 저장할 수 없다 |
| Q4 | 면접이 몰려 끝날 때 **결과(10분) · 녹화 합치기(15분)** 마감을 지키나 | 결과 · 채점은 작업자 1개, 녹화 합치기는 1코어 작업자 1개다 |
| Q5 | 웹 · API(BE · FE)는 초당 몇 요청까지 응답 시간을 지키나, 무엇이 먼저 막히나 | 로그인(PBKDF2) · 매 요청 회원 확인(DB) · FE 서버 렌더링이 CPU를 나눠 쓴다 |
| Q6 | 오래 돌리면 무엇이 쌓이나(메모리 누수, Redis 192MB, CPU 버스트 크레딧) | Redis가 차면 쓰기가 거부되어 로그인까지 막힌다(`noeviction`) |

범위 밖:

- 외부 서비스(GMS · Soniox · ElevenLabs · Jev) 자체의 성능. 우리 서버가 아니고, 대량 호출은 비용 · 다른 팀(GMS 공용)에 영향을 준다(3.4)
- 보안 · DDoS 내성, 관리 페이지(`/admin/`), 회사 카드 파이프라인

## 2. 병목 가설

코드와 운영 설정을 읽고 세운 가설이다. 시나리오(6장)는 이 가설을 하나씩 확인하도록 짰다. 확인하면 결과 기록(8장)에 맞음 · 틀림을 남긴다.

| # | 가설 | 근거 | 확인 지표 | 막히면 보이는 증상 |
|---|---|---|---|---|
| H1 | PLAN 작업자가 1개라 면접 만들기가 몰리면 대기열이 길어져 3분 마감을 넘긴다 | `a301-prod-ai-plan` 1개, 작업을 하나씩 처리(`ai/app/worker/main.py`). 마감은 `requestedAt` 기준 180초(`with_deadline`) | `a301_ai_jobs_queued{queue="ai:jobs:plan"}`, `plan.failed`(`TIMED_OUT`) 로그, 5.1 → `planStatus=READY` 시간 | 화면이 "질문 준비 중"에서 멈췄다가 실패 |
| H2 | 자소서 검증이 스레드 하나라 지원서 저장이 몰리면 BE의 8초 대기를 넘긴다 | `ai/app/worker/checks.py`(BRPOP 하나씩), BE `RedisCoverLetterCheckQueue`(최대 8초), Jev 시간 제한 5초 | 4.1 응답 중 `COVER_LETTER_CHECK_UNAVAILABLE` 비율, 4.1 응답 시간 | 지원서 저장 실패 |
| H3 | 로그인이 몰리면 비밀번호 해시(PBKDF2-SHA256 310,000회, Spring 5.8 기본값)가 CPU를 다 쓴다 | `auth/config/SecurityConfig.java`의 `Pbkdf2PasswordEncoder.defaultsForSpringSecurity_v5_8()` | BE 컨테이너 CPU, 1.3 p95, 같은 시간 다른 API p95 | 로그인뿐 아니라 모든 API가 느려짐 |
| H4 | 모든 인증 요청이 회원 확인으로 DB를 한 번 더 부르고, 커넥션 풀이 기본값 10이라 풀 대기가 생긴다 | JWT 디코더가 요청마다 탈퇴 여부 조회(`auth/config/SecurityConfig.java`의 `findByIdAndDeletedAtIsNull`), `application.yml`에 Hikari 설정 없음 | `hikaricp_connections_pending`, DB 연결 수, API p95 | CPU는 여유인데 응답이 느림 |
| H5 | FE가 2초마다 다시 그리기(`router.refresh`)로 서버 렌더링을 해 FE(Node 1프로세스, 512m)가 먼저 막힌다 | 질문 준비 · 질문 전환 · 결과 분석 대기 중 2초 폴링(`plan-progress.tsx`, `interview-room.tsx`), 다시보기 10초 | FE 컨테이너 CPU(1코어 근처면 포화), 페이지 응답 시간 | 화면 전환 · 상태 갱신이 늦음 |
| H6 | 에이전트가 면접마다 프로세스를 띄워(약 150~200MB, 추정) 동시 면접 수를 메모리 · CPU가 정한다. **상한을 넘었을 때 거절하는 코드가 없어** 넘치면 OOM으로 진행 중인 면접이 모두 끊길 수 있다 | `mem_limit: 4g`, `ai/app/agent/main.py`의 `AgentServer`에 동시 면접 상한 없음(AI 명세 6.5 `CAPACITY_EXCEEDED`가 아직 코드에 없음) | ai-agent 메모리 · CPU, 면접 1건당 증가량, OOM kill 수 | 면접 중 면접관이 갑자기 사라짐 |
| H7 | LiveKit(단일 UDP 포트 모드)과 Egress(트랙 녹화 · S3 업로드)가 동시 면접이 늘면 CPU · 대역폭을 먼저 쓴다 | `livekit.yaml` `udp_port: 7882`, Egress `mem_limit: 1g` | 패킷 손실률 · 지터 p95(LiveKit), Egress 메모리 · 녹화 실패, 서버 네트워크 송수신 | 음성이 끊기거나 녹화가 빠짐 |
| H8 | 결과 · 채점 작업자가 1개라 면접이 몰려 끝나면 답변마다 쌓인 채점(SCORE_ANSWER)과 결과(EVALUATE)가 밀려 10분 마감을 넘긴다 | `a301-prod-ai-analysis` 1개, 큐 `ai:jobs`에 채점 · 결과가 함께 들어감 | `a301_ai_jobs_queued{queue="ai:jobs"}`, 5.8 → `COMPLETED` 시간, `evaluation.failed` | 결과 화면이 "분석 중"에서 실패 |
| H9 | 녹화 합치기 작업자(1코어 · 1개)가 몰리면 다시보기 15분 대기를 넘긴다 | `a301-prod-ai-recording` `cpus: 1`, BE `MERGE_WAIT` 15분 | `a301_ai_jobs_queued{queue="ai:jobs:recording"}`, `recordings.status` | 다시보기 실패 |
| H10 | 오래 돌리면 Redis(192MB, `noeviction`)가 찬다 | 리프레시 토큰 30일, 멱등성 응답 24시간, 처리 중 리스트 | Redis 메모리 %, 키 수 | 로그인 · 면접 만들기 쓰기 거부 |
| H11 | 부하가 오래가면 Lightsail **CPU 버스트 크레딧**이 바닥나 서버 전체가 느려진다 | 배포 계획 3.1 "CPU 버스트" [확인 필요]. 콘솔 권한이 없어 크레딧을 직접 볼 수 없다 | node-exporter CPU `steal` 비율, 같은 부하에서 시간이 지나며 p95가 오르는지 | 시작 30분은 괜찮다가 갑자기 전부 느려짐 |
| H12 | 부하 발생기 IP 하나에서 오는 대량 요청을 Cloudflare가 막거나 늦춘다 | Cloudflare WAF · Bot 설정 미확인 | k6 응답 코드 403 · 429 · 503, Cloudflare 이벤트 로그 | 서버 지표는 한가한데 k6만 실패 |

## 3. 테스트 환경 · 원칙

### 3.1 대상: 운영 서버 **[제안]**

운영 서버(`hangguet.co.kr`)에 직접 한다.

- 왜: SSAFY 계정이라 스냅샷 · 플랜 변경을 쓸 수 없어(배포 계획 1장) 같은 사양의 복제 서버를 만들 수 없다. 교보재 EC2는 사양 · CPU 버스트 방식이 달라 결과를 운영에 옮길 수 없다. 개발 서버(미니PC)는 LiveKit Cloud를 쓰므로 미디어 쪽을 잴 수 없다
- 대신 지킬 것:
  - 테스트 시간을 팀에 미리 알리고, 그 시간에는 배포(`prod-deploy`)를 누르지 않는다
  - 시작 전에 DB 백업을 한 번 직접 돌린다(`/opt/a301/backup.sh`). 매일 04:30 백업 cron과 겹치는 시간은 피한다
  - 실제 사용자가 적은 시간대에 한다. 시간대는 **[미정]**(접속 기록을 보고 팀이 정함). 테스트 데이터 삭제(3.7)까지 **같은 날 0시 전에** 끝나도록 잡는다
  - 3.5의 중단 조건에 걸리면 바로 멈춘다

### 3.2 부하 발생기: 팀 노트북 **[결정]**

부하는 **팀 노트북**에서 보낸다. 기본은 인프라 담당 노트북 1대이고, 브라우저 시나리오가 한 대를 넘으면 팀원 노트북을 더한다.

| 항목 | 내용 | 왜 |
|---|---|---|
| 기본 장비 | 인프라 노트북(Samsung 960XGL): Core Ultra 7 155H(16코어 · 22스레드), 메모리 32GB, Windows 11, **Wi-Fi만 있음**(유선 포트 없음) | 추가 비용 없이 바로 쓸 수 있다. 운영 서버 밖에서 보내므로 운영 서버 자원을 재는 데 섞이지 않는다 |
| 웹 · API(S1~S4) | 노트북 1대로 충분하다. k6 HTTP는 VU당 메모리가 작아 수백 요청/초도 노트북 한 대가 감당한다 | 목표(L2)가 약 30 요청/초이고, 한계 탐색도 노트북 CPU보다 Wi-Fi · 서버가 먼저 막힌다 |
| 브라우저(S5) | 노트북 1대에 Chromium **약 10~15개**까지로 본다 **[확인 필요]** S0에서 1개당 CPU · 메모리를 재서 정한다. 넘으면 팀원 노트북을 더해 VU를 나눈다(예: 동시 20건 = 노트북 2대 × 10건) | Chromium 1개가 약 300~500MB를 쓰고, 시선 추적(`use-gaze-tracker.ts`)과 영상 인코딩이 노트북 CPU를 쓴다. 평소 다른 프로그램이 이미 20GB 가까이 쓰고 있어 실제로 쓸 수 있는 메모리는 그보다 작다 |
| 도구 | k6 버전 고정(시작 시점 최신 안정판), Windows용 k6를 바로 설치한다(`winget install k6`). 브라우저 시나리오는 k6 browser 모듈 + 설치된 Chrome(`K6_BROWSER_EXECUTABLE_PATH`) | 노트북마다 같은 버전을 써야 회차끼리 비교할 수 있다. WSL 안에서 돌리면 네트워크 · 브라우저 설정이 한 단계 더 생긴다 |
| 노트북 준비 | 전원 연결, 전원 모드 "최고 성능", 절전 · 화면 꺼짐 끄기, 다른 프로그램(브라우저 · IDE · Docker Desktop) 닫기, Windows 업데이트 미루기. Tailscale은 끄거나 exit node를 쓰지 않는지 확인한다 | 배터리 모드 · 절전이면 CPU가 느려져 노트북이 병목이 된다. 소크(S7) 2시간 동안 꺼지면 안 된다. Tailscale exit node로 나가면 경로가 바뀐다 |
| 발생기 감시 | 작업 관리자(또는 `perfmon`)로 노트북 CPU · 메모리 · Wi-Fi 송수신을 같이 기록한다. CPU 80%, 메모리 85%를 넘거나 Wi-Fi 송신이 포화되면 그 회차 결과를 쓰지 않는다 | 발생기가 막히면 서버가 느린 것처럼 보인다 |
| 경로 | 실제 사용자와 같은 길(Cloudflare → Tunnel → Nginx)로 보낸다 | Tunnel · Nginx도 병목 후보다(H12). 내부 포트로 바로 보내면 이 구간을 재지 못한다 |

**어디서 돌리느냐(네트워크)에 따라 재는 대상이 달라진다.** 회차마다 어느 네트워크에서 했는지 8장에 적는다.

| 네트워크 | 미디어 경로 | 장점 | 주의 |
|---|---|---|---|
| SSAFY Wi-Fi(강의실) | 바깥 TCP를 443만 허용하므로(배포 계획 4.2) 면접 미디어가 **TURN/TLS 443**으로 간다 | 시연 · 발표 장소와 같은 조건이다. TURN 중계는 LiveKit에 가장 무거운 길이라 결과가 보수적(최악 기준)이 된다 | ① 캠퍼스 전체가 공인 IP 하나를 같이 쓴다. Cloudflare 규칙을 IP로 걸면 캠퍼스 전체가 통과하고(3.3), 같은 Wi-Fi의 다른 교육생 회선을 우리가 차지한다(영상 20개 업로드는 수십 Mbps) ② 학내 방화벽 · 대역폭 제한이 막을 수 있다 ③ 운영 시간 밖에는 쓸 수 없을 수 있다 |
| 집 · 휴대폰 테더링 | UDP 7882로 바로 간다(일반 사용자 대부분의 경로) | 실제 사용자 다수와 같은 경로를 잰다 | 가정 회선 업로드가 영상 수 개~수십 개를 감당하는지 S0에서 먼저 본다(Wi-Fi 1개 업로드 속도 측정) |

- 권장 **[제안]**: 웹 · API(S1~S4)는 어디서 해도 결과가 같으므로 편한 곳에서 한다. 실시간 면접(S5)은 **두 네트워크에서 한 번씩** 해서 UDP 경로와 TURN 경로의 동시 면접 한계를 따로 적는다. 시연이 강의실이면 TURN 결과가 시연 날의 한계다
- Wi-Fi는 지터 · 패킷 손실이 원래 있다. S0에서 면접 1건일 때의 패킷 손실 · 지터를 **기준값**으로 적고, 동시 수를 늘렸을 때는 기준값보다 늘어난 만큼을 서버 탓으로 본다. 노트북 한 대에서 늘어나는지, 여러 노트북에서 같이 늘어나는지도 비교한다(노트북 Wi-Fi만의 문제인지 가린다)

### 3.3 Cloudflare **[미정]**

테스트 전에 Cloudflare 대시보드에서 WAF · Rate Limiting · Bot Fight Mode 설정을 확인한다. 발생기 IP를 막는 규칙이 있으면 **테스트 시간에만** 발생기 IP를 건너뛰는 규칙을 둔다. 끝나면 지운다.

- 왜: 발생기 IP 하나에서 실제 사용자 수백 명 분량이 나가므로, Cloudflare가 공격으로 보고 막으면 서버까지 부하가 가지 않는다(H12). 반대로 규칙을 영구히 풀어 두면 실제 공격도 통과한다
- 실제 사용자는 IP가 여러 개라 이 규칙이 없어도 된다. 그래서 "건너뛰기"는 테스트 장비에만 준다
- SSAFY Wi-Fi에서 돌릴 때는 IP 규칙이 캠퍼스 전체에 걸린다(3.2). 그래서 IP 대신 **테스트 시간에만 쓰는 비밀 헤더**(예: `X-Loadtest-Key`, 값은 발생기 환경 변수에만)를 k6가 보내고, 그 헤더가 있는 요청만 건너뛰는 규칙을 둔다 **[제안]**. 집 · 테더링이면 그 IP로 걸어도 된다
- 브라우저 시나리오(S5)는 실제 Chrome이 FE를 부르므로 헤더를 넣기 어렵다. S5 요청 수는 적어 규칙에 걸릴 가능성이 낮으니, S0에서 걸리는지 먼저 본다

### 3.4 외부 API 비용 · 스텁 **[제안]**

면접 1건이 외부 API를 부른다: GMS(PLAN · 채점 · 결과), Soniox(STT, 답변 음성 초당 과금), ElevenLabs(TTS, 글자 수 과금), Jev(리액션 · 자소서 검증). 동시 수십 건을 실제 API로 돌리면 비용이 크고, GMS는 SSAFY 공용이라 다른 팀까지 느려질 수 있다. 그래서 두 층으로 나눈다.

| 층 | 무엇 | 언제 |
|---|---|---|
| **보정(실제 API)** | 실제 API로 면접 1~3건. 호출별 지연 시간 · 토큰 수 · 비용을 잰다. AI 지표(`a301_agent_soniox_audio_seconds`, `a301_agent_elevenlabs_characters`, `a301_agent_jev_requests`)와 로그의 `promptTokens`/`completionTokens`로 1건당 사용량을 계산한다 | 맨 처음(6장 S0) |
| **부하(스텁)** | 외부 API 대신 **보정에서 잰 지연 시간을 흉내 내는 스텁**을 부른다 | 동시 수가 큰 시나리오(S3 · S4 · S5 · S6) |

- GMS: `LLM_CHAT_URL`이 환경 변수라 **코드를 고치지 않고** 스텁(OpenAI 호환 `chat/completions`, 지연 시간 · JSON 응답 고정)으로 바꿀 수 있다. 테스트 시간에만 compose 덮어쓰기 파일(`deploy/prod/compose.loadtest.yml` **[제안]**)로 AI 작업자를 다시 띄우고, 끝나면 원래대로 띄운 뒤 `LLM_CHAT_URL`이 GMS인지 확인한다
- Soniox · ElevenLabs · Jev: 주소가 코드에 고정되어 있다(`ai/app/agent/stt.py`, `tts.py`, `jev.py`, `ai/app/interview/cover_letter.py`). 스텁을 쓰려면 **주소를 환경 변수로 바꿀 수 있게 하는 AI 작업**이 먼저 필요하다 **[제안]**
  - 그 작업 전에는 실시간 면접 시나리오(S5)를 실제 Soniox로 돌린다. 이때 ElevenLabs · Jev 키를 비우면 질문 글만 · 리액션 없이 진행되어 비용은 줄지만 **실제보다 가벼운 부하**가 되므로 결과에 그렇게 적는다
- 스텁 지연 시간은 보정에서 잰 값의 p50 · p95를 쓴다. 왜: 작업자는 응답을 기다리는 동안 다음 작업을 못 하므로, 지연 시간이 곧 처리량이다. 스텁이 즉시 응답하면 H1 · H8을 과소평가한다
- 실제 API를 쓰는 회차의 예상 비용은 보정 결과(1건당 사용량 × 건수)로 계산해 팀 승인을 받고 돌린다 **[미정]**

### 3.5 중단 조건(즉시 멈춤) **[제안]**

k6 `thresholds`의 `abortOnFail`과 사람이 보는 Grafana 둘 다로 건다. 하나라도 걸리면 k6를 멈추고 원인을 기록한다.

- 테스트 계정이 아닌 실제 사용자 요청에서 5xx · 오류 로그가 보임
- 서버 메모리 90% 이상, 디스크 85% 이상, Redis 메모리 85% 이상
- 컨테이너 OOM kill · 재시작 발생(단, H6 한계 확인 회차에서 에이전트 OOM을 확인하는 것은 예외. 그 회차는 실제 사용자가 면접 중이 아닐 때만 한다)
- 5xx 비율 5% 이상이 1분 넘게 지속

멈춘 뒤 서버가 스스로 돌아오지 않으면 해당 컨테이너만 `docker compose -p a301-prod restart <서비스>`로 다시 띄운다.

### 3.7 테스트 데이터 삭제 **[결정]**

테스트 계정(`loadtest+…@<테스트 도메인>`)의 데이터를 **한 트랜잭션에서** 지운다. 스크립트는 `loadtest/seed/cleanup.sql`(6.1)에 두고, **개발 서버에서 먼저 돌려 본 뒤** 운영에 쓴다.

**무엇을 지우나(판단 기준)**: 부하 테스트가 만드는 데이터는 모두 테스트 계정이 만든다. 그래서 **테스트 계정 id 목록 하나만 정하고**, 나머지는 FK를 따라 그 계정에 딸린 것만 지운다. 시각(테스트 시간대)으로 고르지 않는다. 같은 시간에 들어온 실제 사용자 데이터까지 지울 수 있기 때문이다.

1. **기준 목록 = 가입 스크립트가 남긴 id 목록**. 가입(seed) 스크립트가 만든 회원 id를 파일(`loadtest/seed/accounts.csv`, 비밀번호 없이 id · 이메일만)로 남기고, 삭제는 이 id로만 한다
   - 이메일 패턴(`loadtest+%@<테스트 도메인>`)은 **확인용**으로만 쓴다. 목록의 id가 모두 이 패턴인지, 패턴인 회원이 모두 목록에 있는지 비교하고, 하나라도 다르면 지우지 않고 멈춘다
   - 왜 패턴만으로 고르지 않나: 가입 때 이메일 인증이 없어 누구나 그 패턴으로 가입할 수 있다. 목록과 패턴이 둘 다 맞아야 테스트 계정으로 본다
   - 테스트 도메인은 **우리가 가진 도메인의 하위 도메인**(예: `loadtest.hangguet.co.kr`)으로 한다 **[제안]**. 남의 도메인을 쓰면 실제 그 주소의 주인과 겹칠 수 있다
2. **딸린 데이터**: 목록의 회원 id에서 시작해 아래만 지운다
   - 회원 id로 찾는 것: `interview_sessions` · `applications` · `practice_logs` · `user_agreements` · `user_social_accounts` · `notice_reads` · `streak_freezes` · `streak_freeze_grant_targets` · `password_changes` · `inquiries`
   - 면접 id로 찾는 것: `interview_plans` · `interview_questions` · `answers`(질문으로) · `recordings` · `session_scores` · `speech_metrics` · `ai_job_outbox`
   - S3: 테스트 면접의 `recordings.object_key`와 `recordings/raw/{면접 id}/`
3. **지우지 않는 것**: 관리자가 만든 것(공지 · 유지권 배포 `streak_freeze_grants`), 다른 회원의 데이터. 테스트 중 전체 유지권 배포가 있었다면 테스트 계정이 받은 유지권(`streak_freezes`)만 지우고 배포 자체는 남긴다
4. **지우기 전 확인(드라이런)**: 같은 스크립트를 커밋 없이 돌려 테이블별로 지울 행 수를 뽑는다. 계정 수 · 면접 수가 k6 결과(만든 면접 수)와 맞는지, 테스트 계정의 데이터가 모두 테스트 시간대 안에 만들어졌는지 본다. 시간대 밖 데이터가 있으면 멈추고 원인을 확인한다

**언제**: 테스트와 삭제를 **같은 날 0시 전에** 끝낸다.

- 왜: 0시 작업이 그날 지표를 `admin_daily_metrics`에 굳히기 때문이다. 0시 전에 지우면 그날 줄이 깨끗한 값으로 기록되어 따로 고칠 것이 없다
- 0시를 넘겼으면: 다음 날 테스트 날짜의 `admin_daily_metrics` 줄을 지우고 BE를 다시 시작한다. BE는 기동할 때 **전날** 줄이 없으면 다시 기록한다(`AdminDailyMetricService.recordYesterdayIfAbsent`). 이틀 이상 지나면 이 방법이 안 되므로 반드시 다음 날 안에 한다. 다시 기록한 줄의 상태 값(회원 수 등)은 다시 기록한 시각 기준이다

**순서**:

1. 테스트 트래픽이 모두 끝났는지 확인한다. 진행 중인 면접이 없고, AI 작업 큐(`ai:jobs*`)와 결과 큐(`ai:results`)가 비어 있어야 한다. 늦게 온 결과가 지운 면접을 다시 건드리지 않게 하기 위해서다
2. 테스트 계정을 탈퇴시킨다(2.7). 리프레시 토큰이 Redis에서 함께 지워진다(`revokeAll`)
3. DB를 백업한다(`/opt/a301/backup.sh`). 테스트 전 백업과 별도로, 테스트 중 들어온 실제 사용자 데이터까지 담기 위해서다
4. S3에서 지울 키 목록을 만든다: 테스트 면접의 `recordings.object_key`(합친 mp4)와 `recordings/raw/{면접 id}/`(원본 트랙)
5. DB 삭제(한 트랜잭션). 테스트 계정 id를 임시 테이블에 담고, FK에 ON DELETE가 없으므로 자식부터 지운다
   1. 면접에 딸린 것: `recordings` → `session_scores` · `speech_metrics` · `interview_plans` → `answers` → `interview_questions` → `ai_job_outbox`(FK 없음, `session_id`로 찾음) → `interview_sessions`
   2. 회원에 딸린 것: `applications` · `practice_logs` · `user_agreements` · `user_social_accounts` · `notice_reads` · `streak_freezes` · `streak_freeze_grant_targets` · `password_changes` · `inquiry_messages` → `inquiries`
   3. `users`
   4. 지운 행 수가 예상(계정 수 · 면접 수)과 맞는지 확인한 뒤 커밋한다
6. 4에서 만든 목록으로 S3 객체를 지운다. DB를 먼저 지우는 이유: S3를 먼저 지우면 DB 커밋이 실패했을 때 다시보기가 깨진 면접이 남는다
7. 관리자 홈(8.15)에서 회원 수 · 면접 수 · 평균이 테스트 전 값으로 돌아왔는지 확인한다

Redis에 남는 것(면접 진행 상태 1일, 멱등성 응답 24시간)은 TTL로 사라지므로 따로 지우지 않는다.

| 결과 대기 | 다시 그리기 → 5.2 | **2초마다**, 결과가 나올 때까지 | |
| 결과 · 다시보기 | 6.3 · 6.4 | 다시보기는 합치기 전이면 **10초마다** | S3 Presigned URL |

- 사용자 한 명이 기다리는 동안 내는 요청은 약 0.5 요청/초다(2초 폴링). 동시에 기다리는 사람이 N명이면 폴링만으로 약 0.5N 요청/초가 된다
- 채팅 면접은 마이크 · 카메라 없이 면접방에 들어가 글로 답한다(5.7). LiveKit · Egress 부담이 작고 STT를 쓰지 않는다

### 4.2 목표 수준 **[제안]**

실제 사용자 수 자료가 아직 없어, 배포 계획 3.2의 설계 상한(동시 면접 약 20건)을 "목표"로 두고 그 위를 한계 탐색으로 잰다. 팀이 예상 사용자 수(발표 · 시연 일정 포함)를 정하면 이 표를 고친다 **[미정]**.

| 수준 | 동시 화상 면접 | 면접 만들기 몰림 | 로그인 몰림 | 웹 · API | 의미 |
|---|---|---|---|---|---|
| L1 평상시 | 5건 | 1분에 5건 | 1분에 30건 | 약 5 요청/초 | 지금 규모. 여기서 기준을 못 지키면 바로 고친다 |
| L2 목표 | 20건 | 1분에 20건 | 1분에 100건 | 약 30 요청/초 | 발표 · 시연처럼 사람이 한꺼번에 몰리는 날. 이 서버 한 대로 지켜야 하는 선 |
| L3 한계 탐색 | 25 · 30 · 35 …(기준이 깨질 때까지) | 기준이 깨질 때까지 | 기준이 깨질 때까지 | 기준이 깨질 때까지 | 이 서버 한 대의 한계값 |

- 왜 면접 만들기 "1분에 20건": 발표 직후 청중이 같이 면접을 만들면 동시 면접 수와 같은 수가 짧은 시간에 몰린다. PLAN 작업자가 1개라 이 경우가 가장 위험하다(H1)

### 5.2 결과 수집

- k6: 회차마다 요약(`--summary-export`)과 HTML 보고서(`K6_WEB_DASHBOARD=true`, `K6_WEB_DASHBOARD_EXPORT`)를 남긴다
- 서버: 기존 Grafana **A301 운영 서버** · **A301 운영 서버 로그** 대시보드를 그대로 쓴다. 회차 시작 · 끝 시각을 기록해 같은 구간을 본다
- k6 지표를 운영 Prometheus로 보내지 않는다 **[제안]**. 왜: 운영 Prometheus는 바깥에 열려 있지 않고, 원격 쓰기를 열려면 설정 변경 · 포트 노출이 필요하다. 시각만 맞추면 두 화면을 나란히 비교할 수 있다
- 회차가 끝나면 8장 표에 결과를 적고, 보고서 파일은 `이해준/load_test_plan/results/<날짜>-<시나리오>/`에 둔다 **[제안]**(개인정보 · 토큰이 들어 있지 않은지 확인한 뒤)

## 6. 시나리오

모든 시나리오는 L1 → L2 → L3 순서로 올리고, 각 단계에서 5.1 기준이 깨지면 그 단계에서 멈춘다. 단계마다 최소 5분(면접은 면접 1건 길이 이상) 유지해 값이 안정된 뒤 잰다.

| ID | 이름 | 확인 가설 | 실행 방식 | 외부 API | 부하 모양 |
|---|---|---|---|---|---|
| S0 | 스모크 · 보정 | — | 브라우저 1 + HTTP 1 | **실제** | 화상 면접 1~3건 전체 흐름. 스크립트 확인, 외부 API 지연 · 사용량 측정(3.4) |
| S1 | 웹 · API 혼합 | H4 · H5 | HTTP(`ramping-arrival-rate`) | 없음 | 홈 · 통계 · 달력 · 기록 · 결과 · 공지 조회를 섞어 5 → 30 → 60 … 요청/초로 올리고 10분 유지 |
| S2 | 로그인 몰림 | H3 | HTTP(`ramping-arrival-rate`) | 없음 | 1분 동안 30 → 100 → 200 …건. 같은 시간에 S1을 L1로 깔아 다른 API가 느려지는지 본다 |
| S3 | 지원서 저장 몰림 | H2 | HTTP(`shared-iterations`) | Jev(스텁 권장) | 동시 1 · 3 · 5 · 10 · 20건을 한 번에 저장 |
| S4 | 면접 만들기 몰림 | H1 · H5 | HTTP | GMS 스텁 | 1분 안에 5 · 10 · 20 · 30건 만들기 → 사용자마다 2초 폴링(FE 페이지 다시 그리기와 같은 요청)으로 READY까지 시간 측정 |
| S5 | 동시 화상 면접 | H6 · H7 · H8 · H9 | **k6 browser**(가짜 카메라 · 마이크) | Soniox 실제(3.4), GMS 스텁 | 동시 면접 1 · 5 · 10 · 15 · 20 · 25 …건. 단계마다 면접 1건이 끝까지 돈다. 끝난 뒤 결과 · 합치기 대기열이 비는 시간까지 잰다 |
| S6 | 피크 혼합 | 전부 | S1 + S2 + S4 + S5 동시 | S5와 같음 | L2 값으로 30분. "발표 직후" 상황 |
| S7 | 장시간(소크) | H10 · H11 | S1 + S5 | S5와 같음 | L2의 50%로 2시간. 메모리 · Redis · 디스크(Loki) 증가 추세와 `steal` 변화를 본다 |

시나리오별 주의:

- **S1 · S4 요청 방식**: 조회 · 폴링은 실제 화면처럼 **FE 페이지**로 보낸다. 쿠키 `hk_access`에 BE 액세스 토큰을 넣고, 다시 그리기는 `RSC: 1` 헤더로 같은 페이지를 GET한다. 쓰기(5.1 · 5.4 · 5.8)는 FE의 서버 액션 대신 **BE API를 직접**(`/be/api/v1`, `Authorization: Bearer`, `Idempotency-Key`) 부른다
  - 왜: 폴링 비용의 대부분이 FE 서버 렌더링이라(H5) BE만 부르면 FE 부담을 재지 못한다. 서버 액션은 빌드마다 바뀌는 액션 id가 필요해 스크립트로 흉내 내기 어렵고, 쓰기 요청은 수가 적어 FE 부담이 작다
- **S4에서 면접 시작은 하지 않는다**: 5.4를 부르면 에이전트가 배정되는데, 아무도 들어오지 않는 방에 에이전트 프로세스가 떠 S5 결과를 흐린다. 만든 면접은 그대로 둔다(READY 상태는 연습 기록에 들어가지 않는다)
- **S5 가짜 장치**: `K6_BROWSER_ARGS`로 Chromium에 `use-fake-ui-for-media-stream`, `use-fake-device-for-media-stream`, `use-file-for-fake-audio-capture=<답변.wav>`, `use-file-for-fake-video-capture=<얼굴.y4m>`를 넘긴다. 실제 FE 화면(로그인 → 면접 만들기 → 장치 점검 → 면접방)을 그대로 밟는다
  - 노트북 1대에 Chromium 약 10~15개까지로 본다(3.2). 그 이상은 팀원 노트북을 더해 노트북마다 같은 k6 스크립트를 `N`(면접 수) · 계정 범위만 다르게 넣어 **같은 시각에** 시작한다(예: 노트북 A는 계정 1~10, B는 11~20). 노트북끼리 시계가 다르면 시작이 어긋나므로 시작 시각을 환경 변수로 주고 그때까지 기다리게 한다 **[제안]**
  - 시선 추적(`use-gaze-tracker.ts`)과 영상 인코딩이 노트북 CPU를 쓴다. 노트북 CPU가 먼저 차면(3.2) 그 노트북의 면접 수를 줄이고 노트북을 늘린다
  - 노트북 여러 대가 같은 Wi-Fi(공유기)에 붙으면 공유기 업로드가 먼저 막힐 수 있다. 노트북마다 송신량을 기록해 합이 회선 업로드에 가까우면 그 회차는 쓰지 않는다
- **S5 동시 수 올리는 법**: `ramping-vus`가 아니라 단계마다 정해진 수의 면접을 거의 같은 때 시작하고(`per-vu-iterations`, 시작 시각 몇 초씩 분산) 그 면접이 끝날 때까지 유지한다. 왜: 면접 1건이 약 10분이라 VU 수를 계속 바꾸면 "동시 몇 건"이 흐려진다
- **에이전트 한계 회차(L3)**: H6처럼 상한 거절이 없어 넘치면 그 순간 진행 중인 면접이 모두 끊긴다. 에이전트 메모리가 상한의 85%에 닿으면 더 올리지 않고 멈춘다. 1건당 메모리 증가량으로 한계를 계산한다

S4 예시(형태만, 실제 응답 필드는 API 명세로 맞춘다):

```js
import http from "k6/http";
import { check, sleep } from "k6";
import { Trend, Counter } from "k6/metrics";
import { uuidv4 } from "https://jslib.k6.io/k6-utils/1.4.0/index.js";
import { login, account } from "../lib/auth.js";

const BE = `${__ENV.BASE_URL}/be/api/v1`;
const planReady = new Trend("plan_ready_seconds");
const planFailed = new Counter("plan_failed");

export const options = {
  scenarios: {
    burst: { executor: "per-vu-iterations", vus: Number(__ENV.N || 5), iterations: 1, maxDuration: "6m" },
  },
  thresholds: {
    plan_ready_seconds: ["p(95)<90", "max<180"],
    plan_failed: ["count<1"],
    http_req_failed: [{ threshold: "rate<0.05", abortOnFail: true }],
  },
};

export default function () {
  const me = account(__VU);
  const token = login(me);
  const auth = { Authorization: `Bearer ${token}`, "Content-Type": "application/json" };

  sleep(Math.random() * 60); // 1분 안에 흩어서 만든다
  const created = http.post(
    `${BE}/interview-sessions`,
    JSON.stringify({ applicationId: me.applicationId, persona: "COFFEE_CHAT", mode: "VIDEO" }),
    { headers: { ...auth, "Idempotency-Key": uuidv4() }, tags: { type: "write" } },
  );
  check(created, { "5.1 201": (r) => r.status === 201 });
  const id = created.json("id");
  const started = Date.now();

  // 화면과 같이 2초마다 확인한다(실제 스크립트는 FE 페이지 다시 그리기로 보낸다)
  while (Date.now() - started < 200_000) {
    sleep(2);
    const s = http.get(`${BE}/interview-sessions/${id}`, { headers: auth, tags: { type: "read" } });
    const plan = s.json("planStatus");
    if (plan === "READY") return planReady.add((Date.now() - started) / 1000);
    if (plan === "FAILED") return planFailed.add(1);
  }
  planFailed.add(1);
}
```

## 8. 결과 기록

### 8.1 결과 보고에 담을 값

테스트가 끝나면 아래 값을 정리해 팀에 공유한다. 이 값을 보고 대응(스케일 아웃 등)을 정한다.

| 값 | 어디서 |
|---|---|
| 시나리오별로 **기준(5.1)이 처음 깨진 부하 수준**과 그때 먼저 막힌 구성 요소(가설 번호) | k6 결과 + Grafana |
| 면접 1건당 자원: 에이전트 메모리 · CPU, LiveKit · Egress CPU · 메모리, 서버 네트워크 송수신 | S5 단계별 증가량 |
| 작업자 처리량: 큐별 분당 처리 건수(PLAN · 채점 · 결과 · 합치기), 작업 1건 처리 시간 | `a301_ai_jobs_queued` 변화, 작업자 로그 |
| 웹 · API: 기준을 지킨 최대 요청/초, 그때 BE · FE · DB 자원 | S1 · S2 |
| 장시간: 시간당 메모리 · Redis · 디스크 증가량, `steal` 변화 | S7 |
| 면접 1건당 외부 API 사용량 · 비용 | S0 |
| 네트워크별 차이(UDP · TURN) | S5 두 회차 비교 |

### 8.2 회차 기록
