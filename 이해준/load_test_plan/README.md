## 1. 목적 · 범위

운영 서버는 Lightsail 한 대(4코어 · 15GB)에 모든 서비스가 있다. 배포 계획 3.2는 이 서버의 한계를 "동시 면접 약 20~30건(메모리 기준), CPU · Egress · AI 작업자가 먼저 막을 수 있음"으로 **추정**만 해 두었고, 13장에 동시 면접 수 · 에이전트 메모리 · Egress 메모리가 **[미정] 실측**으로 남아 있다.

테스트는 운영 서버가 아니라 **운영과 같은 사양으로 따로 만든 EC2(이하 테스트 서버)**에 운영과 같은 이미지 · 같은 compose를 띄워서 한다(3.1).

이 테스트의 목적은 두 가지다.

1. **어디가 먼저 막히는지**, 어느 부하에서 막히는지 찾는다. 이 결과를 보고 스케일 아웃 등 대응을 정한다(대응은 이 문서 범위 밖)
2. 배포 계획 13장의 [미정] 값(동시 면접 수, 컨테이너별 메모리 상한)을 실측값으로 채운다

이 테스트로 답할 질문:

| # | 질문 | 왜 중요한가 |
|---|---|---|
| Q1 | 화상 면접을 **동시에 몇 건**까지 품질(음성 끊김 · 질문 지연)을 지키며 돌릴 수 있나 | 서비스 핵심 기능이고, 넘치면 진행 중인 면접이 모두 끊길 수 있다(에이전트 메모리 4g 공유) |
| Q2 | 면접 만들기가 몰릴 때 **질문 생성(PLAN) 3분 마감**을 몇 건까지 지키나 | PLAN 작업자는 1개이고 작업을 하나씩 처리한다. 사용자가 화면 앞에서 기다린다 |
| Q3 | 지원서 저장(자소서 검증, 최대 8초 대기)을 동시에 몇 건까지 받나 | 검증은 `ai-analysis` 안의 스레드 하나가 처리한다. 밀리면 지원서를 저장할 수 없다 |
| Q4 | 면접이 몰려 끝날 때 **결과(10분) · 녹화 합치기(15분)** 마감을 지키나 | 결과 · 채점은 작업자 1개, 녹화 합치기는 1코어 작업자 1개다 |
| Q5 | 웹 · API(BE · FE)는 초당 몇 요청까지 응답 시간을 지키나, 무엇이 먼저 막히나 | 로그인(PBKDF2) · 매 요청 회원 확인(DB) · FE 서버 렌더링이 CPU를 나눠 쓴다 |
| Q6 | 오래 돌리면 무엇이 쌓이나(메모리 누수, Redis 192MB, CPU 버스트 크레딧) | Redis가 차면 쓰기가 거부되어 로그인까지 막힌다(`noeviction`) |

범위 밖:

- 외부 서비스(GMS · Soniox · ElevenLabs · Jev) 자체의 성능. 우리 서버가 아니고, 대량 호출은 비용 · 다른 팀(GMS 공용)에 영향을 준다(3.4)
- 보안 · DDoS 내성, 관리 페이지(`/admin/`), 회사 카드 파이프라인
- 운영 서버 자체에 부하를 주는 것(테스트 서버로 대신한다, 3.1)

## 3. 테스트 환경 · 원칙

### 3.1 대상: 운영과 같은 사양의 테스트 서버(EC2) **[결정]**

운영 서버(`hangguet.co.kr`)에는 부하를 주지 않는다. 운영과 같은 사양의 EC2를 따로 만들고, 운영과 **같은 이미지 태그 · 같은 compose**(`deploy/prod/compose.yml`)로 띄운다. 테스트가 끝나면 서버째 지운다(3.7).

- 왜:
  - 실제 사용자에게 영향이 없다. 한계 탐색(L3)에서 에이전트 OOM(H6)처럼 진행 중인 면접이 모두 끊기는 지점까지 끝까지 확인할 수 있다
  - 테스트 데이터가 운영 DB · S3 · 관리자 지표에 섞이지 않는다. 운영 DB에서 테스트 데이터를 직접 지우는 작업이 없어진다
  - 테스트 시간대 · 배포 금지 · 0시 전 삭제 같은 운영 쪽 제약 없이 같은 회차를 몇 번이고 다시 돌릴 수 있다
  - 개발 서버(미니PC)는 LiveKit Cloud를 쓰므로 미디어 쪽을 잴 수 없어 대신할 수 없다
- 대가: 결과는 "운영과 같은 사양의 다른 서버"에서 잰 값이다. 3.1.2의 차이를 결과에 같이 적고, 운영에 옮길 때 감안한다

#### 3.1.1 서버 사양 **[제안]**

| 항목 | 값 | 왜 |
|---|---|---|
| 계정 · 리전 | **우리 AWS 계정**(인프라 예산 $100, S3를 쓰는 계정) **[결정]**, 서울(`ap-northeast-2`) | 인스턴스 유형 · 크레딧 모드 · 보안 그룹 · CloudWatch를 우리가 직접 정할 수 있어 운영과 같은 사양을 맞출 수 있다. 같은 리전이라 노트북 → 서버 지연이 운영과 비슷하다 |
| 예상 요금 | t3.xlarge 서울 시간당 약 $0.2. 켜 두는 시간 30~50시간에 디스크 · 탄력적 IP · 데이터 전송을 더해 **대략 $10~20(추정)** | 예산 $100 안에서 S3 비용과 나눠 쓴다. 회차가 없는 날은 서버를 중지해 요금을 줄인다(3.1.4) |
| 인스턴스 | `t3.xlarge`(4 vCPU · 16GiB), CPU 크레딧 **standard** 모드 | 운영 Lightsail($84 플랜, 4 vCPU · 16GB)과 코어 · 메모리가 같고, 같은 버스트형에 기준치도 vCPU당 40%로 같다. T3의 기본값인 unlimited 모드는 크레딧이 바닥나도 느려지지 않고 요금을 더 내므로, 운영처럼 기준치로 떨어지는 standard로 둔다(H11) |
| 디스크 | gp3, 약 100GB | 녹화는 S3로 가고 Loki도 7일만 보관해 테스트에는 이 정도면 충분하다 |
| OS · 런타임 | Ubuntu 24.04, Docker · Compose를 운영과 같은 버전, 스왑 4GB(`vm.swappiness=10`), 시간대 `Asia/Seoul`, 로그 10MB × 3 | 배포 계획 3.1 셋팅을 그대로 따라 서버 설정 차이를 없앤다 |
| 공인 IP | 탄력적 IP | 서버를 껐다 켜도 IP가 그대로라 TURN DNS · LiveKit 외부 IP를 다시 맞추지 않아도 된다 |
| 보안 그룹 | 들어오는 것: 22/tcp(팀 IP만), 7881/tcp, 7882/udp, 3478/udp, 443/tcp | 운영(배포 계획 5.2)과 같은 포트. 웹 · 시그널링 · Grafana는 운영처럼 Tunnel로만 받는다 |

#### 3.1.2 운영과 다른 점 (결과에 같이 적는다)

| 항목 | 차이 | 결과를 볼 때 |
|---|---|---|
| CPU 크레딧 잔량 | 기준치는 둘 다 vCPU당 40%로 같다(배포 계획 3.1). 다만 테스트를 시작할 때 쌓여 있는 크레딧 양은 서버마다 다르다. **T3 standard는 크레딧 0으로 시작한다**(시작 크레딧은 T2에만 있다) | 만든 직후에는 40%를 넘을 수 없어 결과가 실제보다 나쁘게 나온다. 서버를 만든 뒤 **24시간 이상 켜 두어** 크레딧을 가득 채운 다음 첫 회차를 한다(운영은 평소 한가해 크레딧이 차 있다고 본다). 중지해도 크레딧은 7일간 남는다. 시작할 때 크레딧 잔량(`CPUCreditBalance`)을 회차마다 적고, 운영의 최악 조건(크레딧이 바닥난 상태)은 크레딧을 다 쓴 뒤의 구간으로 본다 |
| 물리 CPU · 디스크 · 네트워크 | 코어 수가 같아도 CPU 세대, 디스크(gp3 기본 3,000 IOPS), 네트워크 대역폭이 다를 수 있다 | 운영과 직접 비교하지 않는다 **[결정]**. 왜: 운영에 부하를 주지 않는다는 결정을 지키고, 코어 · 메모리 · CPU 기준치가 같아 차이가 작다고 본다. 결과에 "테스트 서버 기준"이라고 적는다 |
| DB 데이터 양 | 테스트 서버 DB는 테스트 계정 · 지원서만 있는 상태에서 시작한다(3.6) | 데이터가 적으면 같은 조회도 운영보다 빠르게 나온다. 운영도 막 열어 데이터가 적으므로 차이가 작다고 본다. 결과에 "빈 DB 기준"이라고 적는다 |
| 주소 · 버킷 · 키 | 테스트 전용(3.1.3 · 3.1.4) | 성능에는 영향이 없다 |

#### 3.1.3 구성 · 배포 **[제안]**

운영 compose를 그대로 쓰고, 테스트 서버에서 달라야 하는 값만 덮어쓰기 파일(`loadtest/server/compose.loadtest.yml`)로 바꾼다.

```bash
IMAGE_TAG=<운영에 떠 있는 태그> docker compose \
  -f deploy/prod/compose.yml -f loadtest/server/compose.loadtest.yml up -d
```

- 이미지는 **운영에 떠 있는 것과 같은 태그**를 받는다. 왜: 운영에서 도는 코드를 그대로 잰다
- 컨테이너 이름(`a301-prod-*`)은 바꾸지 않는다. 왜: Grafana 대시보드 · Alloy 로그 수집 · Prometheus 대상이 컨테이너 이름으로 되어 있어 그대로 쓸 수 있고, 서버가 달라 운영과 겹치지 않는다
- CI 잡을 만들지 않고 서버에서 손으로 띄운다. 왜: 몇 번 띄우고 지울 서버라 러너 · 잡을 만드는 비용이 더 크다
- Docker Hub는 운영 pull 토큰을 쓰지 않고 **테스트용 읽기 전용 토큰**을 따로 만들어 정리할 때 지운다. 왜: 운영 토큰을 다른 서버에 복사하지 않는다
- 비밀값(`DB_PASSWORD` · `JWT_SECRET` · `INQUIRY_ENCRYPTION_KEY` · LiveKit 키 · Grafana 비밀번호)은 테스트 서버에서 새로 만들어 `.env`(권한 600)에 둔다. 운영 값을 쓰지 않는다. 외부 API 키(Soniox · ElevenLabs · Jev · GMS)는 하나뿐이라 운영과 같은 키를 쓴다(사용량 한도를 운영과 나눠 쓴다, 3.4)

덮어쓰기 파일에서 바꾸는 값:

| 항목 | 운영 | 테스트 서버 |
|---|---|---|
| 웹 · 시그널링 · Grafana 주소 | `hangguet.co.kr` · `rtc.` · `grafana.` (Tunnel `a301-prod`) | `lt.hangguet.co.kr` · `rtc-lt.hangguet.co.kr` · `grafana-lt.hangguet.co.kr` (Tunnel `a301-loadtest`, 토큰은 `.env`) |
| `LIVEKIT_PUBLIC_URL` · `GF_SERVER_ROOT_URL` | 운영 주소 | 위 테스트 주소 |
| TURN | `turn.hangguet.co.kr` 인증서 | `turn-lt.hangguet.co.kr`(프록시 끈 A 레코드 → 탄력적 IP). 인증서는 운영처럼 certbot DNS 방식으로 받고, 이 도메인을 적은 테스트용 `loadtest/server/livekit.yaml`을 붙인다 |
| S3 버킷 · 키 | `hanggeut-a301-prod`, IAM `a301-prod-app` · `a301-prod-egress` | 테스트 전용(3.1.4) |
| `LLM_CHAT_URL`(AI 작업자) | GMS | GMS 스텁(3.4). 보정(S0)만 GMS |
| 소셜 로그인 키 | 있음 | 넣지 않는다(시나리오에 없음) |
| 회사 카드 버킷(`COMPANY_S3_BUCKET`) | `hanggeut-a301-company` | 비운다. 비우면 BE의 회사 카드 적재가 꺼진다(`CompanyCardProperties.enabled()`) |

- 주소를 한 단계 하위 도메인(`rtc-lt.`)으로 짓는 이유: Cloudflare 무료 인증서는 `*.hangguet.co.kr` 한 단계만 덮어 `rtc.lt.hangguet.co.kr` 같은 두 단계 이름은 인증서 오류가 난다

#### 3.1.4 S3 · IAM **[제안]**

테스트 전용 버킷(`hanggeut-a301-loadtest`, 이름 **[제안]**) 하나와 IAM 사용자 둘(앱 · 녹화)을 운영(배포 계획 6.1 · 6.2)과 같은 정책 모양으로 만든다. CORS 출처만 `https://lt.hangguet.co.kr`로 둔다.

- 왜 운영 버킷을 쓰지 않나: 운영 버킷 CORS는 `https://hangguet.co.kr`만 받아 테스트 주소에서 올리는 요청이 막힌다. 운영 키를 다른 서버에 두게 되고, 테스트 녹화가 운영 녹화와 섞인다
- 회사 카드 버킷(`hanggeut-a301-company`) 권한은 주지 않는다. `COMPANY_S3_BUCKET`을 비워 적재를 끈다(3.1.3). 왜: 권한이 없어도 BE는 뜨지만(적재 스케줄러가 오류를 잡고 경고만 남긴다) 매시 경고 로그가 쌓이고, 부하 테스트 시나리오에는 회사 카드 적재가 없다
- 회차 사이에 며칠 쉬면 서버를 **중지**해 둔다. 중지 중에는 디스크 · 탄력적 IP 요금만 나간다

### 3.2 부하 발생기: 팀 노트북 **[결정]**

부하는 **팀 노트북**에서 보낸다. 기본은 인프라 담당 노트북 1대이고, 브라우저 시나리오가 한 대를 넘으면 팀원 노트북을 더한다.

| 항목 | 내용 | 왜 |
|---|---|---|
| 기본 장비 | 인프라 노트북(Samsung 960XGL): Core Ultra 7 155H(16코어 · 22스레드), 메모리 32GB, Windows 11, **Wi-Fi만 있음**(유선 포트 없음) | 추가 비용 없이 바로 쓸 수 있다. 테스트 서버 밖에서 보내므로 서버 자원을 재는 데 섞이지 않는다 |
| 웹 · API(S1~S4) | 노트북 1대로 충분하다. k6 HTTP는 VU당 메모리가 작아 수백 요청/초도 노트북 한 대가 감당한다 | L2가 약 30 요청/초이고, 한계 탐색도 노트북 CPU보다 Wi-Fi · 서버가 먼저 막힌다 |
| 브라우저(S5) | 노트북 1대에 Chromium **약 10~15개**까지로 본다 **[확인 필요]** S0에서 1개당 CPU · 메모리를 재서 정한다. 넘으면 팀원 노트북을 더해 VU를 나눈다(예: 동시 20건 = 노트북 2대 × 10건) | Chromium 1개가 약 300~500MB를 쓰고, 시선 추적(`use-gaze-tracker.ts`)과 영상 인코딩이 노트북 CPU를 쓴다. 평소 다른 프로그램이 이미 20GB 가까이 쓰고 있어 실제로 쓸 수 있는 메모리는 그보다 작다 |

**어디서 돌리느냐(네트워크)에 따라 재는 대상이 달라진다.** 회차마다 어느 네트워크에서 했는지 8장에 적는다.

| 네트워크 | 미디어 경로 | 장점 | 주의 |
|---|---|---|---|
| SSAFY Wi-Fi(강의실) | 바깥 TCP를 443만 허용하므로(배포 계획 4.2) 면접 미디어가 **TURN/TLS 443**으로 간다 | 시연 · 발표 장소와 같은 조건이다. TURN 중계는 LiveKit에 가장 무거운 길이라 결과가 보수적(최악 기준)이 된다 | ① 캠퍼스 전체가 공인 IP 하나를 같이 쓴다. Cloudflare 규칙은 IP가 아니라 테스트 서버 주소에 걸어 문제가 없지만(3.3), 같은 Wi-Fi의 다른 교육생 회선을 우리가 차지한다(영상 20개 업로드는 수십 Mbps) ② 학내 방화벽 · 대역폭 제한이 막을 수 있다 ③ 운영 시간 밖에는 쓸 수 없을 수 있다 |
| 집 · 휴대폰 테더링 | UDP 7882로 바로 간다(일반 사용자 대부분의 경로) | 실제 사용자 다수와 같은 경로를 잰다 | 가정 회선 업로드가 영상 수 개~수십 개를 감당하는지 S0에서 먼저 본다(Wi-Fi 1개 업로드 속도 측정) |

- 권장 **[제안]**: 웹 · API(S1~S4)는 어디서 해도 결과가 같으므로 편한 곳에서 한다. 실시간 면접(S5)은 **두 네트워크에서 한 번씩** 해서 UDP 경로와 TURN 경로의 동시 면접 한계를 따로 적는다. 시연이 강의실이면 TURN 결과가 시연 날의 한계다
- Wi-Fi는 지터 · 패킷 손실이 원래 있다. S0에서 면접 1건일 때의 패킷 손실 · 지터를 **기준값**으로 적고, 동시 수를 늘렸을 때는 기준값보다 늘어난 만큼을 서버 탓으로 본다. 노트북 한 대에서 늘어나는지, 여러 노트북에서 같이 늘어나는지도 비교한다(노트북 Wi-Fi만의 문제인지 가린다)

### 3.3 Cloudflare **[제안]**

`hangguet.co.kr`은 **Free 요금제**다. 11/02 확인 결과 사용자 지정 규칙 · 속도 제한 규칙 · 관리형 규칙이 **하나도 없고** Bot Fight Mode도 **꺼져 있다**. 그래서 **건너뛰기 규칙 없이 시작**한다. S0에서 발생기 요청이 막히면(403 · 429 · 챌린지 페이지) 그때 **테스트 서버 주소(`lt.` · `rtc-lt.` · `grafana-lt.`)로 가는 요청만** 건너뛰는 규칙을 둔다 **[제안]**. 규칙을 만들었다면 테스트 서버를 지울 때 같이 지운다(3.7).

- 규칙이 없어도 Cloudflare의 기본 보호(HTTP DDoS 방어 · Browser Integrity Check)는 항상 켜져 있다. 목표 부하(약 30~60 요청/초)에서 걸릴 가능성은 낮지만, 걸리면 k6 결과에 403 · 503이 보이므로 S0 · S1에서 먼저 확인한다

- 왜: 발생기 IP 하나에서 실제 사용자 수백 명 분량이 나가므로, Cloudflare가 공격으로 보고 막으면 서버까지 부하가 가지 않는다(H12)
- 왜 IP나 비밀 헤더가 아니라 주소로 거나: 규칙이 테스트 서버 주소에만 걸리므로 운영 주소(`hangguet.co.kr`)의 보호는 그대로다. SSAFY Wi-Fi처럼 캠퍼스 전체가 공인 IP 하나를 같이 쓰는 곳(3.2)에서도 운영에는 영향이 없고, 헤더를 넣기 어려운 브라우저 시나리오(S5)도 같은 규칙으로 통과한다
- 테스트 서버 주소는 테스트하는 동안만 있는 주소라 보호를 풀어 두는 위험이 작다. 그래도 S0에서 규칙이 실제로 적용되는지(403 · 429가 없는지) 먼저 본다
- Free 요금제에서 할 수 있는 것: 사용자 지정 규칙(도메인당 5개)에 Skip 동작을 써서 테스트 서버 주소만 건너뛸 수 있다. 다만 **Bot Fight Mode는 규칙으로 건너뛸 수 없다**. **꺼져 있다**(11/02 확인)는 것을 확인했으므로 건드릴 것이 없다. 나중에 켜면 도메인 전체에 걸리므로, 테스트하는 동안만 끄고 끝나면 다시 켜야 한다

### 3.4 외부 API · 스텁 **[제안]**

면접 1건이 외부 API를 부른다: GMS(PLAN · 채점 · 결과), Soniox(STT, 답변 음성 초당 과금), ElevenLabs(TTS, 글자 수 과금), Jev(리액션 · 자소서 검증). 동시 수십 건을 실제 API로 돌리면 비용이 크고, GMS는 SSAFY 공용이라 다른 팀까지 느려질 수 있다. 그래서 두 층으로 나눈다.

| 층 | 무엇 | 언제 |
|---|---|---|
| **보정(실제 API)** | 실제 API로 면접 1~3건. 외부 API에 묶인 단계의 **지연 시간**을 잰다(스텁 지연값의 근거). 사용량 · 비용은 재지 않는다 **[결정]**(이 테스트는 서버 자원을 보는 것이 목적이다) | 맨 처음(6장 S0) |
| **부하(스텁)** | 외부 API 대신 **보정에서 잰 지연 시간을 흉내 내는 스텁**을 부른다 | 동시 수가 큰 시나리오(S3 · S4 · S5 · S6) |

- GMS: `LLM_CHAT_URL`이 환경 변수라 **코드를 고치지 않고** 스텁(OpenAI 호환 `chat/completions`, 지연 시간 · JSON 응답 고정)으로 바꿀 수 있다. 테스트 서버의 덮어쓰기 파일(3.1.3)에서 AI 작업자의 `LLM_CHAT_URL`을 스텁으로 두고, 보정(S0)만 GMS로 띄운다. 운영 설정은 건드리지 않으므로 원래대로 되돌리는 작업이 없다
  - 스텁은 테스트 서버 안에 작은 컨테이너(`cpus: 0.25`)로 띄운다 **[제안]**. 왜: 지연만 흉내 내고 연산이 거의 없다. 회차마다 스텁 컨테이너 CPU를 같이 보고 무시할 만한지 확인한다
- Soniox · ElevenLabs · Jev: 주소가 코드에 고정되어 있다(`ai/app/agent/stt.py`, `tts.py`, `jev.py`, `ai/app/interview/cover_letter.py`). 스텁을 쓰려면 **주소를 환경 변수로 바꿀 수 있게 하는 AI 작업**이 먼저 필요하다 **[제안]**
  - 그 작업 전에는 실시간 면접 시나리오(S5)를 실제 Soniox로 돌린다. 이때 ElevenLabs · Jev 키를 비우면 질문 글만 · 리액션 없이 진행되어 비용은 줄지만 **실제보다 가벼운 부하**가 되므로 결과에 그렇게 적는다
- 스텁 지연 시간은 보정에서 잰 값의 p50 · p95를 쓴다. 왜: 작업자는 응답을 기다리는 동안 다음 작업을 못 하므로, 지연 시간이 곧 처리량이다. 스텁이 즉시 응답하면 H1 · H8을 과소평가한다

### 3.5 중단 조건(즉시 멈춤) **[제안]**

테스트 서버라 실제 사용자를 지키는 조건은 없다. 대신 **측정값을 믿을 수 없게 되거나, 외부 서비스에 되돌리기 어려운 영향이 생길 때** 멈춘다. k6 `thresholds`의 `abortOnFail`과 사람이 보는 Grafana 둘 다로 건다. 하나라도 걸리면 k6를 멈추고 원인을 기록한다.

- 외부 API: 외부 API(특히 SSAFY 공용 GMS)가 429 · 오류를 돌려줌(다른 팀에 영향)
- 발생기: 노트북 CPU · 메모리 · Wi-Fi가 포화됨(3.2). 그 회차 결과는 쓰지 않는다
- 서버: 디스크 85% 이상, SSH가 응답하지 않음. 왜: 로그 · DB가 디스크를 채우면 서버를 되살리기 어렵다
- 한계 판정 기준(5.1)이 깨지는 것은 측정 대상이라 **중단 조건이 아니다**. 품질 · 지속 가능 한계가 나와도 계속 올린다. 기능 한계가 나오면 그 단계까지 기록하고 그 시나리오는 더 올리지 않는다(그 위는 실패만 늘어난다). 에이전트 OOM(H6)도 끝까지 확인한다

멈춘 뒤 서버가 스스로 돌아오지 않으면 해당 컨테이너만 `docker compose restart <서비스>`로 다시 띄운다. 그래도 안 되면 다음 회차 전에 서버를 다시 만든다.

### 3.6 테스트 데이터 **[제안]**

| 항목 | 방법 | 왜 |
|---|---|---|
| 계정 | 테스트 서버에 이메일 `loadtest+NNN@loadtest.hangguet.co.kr`로 미리 가입(1.2). 비밀번호는 발생기 환경 변수로만 둔다 | 테스트 서버 DB에는 테스트 계정만 있지만, 패턴을 정해 두면 k6 계정 목록(`accounts.js`)을 만들고 결과를 볼 때 헷갈리지 않는다. 가입은 회차 전에 끝내 가입 부하가 결과에 섞이지 않게 한다 |
| 지원서 | 계정마다 1개를 미리 만든다. 자소서는 지어낸 글(개인정보 없음) 몇 종류를 돌려 쓴다 | 지원서 저장은 자소서 검증(Jev)을 부르므로, 지원서 저장 자체를 재는 S3 말고는 미리 만들어 재사용한다 |

| 데이터 양 **[결정]** | 테스트 계정 · 지원서 말고는 **미리 채우지 않는다**. 운영 데이터도 복사하지 않는다 | 운영은 10월 말에 열어 데이터가 아직 적으므로 빈 DB와 차이가 작다. 시드 작업이 가장 적다. 운영 데이터는 개인정보라 테스트 서버로 옮기지 않는다. 운영 데이터가 많이 쌓이면 그때 다시 잰다(3.1.2) |

### 3.7 테스트 서버 정리 **[제안]**

모든 회차가 끝나면 테스트 서버와 테스트용으로 만든 것을 **모두 지운다**. 운영 쪽에는 지울 것이 없다.

- 왜 서버째 지우나: 테스트 데이터 · 비밀값이 어디에도 남지 않고, 켜 둔 시간만큼 요금이 나간다

**순서**:

1. **결과 내보내기**: 서버를 지우면 Prometheus · Loki 데이터도 같이 사라지므로 먼저 남긴다
   - 회차마다 Grafana 대시보드에서 회차 구간 화면을 저장한다(8장 보고서용)
   - 지우기 직전 EBS 스냅샷을 하나 떠 둔다 **[제안]**. 결과를 다시 볼 일이 생기면 스냅샷으로 서버를 다시 띄워 지표를 본다. 결과 정리(8.1)를 팀에 공유하면 스냅샷도 지운다
2. EC2 종료(terminate), EBS 볼륨이 같이 지워졌는지 확인, 탄력적 IP 해제(붙인 서버가 없어도 요금이 나간다)
3. S3 테스트 버킷을 비우고 삭제, 테스트 IAM 사용자 · 액세스 키 삭제
4. Cloudflare: Tunnel `a301-loadtest`, DNS(`lt` · `rtc-lt` · `grafana-lt` · `turn-lt`), 건너뛰기 규칙(3.3) 삭제. Bot Fight Mode는 꺼져 있어 되돌릴 것이 없다(3.3)
5. Docker Hub 테스트용 pull 토큰 삭제
6. 남는 것 확인: 외부 API 키는 운영과 같은 키라 지우지 않는다. 운영 설정(`deploy/prod/`)은 건드리지 않았으므로 되돌릴 것이 없다

### 4.1 사용자 한 명이 만드는 요청 (화상 면접 1회)

코드에서 확인한 실제 호출이다. k6 스크립트는 이 순서와 간격을 그대로 흉내 낸다.

| 단계 | 화면 → 서버 | 간격 · 횟수 | 서버 쪽 일 |

### 4.2 부하 단계 **[결정]**(L1 · L3 값은 **[제안]**)

부하는 아래 단계로 올린다. 단계는 넘어야 할 목표가 아니라 **한계(5.1)를 찾아가는 중간 지점**이다. L2는 **동시 화상 면접 20건**으로 둔다. 배포 계획 3.2의 추정(동시 면접 약 20~30건)의 아래쪽이라, "지금 서버가 20건을 감당하는가"를 결과에서 바로 읽을 수 있다.

| 단계 | 동시 화상 면접 | 면접 만들기 몰림 | 로그인 몰림 | 웹 · API | 의미 |
|---|---|---|---|---|---|
| L1 평상시 | 5건 | 1분에 5건 | 1분에 30건 | 약 5 요청/초 | 지금 규모. 여기서 이미 한계가 나오면 바로 고친다 |
| L2 확인 지점 | 20건 | 1분에 20건 | 1분에 100건 | 약 30 요청/초 | 발표 · 시연처럼 사람이 한꺼번에 몰리는 날 |
| L3 한계 탐색 | 25 · 30 · 35 …(기능 한계가 나올 때까지) | 〃 | 〃 | 〃 | 이 서버 한 대의 한계값 |

- 왜 면접 만들기 "1분에 20건": 발표 직후 청중이 같이 면접을 만들면 동시 면접 수와 같은 수가 짧은 시간에 몰린다. PLAN 작업자가 1개라 이 경우가 가장 위험하다(H1)

## 5. 한계 판정 기준 · 측정 지표

### 5.1 한계 판정 기준 **[결정]**

이 테스트는 합격 · 불합격을 가리지 않는다. 목적은 **이 서버가 동시에 어디까지 견디는지, 그때 자원이 얼마나 드는지** 알아서 스케일 아웃을 정하는 것이다(1장). 아래 기준은 "어디까지를 견딘다고 볼지"를 정하는 선이다. 부하를 올리다가 각 종류에서 기준이 **처음 깨진 단계**를 그 시나리오의 한계로 기록한다.

- 왜 기준이 필요한가: 서버는 대부분 한 번에 죽지 않고 점점 느려진다. 기준 없이는 "한계가 몇 건인지"가 정해지지 않고, 스케일 아웃을 언제 해야 하는지도 정할 수 없다

| 한계 | 기준(하나라도 깨지면 그 단계가 한계) | 의미 | 어디서 보나 |
|---|---|---|---|
| **기능 한계** | 오류율 ≥ 1%. AI 작업이 코드의 마감을 넘겨 실패(질문 준비 3분 `TIMED_OUT`, 결과 10분, 녹화 합치기 15분, 자소서 검증 8초 `COVER_LETTER_CHECK_UNAVAILABLE`). 면접방 입장 실패. 컨테이너 OOM · 재시작 | 서비스가 실제로 깨진다. **이 부하 전에 스케일 아웃이 반드시 필요한 선** | k6 `http_req_failed` · 사용자 지표(`plan_ready_seconds` · `evaluation_seconds`), 지원서 저장 응답, DB `recordings.status`, Grafana 컨테이너 줄 |
| **품질 한계** | API 조회 p95 ≥ 300ms, 쓰기(5.1 · 5.4 · 5.8 등) · 로그인 p95 ≥ 1s, 페이지(FE 서버 렌더링) p95 ≥ 1.5s. 패킷 손실 ≥ 2%, 지터 p95 ≥ 30ms(S0에서 잰 Wi-Fi 기준값에서 늘어난 만큼, 3.2). 답변 끝 → 다음 질문 p95 ≥ 5초 | 깨지지는 않지만 사용자가 느리다고 느낀다. **스케일 아웃을 준비할 선** | k6 `http_req_duration{type:…}`, Grafana LiveKit 줄, 질문 전환은 테스트 후 DB에서 `answers` · `interview_questions.created_at` 간격 계산 **[제안]** |
| **지속 가능 한계** | 서버 CPU 평균 ≥ 40%가 10분 넘게 이어짐 | 이 위로 오래 가면 크레딧이 바닥나 서버 전체가 40%로 묶인다. 짧은 피크는 버티지만 **평소 부하는 이 아래여야 한다** | Grafana 전체 현황, CloudWatch `CPUCreditBalance` |

- 왜 지속 가능 한계를 따로 두나: 서버 CPU 기준치가 vCPU당 40%다(배포 계획 3.1). 평균 40%를 넘는 동안에는 크레딧을 쓰고, 다 쓰면 40%로 묶인다. 그래서 같은 부하라도 30분은 버티고 몇 시간은 못 버틸 수 있다. "10분 넘게"는 단계 하나를 유지하는 시간(면접 1건 길이)에 맞췄다. 몇 초짜리 순간 피크는 크레딧에 주는 영향이 작아 세지 않는다
- 왜 AI 작업은 마감 초과만 기준으로 두나: 마감을 넘으면 작업이 실패 처리되어 화면이 "실패"로 바뀌므로 기능이 깨진 것이다. 그 전까지 걸린 시간 · 대기열 길이 · 작업자별 분당 처리 건수는 측정값으로 기록한다(8.1). GMS는 스텁으로 지연을 고정하므로(3.4) 남는 대기 시간은 우리 서버의 작업자 구성이 만든 값이다
- **자원은 판정하지 않고 측정한다**: 컨테이너별 CPU · 메모리(`mem_limit` 대비), Redis 메모리, DB 연결 수, CPU `steal`, 네트워크 송수신을 단계마다 기록한다. 스케일 아웃 규모를 계산하는 재료다(8.1). 운영 대시보드의 색(70% 노랑 · 85% 빨강)은 화면에서 보기 위한 표시로만 쓴다

결과는 시나리오마다 아래 모양으로 남긴다(8.1).

```
S5 동시 화상 면접 (UDP 경로)
  기능 한계: 30건 — 에이전트 OOM (H6)
  품질 한계: 25건 — 다음 질문까지 p95 7초 (H8)
  지속 가능 한계: 15건 — CPU 평균 42%
  1건당: 에이전트 메모리 +130MB, CPU +2.5%, 서버 송신 +0.4Mbps
```
(숫자는 예시)

### 5.2 결과 수집

- k6: 회차마다 요약(`--summary-export`)과 HTML 보고서(`K6_WEB_DASHBOARD=true`, `K6_WEB_DASHBOARD_EXPORT`)를 남긴다
- 서버: 테스트 서버에 운영과 같은 Grafana 대시보드(**A301 운영 서버** · **A301 운영 서버 로그**)가 그대로 뜬다(`grafana-lt.hangguet.co.kr`). 회차 시작 · 끝 시각을 기록해 같은 구간을 본다. 크레딧 잔량(`CPUCreditBalance`)은 CloudWatch에서 같은 구간을 본다
- k6 지표를 서버 Prometheus로 보내지 않는다 **[제안]**. 왜: Prometheus는 운영과 같이 바깥에 열려 있지 않고, 원격 쓰기를 열려면 설정 변경 · 포트 노출이 필요하다. 시각만 맞추면 두 화면을 나란히 비교할 수 있다
- 서버를 지우면 서버 쪽 지표 · 로그도 사라지므로, 정리(3.7) 전에 결과를 내보낸다
- 회차가 끝나면 8장 표에 결과를 적고, 정리한 보고서는 `loadtest/report/<시나리오>-<날짜>.md`에 둔다(예: [S0 결과](../../loadtest/report/s0-2026-11-02.md)). k6 원본 출력 · 화면 캡처는 `loadtest/results/`(커밋하지 않음)에 남는다 **[결정]**(개인정보 · 토큰이 들어 있지 않은지 확인한 뒤)

## 6. 시나리오

모든 시나리오는 L1 → L2 → L3 순서로 올린다. 단계마다 5.1의 세 한계(기능 · 품질 · 지속 가능)를 확인해 처음 깨진 단계를 적고, **기능 한계가 나올 때까지** 올린다. 단계마다 최소 5분(면접은 면접 1건 길이 이상) 유지해 값이 안정된 뒤 잰다.

| ID | 이름 | 확인 가설 | 실행 방식 | 외부 API | 부하 모양 |
|---|---|---|---|---|---|
| S0 | 스모크 · 보정 | — | 브라우저 1 + HTTP 1(`s0-browser.js` · `s0-smoke.js`) | **실제** | HTTP: 지원서 저장 → 질문 준비 → 시작 → 바로 끝내기. 브라우저: 화상 면접 1건 전체 흐름. 스크립트 확인, 외부 API 지연 측정(3.4), 면접 1건당 서버 자원 |
| S1 | 웹 · API 혼합 | H4 · H5 | HTTP(`ramping-arrival-rate`) | 없음 | 홈 · 통계 · 달력 · 기록 · 결과 · 공지 조회를 섞어 5 → 30 → 60 … 요청/초로 올리고 10분 유지 |
| S2 | 로그인 몰림 | H3 | HTTP(`ramping-arrival-rate`) | 없음 | 1분 동안 30 → 100 → 200 …건. 같은 시간에 S1을 L1로 깔아 다른 API가 느려지는지 본다 |
| S3 | 지원서 저장 몰림 | H2 | HTTP(`shared-iterations`) | Jev(스텁 권장) | 동시 1 · 3 · 5 · 10 · 20건을 한 번에 저장 |
| S4 | 면접 만들기 몰림 | H1 · H5 | HTTP | GMS 스텁 | 1분 안에 5 · 10 · 20 · 30건 만들기 → 사용자마다 2초 폴링(FE 페이지 다시 그리기와 같은 요청)으로 READY까지 시간 측정 |
| S5 | 동시 화상 면접 | H6 · H7 · H8 · H9 | **k6 browser**(가짜 카메라 · 마이크) | Soniox 실제(3.4), GMS 스텁 | 동시 면접 1 · 5 · 10 · 15 · 20 · 25 …건. 단계마다 면접 1건이 끝까지 돈다. 끝난 뒤 결과 · 합치기 대기열이 비는 시간까지 잰다 |
| S6 | 피크 혼합 | 전부 | S1 + S2 + S4 + S5 동시 | S5와 같음 | 네 시나리오를 같은 단계 비율로 섞어 L1 → L2 → L3로 올린다. 따로 돌렸을 때보다 한계가 얼마나 낮아지는지 본다. L2는 30분 유지("발표 직후" 상황) |
| S7 | 장시간(소크) | H10 · H11 | S1 + S5 | S5와 같음 | S5에서 찾은 **지속 가능 한계 바로 아래** 부하로 2시간. 그 부하를 정말 계속 버티는지, 메모리 · Redis · 디스크(Loki)가 쌓이는지, `steal` · 크레딧이 어떻게 변하는지 본다 |

시나리오별 주의:

- **면접 진행은 브라우저로만 할 수 있다**(11/02 S0에서 확인): 채팅 면접도 질문은 에이전트가 면접방(LiveKit)에서 내고, 에이전트는 사용자가 방에 들어올 때까지 기다린다(`ai/app/agent/main.py` `first_participant`). BE의 "지금 질문"(5.5)은 에이전트가 보내는 `question.started`를 받아야 생기므로, k6 HTTP로 면접을 시작하면 첫 질문이 나오지 않는다. 그래서 질문 · 답변 · 채점(H8) · 녹화(H9) 부하는 브라우저 시나리오(S5)로만 만든다. HTTP 시나리오가 면접을 시작했다면 5.8로 바로 끝내 에이전트를 놓아준다(답변 0개 → `ABORTED`)
- **S1 · S4 요청 방식**: 조회 · 폴링은 실제 화면처럼 **FE 페이지**로 보낸다. 쿠키 `hk_access`에 BE 액세스 토큰을 넣고, 다시 그리기는 `RSC: 1` 헤더로 같은 페이지를 GET한다. 쓰기(5.1 · 5.4 · 5.8)는 FE의 서버 액션 대신 **BE API를 직접**(`/be/api/v1`, `Authorization: Bearer`, `Idempotency-Key`) 부른다
  - 왜: 폴링 비용의 대부분이 FE 서버 렌더링이라(H5) BE만 부르면 FE 부담을 재지 못한다. 서버 액션은 빌드마다 바뀌는 액션 id가 필요해 스크립트로 흉내 내기 어렵고, 쓰기 요청은 수가 적어 FE 부담이 작다
  - Next.js는 RSC 요청 주소에 헤더로 계산한 `_rsc` 쿼리가 없으면 307로 다시 보낸다(11/02 S1 시험 실행에서 확인). 헤더가 `RSC: 1`뿐이면 기대값이 빈 값이라 주소에 `_rsc`만 붙인다(`loadtest/lib/api.js` `page()`)
- **S4에서 면접 시작은 하지 않는다**: 5.4를 부르면 에이전트가 배정되는데, 아무도 들어오지 않는 방에 에이전트 프로세스가 떠 S5 결과를 흐린다. 만든 면접은 그대로 둔다(READY 상태는 연습 기록에 들어가지 않는다)
- **S5 가짜 장치**: `K6_BROWSER_ARGS`로 Chromium에 `use-fake-ui-for-media-stream`, `use-fake-device-for-media-stream`, `use-file-for-fake-audio-capture=<답변.wav>`, `use-file-for-fake-video-capture=<얼굴.y4m>`를 넘긴다. 실제 FE 화면(로그인 → 면접 만들기 → 장치 점검 → 면접방)을 그대로 밟는다
  - 노트북 1대에 Chromium 약 10~15개까지로 본다(3.2). 그 이상은 팀원 노트북을 더해 노트북마다 같은 k6 스크립트를 `N`(면접 수) · 계정 범위만 다르게 넣어 **같은 시각에** 시작한다(예: 노트북 A는 계정 1~10, B는 11~20). 노트북끼리 시계가 다르면 시작이 어긋나므로 시작 시각을 환경 변수로 주고 그때까지 기다리게 한다 **[제안]**
  - 영상 인코딩과 면접관 3D 화면이 노트북 CPU를 쓴다. 노트북 CPU가 먼저 차면(3.2) 그 노트북의 면접 수를 줄이고 노트북을 늘린다. 시선 추적(`use-gaze-tracker.ts`)은 테스트 서버 이미지(master)에 아직 없다. 들어오면 CPU를 더 쓰므로 노트북 1대당 면접 수를 다시 잰다
  - 가짜 마이크 파일(`media/answer.wav`)은 Windows 음성 합성(ko-KR)으로 만든 지어낸 답변 5개에 8초 침묵을 붙인 것이다. Soniox가 실제로 인식해 답변 5개가 저장되는 것을 S0에서 확인했다. 카메라 파일은 얼굴이 아닌 단순한 영상이다(지금 화면에는 얼굴 검사가 없다)
  - 노트북 여러 대가 같은 Wi-Fi(공유기)에 붙으면 공유기 업로드가 먼저 막힐 수 있다. 노트북마다 송신량을 기록해 합이 회선 업로드에 가까우면 그 회차는 쓰지 않는다
- **S5 단계 [결정]**: S0 · S1에서 동시 3건이 이미 지속 가능 한계 부근이라 1 · 3 · 5 · 8 · 10건으로 촘촘하게 올린다(`loadtest/s5-levels.sh`). 이 규모면 GMS 호출이 면접 1건에 7번 안팎이라 실제 API로 돌린다. 부하 테스트 Chromium은 WebGL을 끈다(면접관 3D를 CPU로 그려 Chromium 1개가 노트북 약 9코어를 쓴다. 끄면 약 1.5코어 · 430MB. 화면은 정지 이미지로 대신하고 3D는 사용자 PC 일이라 서버 부하는 같다)
- **S5 동시 수 올리는 법**: `ramping-vus`가 아니라 단계마다 정해진 수의 면접을 거의 같은 때 시작하고(`per-vu-iterations`, 시작 시각 몇 초씩 분산) 그 면접이 끝날 때까지 유지한다. 왜: 면접 1건이 약 10분이라 VU 수를 계속 바꾸면 "동시 몇 건"이 흐려진다
- **에이전트 한계 회차(L3)**: H6처럼 상한 거절이 없어 넘치면 그 순간 진행 중인 면접이 모두 끊긴다. 테스트 서버라 실제 OOM이 나는 지점까지 올린다(3.5). 1건당 메모리 증가량으로 계산한 한계와 실제로 OOM이 난 동시 면접 수를 같이 적는다. 왜: 운영에서는 이 지점을 일부러 넘길 수 없으므로, 에이전트에 동시 면접 상한(AI 명세 6.5 `CAPACITY_EXCEEDED`)을 넣을 때 이 값을 근거로 쓴다

S4 예시(형태만, 실제 응답 필드는 API 명세로 맞춘다):

```js
import http from "k6/http";
import { check, sleep } from "k6";
import { Trend, Counter } from "k6/metrics";
import { uuidv4 } from "https://jslib.k6.io/k6-utils/1.4.0/index.js";
import { login, account } from "../lib/auth.js";

const BE = `${__ENV.BASE_URL}/be/api/v1`;
const planReady = new Trend("plan_ready_seconds");
const planFailed = new Counter("plan_failed");

export const options = {
  scenarios: {
    burst: { executor: "per-vu-iterations", vus: Number(__ENV.N || 5), iterations: 1, maxDuration: "6m" },
  },
  thresholds: {
    plan_ready_seconds: ["max<180"], // 마감(3분)을 넘기면 기능 한계(5.1). p95는 측정값으로 남긴다
    plan_failed: ["count<1"],
    http_req_failed: [{ threshold: "rate<0.05", abortOnFail: true }],
  },
};

export default function () {
  const me = account(__VU);
  const token = login(me);
  const auth = { Authorization: `Bearer ${token}`, "Content-Type": "application/json" };

  sleep(Math.random() * 60); // 1분 안에 흩어서 만든다
  const created = http.post(
    `${BE}/interview-sessions`,
    JSON.stringify({ applicationId: me.applicationId, persona: "COFFEE_CHAT", mode: "VIDEO" }),
    { headers: { ...auth, "Idempotency-Key": uuidv4() }, tags: { type: "write" } },
  );
  check(created, { "5.1 201": (r) => r.status === 201 });
  const id = created.json("id");
  const started = Date.now();

  // 화면과 같이 2초마다 확인한다(실제 스크립트는 FE 페이지 다시 그리기로 보낸다)
  while (Date.now() - started < 200_000) {
    sleep(2);
    const s = http.get(`${BE}/interview-sessions/${id}`, { headers: auth, tags: { type: "read" } });
    const plan = s.json("planStatus");
    if (plan === "READY") return planReady.add((Date.now() - started) / 1000);
    if (plan === "FAILED") return planFailed.add(1);
  }
  planFailed.add(1);
}
```

### 7.2 진행 순서 **[제안]**

0. **테스트 서버 준비**: 서버를 만들고 운영과 같은 이미지 태그로 띄운다(3.1). 브라우저로 면접 1건을 직접 끝까지 해 보고 녹화 · 다시보기까지 되는지 본다
1. **보정**: S0(실제 API, 1~3건). 면접 1건 길이 · 외부 API 지연 · 1건당 에이전트 메모리를 잰다
2. **단일 구성 요소**: S1 → S2 → S3 → S4 → S5 순서. 하나씩 따로 돌려야 어느 가설이 맞는지 가릴 수 있다
3. **결과 정리**: 회차마다 8장에 남기고, 먼저 막힌 곳 · 그때의 부하 수준 · 1건당 자원 사용량(8.1)을 정리해 팀에 공유한다. 설정이 바뀌면 같은 시나리오 · 같은 수준으로 다시 재서 전후를 비교한다
4. **혼합**: S6(피크 혼합) 30분
5. **장시간**: S7 2시간
6. **정리**: 결과를 내보내고 테스트 서버 · 버킷 · 주소 · 토큰을 지운다(3.7). 실측값(컨테이너 메모리 · 동시 면접 수)은 배포 계획 3.2 · 13장의 [미정] 칸에 옮기고, 테스트 서버에서 잰 값이라는 것과 운영과 다른 점(3.1.2)을 같이 적는다
