### 1.2 운영 서버 구성

운영 환경은 AWS EC2 한 대(`t3.xlarge`, 4코어 · 16GB, Ubuntu 24.04)에서 Docker Compose로 모든 서비스를 실행합니다. 정의 파일은 `deploy/prod/compose.yml`이고, Compose 프로젝트 이름은 `a301-prod`입니다.

| 컨테이너 | 이미지 | 역할 |
|---|---|---|
| `a301-prod-nginx` | `nginx:1.30.6-alpine` | 외부 요청을 받는 입구(80 · 443). 도메인 이름에 따라 요청을 나눕니다 |
| `a301-prod-fe` | `hanggeut/a301:fe-<태그>` | 사용자 화면 |
| `a301-prod-be` | `hanggeut/a301:be-<태그>` | API 서버 |
| `a301-prod-admin` | `hanggeut/a301:admin-<태그>` | 관리 페이지 |
| `a301-prod-ai` | `hanggeut/a301:ai-<태그>` | AI 서버 상태 확인(FastAPI) |
| `a301-prod-ai-agent` | 〃 | 면접 진행(STT · 반응 판단 · TTS · 꼬리질문) |
| `a301-prod-ai-analysis` · `-ai-plan` · `-ai-recording` | 〃 | 분석 작업자. 각각 채점 · 결과 생성, 질문 생성, 녹화 합치기를 맡습니다 |
| `a301-prod-postgres` | `postgres:18.6-alpine` | DB |
| `a301-prod-redis` | `redis:7.4-alpine` | 세션 · 리프레시 토큰 · AI 작업 큐 · LiveKit 내부 메시지 |
| `a301-prod-livekit` | `livekit/livekit-server:v1.13.10` | 미디어 서버(WebRTC)와 내장 TURN |
| `a301-prod-egress` | `livekit/egress:v1.15.0` | 화상 면접 녹화 |
| `a301-prod-prometheus` · `-grafana` · `-loki` · `-alloy` · `-blackbox` · `-node-exporter` · `-cadvisor` · `-redis-exporter` · `-postgres-exporter` | 공식 이미지(버전은 2.4) | 모니터링 |

요청은 다음과 같이 흐릅니다.

- **화면 · API**: 브라우저 → Nginx(443) → FE → BE → PostgreSQL · Redis 순서로 처리합니다. 브라우저는 AI 서버나 외부 API에 직접 접속하지 않습니다.
- **면접방**: BE가 LiveKit 입장 토큰을 발급하고 AI 에이전트를 면접방에 배정합니다. 브라우저는 시그널링 주소(`wss://rtc.hangguet.co.kr`)와 미디어 포트로 LiveKit에 접속합니다.
- **BE와 AI 사이**: HTTP를 쓰지 않고 Redis 큐(`ai:jobs*` · `ai:results`)로만 메시지를 주고받습니다. AI는 DB에 접속하지 않습니다.

### 2.5 주요 설정 값

**포트**

| 서비스 | 컨테이너 포트 | 서버에 여는 포트 |
|---|---|---|
| Nginx | 443, 8080(http → https), 80(상태 확인) | `443/tcp`, `80/tcp` |
| LiveKit | 7880(시그널링), 7881/tcp, 7882/udp, 3478/udp, 443(TURN/TLS) | `7881/tcp`, `7882/udp`, `3478/udp` |
| BE | 8080(API), 8081(Actuator) | `127.0.0.1:18084` → 8081(상태 확인 전용) |
| FE | 3000 | `127.0.0.1:18082`(상태 확인 전용) |
| AI(FastAPI) | 8000 | `127.0.0.1:18083`(상태 확인 전용) |
| PostgreSQL · Redis | 5432 · 6379 | 열지 않음 |

**Nginx 라우팅** (`deploy/prod/nginx.conf`)

| 도메인 | 경로 | 전달 대상 |
|---|---|---|
| `hangguet.co.kr` | `/` | FE `a301-prod-fe:3000` |
| | `/be/` | BE `a301-prod-be:8080`(`/be`를 떼고 전달) |
| | `/admin/` | 관리 페이지 `a301-prod-admin:80` |
| | `/be/docs` · `/be/swagger-ui` · `/be/v3/api-docs` | 404(운영에서는 Swagger 비공개) |
| `rtc.hangguet.co.kr` | `/` | LiveKit 시그널링 `a301-prod-livekit:7880`(WebSocket) |
| `grafana.hangguet.co.kr` | `/` | Grafana `a301-prod-grafana:3000` |
| `turn.hangguet.co.kr` | (TLS를 풀지 않음) | LiveKit TURN/TLS `a301-prod-livekit:443` |

- 443 포트 하나를 TLS 접속의 도메인 이름(SNI)으로 나눕니다. 웹 도메인 3개는 Nginx가 TLS를 해제하고, `turn.` 도메인은 해제하지 않은 채 LiveKit으로 전달합니다.
- 요청 수는 IP별로 제한합니다. 로그인은 분당 60회, 비밀번호 재설정은 분당 10회, BE API는 초당 30회, 화면은 초당 100회입니다.
- 요청 본문은 최대 1MB입니다(`client_max_body_size 1m`). 파일은 브라우저가 S3 Presigned URL로 직접 올리므로 Nginx를 거치지 않습니다.

**JVM · 메모리 상한**

| 서비스 | 설정 |

## 3. 환경 변수

### 3.1 값을 넣는 곳

| 환경 | 넣는 곳 |
|---|---|
| 로컬 | 루트의 `.env.example`을 `.env`로 복사해 씁니다. BE · AI에는 실행할 때 셸 환경 변수로 전달합니다 |
| 운영(비밀값) | **GitLab > Settings > CI/CD > Variables**. 배포 작업이 환경 변수로 받아 Compose에 전달합니다 |
| 운영(비밀이 아닌 값) | `deploy/prod/compose.yml`에 직접 적혀 있습니다(도메인, 버킷 이름, 모델 이름 등) |
| ASG 인스턴스 | AWS SSM Parameter Store의 `/a301/prod/agent/*` · `/a301/prod/egress/*`(6.6) |

GitLab 변수는 **Protected · Masked**로 등록합니다. Protected 변수는 보호 브랜치(`master`) 파이프라인에서만 읽을 수 있습니다. 환경 범위(Environment scope)는 아래 표의 「범위」 열을 따릅니다.

### 3.2 GitLab CI/CD Variables

운영 배포에 필요한 값입니다. Compose가 파일 전체를 해석하므로 **필수 값이 하나라도 없으면 배포가 중단됩니다.** 이때 빠진 변수 이름이 로그에 나옵니다.

| 이름 | 필수 | 범위 | 사용처 | 값 · 만드는 방법 |
|---|---|---|---|---|
| `DB_PASSWORD` | O | `prod/*` | PostgreSQL, BE, postgres-exporter | 충분히 긴 임의 문자열. **DB 볼륨을 처음 만들 때만 적용됩니다** |
| `REDIS_PASSWORD` | O | `prod/*` | Redis, BE, AI, LiveKit, Egress | `openssl rand -hex 24`. 공백 · 따옴표를 넣지 않습니다 |
| `JWT_SECRET` | O | `prod/*` | BE(액세스 토큰 서명, HS256) | 32바이트 이상 문자열 |
| `INQUIRY_ENCRYPTION_KEY` | O | `prod/*` | BE(문의 제목 · 본문 AES-256 암호화) | `openssl rand -base64 32`. **잃어버리면 저장된 문의를 복호화할 수 없습니다** |
| `ADMIN_LOGIN_ID` · `ADMIN_PASSWORD` | O | All | BE(관리 페이지 계정) | 처음 기동할 때 계정이 없으면 생성합니다 |
| `ADMIN_NAME` | | All | BE | 없으면 `운영자` |
| `GRAFANA_ADMIN_PASSWORD` | O | All | Grafana `admin` 계정 | Grafana 볼륨을 처음 만들 때만 적용됩니다 |
| `LIVEKIT_API_KEY` · `LIVEKIT_API_SECRET` | O | `prod/*` | LiveKit, Egress, BE, AI | 셀프 호스팅이므로 직접 정합니다. 키는 영문 · 숫자 · `_` · `-`만, 시크릿은 32자 이상 |
| `LIVEKIT_EGRESS_S3_ACCESS_KEY` · `LIVEKIT_EGRESS_S3_SECRET` | O | `prod/*` | BE(녹화 요청에 담아 Egress에 전달) | 녹화용 AWS IAM 사용자의 액세스 키 |
| `AWS_ACCESS_KEY_ID` · `AWS_SECRET_ACCESS_KEY` | O | `prod/*` | BE(프로필 사진), AI(녹화 합치기), DB 백업 | 앱용 AWS IAM 사용자의 액세스 키 |
| `SONIOX_API_KEY` | O | All | AI 에이전트(STT) | Soniox 콘솔에서 발급 |
| `LLM_API_KEY` | O | All | AI 에이전트 · 분석 작업자(LLM) | SSAFY GMS 키 |
| `ELEVENLABS_API_KEY` | | All | AI 에이전트(TTS) | 없으면 질문을 글로만 보여 줍니다 |
| `JEV_API_KEY` | | All | AI 에이전트(반응 판단), 분석 작업자(자기소개서 검증) | 없으면 면접관 반응이 없고 **지원서를 저장할 수 없습니다** |
| `KAKAO_CLIENT_ID` · `KAKAO_CLIENT_SECRET` | | All | BE, FE(ID만) | 없으면 카카오 로그인만 503으로 응답합니다 |
| `GOOGLE_CLIENT_ID` · `GOOGLE_CLIENT_SECRET` | | All | BE | 없으면 구글 로그인 API만 503으로 응답합니다 |
| `MAIL_USERNAME` · `MAIL_PASSWORD` | | All | BE(비밀번호 찾기 메일) | Gmail 주소와 앱 비밀번호. 없으면 메일만 보내지 않습니다 |
| `DOCKERHUB_PUSH_TOKEN` | O | `prod/*` | `prod-build` 작업 | Docker Hub 액세스 토큰(Read & Write) |
| `DOCKERHUB_PULL_TOKEN` | O | `prod/*` | `prod-deploy` 작업 | Docker Hub 액세스 토큰(Read-only) |
| `AGENT_IDLE_PROCESSES` | | `prod/*` | AI 에이전트 | 미리 실행해 둘 프로세스 수(0 이상의 정수). 없으면 CPU 수 |
| `SONIOX_STT_MODEL` | | | AI 에이전트 | 없으면 `stt-rt-v6` |
| `AGENT_ASG_ENABLED` · `EGRESS_ASG_ENABLED` · `MAIN_TAILSCALE_IP` · `AGENT_REFRESH_AWS_ACCESS_KEY_ID` · `AGENT_REFRESH_AWS_SECRET_ACCESS_KEY` | | `prod/*` | 배포 스크립트 | ASG를 쓸 때만 등록합니다(6.6) |
| `SONAR_HOST_URL` · `SONAR_TOKEN` | | All | 정적 분석 작업 | 배포와 관계없습니다. 없으면 분석 작업만 실패합니다(실패 허용) |

## 5. 운영 서버 배포

### 5.1 배포 흐름

```
develop → Release MR → master 병합
  → prod-build  (자동)   : be · fe · ai · admin 이미지 빌드 → Docker Hub에 push
  → prod-deploy (▶ 버튼) : 운영 서버의 러너가 deploy/prod/deploy.sh 실행
```

- 이미지는 Docker Hub 비공개 저장소 `hanggeut/a301` 하나에 올리고, 서비스는 태그 접두사로 구분합니다(`be-` · `fe-` · `ai-` · `admin-` 뒤에 커밋 짧은 SHA).
- `prod-build`는 Docker가 설치된 러너(태그 `a301-mock-deploy`)에서, `prod-deploy`는 운영 서버에 설치한 shell 러너(태그 `a301-prod`, protected)에서 실행됩니다.
- `prod-deploy`는 사람이 직접 눌러야 실행됩니다. 배포 중 에이전트와 LiveKit이 재시작되면 진행 중인 면접이 끊길 수 있기 때문입니다.

### 5.2 새 서버 준비

처음 한 번만 하는 작업입니다.

**① 서버 기본 설정**

```bash
# Docker Engine과 Compose plugin을 공식 저장소에서 설치한 뒤
sudo timedatectl set-timezone Asia/Seoul
# 스왑 4GB 생성(vm.swappiness=10)
# Docker 로그 설정: json-file, 10MB × 3개(/etc/docker/daemon.json)

sudo mkdir -p /opt/a301/backup      # 배포 폴더. 러너 계정 소유로 둡니다
```

**② 방화벽(ufw)**

규칙을 잘못 넣어 접속이 끊길 때를 대비해, SSH 창을 하나 더 열어 둔 채로 진행합니다.

```bash
sudo ufw allow 80/tcp       # http → https
sudo ufw allow 443/tcp      # 웹 HTTPS + TURN/TLS
sudo ufw allow 7881/tcp     # 미디어 예비 경로
sudo ufw allow 7882/udp     # 미디어
sudo ufw allow 3478/udp     # TURN/UDP
sudo ufw status numbered
```

클라우드 보안 그룹을 쓰는 서버라면 보안 그룹에도 같은 포트를 엽니다.

**③ 도메인(DNS)**

아래 4개 이름을 서버 공인 IP를 가리키는 A 레코드로 등록합니다. Cloudflare를 쓴다면 **프록시를 꺼야 합니다(회색 구름).** TURN/TLS와 WebRTC 미디어는 HTTP 프록시를 통과하지 못하기 때문입니다.

| 이름 | 용도 |
|---|---|
| `hangguet.co.kr` | 서비스 화면 · API |
| `rtc.hangguet.co.kr` | LiveKit 시그널링 |
| `turn.hangguet.co.kr` | TURN/TLS |
| `grafana.hangguet.co.kr` | 모니터링 대시보드 |

다른 도메인을 쓴다면 6.8에 정리한 파일도 함께 고칩니다.

**④ 인증서(Let's Encrypt)**

certbot과 Cloudflare DNS 플러그인(DNS-01 방식)으로 인증서 2개를 발급합니다. Nginx와 LiveKit은 `/etc/letsencrypt` 폴더를 읽기 전용으로 마운트해 씁니다.

```bash
sudo apt install certbot python3-certbot-dns-cloudflare

# Cloudflare API 토큰 파일을 만듭니다(권한 600). 경로는 예시입니다
#   dns_cloudflare_api_token = <DNS 편집 권한만 있는 토큰>
CF_INI=/root/.secrets/cloudflare.ini

# 웹 인증서 → /etc/letsencrypt/live/hangguet.co.kr/
sudo certbot certonly --dns-cloudflare --dns-cloudflare-credentials "$CF_INI" \
  -d hangguet.co.kr -d rtc.hangguet.co.kr -d grafana.hangguet.co.kr

# TURN 인증서 → /etc/letsencrypt/live/turn.hangguet.co.kr/
sudo certbot certonly --dns-cloudflare --dns-cloudflare-credentials "$CF_INI" \
  -d turn.hangguet.co.kr
```

갱신은 certbot이 설치하는 `certbot.timer`가 자동으로 합니다. 갱신된 인증서를 반영하도록 `/etc/letsencrypt/renewal-hooks/deploy/`에 스크립트 2개를 둡니다. 두 스크립트 모두 `$RENEWED_LINEAGE`를 확인해 자기 인증서가 갱신됐을 때만 동작해야 합니다(이유는 6.4).

| 스크립트 | 동작 예 |
|---|---|
| `reload-nginx.sh` | 웹 인증서가 갱신되면 `docker exec a301-prod-nginx nginx -s reload` |
| `restart-livekit.sh` | TURN 인증서가 갱신되면 `docker restart a301-prod-livekit` |

**⑤ GitLab Runner**

운영 서버에 GitLab Runner(shell executor)를 설치하고, 태그 `a301-prod`를 붙여 Protected 러너로 등록합니다. 러너 계정을 `docker` 그룹에 추가하고 `/opt/a301` 폴더의 소유자를 러너 계정으로 바꿉니다.

**⑥ 외부 리소스**

[02_외부_서비스.md](02_외부_서비스.md)를 참고해 AWS S3 버킷과 IAM 키, Docker Hub 저장소와 토큰, 외부 API 키를 준비하고, 3.2의 GitLab 변수를 모두 등록합니다.

**⑦ DB 백업 cron**

러너 계정의 crontab에 아래 줄을 추가합니다. 매일 04:30에 DB를 백업합니다.

```

```

`backup.sh`와 S3 키 파일(`/opt/a301/backup.env`)은 배포 스크립트가 배포할 때마다 복사 · 생성합니다.

### 5.3 배포 실행

**CI로 배포하기(기본)**

1. `develop` → `master` Release MR을 병합합니다.
2. `prod-build`가 자동으로 이미지 4개를 빌드해 올립니다.

**CI 없이 서버에서 직접 배포하기**

3.2의 값을 모두 환경 변수로 지정한 뒤 저장소 루트에서 `deploy.sh`를 실행합니다. 설정 해시(6.2)가 필요하므로 `docker compose`를 직접 실행하지 말고 반드시 `deploy.sh`를 씁니다.

### 5.4 `deploy.sh`의 처리 순서

1. 설정 파일(`nginx.conf` · `livekit.yaml` · `prometheus.yml` · `blackbox.yml` · `loki.yml` · `alloy.alloy` · `grafana/`)의 내용 해시를 계산합니다.
2. pull 토큰으로 Docker Hub에 로그인합니다. 작업이 끝나면 로그아웃합니다.
3. Compose 설정을 검사하고 이미지를 내려받습니다. 여기까지 실패하면 서버는 이전 상태 그대로 남습니다.
4. `backup.sh`와 S3 키 파일을 `/opt/a301/`에 둡니다.
5. `deploy/prod/`를 `/opt/a301/prod/`로 복사하고, `livekit.yaml`의 웹훅 키 자리에 `LIVEKIT_API_KEY`를 채운 뒤 `docker compose up -d --remove-orphans`를 실행합니다. 이미지 · 환경 변수 · 설정 해시가 바뀐 서비스만 다시 만들어집니다.
6. 모든 컨테이너의 실행 · healthy 상태, 내부 상태 확인 주소, 외부 주소, 서버 443 · 80 직접 접속을 확인하고, 20초 동안 재시작이 없는지 봅니다.
7. 서비스마다 최신 이미지 3개만 남기고 나머지를 지웁니다.

## 6. 배포 시 특이사항

### 6.1 배포 중에는 진행 중인 면접이 끊길 수 있습니다

에이전트나 LiveKit 컨테이너가 다시 만들어지면 진행 중인 면접방이 닫힙니다. 그래서 `prod-deploy`를 수동 실행으로 두었습니다. Grafana 대시보드에서 진행 중인 면접방이 0개인지 확인한 뒤 배포합니다.

### 6.2 설정 파일 변경 반영(설정 해시)

Compose에 파일로 마운트한 설정(`nginx.conf` 등)은 내용만 바뀌면 `up -d`가 컨테이너를 다시 만들지 않습니다. 그래서 `deploy.sh`가 파일 내용 해시를 컨테이너 라벨(`a301.config-hash`)로 붙이고, 해시가 바뀐 서비스만 다시 만들도록 했습니다.

- 해시 7개가 필수 값이므로 `docker compose up`을 직접 실행하면 중단됩니다. 항상 `deploy.sh`로 배포합니다.
- LiveKit 설정을 바꾸지 않은 배포에서는 LiveKit이 재시작되지 않습니다.

### 6.3 DB

- 스키마는 Flyway 마이그레이션 파일(`backend/src/main/resources/db/migration/`의 `V1` ~ `V29`)로만 만듭니다. BE가 기동할 때 자동으로 적용되고, JPA는 스키마를 검증(`validate`)만 합니다. **빈 DB에 BE를 실행하면 전체 스키마가 만들어집니다.**
- 롤백해도 스키마는 되돌아가지 않습니다. 마이그레이션이 포함된 배포를 되돌릴 때는 이전 BE가 새 스키마에서도 기동하는지 먼저 확인합니다.
- `POSTGRES_PASSWORD`(= `DB_PASSWORD`)는 **DB 볼륨을 처음 만들 때만** 적용됩니다. 나중에 GitLab 변수만 바꾸면 BE가 DB에 접속하지 못하므로, DB 안에서도 `ALTER USER`로 비밀번호를 함께 바꿔야 합니다. Grafana 관리자 비밀번호도 같은 방식입니다.
- 백업: 매일 04:30에 `pg_dump`(custom 형식)로 덤프해 서버의 `/opt/a301/backup/`(7일 보관)과 S3 `backup/`에 저장합니다.

### 6.4 인증서 갱신 스크립트

`renewal-hooks/deploy/`에 둔 스크립트는 어떤 인증서가 갱신되든 모두 실행됩니다. 조건 없이 두면 웹 인증서가 갱신될 때도 LiveKit이 재시작되어 면접이 끊깁니다. 그래서 각 스크립트 첫머리에서 `$RENEWED_LINEAGE`가 자기 인증서 경로인지 확인합니다.

### 6.5 네트워크

- **Docker가 연 포트는 ufw 규칙을 거치지 않습니다.** 그래서 DB · Redis · BE는 포트를 열지 않거나 `127.0.0.1`에만 엽니다. `compose.yml`을 수정할 때 포트가 `0.0.0.0`에 열리지 않도록 주의합니다.
- **TURN/TLS는 443 포트를 써야 합니다.** 외부 TCP 연결을 80 · 443만 허용하는 학교 · 회사 와이파이에서도 면접방에 들어올 수 있게 하기 위해서입니다. 그래서 Nginx가 443을 SNI로 나눠 웹과 TURN이 함께 씁니다.
- **MPTCP를 꺼 두었습니다.** Nginx와 LiveKit 컨테이너에 `sysctls: net.mptcp.enabled=0`이 있습니다. MPTCP를 지원하지 않는 커널(Docker Desktop 등)에서는 이 설정 때문에 컨테이너가 시작되지 않으므로, **운영 `compose.yml`은 Linux 서버에서만 실행합니다.**
- LiveKit은 `use_external_ip: true` 설정으로 서버 공인 IP를 직접 찾습니다. 찾지 못하는 환경이라면 `livekit.yaml`의 `rtc.node_ip`에 공인 IP를 적습니다.

### 6.6 AI 에이전트 · 녹화(Egress) 오토스케일링(선택)

기본 구성은 서버 한 대에 모든 서비스를 올리는 방식이며, 이 구성만으로 서비스가 동작합니다. 동시 면접이 많을 때를 대비해 에이전트와 Egress만 팀 AWS 계정의 Auto Scaling Group(ASG)으로 분리할 수 있습니다.

| GitLab 변수(범위 `prod/*`) | 동작 |
|---|---|
| 없음(기본) | `compose.yml`만 씁니다. 에이전트와 Egress가 메인 서버에서 실행됩니다 |
| `AGENT_ASG_ENABLED=true` | `compose.asg.yml`을 덧붙입니다. 메인 서버의 에이전트를 끄고, LiveKit 7880 · Redis 6379 · Prometheus 9090 · Loki 3100 포트를 Tailscale IP(`MAIN_TAILSCALE_IP`)에만 엽니다. 배포가 끝나면 `deploy/asg/ci-agent-refresh.sh`가 ASG 인스턴스를 새 버전으로 교체합니다 |
| `EGRESS_ASG_ENABLED=true` | 메인 서버의 Egress도 끕니다. `AGENT_ASG_ENABLED=true`와 함께 써야 합니다 |

- ASG 인스턴스는 Tailscale로 메인 서버에 접속하고, 필요한 설정값은 SSM Parameter Store에서 읽습니다.
- 인스턴스를 줄이거나 교체할 때는 진행 중인 면접 · 녹화가 끝날 때까지(최대 3900초) 기다린 뒤 종료합니다.
- 리소스 생성 방법, SSM 매개변수 목록, 전환 순서는 [`deploy/asg/README.md`](../deploy/asg/README.md)에 있습니다.
- 변수를 지우고 다시 배포하면 서버 한 대 구성으로 돌아갑니다.

### 6.7 외부 API 한도

- **Soniox 실시간 인식은 계정당 동시 연결이 10개입니다.** 그래서 화상 면접 동시 진행 상한을 운영 8개(`INTERVIEW_MAX_VIDEO` 기본값), 개발 2개로 나눠 두었습니다. 상한을 넘으면 면접 시작 API가 503 `INTERVIEW_CAPACITY_FULL`로 응답합니다. 계정 한도가 다르다면 이 값을 조정합니다.
- `JEV_API_KEY`가 없으면 자기소개서 검증이 모두 실패해 **지원서를 저장할 수 없습니다.**
- `ELEVENLABS_API_KEY`가 없으면 면접관 음성 없이 질문을 글로만 보여 줍니다.
