# 골든셋 라벨링 안내

채점자가 읽는 문서다. 기준은 [효용지표](../../../../docs/효용지표.md) 5장을 따른다.

## 지켜 주세요

- 이 폴더의 `sheet.csv`와 이 문서만 봅니다. `blind_map.json`, 다른 채점자의 `rater-*` 파일, 상위 폴더의 `items.jsonl`·`answers.json`·`variants.json`은 **열지 않습니다**. 답변의 의도 단계와 변형 종류가 들어 있습니다
- AI 판정 결과도 보지 않습니다
- 다 끝날 때까지 다른 채점자와 이야기하지 않습니다
- 답변을 직접 쓴 사람은 라벨링하지 않습니다

## 하는 방법

1. `sheet.csv`를 복사해 `rater-<영문 이니셜>.csv`로 저장합니다(예: `rater-hg.csv`)
2. 행마다 자기소개서·질문·채점 기준·답변을 읽고 `JOB_FIT`·`COVER_LETTER`·`LOGIC`·`DELIVERY` 칸에 1·2·3 중 하나를 적습니다
3. 항목마다 **따로** 판단합니다. 한 항목이 낮다고 다른 항목까지 낮추지 않습니다
4. 다 채우면 저장소 `ai` 폴더에서 아래를 실행해 빈칸이 없는지 확인합니다

```bash
uv run python -m eval.golden.collect_labels rater-hg
```

120행이며 2~3시간 걸립니다.

## 단계 기준

| 항목 | 3 좋아요 | 2 보통 | 1 아쉬워요 |
|---|---|---|---|
| `JOB_FIT` 직무 적합 | 질문이 확인하는 역량에 대해 본인이 한 구체적 행동·방법과 그 방법을 고른 이유를 들어 경험과 직무 요구를 연결한다 | 관련 경험과 본인 행동은 있지만 방법을 고른 이유나 직무 요구와의 연결이 빠졌다 | 결과·수치나 일반론만 있고 본인이 한 행동·방법이 없다 |
| `COVER_LETTER` 자소서 검증 | 자기소개서의 해당 주장과 어긋나지 않고, 과정·수치·본인 역할을 구체적으로 설명해 주장을 뒷받침한다 | 어긋나지는 않지만 뒷받침이 일부만 구체적이다 | 자기소개서와 어긋나거나 근거 없이 주장만 반복한다 |
| `LOGIC` 논리 | 원인(상황) → 조치 → 결과(확인 방법) 순서가 분명하다 | 셋 중 하나가 빠졌거나 서로 이어지지 않는다 | 셋 중 둘 이상이 빠졌거나 결과만 나열한다 |
| `DELIVERY` 전달 | 질문에 대한 답(핵심)이 앞에 나오고 군더더기 없이 읽힌다 | 핵심은 있지만 뒤에 나오거나 장황하다 | 무엇을 말하려는지 알기 어렵다 |

- 가정 상황 질문("~했다면 어떻게 하겠습니까?")은 원인을 문제 정의로, 조치를 적용할 방법과 그 이유로, 결과를 적용 결과를 확인할 방법으로 읽습니다
- 자기소개서에 없는 내용을 답변에서 더 말하는 것은 어긋남이 아닙니다. 수치·역할·사실이 자기소개서와 **다를 때** 어긋남입니다
- 존댓말·반말, 문장 부호, 사소한 오타는 단계에 반영하지 않습니다

## 단계별 예시

골든셋에 들어 있지 않은 질문 하나로 항목마다 단계별 예시를 보입니다. 예시는 그 항목만 보고 판단한 것입니다.

> **자기소개서(다솜커머스 · 백엔드 개발자)** "… 동시 사용자 1,000명 부하 테스트에서 초과 발급 0건, 95퍼센트 응답 시간 180밀리초를 확인했습니다."
>
> **질문** 부하 테스트에서 동시 사용자 1,000명과 95퍼센트 응답 시간 180밀리초는 각각 어떤 기준과 측정 방식으로 산출했는지 설명해 주세요.

### `JOB_FIT`

| 단계 | 예시 | 이유 |
|---|---|---|
| 3 | 쿠폰 이벤트는 시작 순간 요청이 몰리는 게 핵심이라, 실제 이벤트처럼 1,000명이 같은 순간에 발급을 누르도록 부하 도구 시나리오를 제가 짰습니다. 평균 대신 95퍼센트 응답 시간을 본 이유는 몰리는 순간 느려지는 소수 사용자를 놓치지 않기 위해서였습니다. | 본인 행동 + 방법 + 그 방법을 고른 이유 |
| 2 | 부하 도구로 1,000명이 동시에 발급을 누르게 해서 측정했고, 95퍼센트 응답 시간이 180밀리초로 나왔습니다. | 행동은 있지만 이유가 없다 |
| 1 | 부하 테스트 결과 1,000명에서도 95퍼센트 응답 시간이 180밀리초로 잘 나왔습니다. | 결과만 있다 |

### `COVER_LETTER`

| 단계 | 예시 | 이유 |
|---|---|---|
| 3 | 1,000명이 동시에 발급을 누르는 테스트를 다섯 번 반복했고, 매번 발급 내역이 정확히 100건인지 세어 초과 발급 0건을 확인했습니다. 응답 시간은 부하 도구가 요청마다 기록한 값에서 95퍼센트 지점을 뽑았고 180밀리초였습니다. | 주장과 같고 과정·수치로 뒷받침한다 |
| 2 | 자기소개서에 쓴 1,000명 테스트는 제가 직접 돌렸고 결과도 거기 쓴 것과 같았습니다. | 어긋나지 않지만 뒷받침이 거의 없다 |
| 1 | 500명으로 테스트했을 때 95퍼센트 응답 시간이 1초 정도 나왔습니다. | 인원·수치가 자기소개서와 다르다 |

### `LOGIC`

| 단계 | 예시 | 이유 |
|---|---|---|
| 3 | 처음에는 평균 응답 시간만 봐서 몰리는 순간 느려지는 요청이 가려졌습니다. 그래서 95퍼센트 값을 따로 뽑도록 측정을 바꿨고, 1,000명이 몰리는 순간에도 요청 95퍼센트가 180밀리초 안에 끝나는 것을 확인했습니다. | 원인 → 조치 → 결과 |
| 2 | 95퍼센트 값을 따로 뽑도록 측정을 바꿨고, 그래서 180밀리초라는 값을 얻었습니다. | 원인이 빠졌다 |
| 1 | 180밀리초가 나왔고 초과 발급도 없었습니다. | 결과만 있다 |

### `DELIVERY`

| 단계 | 예시 | 이유 |
|---|---|---|
| 3 | 1,000명은 이벤트 예상 최대 동시 접속자 수였고, 180밀리초는 그 상태에서 요청 95퍼센트가 끝난 시간입니다. 둘 다 부하 도구가 남긴 요청 기록에서 계산했습니다. | 답이 먼저 나오고 간결하다 |
| 2 | 테스트 도구를 고르는 데 시간이 좀 걸렸는데 여러 개를 비교해 봤고요, 그중 하나로 돌렸습니다. 1,000명은 이벤트 예상 최대 동시 접속자 수였고 180밀리초는 요청 95퍼센트가 끝난 시간입니다. | 답은 있지만 뒤에 나온다 |
| 1 | 그게 테스트를 하면서 숫자가 여러 개 나왔는데 1,000명이었던 것도 있고 아무튼 180이 나와서 괜찮다고 봤던 것 같고 그 외에도 여러 가지를 봤습니다. | 무엇을 답하는지 알기 어렵다 |

## 라벨링이 끝나면

채점자가 모두 끝내면 `ai` 폴더에서 합의 라벨을 만듭니다.

```bash
uv run python -m eval.golden.make_consensus
```

과반이 없는 항목은 `disputes.csv`에 모입니다. 채점자가 함께 토론해 `합의`·`이유` 칸을 채운 뒤 다시 실행하면 `consensus.json`이 만들어집니다.
