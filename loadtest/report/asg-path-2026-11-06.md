# 에이전트 ASG 운영 경로 재현 (2026-11-06, 테스트 서버)

[에이전트 · Egress 오토스케일링 계획](../../이해준/agent_autoscale_plan/README.md) 10.1의 3번(테스트 서버에서 운영 경로 재현)을 진행했다. 11/03 시험은 같은 VPC 사설망과 간이 user data였지만, 이번에는 운영과 같은 구성을 테스트 서버에서 그대로 띄웠다. 운영 구성은 **Tailscale + Redis 비밀번호 + [`deploy/asg/`](../../deploy/asg/README.md) 키트(감시 스크립트 · 축소 보호 · 수명 주기 훅 · Alloy)** 다. 순서는 [`loadtest/agent/README.md`](../agent/README.md) 「운영 경로 재현」이다.

## 요약

- **운영 경로는 동작한다.**
  - 에이전트 인스턴스는 부팅 약 50초 뒤 tailnet에 가입해 직접 연결됐다(1ms).
  - Redis 비밀번호로 LiveKit · BE · AI · Egress가 모두 붙었다.
  - 화상 면접이 녹화 · 결과 · 다시보기까지 끝났다.
  - 지표 · 로그는 메인 Prometheus · Loki로 들어왔다.
  - 테스트 서버를 재부팅해도 7880 · 6379 · 9090 · 3100이 Tailscale IP에 다시 묶였다.
- **줄이기는 진행 중 면접을 지킨다.**
  - 면접 중에 ASG로 인스턴스를 종료하면 면접을 끝까지 마치고 약 10초 뒤 꺼진다(drain).
  - 2대에서 1대로 줄이면 면접이 없는 대를 먼저 내린다(축소 보호).
  - 새 인스턴스는 시작부터 면접을 받기까지 **약 2분 15초**가 걸린다.
- **인스턴스가 갑자기 사라지면 LiveKit에 유령 작업자가 약 14분 남는다.**
  - 그동안 새 면접이 그 유령에게 배정되면 다른 대로 다시 주지 않아, 면접관 없이 `IN_PROGRESS`로 남는다. 이번에 2건이 그랬다(642 · 647).
  - LiveKit 컨테이너의 TCP 재전송 상한을 낮추면(`tcp_retries2=8`) **약 2분으로 줄어든다.**
- **면접 도중 에이전트를 잃으면 그 면접은 끝나지 않는다.**
  - 지원자가 떠나도 면접방이 닫히지 않으면 에이전트 작업이 계속 "진행 중"으로 남는다.
  - 그래서 **축소 보호가 풀리지 않아 인스턴스가 내려가지 않는다**(되돌리기 시험에서 방을 직접 닫아야 했다).
- **되돌리기**: 메인 서버 에이전트를 켜면 9초 뒤 면접을 받는다. ASG 쪽은 진행 중 면접이 끝나고 약 1분 뒤 빠진다.
- **한 대 한계(`t3.small`)**: 동시 8 · 10건 모두 배정 실패 · 거절 0이었다. 1건당 에이전트 약 0.08코어이고, 인스턴스 1분 평균 최대 44 · 43%였다. 확장 기준(40%)은 대당 약 7건이다. 실패는 모두 결과 분석 화면 시간 초과(채점 작업자 1개, 최대 427초)였다
- Tailscale 60초 끊김은 진행 중 면접을 잃고, 에이전트는 복구 11초 뒤 다시 등록했다. 이 항목은 더 다루지 않는다.

## 3. 장애: 인스턴스가 갑자기 사라질 때

면접 중 인스턴스를 EC2에서 강제 종료했다(`terminate-instances`).

### 3.1 기본값

| 시각(UTC) | 일 |
|---|---|
| 07:23:53 | 면접 646 배정 |
| 07:24:35 | 강제 종료 |
| 07:26:28 | LiveKit이 면접방의 면접관 참가자를 끊음(약 2분, 참가자 연결은 LiveKit이 스스로 생존을 확인한다) |
| 07:27:50 | 교체 인스턴스 등록 |
| 07:38:21 | **새 면접 647이 유령 작업자에게 배정 → 3초 뒤 `failed to assign job … context deadline exceeded, retry: false`** |
| ~07:38:30 | 유령 작업자 연결이 끊김(마지막 재전송 14회) |

- 유령 작업자는 **약 14분** 남았다.
  - LiveKit 서버는 작업자가 등록된 뒤 생존을 확인하지 않는다(v1.13.10 `pkg/service/agenthandler.go`). 연결은 TCP 수준에서 실패해야 정리된다.
  - 끊긴 상대에게 보낸 데이터는 리눅스 기본값(`tcp_retries2=15`)이면 15분 가까이 재전송된다.
- 유령에게 배정이 실패하면 LiveKit은 다른 작업자로 다시 주지 않는다. 그래서 면접이 면접관 없이 남는다.
  - 이번에 642(06:53, 11/06 오전 시험)와 647이 그랬다.
  - 확률은 살아 있는 대와 유령의 부하 비율로 정해진다(가중 무작위).
- 진행 중이던 면접 646도 면접관이 나간 뒤 `IN_PROGRESS`로 남았다.

### 3.2 대책: LiveKit 컨테이너의 `tcp_retries2=8`

[`loadtest/server/compose.ghost-tcp.yml`](../server/compose.ghost-tcp.yml)을 더해 LiveKit 컨테이너 네트워크 네임스페이스에만 재전송 상한을 낮췄다. Docker가 이 포트를 DNAT로 넘기므로 LiveKit 소켓이 끊긴 상대를 직접 본다.

| | 기본값(15) | 8 |
|---|---|---|
| 유령 작업자가 남은 시간 | 약 14분 | **약 2분**(07:42:42 종료 → 07:44:40 무렵 정리) |
| 면접관 참가자 정리 | 약 2분 | 약 2분 |

- 8은 약 100초 동안 응답이 없으면 끊는 값이다. 사용자 쪽 TCP도 같은 값을 쓴다(7881 미디어 예비 경로 · Nginx를 거친 시그널링 · TURN/TLS). 그래서 100초 넘게 응답이 없는 사용자 연결도 끊긴다. 보통 그 전에 브라우저가 다시 연결한다.
- 유령이 2분 남는 동안의 배정 실패는 여전히 생길 수 있다. 사용자에게 보이는 처리는 BE 요청 1(면접관이 안 들어오면 `START_FAILED` → [다시 시작])이 맡는다.

## 4. 면접 도중 에이전트를 잃은 면접

- 에이전트 작업은 **면접방이 닫혀야** 끝난다(`ai/app/agent/main.py` `entrypoint`).
- BE는 면접이 정상으로 끝날 때만 방을 닫는다. 그래서 도중에 멈춘 면접은 지원자가 떠나도 방이 남는다.
- 그 결과 에이전트가 다시 붙어(Tailscale 시험의 649) 혼자 방에 남으면, 진행 중 면접 수가 계속 1로 잡힌다. 감시 스크립트의 축소 보호가 풀리지 않아 **그 인스턴스는 줄일 수 없다.**
  - 되돌리기 시험에서 649 방을 LiveKit API로 닫자 16초 뒤 보호가 풀리고 47초 뒤 인스턴스가 빠졌다.
- 인스턴스 새로 고침 · 비정상 교체는 훅의 `docker stop --time 1800`이 30분 뒤 강제로 끝내므로 멈추지는 않는다. 다만 30분을 기다린다.
- 대책 후보
  - BE: 지원자가 떠난 뒤 정한 시간 안에 돌아오지 않거나 진행이 없는 면접은 방을 닫고 실패 처리한다. 11/03 보고서의 631(`IN_PROGRESS` 남음)과 같은 문제다.
  - AI: 에이전트 작업에 최대 시간을 둔다.

## 6. 한 대에 몰림(`t3.small` 1대, 3초 간격)

| | 동시 8건 | 동시 10건 |
|---|---|---|
| 배정 실패 · 거절 | 0 | 0 |
| 첫 질문(평균 / 최대) | 13.1 / 22.2초 | 15.0 / 25.9초 |
| 질문 간격(평균 / 최대) | 22.3 / 50.6초 | 22.1 / 42.8초 |
| 에이전트 컨테이너 CPU(1분 평균 최대) | 0.67코어 | 0.83코어 |
| 인스턴스 CPU(1분 평균 최대 / 5초 최대) | 44% / 62% | 43% / 50% |
| 면접 실패 | 2건(결과 분석 화면 시간 초과, 아래) | 1건(결과 분석 화면 시간 초과) |

- 8건이 겹친 구간에서 에이전트는 1건당 **약 0.08코어**다. 개발 서버 측정을 `t3`로 환산한 값(약 0.1코어, [에이전트 CPU 보고서](agent-cpu-dev-2026-11-05.md))과 맞는다.
- 확장 기준(인스턴스 평균 CPU 40%)에는 대당 **약 7건**에서 닿는다(계획 4.1의 추정과 같음).
- 8건의 실패 2건은 에이전트가 아니라 메인 서버 **채점 작업자 1개**가 결과를 차례로 만들어 결과 화면이 늦어진 것이다. 결과 대기는 최대 245초였다. 계획 1장의 "AI 작업자 2개"와 같은 문제다.
- 면접이 짧아(약 2~3분) CPU가 겹치는 시간이 짧다. 실제 10분 면접의 평균은 이보다 고르게 퍼진다.

- 10건에서도 거절(작업자 가득 참)은 없었다. 3초 간격 시작이라 10건이 완전히 겹친 시간은 짧았고, 1분 평균은 8건과 비슷한 43%였다. LiveKit 거절 기준(에이전트 부하 70%)에는 닿지 않았다
- 10건의 결과 대기는 최대 427초로 8건(245초)보다 길었다. 채점 작업자 1개가 병목이다

## 8. 한계

- 메인 서버와 에이전트가 같은 VPC라 Tailscale이 사설 IP로 직접 연결됐다. 운영은 계정이 달라 공인 IP로 붙는다(UDP 41641, 보안 그룹에 열어 둠).
