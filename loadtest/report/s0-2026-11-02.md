# S0 스모크 · 보정 결과 (2026-11-02)

[부하 테스트 계획](../../이해준/load_test_plan/README.md) 6장의 S0 결과다. 부하를 준 회차가 아니라 **스크립트가 맞는지 확인하고, 이후 회차의 기준값을 잰 회차**다.

## 요약

- HTTP 흐름(`s0-smoke.js`)과 실제 화면으로 하는 화상 면접(`s0-browser.js`)이 테스트 서버에서 모두 끝까지 동작했다. 실패 0건
- 외부 API에 묶인 단계의 지연: 지원서 저장(Jev) **약 0.5초**, 질문 준비(GMS PLAN) **5~7초**, 결과(GMS 채점) **14~20초**, 질문 음성 합성(ElevenLabs) **0.4~0.7초**
- **면접 1건당 서버 자원**: 서버 CPU **+8%p(약 0.32코어)**, 에이전트 메모리 **+약 350MB**(캐시가 아니라 프로세스가 직접 쓰는 메모리)
- 이 값으로 단순 계산하면 **CPU가 먼저 막힌다**: 기준치 40%에 약 4건, 에이전트가 새 면접을 받지 않는 70%에 약 7~8건, 에이전트 메모리 상한 4GB에 약 11건. 목표 단계 L2(동시 20건)보다 낮다. 1건만 잰 값이라 S5에서 기울기를 확인한다
- **k6 HTTP로는 면접을 진행할 수 없다**. 질문 · 답변 · 채점 · 녹화 부하는 브라우저 시나리오로만 만든다

| 질문 준비(장치 점검 화면 도착 → 준비 완료, GMS PLAN + 면접관 3D 모델) | 6.5초 | 6.8초 | 6.7초 |

## 4. 면접 1건당 서버 자원

같은 서버에서 면접이 없을 때(12:23:50~12:28:50, 5분)와 면접 10이 진행된 때(12:29:25~12:31:25, 2분)를 비교했다. 서버 Prometheus(30초 수집)의 cAdvisor 지표이고 `loadtest/server/resources.sh`로 뽑았다.

**서버 전체**

| 항목 | 대기 | 면접 1건 | 증가 |
|---|---|---|---|
| CPU 평균 | 9% | 17% | +8%p(약 0.32코어) |
| CPU 최대 | 14% | 20% | |
| steal 최대 | 0.4% | 0.2% | 없음 |
| 메모리 최대 | 18% | 19% | |

**컨테이너별**(CPU는 코어 수, 메모리는 working set 최대)

| 컨테이너 | CPU 대기 → 면접 | 메모리 대기 → 면접 | 증가 |
|---|---|---|---|
| ai-agent | 0.05 → 0.25 | 100MB → 455MB | **+0.20코어 · +355MB** |
| egress | 0.01 → 0.10 | 26MB → 93MB | +0.09코어 · +67MB |
| livekit | 0.00 → 0.05 | 46MB → 61MB | +0.05코어 · +15MB |
| ai-recording | 0.03 → 0.05 | 68MB → 68MB | 녹화 합치기(2초 남짓)라 거의 안 보임 |
| be | 0.01 → 0.02 | 575MB → 577MB | 거의 그대로 |
| fe · postgres · redis · nginx | 0.00~0.01 | 변화 없음 | |

- ai-agent 메모리는 **거의 모두 프로세스가 직접 쓰는 메모리**다(RSS 97MB → 448MB, 파일 캐시 0MB). 면접마다 새로 뜨는 처리 프로세스가 쓰는 메모리이고, 메모리가 모자라도 커널이 회수할 수 없다
- 에이전트 메모리 상한(`mem_limit` 4g) 대비 11%, BE는 1280m 대비 45%다(BE는 대기 때부터 이 정도다)

### 단순 계산으로 본 한계(추정)

| 한계(계획 5.1) | 계산 | 동시 면접 |
|---|---|---|
| 지속 가능 한계(서버 CPU 평균 40%) | (40% − 대기 9%) ÷ 8%p | **약 4건** |
| 에이전트 새 면접 거절(부하 0.7, 가설 H6) | (70% − 9%) ÷ 8%p | **약 7~8건** |
| 에이전트 메모리 OOM(4g) | (4096 − 100) ÷ 355MB | 약 11건 |

- **CPU가 메모리보다 먼저 막힐 것으로 보인다.** 막히는 모습은 OOM으로 진행 중인 면접이 끊기는 것보다, CPU가 70%를 넘을 때 **새 면접방에 면접관이 들어오지 않는** 쪽이 먼저일 수 있다(H6)
- 목표 단계 L2(동시 20건)보다 한참 낮다. 그래서 S5 단계를 1 · 3 · 5 · 8 · 10 …건으로 촘촘하게 잡는 것이 좋다

이 계산을 그대로 믿기 어려운 이유:
- 1건만 쟀고 수집 간격이 30초다. 면접방에 있던 시간(약 113초)에 비해 표본이 적다(구간 2분 = 표본 4개)
- 처리 프로세스를 처음 띄우는 비용이 섞였을 수 있다. 여러 건이면 공유 라이브러리가 겹쳐 2건째부터는 덜 늘어날 수 있다
- 가짜 답변이라 실제 면접보다 말하는 시간 비율이 높거나 낮을 수 있다
- 미디어 경로(UDP · TURN)에 따라 LiveKit CPU가 다르다. 이번 경로는 확인하지 않았다

## 5. 발견한 것

1. **k6 HTTP로는 면접을 진행할 수 없다.** 채팅 면접도 질문은 에이전트가 면접방(LiveKit)에서 내고, 에이전트는 사용자가 방에 들어올 때까지 기다린다(`ai/app/agent/main.py` `first_participant`). BE의 "지금 질문"(5.5)은 에이전트가 보내는 `question.started`를 받아야 생기므로 HTTP로 시작한 면접은 첫 질문이 나오지 않는다(60초 동안 202). 그래서 질문 · 답변 · 채점(H8) · 녹화(H9) 부하는 S5(브라우저)로만 만든다. 계획 6장에 반영했다
2. **에이전트에 CPU 기준 거절 장치가 있다.** 테스트 서버를 띄운 직후 첫 면접에서 에이전트가 `worker is at full capacity, marking as unavailable (load 0.76 > 0.7)`을 남겼다. LiveKit 에이전트 기본 장치로, 부하가 0.7을 넘으면 새 면접을 받지 않는다. 가설 H6에 반영했다
3. **에이전트 메모리가 추정의 약 두 배다.** 계획은 면접 1건에 150~200MB로 추정했는데 실측은 약 350MB(RSS)였다
4. **운영 Prometheus가 에이전트 지표를 모으지 않는다.** 에이전트는 `:9464/metrics`로 진행 중인 면접 수(`a301_agent_active_interviews`) 등을 내보내지만 `deploy/prod/prometheus.yml`에 수집 대상이 없다. S5에서 동시 면접 수를 서버 쪽에서 확인하려면 테스트 서버에 수집을 더하는 것이 좋다
5. 0개 답변으로 끝낸 면접(5.8)은 `ABORTED`가 되고 에이전트도 방을 나간다. HTTP 시나리오가 면접을 시작하면 이 방법으로 정리한다
