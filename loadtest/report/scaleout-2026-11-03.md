# 에이전트 분리 · scale out 중간 결과 (2026-11-03)

[에이전트 오토스케일링 계획](../../이해준/agent_autoscale_plan/README.md) 9장 검증의 1 · 2단계를 테스트 서버에서 진행했다. AI 면접관(에이전트)을 메인 서버에서 떼어 EC2 Auto Scaling Group(고정 대수, `t3.medium`)으로 띄웠다. 2단계(분리 효과 측정)를 하다가 **면접이 질문 도중 멈추는 현상**을 발견해, 측정을 멈추고 원인을 추적했다. 원인은 아직 확정하지 못했고, 이 문서는 그 과정과 지금까지 확인한 사실을 남긴다.

## 요약

- **분리 구성 자체는 동작한다.** ASG 인스턴스의 에이전트가 사설망으로 LiveKit(7880) · Redis(6379)에 붙어 면접 · 녹화 · 결과 · 다시보기까지 끝까지 됐다
- **drain(줄일 때 면접 보호)이 의도대로 동작한다.** 면접 중에 종료 신호를 보내도 질문 5개를 끝까지 진행하고, 면접이 끝난 1초 뒤에 컨테이너가 내려갔다
- **분리 뒤 면접이 질문 도중 멈추는 현상이 새로 나왔다.** 분리 전에는 0건(에이전트 로그 기준 면접 127건)이었는데, 분리 뒤 첫 두 회차에서 20건 중 5건이 멈췄다. 공통 증상은 에이전트가 화면에 보내는 상태 메시지(RPC)가 3초 시간 초과로 실패하고, 그 뒤 답변을 듣기 시작하지 않는 것이다
- **그 뒤 원인 조사 회차에서는 재현되지 않았다**(원격 에이전트 면접 21건 모두 정상). 특정 인스턴스 · 공인 IP 경로 · CPU 몰림은 원인이 아닌 것으로 좁혔고, 재현 조건은 찾지 못했다
- **매번 재현되는 차이 두 가지**
  - 원격 에이전트의 첫 질문이 **9~14초**로 메인 서버 안(4~6초)보다 4~6초 느리다
  - 막 켜진 인스턴스가 첫 면접을 받는 순간 **CPU 부하 0.97로 "가득 참"**이 된다(면접마다 프로세스를 새로 띄우는 설정, `num_idle_processes=0`)
- **LiveKit 배정은 고르지 않다.** 5건 8분 동안 한 대가 13건 중 10건을 받았다

## 1. 구성

| 구분 | 내용 |
|---|---|
| 메인(테스트) 서버 | EC2 `t3.xlarge`(`ap-northeast-2d`). `loadtest/server/compose.agent-split.yml`로 메인 서버 에이전트를 끄고 LiveKit 7880 · Redis 6379를 사설 IP(`172.31.54.174`)에만 엶 |
| 에이전트 ASG | `t3.medium`(unlimited), 기본 VPC의 `2a` · `2b`, 고정 대수(1~3대). 시작 템플릿 user data(`loadtest/agent/user-data.sh`)가 SSM에서 값을 읽고 운영과 같은 AI 이미지(`e9874c74`)로 에이전트 1개를 띄움 |
| 연결 | 시그널링은 사설 IP 7880, 미디어(WebRTC)는 LiveKit이 알려 주는 공인 IP의 UDP 7882, 결과는 사설 IP Redis |
| 부하 | S5 · S6 스크립트(화상 면접만 켠 `MIX`), 인프라 노트북 1대, SSAFY 네트워크(브라우저는 TURN 443) |

## 2. 1단계: 기능 · drain

| 시험 | 결과 |
|---|---|
| 면접 1건(529) | 완료. 첫 질문 6.3초, 질문 간격 20~22초, 결과 25.8초, 다시보기 2.7초 |
| drain(530) | 면접관 입장 직후(10:52:37) 컨테이너에 SIGTERM. 질문 1~5를 정상 간격으로 진행, **10:54:27.5 면접 종료(답변 5개 저장) → 10:54:28 컨테이너 종료**. 결과 · 다시보기 정상 |

drain은 livekit-agents 1.8.8의 기본 동작이다. SIGTERM을 받으면 새 면접을 받지 않고(`closing worker`) 진행 중인 면접이 끝날 때까지 기다린다(`drain_timeout` 기본 3600초).

|---|---|---|---|---|
| 분리 1차(11:00) | 원격 A · B | 7 | **4**(모두 B) | 위 3장 |
| 분리 2차(11:14, 5건 8분) | 원격 A · B | 13 | **1**(548, A) | B가 13건 중 10건을 받았고 모두 정상. 548은 상태 메시지 시간 초과 뒤 10분 동안 아무 진행 없음(STT 연결도 안 함) |
| 분리 전 기록(Loki) | 메인 서버 안 | 127 | 0 | S5 첫 회차 · S5 재측정 · S6(서버 CPU 94%까지)에서 "화면 전달 실패" 0건 |
| **대조군**(12:00, 5건 8분) | 메인 서버 안 1개 | 15 | **0** | "화면 전달 실패" 0, 첫 질문 4.2~6.3초 |
| 사설 IP 실험(12:13) | 원격 | – | – | LiveKit 미디어 주소를 사설 IP로 고정하자 원격 에이전트는 사설 IP로 붙었지만 **브라우저(TURN)가 연결되지 못해 무효**. 원래 설정으로 되돌림 |
| **비교 실험**(12:28, 5건 10분) | 원격 2 + 메인 서버의 "원격 흉내" 1(기본 브리지 · 사설 IP 접속 · CPU 2개) | 18 | **0** | 원격1 9건 · 원격2 3건 · 흉내 6건 모두 정상 |
| **새 인스턴스**(12:45, 5건 6분) | 새 인스턴스 1 + 원격 2 | 9 | **0** | 새 인스턴스가 첫 면접 때 부하 0.97로 "가득 참" → 2초 뒤 회복. 이후 정상 |

**원인에서 뺀 것**

| 가설 | 근거 |
|---|---|
| 특정 인스턴스(B) | 2차에서 B가 10건을 모두 정상 처리, 멈춘 548은 A |
| 공인 IP 경로 | 대조군(메인 서버 에이전트)도 공인 IP로 나갔다 들어오는 경로였는데 0건 |
| 메인 서버 · 발생기 CPU | 실패 시각 메인 서버 CPU 7~33%, 노트북 최대 8코어(약 36%) |
| 원격 인스턴스 CPU(평균) | 실패 구간 5분 평균 17~26%(순간 몰림은 이 해상도로 못 봄) |

**남은 가설**

- 원격 에이전트와 LiveKit 사이(인스턴스 간 네트워크, 가용 영역 `2a` · `2b` ↔ `2d`)에서 데이터 채널 메시지가 간헐적으로 늦거나 막힘
- 면접을 받는 순간의 프로세스 기동 부하(새 인스턴스에서 0.97 확인)와 겹칠 때 첫 메시지가 늦어짐

**코드에서 확인한 것**: 상태 메시지(RPC) 실패는 잡아서 로그만 남기고 진행하도록 짜여 있다(`ai/app/agent/main.py` · `question.py`). 그런데 548은 그 뒤 답변 듣기를 시작하지 않았다. 질문 음성 재생 등 다른 단계에서 기다리다 멈춘 것으로 보이며, **그 단계에 시간 상한이 없어 한 번 걸리면 면접이 무한정 멈춘다.**

## 5. 그 밖에 관찰한 것

- **원격 에이전트 첫 질문 지연**: 메인 서버 안 4~6초 → 원격 9~14초(새 인스턴스 · 기존 인스턴스 모두). 매번 재현된다
- **LiveKit 배정 쏠림**: 2차에서 B 10 · A 3, 비교 실험에서 원격1 9 · 원격2 3 · 흉내 6. LiveKit은 부하 70% 아래인 작업자 중 하나를 고르며, 부하가 CPU 5초 평균이라 몰리는 순간에는 모두 한가해 보인다
- **로그인 화면 실패**(부하 스크립트): 로그인 화면이 다 그려지기 전(한글 글꼴이 아직 안 뜬 상태)에 입력해 실패하는 일이 오늘 5번 있었다. 에이전트와 무관한 발생기 쪽 문제다

## 6. 조치 후보

| 파트 | 조치 | 이유 |
|---|---|---|
| AI | 질문 음성 재생 · 상태 알림에 시간 상한을 두고, 넘기면 다음 단계로 넘어가거나 면접을 실패로 끝냄 | 원인과 관계없이 면접이 무한정 멈추는 것을 막는다 |
| AI | `num_idle_processes` 1~2(프로세스 미리 띄우기) | 첫 면접 때 CPU 순간 포화 · 첫 질문 지연을 줄인다 |
| AI | 부하를 "진행 중 면접 수 ÷ 대당 상한"으로(`load_fnc`) | 배정 쏠림을 막고 오토스케일 기준(대당 5건)과 맞춘다 |

| 인프라 | 원격 에이전트 로그 · 지표를 메인 Loki · Prometheus로 보냄(인스턴스 Alloy) | 원격 로그를 Session Manager로만 볼 수 있어 추적이 느렸다 |
| 인프라 | 다음 회차에 에이전트 `--log-level debug`로 멈춤 재현 시 어느 단계에서 기다리는지 기록 | 재현 조건을 찾기 위해 |
| 부하 스크립트 | 로그인 화면 입력 전에 화면이 다 그려질 때까지 기다림 | 발생기 쪽 실패 제거 |
