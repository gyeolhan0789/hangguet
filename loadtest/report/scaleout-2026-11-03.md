# 에이전트 분리 · scale out 중간 결과 (2026-11-03)

[에이전트 오토스케일링 계획](../../이해준/agent_autoscale_plan/README.md) 9장 검증의 1 · 2단계를 테스트 서버에서 진행했다. AI 면접관(에이전트)을 메인 서버에서 떼어 EC2 Auto Scaling Group(고정 대수, `t3.medium`)으로 띄웠다. 2단계 첫 시도에서 **면접이 질문 도중 멈추는 현상**을 발견해 측정을 멈추고 원인을 추적했고, 이후 2단계(분리 효과 측정)를 다시 끝까지 돌렸다(5장).

## 요약

- **분리 효과: 같은 동시 5건에서 메인 서버 CPU가 44% → 24%로 내려갔다.** 분리 뒤에는 동시 10건도 35%로 지속 가능 기준(40%) 아래다. 메인 서버에서 가장 큰 몫은 이제 Egress(녹화)다(5장)
- **분리 구성 자체는 동작한다.** ASG 인스턴스의 에이전트가 사설망으로 LiveKit(7880) · Redis(6379)에 붙어 면접 · 녹화 · 결과 · 다시보기까지 끝까지 됐다
- **drain(줄일 때 면접 보호)이 의도대로 동작한다.** 면접 중에 종료 신호를 보내도 질문 5개를 끝까지 진행하고, 면접이 끝난 1초 뒤에 컨테이너가 내려갔다
- **면접 멈춤은 간헐적이고, 분리가 원인이라는 근거는 약하다.** 분리 직후(11:00~11:20) 20건 중 5건이 멈췄지만, 같은 시간대에 나란히 비교한 회차(원격 vs 메인 서버 안)에서는 둘 다 0이었다. 2단계 재측정에서 멈춘 1건(631)은 DEBUG 로그로 보니 **에이전트는 면접을 끝까지 했는데 화면이 질문 3에서 갱신되지 않은 것**이었다(4장). 멈춤의 상당 부분이 화면(브라우저) 쪽일 가능성이 있다
- **화면이 멈추면 면접이 `IN_PROGRESS`로 영원히 남는다.** 답변 5개가 다 저장됐는데 화면이 "면접 종료"를 보내지 못해 결과가 만들어지지 않았다(631)
- **녹화 합치기가 트랙이 다시 올라온 면접에서 실패한다.** 지원자 마이크 트랙이 면접 중 한 번 내려갔다 올라와 음성 파일이 2개가 되자 "같은 종류의 트랙이 여러 개다"로 실패했다(608)
- **매번 재현되는 차이 두 가지**
  - 원격 에이전트의 첫 질문이 **9~14초**로 메인 서버 안(4~6초)보다 4~6초 느리다
  - 막 켜진 인스턴스가 첫 면접을 받는 순간 **CPU 부하 0.97로 "가득 참"**이 된다(면접마다 프로세스를 새로 띄우는 설정, `num_idle_processes=0`)
- **LiveKit 배정은 고르지 않다.** 5건 8분 동안 한 대가 13건 중 10건을 받았다

## 2. 1단계: 기능 · drain

| 시험 | 결과 |
|---|---|
| 면접 1건(529) | 완료. 첫 질문 6.3초, 질문 간격 20~22초, 결과 25.8초, 다시보기 2.7초 |
| drain(530) | 면접관 입장 직후(10:52:37) 컨테이너에 SIGTERM. 질문 1~5를 정상 간격으로 진행, **10:54:27.5 면접 종료(답변 5개 저장) → 10:54:28 컨테이너 종료**. 결과 · 다시보기 정상 |

drain은 livekit-agents 1.8.8의 기본 동작이다. SIGTERM을 받으면 새 면접을 받지 않고(`closing worker`) 진행 중인 면접이 끝날 때까지 기다린다(`drain_timeout` 기본 3600초).

**남은 가설**

- 원격 에이전트와 LiveKit 사이(인스턴스 간 네트워크, 가용 영역 `2a` · `2b` ↔ `2d`)에서 데이터 채널 메시지가 간헐적으로 늦거나 막힘
- 면접을 받는 순간의 프로세스 기동 부하(새 인스턴스에서 0.97 확인)와 겹칠 때 첫 메시지가 늦어짐

**코드에서 확인한 것**: 상태 메시지(RPC) 실패는 잡아서 로그만 남기고 진행하도록 짜여 있다(`ai/app/agent/main.py` · `question.py`). 그런데 548은 그 뒤 답변 듣기를 시작하지 않았다. 질문 하나를 말하는 흐름(`question.py` `ask`)은 "말하기 시작" 알림(RPC, 최대 3초) → **음성 재생 대기(`wait_for_playout()`, 시간 상한 없음)** → "말하기 끝" 알림 → 답변 듣기 순서다. 548은 첫 알림이 시간 초과된 뒤 아무 기록이 없어, **재생 대기에서 멈춘 것**과 맞는다. 원인이 무엇이든 그 단계에 상한이 없어 한 번 걸리면 면접이 무한정 멈춘다.

## 5. 2단계: 분리 효과(13:01~13:39)

원격 에이전트 2대(DEBUG 로그), 화상 면접만 동시 5 → 8 → 10건(각 8분, 사이 2분 쉼). 비교 기준은 같은 날 같은 방식으로 잰 **대조군**(에이전트를 메인 서버 안에 두고 동시 5건 8분, 12:00)이다. 서버 자원은 단계 8분 구간 평균(`server/resources.sh`).

| 동시 면접 | 메인 서버 CPU 평균(최대) | Egress CPU · 메모리 | LiveKit | 합치기(ai-recording) | ai-agent(메인 서버) |
|---|---|---|---|---|---|
| 5건, 에이전트 메인 서버 안(대조군) | **44%**(58%) | 0.42 · 463MB | 0.16 | 0.32 | 0.51(최대 0.78) |
| **5건, 분리** | **24%**(39%) | 0.25 · 455MB | 0.11 | 0.20 | – |
| **8건, 분리** | **32%**(52%) | 0.35(최대 0.78) · 630MB | 0.13 | 0.19 | – |
| **10건, 분리** | **35%**(64%) | 0.45(최대 1.12) · **743MB(73%)** | 0.14 | 0.22(최대 0.97) | – |

| 동시 면접(분리) | 면접 | 첫 질문 중간값(최대) | 질문 간격 p90 | 질문 준비 평균 | **결과 대기 평균(최대)** |
|---|---|---|---|---|---|
| 5건 | 12건 완료 + 녹화 실패 1(608) | 9.8초(15.1초) | 22.1초 | 16.5초 | 39초(81초) |
| 8건 | 18건 완료 | 9.3초(21.4초) | 22.2초 | 26.5초 | 102초(200초) |

- **같은 5건에서 메인 서버 CPU 44% → 24%(20%p 감소).** 에이전트 몫(0.51코어, 약 13%p)보다 더 내려간 것은 대조군이 같은 8분에 면접을 더 많이 처리해 녹화 · 합치기도 많았기 때문으로 본다. 분리 뒤에는 10건도 지속 가능 기준(40%) 아래다
- 분리 전 S5 재측정(같은 서버, 면접 진행 2분 평균)은 5 · 8 · 10건에 43 · 61 · 68%였다. 측정 구간이 달라 직접 비교는 대조군(5건)만 한다
- 이제 메인 서버에서 **가장 큰 몫은 Egress**다. 10건에 0.45코어, 메모리 743MB(상한 1GB의 73%). 다음 한계는 Egress 메모리(약 13~14건 추정)다
- **결과 대기가 몰리면 길어진다**(10건 평균 약 4분, 최대 6분). 채점 작업자 1개가 1건(GMS 11번, 약 30초)씩 직렬로 처리한다. 마감(10분) 안이지만 사용자가 기다리는 시간이다(H8)
- 배정은 두 대에 21 · 25건으로 비교적 고르게 나뉘었다
- 면접 46건 중 45건 완료. 실패는 녹화 합치기 1건(608, 아래), 화면 멈춤 1건(631, 4장)이다. 로그인 재시도(부하 스크립트 수정)가 4번 동작해 발생기 쪽 실패는 0이었다

**녹화 합치기 실패(608)**: 지원자 마이크 녹화가 13.8초 만에 끝나고(지원자 트랙이 내려감), 몇 초 뒤 트랙이 다시 올라와 녹화가 새로 시작됐다. 지원자 음성 파일이 2개가 되자 합치기(ai-recording)가 "같은 종류의 트랙이 여러 개다: CANDIDATE_AUDIO"로 실패했고, 다시보기는 "녹화를 불러오지 못했어요"가 됐다. 실제 사용자도 네트워크가 잠깐 끊기거나 마이크를 다시 잡으면 같은 일이 생긴다. 합치기가 같은 종류 파일을 시간순으로 이어 붙여야 한다(AI). 화면이 왜 트랙을 다시 올렸는지는 FE 확인이 필요하다.

## 6. 그 밖에 관찰한 것

- **원격 에이전트 첫 질문 지연**: 메인 서버 안 4~6초 → 원격 9~14초(새 인스턴스 · 기존 인스턴스 모두). 매번 재현된다
- **LiveKit 배정 쏠림**: 2차에서 B 10 · A 3, 비교 실험에서 원격1 9 · 원격2 3 · 흉내 6. LiveKit은 부하 70% 아래인 작업자 중 하나를 고르며, 부하가 CPU 5초 평균이라 몰리는 순간에는 모두 한가해 보인다
- **로그인 화면 실패**(부하 스크립트): 로그인 화면이 다 그려지기 전(한글 글꼴이 아직 안 뜬 상태)에 입력해 실패하는 일이 5번 있었다. 에이전트와 무관한 발생기 쪽 문제라 `lib/browser-interview.js` `loginByUi`를 고쳤다(화면 준비 대기 · 입력값 확인 · 한 번 재시도). 2단계에서 재시도가 4번 동작해 실패 0이었다
