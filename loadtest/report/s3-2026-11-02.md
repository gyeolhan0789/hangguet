# S3 지원서 저장 몰림 결과 (2026-11-02)

[부하 테스트 계획](../../이해준/load_test_plan/README.md) 6장의 S3 첫 회차다. 단계마다 지원서 N건을 같은 순간에 저장해 동시 1 · 3 · 5 · 10 · 20 · 30 · 40 · 50건으로 올렸다(가설 H2). 자소서 검증은 실제 Jev를 불렀다.

## 요약

- **H2 맞음: 자소서 검증이 한 줄로 선다.** 검증 스레드 1개가 Jev를 하나씩 부르므로 동시에 저장한 N건 중 k번째는 앞의 k−1건을 기다린다. 저장 시간이 건수에 비례해 늘었다(10건 최대 2.1초 → 20건 4.3초 → 40건 7.1초 → 50건 8.4초)
- **기능 한계는 동시 약 45건이다.** 검증 1건은 약 0.175초(Jev 0.17~0.20초)이고 BE는 8초까지만 기다린다. 8초 ÷ 0.175초 ≈ 45건이라 **50건에서 4건이 503**(`COVER_LETTER_CHECK_UNAVAILABLE`, "잠시 후 다시 시도해 주세요")이 됐다. 계획의 예상(20건)보다 높다
- **Jev와 서버는 원인이 아니다.** Jev 1건 시간은 몰려도 0.17~0.20초로 그대로였고, 서버 CPU는 최대 20%였다. 한계는 **검증 스레드 1개 × BE 대기 8초**라는 구조가 정한다
- **품질 기준(쓰기 p95 1초)은 동시 3건부터 넘는다.** 1건이 0.5~0.8초(네트워크 약 0.3초 포함)라 2~3건만 겹쳐도 1초를 넘는다. 다만 "같은 순간에 저장" 조건이라 실제 사용자 흐름보다 몰린 경우다
- 한계(계획 5.1)

  | 한계 | 동시 저장 | 근거 |
  |---|---|---|
  | 기능 한계(저장 실패 ≥ 1%) | **50건(계산상 약 45건)** | 50건 중 4건 503(8%) |
  | 품질 한계(쓰기 p95 ≥ 1초) | **3건** | 3건 p95 1.12초, 10건 1.97초 |
  | 지속 가능 한계 | 해당 없음 | 서버 CPU 최대 20% |

### 3.3 자원

- 서버 CPU 평균 10% · 최대 20%, BE 최대 0.35코어, ai-analysis 0.03코어. 검증은 CPU를 거의 쓰지 않고 Jev 응답을 기다리는 일이다
- 몰림이 8초 안에 끝나 Prometheus(30초 수집) · Grafana로는 거의 보이지 않는다. 이번 회차는 Grafana 화면 대신 서버 로그 시각으로 봤다
- 저장을 기다리는 동안 BE 요청 스레드가 1건에 최대 8초씩 잡힌다(50건이면 스레드 50개). CPU는 쓰지 않지만 Tomcat 스레드(200개)를 나눠 쓰므로, 로그인 몰림(S2, 스레드 200개를 다 씀)과 겹치면 서로 영향을 줄 수 있다(S6에서 확인)

## 5. 해석 · 다음

- **같은 순간에 지원서를 저장하는 사용자가 약 45명을 넘으면 일부가 "잠시 후 다시 시도"를 본다.** 평소에는 저장이 흩어져 일어나므로, 분당 약 340건(초당 5.7건)까지는 줄이 쌓이지 않는다. 발표 직후처럼 많은 사람이 같은 때 지원서를 만드는 경우만 걸린다
- 품질 기준 1초는 2~3건만 겹쳐도 넘는다. 화면에서 저장 버튼을 누른 뒤 1~8초를 기다리는 셈이라 사용자 경험으로는 이쪽이 먼저 보인다
- 개선 후보(대응은 이 문서 범위 밖)
  - **검증 스레드 늘리기**(AI): 스레드 N개면 처리량 N배, 8초 안 한계도 N배. Jev가 몰려도 느려지지 않았으므로(한 번에 하나라 확인 범위는 좁다) 2~4개는 무리가 없을 것으로 보인다. Jev의 동시 요청 제한은 확인 필요
  - **BE가 버린 결과 줄이기**: BE가 포기한 뒤에 AI가 Jev를 부르는 경우가 있다(이번 2건). AI의 버림 기준(8초)을 BE 대기보다 조금 짧게 하면 Jev 호출을 아낀다
- 다음 회차: **S4 면접 만들기 몰림**(GMS 스텁 필요). S6에서 S2 · S3 · S5와 겹쳐 본다
