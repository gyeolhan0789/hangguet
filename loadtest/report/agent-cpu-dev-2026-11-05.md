# 면접 에이전트 컨테이너 CPU: 100ms 조각 반영 뒤 (2026-11-05, 개발 서버)

[에이전트 · Egress 오토스케일링 계획](../../이해준/agent_autoscale_plan/README.md)의 면접 1건당 에이전트 CPU(0.12~0.16코어, [S5 보고서](s5-2026-11-02.md))는 음성 조각이 10ms이던 이미지(`e9874c74`)로 잰 값이다. 11/04에 조각을 100ms로 바꿨지만([음성 조각 보고서](agent-audio-2026-11-04.md)) 그때는 서버 전체 CPU만 봤다. 이번에는 개발 서버에서 **에이전트 컨테이너만** 따로 재서, 바뀐 이미지의 1건당 CPU와 대기 상태 CPU를 확인한다.

## 요약

- **면접 1건당 에이전트 CPU는 약 0.18코어다**(개발 서버 Intel N100, 화상 면접 2건 동시, 약 2분). 대기 0.117코어 → 면접 2건 0.486코어
- **이 값은 `t3`의 0.12~0.16과 바로 비교할 수 없다.** N100은 저전력 CPU라 코어 하나가 `t3`(Xeon)보다 느리다. 같은 서버에서 잰 11/04 변경 전후 차이(1건 약 −0.065코어)를 더하면 10ms 시절 이 서버에서는 약 0.25코어다. 같은 비율(약 0.74)을 `t3`에 적용하면 **`t3`에서 1건 약 0.1코어**로 본다 **[추정]**. 확정은 테스트 서버에서 한다(계획 9장 3단계)
- **대기 상태에서도 0.117코어를 쓴다.** 메인 작업자 약 0.04코어 + 미리 띄운 대기 프로세스 4개가 각각 약 0.012코어다. `AGENT_IDLE_PROCESSES`를 정하지 않아 CPU 수(4)만큼 떠 있다
- **면접을 받는 순간 CPU가 튀지 않았다.** 면접방에 들어간 직후 5초도 0.456코어로 면접 중 평균과 비슷하다. 대기 프로세스가 면접을 바로 받았기 때문이다(새 인스턴스 첫 면접 0.97, [scale out 보고서](scaleout-2026-11-03.md))
- 메모리는 1건당 약 45MB로 기존 실측(약 45~50MB)과 같다

## 2. 재는 법

- `loadtest/agent-cpu/sample.sh`가 서버에서 에이전트 컨테이너의 cgroup `cpu.stat`(`usage_usec`)과 `memory.current`를 5초마다 읽는다. 사용한 CPU 시간 ÷ 경과 시간 = 그 5초 동안의 평균 코어 수다
  - `docker stats` · `docker exec`를 쓰지 않는다. 컨테이너 안에 프로세스를 띄우면 그 CPU가 측정값에 섞인다
- 면접 구간은 에이전트 로그의 `LiveKit 방 참가 완료`(13:09:23.7 · 13:09:24.1) ~ `LiveKit 방 연결 종료`(13:11:27.0 · 13:11:27.0)다. 걸친 5초 값(13:09:27 · 13:11:27)은 빼고 그 안의 22개 값을 쓴다
- 대기 상태는 면접 전 5분(13:04:04~13:09:22, 62개)과 면접 뒤 2분(13:11:38~13:13:38, 24개)이다. 질문 준비(PLAN)는 에이전트가 아니라 AI 작업자가 해서 면접 전 구간에 섞이지 않는다
- 대기 상태의 프로세스별 CPU는 서버에서 `top -b -n 2 -d 10`으로 에이전트 컨테이너의 프로세스만 10초 동안 봤다(면접 뒤)

## 4. 대기 상태는 어디서 쓰나

면접 뒤 대기 상태에서 에이전트 컨테이너의 프로세스를 10초 동안 봤다.

| 프로세스 | CPU | 메모리(RSS) |
|---|---|---|
| 메인 작업자(`python -m app.agent.main start`, LiveKit 등록 · 배정 · 부하 보고) | 4.0%(약 0.04코어) | 137MB |
| 대기 프로세스 4개(forkserver 자식, 면접을 받으면 그 면접을 맡는다) | 각 1.1~1.3%(합 약 0.05코어) | 각 321MB(대부분 forkserver와 함께 쓰는 페이지) |
| forkserver · resource tracker | 0% | 379MB · 18MB |

- 합 약 0.09코어로 cgroup 값(0.117)보다 조금 낮다. `top`은 10초 한 번 본 값이라 오차가 있다
- 면접이 대기 프로세스 2개를 가져가면 바로 새 대기 프로세스 2개를 띄웠다(13:09 시작, 각 CPU 시간 약 2.5초). 이 기동 비용은 면접 구간 값에 들어 있다

## 5. 해석

**`t3`로 옮기면** **[추정]**

| | 10ms(`e9874c74`) | 100ms(`75341004`) | 출처 |
|---|---|---|---|
| 개발 서버 N100, 1건 | 약 0.25코어(= 0.18 + 0.065) | **0.18코어** | 이번 측정, 11/04 차이(같은 서버) |
| `t3.xlarge`, 1건 | 0.12~0.16코어 | **약 0.1코어**(× 0.74) | S5, 비율로 환산 |

- 1건이 약 0.1코어면 `t3.small`(2 vCPU) 한 대의 확장 목표(평균 CPU 40%, 0.8코어)는 대기 몫을 빼고 **약 7건**이다(계획 4.1의 5건은 0.15코어 기준). 새 면접 거절(70%)은 약 13건이다
- 11/04 차이(−0.065)는 양쪽 5개 값으로 잰 것이라 "예상과 맞는 결과이지 확실한 증명은 아니다"([음성 조각 보고서](agent-audio-2026-11-04.md) 7장). 그래서 환산값은 범위로 보고, 계획 문서의 대당 건수는 테스트 서버 3단계(develop 이미지)에서 바꾼다

**대기 프로세스 수**

- 대기 프로세스 1개가 약 0.012코어 · 수십 MB(대부분 공유)를 쓴다. 대신 면접을 받는 순간의 튐과 첫 질문 지연을 없앤다(이번 측정에서 튐 없음, 입장 뒤 첫 질문 15초)
- 운영 에이전트 인스턴스(`t3.small`, 2 vCPU)는 기본값이 2개다. 동시에 몰려 시작하는 면접 수만큼 있으면 되고, 그 위는 바로 다음 것을 띄운다. **1~2개**가 적당하다 **[제안]**. 0은 두 번째 동시 배정을 거절하므로 쓰지 않는다(`ai/app/agent/main.py` `create_server` 주석)
- 개발 서버는 4개라 면접이 없어도 0.117코어를 쓴다. 미니PC는 CI 러너와 같이 쓰므로 `dev/*` 변수로 1~2개로 낮추는 것을 검토한다

**면접 중 CPU의 구성**: 가짜 답변이 답변당 약 14초로 짧아, 실제 면접보다 질문 음성을 내보내는 시간의 비중이 크다. 내보내기가 듣기보다 CPU를 더 쓰므로(로컬 5.0~7.6% 대 3.2~3.4%, 11/04 4장) 실제 10분 면접의 평균은 이보다 낮을 가능성이 크다.

## 6. 한계

- 면접 2건 · 1회다. 방향을 보는 값이고, 대당 처리량을 정하는 값이 아니다
- N100과 `t3`는 CPU가 달라 절대값을 옮길 수 없다. 환산은 11/04 같은 서버 차이에 기대고 있다
- 개발 서버는 LiveKit Cloud를 쓴다. 미디어가 인터넷을 거치지만 에이전트가 하는 일(받기 · 풀기 · 압축)은 운영(셀프 호스팅)과 같다
- 면접이 약 2분이라 면접을 받을 때의 비용(배정 · 방 참가 · 대기 프로세스 다시 띄우기)이 평균에 크게 섞인다

## 부록: 다시 재는 법

레포 루트, Git Bash. 개발 서버 SSH(`yobi-server`)가 되어야 한다.

```bash
mkdir -p loadtest/results/agent-cpu
# 1. 기록 시작(20분). 첫 3~5분은 면접 없이 대기 상태를 잰다
ssh yobi-server 'bash -s -- 1200 a301-dev-ai-agent' < loadtest/agent-cpu/sample.sh > loadtest/results/agent-cpu/agent-cpu.csv &
# 2. 면접 2건 동시 진행. 뜬 크롬 창에서 로그인하면 이어서 진행한다
node loadtest/agent-cpu/two-interviews.cjs
# 3. 면접 구간(방 참가 ~ 연결 종료)
ssh yobi-server "docker logs --since 30m a301-dev-ai-agent 2>&1 | grep -E 'LiveKit 방 (참가 완료|연결 종료)'"
```

원본(커밋하지 않음): `loadtest/results/agent-cpu/agent-cpu.csv` · `two-interviews.json`
