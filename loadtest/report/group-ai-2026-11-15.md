# 그룹 면접 AI 성능 시험 (2026-11-15)

[AI 명세](../../docs/AI-명세.md) 6.7 「성능 시험」과 10장 「확인 필요」, [그룹면접 설계](../../docs/그룹면접-설계.md) 12장 「에이전트 부하」에 남은 그룹 면접 AI의 성능을 로컬에서 실제 화면 · 실제 외부 API로 측정한다(S15P31A301-528).
측정 대상은 꼬리질문 판단 응답 시간, 그룹 질문 생성 시간, 다른 참가자 목소리 섞임, 그룹 하나의 에이전트 부하가 개인 면접 몇 건에 해당하는지, 다시보기 구간과 실제 말소리의 일치 여부다.

## 요약

- **꼬리질문 판단은 7초 제한 안에 충분히 도착한다.** GMS 단독 120회 p90 3.3초 · 최대 4.2초(5초 초과 0), 실제 그룹 면접 판단 48회 모두 7초 이내(BE `late=true` 0회), 화면 기준 판단 단계 최대 3.7초다(1장)
- **그룹 질문 생성은 참가자 순서대로 한 건씩 처리된다.** 1건 약 5~8초이므로 3명이 함께 참가하면 마지막 참가자가 약 18초, 그룹 3개(9명)가 같은 순간 참가하면 마지막 참가자가 65초를 대기했다(2장)
- **에이전트는 답변자 목소리만 전사했다.** 차례가 아닌 참가자도 계속 발화하게 한 그룹 21개 세션 답변 126개에서 다른 참가자 주제 낱말이 나온 답변은 0개였다. 다만 답변자 마이크에 다른 목소리가 유입되면, 답변자가 발화를 멈춘 동안에는 답변자 음성의 약 3%(-30dB) 크기도 Soniox가 전사했다(3장)
- **그룹 하나의 에이전트 CPU는 답변 길이에 따라 개인 면접 약 0.8~1.8건에 해당했다.** 답변이 짧으면(평균 8~10초) 그룹이 1.6~1.8건, 답변이 길면(약 60초) 그룹이 약 0.8건이었고, 비율이 역전된 원인은 확인하지 못했다. 운영 DB의 화상 답변은 33개뿐이라 실제 사용자의 답변 길이 분포도 확인하지 못했다(4장 · 8장)
- **BE 동시 상한과는 관계가 없다.** BE 동시 상한(운영 8건)은 에이전트 CPU가 아니라 Soniox 실시간 인식 연결 한도로 정한 값이고, 그룹은 답변자 한 명만 인식하므로 연결 1개를 사용한다(4장)
- **다시보기 구간에서 답변이 잘린 곳은 없었다.** 22개 세션 132개 구간 모두 발화가 멈춘 시각부터 7.17초 이상 지난 뒤 구간이 끝났다. 구간은 DB의 질문 생성 시각부터 답변 종료 시각까지와 정확히 일치한다(5장)
- 측정 중 로컬 Docker DNS가 두 차례 빈 응답을 반환했고, GMS 연결 오류는 재시도 없이 결과 생성 전체를 실패시켰다(6장)

## 1. 꼬리질문 판단 응답 시간

### 1.1 GMS 단독

골든셋 답변(`ai/eval/golden/items.jsonl`) 150개 중 60개를 같은 간격으로 선택해 에이전트와 같은 프롬프트(`group-followup-v1`, `gpt-5.6-terra`)로 요청했다(`loadtest/group-ai/followup_latency.py`). 에이전트는 5초(`GROUP_FOLLOWUP_TIMEOUT`)에서 대기를 중단하지만, 분포를 확인하기 위해 30초까지 대기했다.

| 조건 | p50 | p90 | 최대 | 5초 초과 | 필요 · 불필요 | 출력 오류 |
|---|---|---|---|---|---|---|
| 순차 60회 | 2.60초 | 3.27초 | 4.16초 | 0 | 45 · 15 | 0 |
| 3개 동시 60회 | 2.39초 | 3.20초 | 3.86초 | 0 | 45 · 15 | 0 |

### 1.2 실제 그룹 면접

| 기준 | 값 |
|---|---|
| BE 로그 `꼬리질문 판단`(그룹 8개, 24개 세션) | 48회 모두 `late=false`, GMS 호출(`generationMs`) 1.4~3.6초 |
| 화면이 수신한 판단 단계(`DECIDING`) 길이(그룹 7개, 42회) | 짧은 답변 그룹 2개 동시 p50 2.51초 · 최대 3.67초, 그룹 3개 동시 p50 2.20초 · 최대 2.98초, 긴 답변 그룹 2개 동시 p50 2.51초 · 최대 3.47초 |

- 화면 기준 값은 브라우저가 메시지를 수신한 시각의 차이다. 그룹 3개 회차는 브라우저 9개로 측정 PC 부하가 높아(4장) 수신이 지연되었을 수 있으므로, 판단 시간은 BE 로그를 기준으로 판단한다
- 에이전트 대기 5초는 GMS 최대 4.2초보다 길어 유지한다
- BE 제한 7초(`group.followup-decision-timeout`)는 판단 단계가 최대 3.7초라 여유가 있다. 2~3초로 줄이면 GMS p50(2.4~2.6초)과 겹쳐 제한 시간을 넘는 판단, 즉 누락되는 꼬리질문이 늘어난다

## 2. 그룹 질문 생성 시간

참가할 때마다 그룹용 질문 생성(PLAN, `plan-group-v1`)이 질문 생성 큐에 추가된다(그룹면접 설계 6.1 만들기 · 참가). 세션 생성 시각부터 `interview_plans` 저장 시각까지를 DB에서 측정했다.

| 같은 순간 참가한 인원 | 첫 참가자 | 마지막 참가자 |
|---|---|---|
| 3명(그룹 1개) | 6.2초 | 17.7초 |
| 6명(그룹 2개, 2회) | 15.4 · 15.9초 | 45.0 · 44.6초 |
| 9명(그룹 3개) | 14.2초 | 65.0초 |

- 작업자 1개가 1건씩 처리하므로 질문 생성 완료 간격이 1건 약 5~8초(5.2~8.3초)였다. 개인 면접의 [S4 결과](s4-2026-11-02.md)(1건 약 5초, 분당 약 12건)와 같은 양상이다
- 대기실 [면접 시작]은 마지막 참가 후 42~69초에 활성화되었다(모든 참가자의 질문 준비가 끝나야 활성화된다)

## 3. 다른 참가자 목소리 섞임

### 3.1 답변자만 구독하는지

참가자마다 주제가 다른 답변(`loadtest/group-ai/answers.json`: 개발 · 물류 창고 · 음악 동아리)을 가짜 마이크로 계속 재생했다. 차례가 아닌 참가자도 계속 발화하는 상태다. 에이전트가 답변자 마이크만 구독하면(설계 6.8) 답변 글에 다른 참가자의 주제 낱말이 나오지 않아야 한다(`loadtest/group-ai/mixing.py`).

| 대상 | 답변 | 자기 주제 낱말 포함 | 다른 참가자 주제 낱말 포함 |
|---|---|---|---|
| 짧은 답변 그룹 5개, 15개 세션 | 90 | 52 | **0** |
| 긴 답변 그룹 2개, 6개 세션 | 36 | 35 | **0** |

### 3.2 유입된 목소리를 전사하는지(상한)

답변자(u1) 마이크 음성 25초 3개에 다른 참가자(u2) 목소리를 답변자 음성 실효값 대비 -30 · -20 · -10dB로 합성해, 에이전트와 같은 Soniox 연결로 실시간 속도에 맞춰 전송했다(`loadtest/group-ai/leak_stt.py`). 브라우저 에코 제거(livekit-client 기본 `echoCancellation: true`, FE는 변경하지 않음)를 거치지 않은 단순 합성이므로, 스피커로 나온 상대 목소리가 마이크로 유입되는 실제 경로보다 섞임이 크게 측정되는 최악의 상한이다.

| 음성 | 합성 없음 | -30dB | -20dB | -10dB |
|---|---|---|---|---|
| 1(답변자가 계속 발화) | 섞인 낱말 0 · 119자 | 0 · 119자 | 0 · 119자 | 0 · 119자 |
| 2(답변자가 계속 발화) | 0 · 105자 | 0 · 100자 | 0 · 125자 | 0 · 129자 |
| 3(답변자가 8초 침묵) | 0 · 67자 | **재고 · 물류** · 140자 | **재고 · 물류** · 140자 | **재고 · 물류** · 142자 |

- 답변자가 발화하는 동안 합성한 목소리는 주제 낱말로 나오지 않았다. -20dB부터 글자 수가 늘어(105 → 125 · 129자) 일부 소리가 전사에 포함되었다
- **답변자가 침묵하는 동안에는 -30dB(답변자 음성의 약 3%)의 작은 목소리도 전사했다.** 에코 제거가 없거나 상대 소리가 스피커가 아닌 같은 공간에서 들리면, 답변자가 침묵하는 사이 다른 사람의 말이 답변 글에 포함될 수 있다
- 실제 그룹 면접 경로(3.1)에서는 섞임이 0이었지만, 그 시험은 브라우저마다 다른 가짜 마이크를 사용해 소리가 서로 유입되지 않는 조건이다. 실제 사용자 환경의 유입은 이 시험으로 확인하지 못했고, 안내(설계 6.8: 이어폰 · 차례 외 음소거)가 유일한 대응이다

## 4. 그룹 하나 = 개인 면접 몇 건

에이전트 컨테이너를 CPU 2개(`--cpuset-cpus 2,3`) · 메모리 2GB로 제한하고 대기 프로세스를 2개(`AGENT_IDLE_PROCESSES=2`, 운영 `t3.small` 기본값)로 설정했다. CPU · 메모리는 cgroup에서 5초마다 직접 읽었다(`loadtest/group-ai/sample.sh`). 답변 길이는 짧은 답변(하나에 평균 8~10초)과 긴 답변(약 52~62초, `make-media.ps1 -Long`) 두 조건으로 측정했다.

| 답변 | 회차 | 진행 중 1개당 평균 | 5초 단위 최대(전체) | 메모리 최대 | 질문 1개 간격 | 측정 PC |
|---|---|---|---|---|---|---|
| 짧음 | 개인 1건 | 0.114코어 | 0.185코어 | 567MB | 약 33초 | 포화 0 |
| 짧음 | 개인 2건 동시 | 0.107코어 | 0.355코어 | 632MB | 약 33초 | Windows CPU 80% 초과 표본 2개 |
| 짧음 | 그룹 2개 동시 | 0.195코어 | 0.878코어 | 611MB | 약 26초 | Windows CPU 80% 초과 9/72 |
| 짧음 | 그룹 3개 동시 | 0.181코어 | 1.19코어 | 666MB | 약 27초 | Windows CPU 80% 초과 26/67 |
| 긺 | 그룹 2개 동시 | 0.143코어 | 0.578코어 | 863MB | 약 56초 | Windows CPU 80% 초과 10/149 |
| 긺 | 개인 2건 동시 | 0.177코어 | 1.07코어 | 770MB | 약 70초 | Windows CPU 80% 초과 2/48 |

- 진행 중 1개당 평균 = 에이전트 CPU 시간 ÷ (그룹 · 면접마다 시작부터 종료까지 시간의 합). 대기 상태 에이전트는 약 0.03~0.05코어 · 465MB다. 모든 면접이 진행 중인 구간에서 앞 60초를 제외해 다시 계산해도 같은 양상이었다(짧은 그룹 2개 0.187, 긴 그룹 2개 0.140, 긴 개인 2건 0.180)
- **그룹 하나 ≈ 개인 면접 0.8~1.8건.** 짧은 답변에서는 1.6~1.8건(0.18~0.20 ÷ 0.11), 긴 답변에서는 약 0.8건(0.143 ÷ 0.177)이다
- 짧은 답변은 그룹 · 개인을 각각 두 회차씩 측정해, 같은 종류끼리 차이가 그룹 약 7%(0.195 · 0.181), 개인 약 6%(0.114 · 0.107)였다. 긴 답변은 각각 1회라 편차를 확인하지 못했다
- 답변 길이에 따라 비율이 역전된 원인은 확인하지 못했다. 그룹의 질문 간격은 두 조건 모두 개인 면접의 약 0.8배(26초 대 33초, 56초 대 70초)라 질문 간격만으로는 설명되지 않는다. 긴 답변에서 진행 중 1분당 작업량도 그룹과 개인이 거의 같았다(음성 인식 확정 응답 12.1 · 12.0회, Jev 판단 6.5 · 6.7회, ElevenLabs 약 65 · 81자, 에이전트 로그 · 사용량 지표). 같은 양의 작업에서 개인 면접의 CPU가 더 컸으며, 어느 처리에서 차이가 나는지는 함수 단위 측정이 필요하다
- 긴 답변 개인 2건 진행 중(07:58:58)에 에이전트 이벤트 루프 지연(185~341ms)과 2.5초간 작업 수신 불가(`worker is at full capacity`) 기록이 있다. 답변 중 갱신마다 발화 시간을 다시 계산하는 경로(`interrupt.speaking_ms`)는 한 번에 0.33ms(토큰 240개, 로컬 측정)이고 초당 8회 갱신을 가정하면 60초 답변 하나에 약 0.08초라 원인이 아니며, 그룹도 같은 경로를 사용한다
- **BE 동시 상한과는 관계가 없다.** BE 동시 상한(운영 8건, `interview.capacity.max-video`)은 Soniox 실시간 인식 연결 한도(계정당 10개, 운영 8 · 개발 2)로 정한 값이고(`backend/src/main/resources/application.yml`, BE 설계 5.2), 그룹은 답변자 한 명만 인식하므로 연결 1개를 사용한다. 이 비율은 BE 동시 상한이 아니라 에이전트 서버 한 대의 부하(LiveKit 작업 배정 · 오토스케일)에 영향을 준다
- 첫 회차(짧은 답변 그룹 1개)는 6장의 DNS 장애로 마지막 질문 3개가 답변 없이 2분씩 대기해 비율 계산에서 제외했다
- 질문 준비(`ASKING` → 질문 시작 메시지, 화면 기준)는 123회 p50 0.03~0.07초 · p90 0.61~0.66초 · 최대 1.21초로 임시 값 20초(설계 T2)보다 훨씬 짧다
- 첫 질문은 그룹 시작(`interview_groups.started_at`) 0.9~3.7초 후에 출제되었다(그룹 8개, DB 기준). 그룹 3개 회차의 화면은 첫 질문을 24~25초 후에 수신했다. 화면이 늦게 수신한 원인은 확인하지 못했고(같은 회차 Windows CPU 80% 초과 26/67), 그 회차의 화면 기준 값은 보조 자료로 분류한다
- 그룹 8개 · 면접 29개가 모두 시작되었다(DB에 시작 실패 0). 작업 수신 불가 상태는 위 2.5초 한 번뿐이었고 그동안 들어온 배정 요청은 없었다

### 측정 PC 포화

브라우저(발생기)와 에이전트가 같은 PC에 있으므로 [부하 테스트 계획](../../이해준/load_test_plan/README.md) 3.2의 기준(CPU 80%)을 함께 확인했다. Docker VM CPU는 최대 77%였고 VM 메모리 압박(PSI) · 스왑은 첫 회차를 제외한 모든 회차의 모든 표본에서 0이었다(첫 회차는 진행 중 한 차례 확인해 0). Windows 전체 CPU(`host-sample.ps1`)는 짧은 답변 그룹 3개 회차에서 80% 초과가 26/67이므로 그 회차는 보조 자료로 분류한다. 다만 그 회차의 그룹 1개당 CPU 시간이 2개 회차보다 적어, 포화로 값이 커졌다는 근거는 없다. Windows 메모리는 Docker VM 실행만으로 85%를 넘어 기준으로 사용하지 않고, VM 안 메모리 압박으로 판단했다.

## 5. 다시보기 구간과 실제 말소리

합친 영상(본인 구간만 이어 붙인 mp4) 소리에서 말소리가 없는 구간을 찾고(ffmpeg `silencedetect` -35dB · 0.3초), 구간(`segments[]`)마다 앞 · 뒤를 측정했다(`loadtest/group-ai/segments.py`).

|---|---|---|
| 답변 끝이 잘린 구간(발화가 멈춘 뒤 7초 안에 구간이 끝남) | **0** | **0** |

- 구간은 DB의 질문 생성 시각(`interview_questions.created_at`)부터 답변 종료 시각(`answers.ended_at`)까지와 밀리초 단위까지 일치했다(세션 36의 6개 구간 대조)
- 7초를 넘는 부분은 음성 인식 지연이다. 7초는 마지막 말소리가 인식된 시각부터 계산한다(API 명세 「면접방 메시지」의 화상 답변 끝 판단)
- 짧은 답변의 가짜 마이크는 답변 사이에 8초 침묵하므로, 구간 끝이 발화 종료 후 8초를 넘은 구간(96개 중 66개)에는 다음 답변 앞부분 1~2초가 포함되었다. 실제 사용자는 차례가 끝나면 발화를 멈추므로 시험 조건에 따른 결과다

## 6. 측정 중 발생한 장애와 관찰

### 6.1 로컬 DNS와 GMS 재시도

첫 회차에서 3명 중 2명의 결과 생성이 `GMS_UNAVAILABLE`로 실패했다. GMS를 호출하지 않고 0.02~0.03초 만에 종료되었다.

- Docker Desktop DNS 기록(`%LOCALAPPDATA%\Docker\log\vm\init.log.*`)에서 `gms.ssafy.io` A 레코드 조회 435회 중 빈 응답은 2회이고, 그 시각(06:11:11 · 06:13:30 UTC)이 두 실패와 일치한다. 같은 이미지로 DNS 조회 · GMS 연결을 200회 다시 시도한 결과 모두 성공했다
- 같은 시간대에 에이전트의 Soniox 재연결도 `ClientConnectorDNSError`로 실패해, 그 회차 마지막 질문 3개의 답변 글이 비었다
- GMS 클라이언트는 연결 단계 오류 중 시간 초과가 아닌 오류(`URLError`, 주소 조회 실패 포함)를 재시도하지 않고 즉시 `GmsUnavailableError`로 변환한다(`ai/app/common/gms.py:257-261`). 재시도 반복문(`_send_with_retry`)은 시간 초과와 오류 응답만 재전송한다. 따라서 DNS가 한 차례 실패하면 그 면접의 결과 생성 전체가 실패하고, 실패 로그(`GMS 호출 실패`)도 남지 않는다
- 이 시험의 범위가 아니므로 수정하지 않았다

### 6.2 개인 면접 꼬리질문 4초

긴 답변 개인 2건에서 꼬리질문 생성이 4초(AI 명세 2.2)를 넘겨 예비 질문을 출제한 경우가 3회 있었다(GMS 4.1 · 4.3초에서 시간 초과). 그룹 면접이 아닌 개인 면접의 기준이므로 관찰로만 기록한다.

## 8. 한계

- 측정 대상은 운영과 같은 사양의 테스트 서버(부하 테스트 계획 3.1)가 아니라 측정 PC의 로컬 Docker이고, 발생기와 측정 대상이 같은 PC에 있다. 에이전트를 CPU 2개로 제한했지만 CPU 속도 · 크레딧은 운영 `t3.small`과 다르다. 따라서 절대 대수가 아니라 같은 조건의 개인 대비 그룹 비율만 도출했다. 운영 에이전트 한 대의 처리량은 [오토스케일 계획](../../이해준/agent_autoscale_plan/README.md)(86~91줄, [추정], 이전 이미지 기준)에서 다루며, 그룹 수는 그 값을 이 비율로 환산해 구한다
- 가짜 마이크 답변은 잡음이 없는 합성 음성이고 내용이 질문과 관계없다
- 긴 답변 비율(4장)은 그룹 · 개인 각각 1회 측정한 값이라 편차 폭을 확인하지 못했다
- 실제 사용자의 답변 길이 분포는 확인하지 못했다. 운영 DB의 화상 답변은 33개(면접 10건, 사용자 5명, 10/28~11/09, 그중 26개가 11/06~07)이고, 마지막 인식 단어의 끝 시각 기준 길이가 p50 2.0초 · p90 37.6초 · 최대 267.6초로 실제 사용 분포로 보기에는 표본이 적다. 운영 · 개발 Grafana 로그(개발은 3일 보관)에 남은 답변 길이 기록도 3개뿐이었다
- 목소리 유입 시험(3.2)은 25초 음성 3개로 수행했다
