# A301 그룹 면접 설계

> 초대한 지원자 2~3명이 AI 면접관 1명과 같은 면접방에서 차례로 답하는 그룹 면접(1대다 면접)의 설계다. 아직 구현하지 않았고, 계약(API 명세 · AI 명세)에 반영하기 전 단계다. 구현하면 [BE 설계](BE-설계.md) · [API 명세](API-명세.md) · [AI 명세](AI-명세.md)의 해당 장으로 옮긴다.
> 표기: **[결정]** 팀에서 정한 정책 · **[제안]** 이 문서가 제안하는 기술 방식(확정 전) · **[미정]** AI · FE · 인프라 담당자와 합의가 필요한 것. 임시 값은 "(임시 값)"으로 적는다.

## 1. 범위

**MVP 범위** **[결정]**

- 방장이 그룹을 만들고 초대 코드 · 링크로 다른 회원을 부른다
- 대기실에서 모두 준비되면 방장이 시작한다
- AI 면접관 1명이 공통 질문 · 개인 맞춤 질문 · 꼬리질문을 차례대로 묻는다
- 참가자마다 자기 결과 · 다시보기를 받고, 기존 개인 연습 기록에 반영한다

**범위 밖** **[결정]**: 친구 목록 초대, 참가자 간 피드백, 같은 직군 자동 매칭, AI 면접관 여러 명, WebSocket 전환, 다른 참가자 결과 조회, AI 에이전트 자동 재시작 · 그룹 면접 복구, 방장의 질문 개수 선택(13.1 고도화)

**기존 개인 면접은 바꾸지 않는다** **[결정]**. 그룹 규칙은 그룹에 속한 면접(`interview_sessions.group_id`가 있는 면접)에만 적용한다. 개인 면접의 질문 5개 규칙도 그대로다(10.1).

## 2. 확정 정책

| 구분 | 정책 **[결정]** |
|---|---|
| 방식 | 채팅 · 화상 모두 지원. 방장이 그룹을 만들 때 고르고, 참가자 모두 같은 방식이다 |
| 인원 | 방장 포함 최대 3명. 방장이 정원을 2명 또는 3명으로 고른다 |
| 직군 | 대분류로 구분한다. 그룹과 다른 직군도 안내한 뒤 입장을 허용한다 |
| 기본 질문 | 개인당 4개 = 공통 질문 2개 + 개인 맞춤 질문 2개 |
| 공통 질문 | 자기소개 1개 + 인성 질문 1개(협업 · 갈등 해결 · 문제 해결 등). 모든 참가자에게 같은 질문이고 공개한다 |
| 개인 맞춤 질문 | 각자의 지원서로 만든다. 본인 차례에 공개한다 |
| 꼬리질문 | 개인당 0~2개. 필수가 아니다. AI가 실제 답변을 보고 필요하다고 판단할 때만 만든다. 현재 답변자가 이어서 답한다. 판단은 최종 답변 기준으로 질문마다 한 번만 한다 |
| 꼬리질문 판단 시간 | 처음 제한 시간은 7초. 그 안에 응답이 없으면 꼬리질문 없이 다음 차례로 넘어간다. 실제 응답 시간을 잴 수 있게 만들고, 구현 뒤 충분히 빠르면 2~3초로 줄이는 것을 검토한다 |
| PLAN 재활용 | 개인 면접 PLAN 질문을 꼬리질문 후보로 쓰지 않는다 |
| 차례 · 순서 | 질문 단위로 돌아가며 답한다. 순서는 시작할 때 무작위로 정하고 끝까지 고정한다 |
| 화상 시간 | 기본 질문 · 꼬리질문 각 2분. AI 질문 음성 재생이 끝났다는 이벤트를 받은 뒤 답변 시간을 시작한다. 재생 실패 · 이벤트 누락도 처리한다. 남은 시간 30초 이하일 때 1분 연장 1회. 종료 10초 전 카운트다운. 시간이 다 되면 그때까지의 답변을 자동 제출하고 다음 순서로 넘어간다 |
| 채팅 시간 | 질문당 최대 5분, 연장 없음. 녹화하지 않고 글 답변만 저장한다 |
| 채팅 답변 | 작성 중인 글은 Redis에 임시 저장하고, 제출하거나 5분이 끝나면 BE가 최종 답변으로 확정한다. 작성 중인 글과 최종 답변은 구분한다. 개인 면접의 AI 면접관 실시간 반응 방식을 최대한 재사용한다 |
| 답변 전달 · 채점 | 답변은 DB에 저장한 뒤 AI에 전달한다. 전달이 실패하면 다시 보내고 중복 처리를 막는다. AI 면접관이 멈춰도 저장된 답변으로 따로 채점을 시도하고, 채점이 실패하면 다시 시도하거나 실패 상태로 둔다 |
| 음성 간섭 | 화면이 답변자가 아닌 참가자에게 마이크를 끄라고 안내한다. 서버가 강제로 끄지는 않는다. AI는 현재 답변자의 음성 트랙만 받는다. 다른 참가자 목소리가 새어 들어가는 문제는 완전히 막기 어려우므로 사용자에게 안내한다 |
| 차례 전환 | BE가 다음 답변자 · 마감 시각을 정하고 LiveKit으로 화면과 AI에 바로 알린다. 2초 폴링을 기다리지 않는다 |
| 면접관 | 그룹당 AI 면접관 1명 |
| 초대 · 대기실 | 초대 코드 6자리와 링크. 대기실은 2초 폴링 |
| 방장 이탈 | 남은 참가자 중 가장 먼저 입장한 사람에게 방장 권한을 넘긴다 |
| 진행 중 이탈 | 그 참가자의 차례를 건너뛴다. 2분 안에 다시 들어오면 기존 개인 세션을 이어 가고, 현재 답변자의 차례가 끝난 뒤 답하지 못한 질문부터 진행한다 |
| 종료 | 한 사람의 질문이 모두 끝나면 그 세션을 자동으로 끝낸다. 모든 세션이 끝나면 그룹을 끝낸다. 중복 답변 · 중복 종료를 막는다 |
| AI 장애 | AI 면접관이 멈추면 그룹 면접을 안전하게 끝낸다. 끝난 답변 · 녹화는 보존한다. 답변이 1개 이상이면 부분 결과를 만들고, 없으면 결과 없이 끝낸다. 부분 결과는 정상 결과와 구분한다 |
| 녹화 · 다시보기 | 그룹 전체가 끝난 뒤 합친다. 다시보기에는 본인 답변 구간만 넣는다. 합치기에 실패하면 다시 시도할 수 있다. 준비 전에는 "녹화 처리 중"을 표시한다. 녹화가 늦어도 결과 조회는 막지 않는다 |
| 결과 | 본인만 조회한다. 그룹 면접도 개인 연습 기록에 반영한다 |
| 성능 시험 | AI 담당이 질문 생성 · 음성 처리 · 동시 접속 성능 시험을, BE 담당이 구현 뒤 동시성 · 상태 정합성 · 중복 제출 · 재접속 · 종료 시험을 맡는다 |

## 3. 구조와 역할

### 3.1 구조 **[결정]**

참가자마다 기존 개인 면접(`InterviewSession`)을 하나씩 두고, 그룹 테이블이 그 면접들을 묶는다.

```
interview_groups (방식 · 면접관 · 정원 · 상태 · 공통 질문 · 현재 차례)
 ├─ interview_group_participants ─ interview_sessions (참가자 A의 면접)
 ├─ interview_group_participants ─ interview_sessions (참가자 B의 면접)
 └─ interview_group_participants ─ interview_sessions (참가자 C의 면접)

LiveKit 방 group-{groupId} 1개
 ├─ candidate-{A sessionId} · candidate-{B sessionId} · candidate-{C sessionId}
 └─ interviewer (AI 에이전트 1개)
```

- 질문 · 답변 · 채점 · 결과 · 녹화 · 연습 기록 · 스트릭은 지금처럼 **세션 단위**로 쌓인다. 그래서 결과(6.3) · 다시보기(6.4) · 성장 리뷰(7.x) · 홈 · 통계(3.x)의 계산을 거의 그대로 쓴다
- 왜: 세션과 회원을 N:M으로 바꾸면 결과 · 연습 기록 · 스트릭 · 성장 리뷰 · 관리자 집계를 모두 바꿔야 한다

### 3.2 역할 분담 **[결정]**

| 담당 | 하는 일 |
|---|---|
| **BE** | 진행 상태의 주인. 현재 답변자 · 질문 마감 시각 · 연장 횟수 · 이탈과 재접속 · 답변 제출 검증 · 세션과 그룹 종료를 정하고 저장한다. 차례가 바뀌면 LiveKit 방 정보로 알린다. AI가 멈춰도 BE 혼자 상태를 알고 정리할 수 있다 |
| **AI 에이전트** | 면접 대화. BE가 정한 차례대로 질문을 말하고, 현재 답변자의 음성만 듣고, 리액션을 정하고, 화상 답변을 BE에 넘기고, 꼬리질문이 필요한지 판단해 만든다 |
| **AI 분석 작업자** | 그룹용 PLAN(개인 맞춤 질문 2개), 채점 · 결과, 녹화 합치기 |
| **화면(FE)** | 방 정보로 차례 · 남은 시간을 표시하고, 연장 · 채팅 임시 저장 · 제출을 BE에 보낸다 |

- 앞 초안(에이전트가 진행 판단)과 다른 점: AI가 멈추면 진행 상태도 같이 사라지는 문제를 없애려고 진행 상태를 BE로 옮겼다. AI는 "무엇을 말하고 어떻게 듣는가"만 맡는다

## 4. 데이터 모델

### 4.1 진행 상태를 어디에 둘지: DB **[제안]**

| 기준 | DB(PostgreSQL) | Redis |
|---|---|---|
| 지금 구조에서의 쓰임 | 면접 상태 · 질문 · 답변(잃으면 안 되는 것) | 플랜 · 분석 진행률(잃어도 다시 만들 수 있는 것, BE 설계 7장) |
| 답변 · 세션 종료와 한 트랜잭션 | 된다. 차례 전환 · 답변 저장 · 세션 종료를 같은 잠금 안에서 처리 | 안 된다. DB와 Redis 사이에 어긋남이 생긴다 |
| BE 재시작 · Redis 장애 | 남는다 | TTL · 장애로 사라지면 진행 중 그룹을 알 수 없다 |
| 속도 | 차례 전환은 질문마다 몇 번뿐이라 문제없다 | 빠르지만 필요 없음 |

- **결론**: 현재 답변자 · 마감 시각 · 연장 · 단계 · 이탈 시각은 **DB**에 둔다. AI 장애 때 BE가 정리하려면 진행 상태를 잃지 않아야 하기 때문이다
- **Redis**에는 잃어도 DB로 다시 만들 수 있거나 짧게 쓰는 것만 둔다: 마감 예약 인덱스(DB로 다시 만듦), 채팅 임시 저장, 대기실 접속 시각, 웹훅 중복 확인(4.4)

### 4.2 새 테이블 **[제안]**

**`interview_groups`**

| 컬럼 | 형식 | 설명 |
|---|---|---|
| `id` | BIGINT PK | |
| `host_user_id` | BIGINT FK users | 지금 방장. 위임하면 바뀐다 |

| `common_questions` | JSONB | 시작할 때 고른 공통 질문 2개(`content` · `criteria`, 자기소개 → 인성 순서) |
| `round` | SMALLINT | 현재 라운드 1~4 |
| `phase` | VARCHAR | 현재 단계(5.2) |

| `deadline_at` | TIMESTAMPTZ | 현재 질문의 답변 마감 시각(답변 단계에서만) |
| `extended` | BOOLEAN | 현재 질문에서 연장했는지 |
| `phase_due_at` | TIMESTAMPTZ | 현재 단계가 끝나야 하는 시각. 지나면 정체로 본다(6.11) |
| `progressed_at` | TIMESTAMPTZ | 마지막으로 차례 · 단계가 바뀐 시각 |
| `room_version` | INT | LiveKit 방 정보에 마지막으로 반영한 `turn_version`(6.5 재동기화) |
| `created_at` · `started_at` · `ended_at` | TIMESTAMPTZ | `started_at`은 마지막 시작 시도 시각 |

**`interview_group_participants`**

| 컬럼 | 형식 | 설명 |
|---|---|---|
| `id` · `group_id` · `user_id` | BIGINT | |
| `session_id` | BIGINT FK UNIQUE | 참가자의 세션 |
| `job_category` | VARCHAR | 참가자가 고른 직군 대분류 |
| `joined_at` | TIMESTAMPTZ | 입장 시각. 방장 위임 순서 기준 |
| `ready_at` | TIMESTAMPTZ | 준비 완료 시각. 취소하면 null |
| `turn_order` | SMALLINT | 답변 순서(1부터). 시작 전에는 null |
| `base_done` | SMALLINT | 끝낸 기본 질문 수(답했든 시간이 다 됐든) 0~4 |
| `followups_used` | SMALLINT | 받은 꼬리질문 수 0~2. CHECK |
| `absent_since` | TIMESTAMPTZ | 진행 중 이탈 시각. 돌아오면 null |
| `left_at` | TIMESTAMPTZ | 대기실 · 시작 실패 상태에서 나간 시각 |

- 한 회원은 `WAITING` · `IN_PROGRESS` · `START_FAILED` 그룹 하나에만 참가한다. 여러 테이블에 걸친 조건이라 회원 행을 잠그고 확인한다(9장)

**`group_common_questions`** 공통 질문 문항 은행

| 컬럼 | 설명 |
|---|---|
| `id` · `type` · `content` · `criteria` · `active` | `type`은 `INTRO`(자기소개) · `CHARACTER`(인성). 시작할 때 `INTRO` 1개, `CHARACTER` 1개를 무작위로 고른다. 처음 문항은 Flyway로 넣는다 |

### 4.3 기존 테이블 변경 **[제안]**

| 테이블 | 변경 | 개인 면접 |
|---|---|---|
| `interview_sessions` | `group_id` BIGINT FK null, 인덱스 | null |
| `interview_sessions` | `end_reason` VARCHAR null: `ALL_ANSWERED` · `USER_ENDED` · `DISCONNECTED` · `AI_FAILURE` · `CLEANUP`(6.10) | null(바꾸지 않음) |
| `interview_questions` | `kind` VARCHAR null: `COMMON` · `PERSONAL` · `FOLLOWUP` | null |
| `interview_questions` | `spoken_at` TIMESTAMPTZ null(질문 음성이 끝나 답변 시간을 시작한 시각) · `deadline_at` TIMESTAMPTZ null(연장 반영한 최종 마감) · `closed_at` TIMESTAMPTZ null(답 없이 마감) | null |
| `answers` | `ended_at` TIMESTAMPTZ null: 답변을 끝낸 시각(본인 답변 구간 계산, 6.12) | null |
| `interview_plans` | 그룹 세션은 질문 2개를 저장한다. 테이블 구조는 그대로 | 5개 그대로 |

- 그룹 세션의 질문 `seq`는 그 사람이 받은 순서다. 기본 4개 + 꼬리질문 0~2개라 1~6이다
- 답변은 지금처럼 질문 하나에 하나(`answers.question_id` UNIQUE). 시간이 다 됐는데 답이 없으면 답변 행 없이 질문 행의 `closed_at`만 남긴다

### 4.4 Redis **[제안]**

| 키 | 값 | TTL | 쓰는 곳 |
|---|---|---|---|
| `group:due` | 정렬 집합. 멤버 `groupId`, 점수 `phase_due_at`(epoch 밀리초) | 없음 | 6.11 마감 처리기. 비면 DB의 `IN_PROGRESS` 그룹으로 다시 채운다(기동 때 포함) |
| `group-draft:{sessionId}:{questionId}` | 채팅 **작성 중인 글**, 저장 시각 | 1시간 | 6.7. 질문마다 키가 달라 다른 질문의 글과 섞이지 않는다. 최종 답변은 DB `answers`에만 있고, 확정하면 이 키를 지운다 |
| `group:{groupId}:presence` | Hash. `userId` → 마지막 대기실 조회 시각 | 마지막 쓰기 후 1시간 | 대기실 방장 위임(6.1) |
| `livekit-webhook:{eventId}` | `1` | 1시간 | 웹훅 중복 처리 막기(6.9) |

- 멱등 키는 기존 `idem:{userId}:{Idempotency-Key}`를 쓴다

### 4.5 직군 · 질문 구성

- 직군 대분류는 enum이다. 값 목록은 **[미정]**(FE). 예: `DEVELOPMENT` · `DATA_AI` · `DESIGN` · `PLANNING` · `MARKETING` · `SALES` · `MANAGEMENT_SUPPORT` · `ETC`. 지원서 `job_title`은 자유 글이라 자동 분류하지 않고, 방장 · 참가자가 직접 고른다 **[제안]**
- 공통 질문은 자기소개 · 인성이라 직군과 관계없이 문항 은행에서 고른다 **[제안]**. 직군은 그룹 소개와 다른 직군 안내에만 쓴다
- **개인 맞춤 질문은 그룹용 PLAN으로 2개만 만든다** **[결정]**. PLAN 작업에 `questionCount`(그룹 2, 없으면 5)를 더한다. 개인 면접 PLAN은 그대로 5개다. 형식은 **[미정]**(AI)
- 꼬리질문은 면접 중에 에이전트가 실제 답변으로 만든다. 만들지 못하면 내지 않고 다음 차례로 넘어간다(필수가 아니므로 예비 질문이 없다)

## 5. 상태

### 5.1 그룹 상태 **[제안]**

| 현재 | 사건 | 다음 | 조건 |
|---|---|---|---|
| (없음) | 10.1 그룹 만들기 | `WAITING` | |
| `WAITING` | 10.7 시작 | `IN_PROGRESS` | 방장, 인원 = 정원, 모두 준비 완료, 모든 플랜 `READY` |
| `WAITING` | 모두 나감 · 만든 지 1시간(임시 값) | `CANCELLED` | 1시간은 조회 때 확인 |
| `IN_PROGRESS` | 배정 거절 · 첫 질문 전 AI 응답 없음(6.11) | `START_FAILED` | 그룹에 질문 행이 하나도 없을 때 |
| `START_FAILED` | 10.7 다시 시작 | `IN_PROGRESS` | 남은 참가자 2명 이상 |
| `START_FAILED` | 남은 참가자 1명 이하 | `CANCELLED` | |
| `IN_PROGRESS` | 마지막 세션 종료 | `ENDED` | 6.10 |
| `IN_PROGRESS` | AI 장애 · 안전장치(6.11) | `ENDED` | 남은 세션을 모두 끝낸다 |

### 5.2 진행 단계 `phase` **[제안]**

| 단계 | 뜻 | 다음 사건 | 기한(`phase_due_at`) |
|---|---|---|---|
| `ASKING` | BE가 차례를 정했고 에이전트가 질문을 말할 차례 | 에이전트 `question.started` → `SPEAKING` | 차례를 정한 뒤 20초(임시 값) |
| `SPEAKING` | 질문 음성 재생 중. 답변 시간은 아직 시작 전 | 에이전트 `question.spoken`(재생 끝 · 실패) → `ANSWERING` | `startedAt` + 예상 음성 길이(`speechMs`) + 5초(임시 값). 지나면 이벤트 누락으로 보고 답변 시간을 시작한다(6.4) |
| `ANSWERING` | 답변 중. `deadline_at`까지 | 답변 저장 → `DECIDING`, 마감 → 자동 제출 · 마감 처리(6.6) | 화상 `deadline_at` + 5초(임시 값, 에이전트 자동 제출이 오는 시간), 채팅 `deadline_at` |
| `DECIDING` | 꼬리질문 판단 대기 | 에이전트 `followup.decided` → 다음 차례 | 답변 저장 뒤 7초(`group.followup-decision-timeout`, 결정). 지나면 꼬리질문 없이 넘어간다 |
| `WAITING` | 남은 질문이 이탈한 사람 것뿐이라 재접속을 기다림 | 재접속 → 다음 차례, 2분 초과 → 그 세션 종료 | 가장 이른 `absent_since` + 2분 |

- 시간 값은 BE 설정에 둔다(`group.answer-seconds` 등). 방 정보로 알리므로 AI · FE 배포 없이 바꿀 수 있다

### 5.3 그룹 상태와 세션 상태의 관계

개인 세션의 상태 값 · 전이(BE 설계 4장)는 바꾸지 않는다.

| 그룹 | 참가자 세션 |
|---|---|
| `WAITING` | 모두 `READY` |
| `IN_PROGRESS` | 시작할 때 모두 `IN_PROGRESS`. 사람마다 끝나는 시점이 달라 `ANALYZING` · `ABORTED` 등이 섞인다 |
| `START_FAILED` | 모두 `START_FAILED` |
| `ENDED` | 모두 `IN_PROGRESS`가 아님 |
| `CANCELLED` | 시작 전이면 `READY`로 남는다(연습 면접이 아니라 목록 · 스트릭에 들어가지 않음) |

- 그룹 종료 판단은 "그룹 세션 중 `IN_PROGRESS`가 없음" 하나다
- 그룹 세션은 개인 면접 시작(5.4)으로 시작할 수 없다

## 6. 처리 흐름

### 6.1 그룹 만들기 · 참가 · 대기실

1. **만들기(10.1)** 방장이 방식 · 면접관 · 정원 · 직군 · 자기 지원서를 보낸다. 한 트랜잭션에서 그룹(`WAITING`, 초대 코드) → 방장 세션(기존 5.1 처리 + 그룹용 PLAN 작업) → 참가자 행을 만든다
   - 초대 코드: 헷갈리는 글자(0 · O · 1 · I · L)를 뺀 대문자 · 숫자 6자리. 중복이면 최대 5번 다시 뽑는다 **[제안]**
   - 초대 링크: 화면 주소 `/groups/join?code={초대 코드}`. 모양은 **[미정]**(FE)
2. **초대 확인(10.2)** 코드로 그룹 요약을 준다. 화면은 자기 직군이 그룹과 다르면 안내한 뒤 진행한다
3. **참가(10.3)** 회원 행 → 그룹 행을 잠그고 `WAITING` · 정원 미만 · 다른 그룹 참가 중 아님을 확인한 뒤, 세션(그룹용 PLAN 포함)과 참가자 행을 만든다
4. **대기실(10.4)** 2초마다 부른다. 부를 때마다 `group:{groupId}:presence`에 자기 시각을 남긴다. 플랜이 실패한 참가자는 기존 5.3으로 다시 만든다
5. **준비(10.5)** 화상은 장치 점검 뒤, 채팅은 바로. 다시 누르면 취소
6. **나가기(10.6)** `WAITING` · `START_FAILED`에서만. `left_at`을 남기고 세션은 시작하지 않은 채 둔다
7. **방장 위임** 방장이 나가거나 대기실 조회가 10초(임시 값) 넘게 멈추면 남은 참가자 중 `joined_at`이 가장 이른 사람이 방장이 된다. 다른 참가자의 10.4 조회 때 그룹 행을 잠그고 확인한다(스케줄러 없음). 진행 중 방장 세션이 끝나도 같은 규칙으로 넘긴다
8. 남은 참가자가 없으면 `CANCELLED`

### 6.2 시작 (10.7)

1. 그룹 행 → 세션 행(id 순서)을 잠근다
2. 확인: 방장, `WAITING` · `START_FAILED`, 인원(처음은 정원, 다시 시작은 2명 이상), 모두 준비, 모든 플랜 `READY`
3. 처음 시작이면 `turn_order`를 무작위로 정하고 공통 질문 2개를 고른다. 다시 시작이면 같은 값을 쓴다
4. 모든 세션 `start(now)` → `IN_PROGRESS`. 그룹 `IN_PROGRESS`, 첫 차례(라운드 1, 순서 1번, `ASKING`)를 DB에 남긴다
5. 방 `group-{groupId}`을 첫 차례가 담긴 방 정보(8.2)와 함께 만들고(화상이면 트랙 자동 녹화, 6.12) 에이전트를 배정한다(8.1)
6. 실패하면 방을 지우고 503 `ROOM_UNAVAILABLE`, 트랜잭션을 되돌린다. 기존 5.4처럼 외부 호출을 잠금 안에서 하고, 커밋이 실패해도 방을 지운다
7. 응답에 방장의 입장 정보를 담는다. 다른 참가자는 10.4에서 `IN_PROGRESS`를 보고 5.14로 입장 정보를 받는다

### 6.3 라운드와 차례 정하기 (BE)

기본 질문 4개를 라운드로 묻는다 **[제안]**: 라운드 1 공통(자기소개) → 2 개인 1 → 3 공통(인성) → 4 개인 2. 순서는 `turn_order` 고정이다.

**다음 차례를 정하는 규칙** (차례가 끝날 때마다 그룹 행을 잠그고 한 번 계산)

1. 방금 답한 사람에게 꼬리질문이 정해졌고(`followup.decided` `needed`), `followups_used` < 2이고, 그 사람이 접속 중이면 → 같은 사람의 꼬리질문
2. 돌아온 사람 중 밀린 기본 질문이 있으면(`base_done` < 현재 라운드 − 1, 또는 같은 라운드에서 이미 순서가 지난 경우) → 그 사람의 밀린 기본 질문부터 차례대로
3. 현재 라운드에서 순서상 다음이며, 접속 중이고, 끝나지 않았고, 이 라운드 질문을 아직 안 받은 사람 → 그 사람의 기본 질문
4. 이 라운드에 남은 사람이 없으면 라운드를 올리고 3을 다시 본다
5. 남은 질문이 이탈한 사람 것뿐이면 → `WAITING`
6. 남은 질문이 없으면 → 각자 6.10 완료 처리

- 기본 질문 4개를 끝내고(`base_done` = 4) 꼬리질문도 없으면 그 사람은 완료(`done_at`)다
- 공통 질문은 라운드의 첫 답변자 차례와 밀린 공통 질문 차례에 에이전트가 질문 전체를 말하고, 같은 라운드의 다음 답변자에게는 짧은 호명("다음 지원자분 답변해 주세요", 문구 **[미정]**)만 한다. 방 정보 `announce`(`FULL` · `CALL`)로 알린다
- 개인 질문 · 꼬리질문은 그 사람 차례에 처음 말하므로 "본인 차례에 공개"가 지켜진다

### 6.4 질문 · 답변 · 꼬리질문 흐름

```
BE: 차례 확정(ASKING, turn_version+1) ─ 방 정보 갱신 ─▶ 화면 · 에이전트
에이전트: 질문 음성 송출 시작 ─ question.started(turnVersion, speechMs) ─▶ BE
BE: 질문 행 저장, SPEAKING ─ 방 정보 갱신 (답변 시간은 아직 시작하지 않음)
에이전트: 질문 음성 재생 끝 · 실패 ─ question.spoken(turnVersion, endedAt) ─▶ BE
BE: spoken_at 저장, deadline_at = spoken_at + 답변 시간, ANSWERING ─ 방 정보 갱신
  화상: 에이전트가 답변 끝(7초 침묵 · [답변 완료] · 마감)에 answer.completed ─▶ BE
  채팅: 화면이 5.7로 제출 · 마감이면 BE가 작성 중인 글로 확정(6.7)
BE: 최종 답변 DB 저장, DECIDING ─ 방 정보 갱신 (채팅은 답변 글도 에이전트에 전달, 6.14)
에이전트: 최종 답변으로 꼬리질문 판단 · 생성(한 번) ─ followup.decided ─▶ BE
BE: 다음 차례 계산(6.3) ─ 방 정보 갱신 …
```

**답변 시간 시작** **[결정]** 질문 음성 재생이 끝났다는 이벤트(`question.spoken`)를 받은 시각부터 센다. 채팅도 질문 음성이 끝날 때까지 화면이 입력을 잠그므로(API 명세 면접방 메시지) 같은 규칙을 쓴다 **[제안]**.

| 경우 | 처리 **[제안]** |
|---|---|
| 정상 | 에이전트가 음성 마지막 소리를 보낸 시각을 `endedAt`으로 `question.spoken`(`speech: ENDED`)을 보낸다. 화면에 보내는 `question`(`ended`)과 같은 시점이다 |
| 음성 합성 · 송출 실패 | 에이전트가 `question`(`failed`)을 화면에 보내는 시각을 `endedAt`으로 `question.spoken`(`speech: FAILED`)을 보낸다. 화면은 질문 글로 진행한다(기존 규칙) |
| `question.spoken` 누락 · 지연 | BE는 `question.started`의 예상 음성 길이 `speechMs`로 `SPEAKING` 기한(`startedAt` + `speechMs` + 5초)을 잡는다. 기한까지 오지 않으면 기한을 처리한 시각을 `spoken_at`으로 남기고 그때부터 답변 시간을 시작한다. 5초 여유 동안 지난 시간을 답변 시간에서 빼지 않아 지원자가 손해 보지 않는다 |
| 기한 뒤에 늦게 온 `question.spoken` | 이미 `ANSWERING`이라 버린다(`turnVersion` · 단계 확인) |
| `speechMs` 없음 | 기본 60초(임시 값)로 기한을 잡는다 |
| `question.started`부터 없음 | `ASKING` 기한 초과 → AI 정체(6.11) |
| 질문 음성 재생 중 답변자 이탈 | 6.9 이탈 처리. 돌아오면 질문을 처음부터 다시 말하고 새로 `question.spoken`을 받는다 |

**꼬리질문 판단** 판단 방법은 **[미정]**(AI)

- 에이전트는 방 정보가 `DECIDING`이 된 뒤, 즉 BE가 최종 답변을 저장한 뒤에 판단한다. 화상은 자기가 보낸 답변 글, 채팅은 BE가 보낸 최종 답변 글(6.14)을 쓴다. 채팅 작성 중인 글(`chat.input`)로는 판단하지 않는다 **[결정]**
- 한 질문에 한 번만 판단한다. 같은 `(sessionId, seq)`의 답변 글을 다시 받으면 새로 판단하지 않고 처음 판단 결과를 다시 보낸다
- 필요하면 질문 글 · 채점 기준을 만들어 `followup.decided`(`needed: true`)에, 아니면 `needed: false`. 남은 꼬리질문 수(방 정보 `followupsLeft`)가 0이거나 답 없이 마감된 질문은 판단하지 않는다(BE도 `DECIDING`을 거치지 않고 바로 다음 차례)
- **제한 시간 7초** **[결정]** BE가 `DECIDING`을 시작한 시각부터 센다. 지나면 꼬리질문 없이 다음 차례로 넘어가고, 그 뒤 온 판단은 버린다. 값은 BE 설정 `group.followup-decision-timeout`이라 배포 없이 2~3초로 줄일 수 있다
- 만든 꼬리질문은 BE가 다음 차례로 정할 때까지 에이전트가 들고 있다. 다음 차례가 그 사람의 `FOLLOWUP`이면 그 질문을 말한다. 그 사이 그 사람이 이탈하면 버린다(필수가 아니므로)

**응답 시간 측정** **[제안]** 2~3초로 줄일 수 있는지 판단하려고 제한 시간을 넘긴 판단까지 잰다.

| 어디서 | 무엇을 |
|---|---|
| BE | `DECIDING` 시작부터 `followup.decided` 도착까지를 Micrometer 타이머 `group.followup.decision`으로 남긴다. 태그 `outcome`: `needed` · `not_needed` · `late`(7초 뒤 도착, 버렸지만 시간은 기록) · `missing`(끝내 오지 않음). 백분위(p50 · p90 · p99)를 본다 |
| AI | `followup.decided`에 `receivedAt`(판단을 시작한 시각) · `generationMs`(GMS 호출 시간)를 담는다. BE는 이 값을 로그에 남겨 전달 지연(큐 · LiveKit)과 생성 시간을 나눠 본다 |
| 판단 기준 | 구현 뒤 실제 그룹 면접에서 `late` + `missing` 비율과 p90을 보고 2~3초로 줄일지 정한다 |

- 질문 행은 지금처럼 `question.started`로 만든다. `kind`를 같이 저장하고, `spoken_at` · `deadline_at`은 `question.spoken` 처리 때 채운다

### 6.5 차례 전환 전달 · 재동기화

**전달: LiveKit 방 정보(room metadata)** **[제안]**

- BE는 차례 · 단계가 바뀌는 트랜잭션을 커밋한 직후 LiveKit `UpdateRoomMetadata`로 방 정보(8.2)를 바꾼다. 화면 · 에이전트는 `RoomMetadataChanged` 이벤트로 바로 받는다. 접속할 때도 현재 방 정보를 받는다. 폴링이 필요 없다
- 방 정보에 `turnVersion`을 담는다. 받는 쪽은 가지고 있는 값보다 작거나 같은 버전을 버린다. 순서가 뒤바뀌어 와도 상태가 뒤로 가지 않는다
- 남은 시간은 `deadlineAt`과 `serverTime`(방 정보를 만든 BE 시각)을 같이 보낸다. 화면은 받은 순간의 자기 시계와 `serverTime`의 차이로 시계 오차를 보정해 남은 시간을 그린다. 브라우저 시계가 틀려도 마감 표시가 맞는다

**큐 지연 줄이기** **[제안]**

- 에이전트가 보내는 그룹 면접 결과 메시지(`question.started` · `answer.completed` · `followup.decided`)는 **그룹 전용 결과 큐 `ai:results:group`** 로 보내고, BE가 전용 스레드 하나로 처리한다. 기존 `ai:results`는 결과 생성 저장(`evaluation.completed`)처럼 무거운 처리가 섞여 있어, 같은 큐면 차례 전환이 그 뒤에 줄을 선다
- 한 그룹의 메시지는 한 큐 · 한 스레드라 순서가 지켜진다(`question.started` → `answer.completed`)
- 방 정보 갱신은 커밋 뒤 바로 부른다. 실패해도 업무는 성공이고 재동기화가 고친다
- 채팅 답변 글은 BE가 LiveKit `SendData`로 에이전트에 바로 보낸다(8.3). 화면을 거치지 않아 BE 자동 제출도 같은 경로를 탄다

**재동기화** **[제안]**

| 어긋남 | 감지 | 처리 |
|---|---|---|
| 방 정보 갱신 실패 | DB `room_version` < `turn_version` | 마감 처리기(6.11)가 1초마다 돌 때 다시 보낸다 |
| 화면이 이벤트를 놓침 · 새로고침 | 화면 | 접속하면 방 정보를 다시 받는다. 방 정보를 받지 못한 채 3초(임시 값)가 지나면 10.4를 한 번 불러 같은 차례 정보를 받는다 |
| 에이전트가 이벤트를 놓침 | BE: `ASKING` 기한 초과 | 6.11 정체 처리 전에 방 정보를 한 번 더 보낸다 |
| 웹훅 누락으로 접속 상태가 틀림 | 15초(임시 값)마다 LiveKit `ListParticipants`와 DB 비교 | DB를 LiveKit 기준으로 고친다(6.9) |

### 6.6 답변 시간 · 마감

| | 화상 | 채팅 |
|---|---|---|
| 시간 | 2분, 30초 이하일 때 1분 연장 1회 | 5분, 연장 없음 |
| 시작 | 질문 음성 재생 끝(`spoken_at`, 6.4) | 같음 |
| 마감 기준 | BE의 `deadline_at` = `spoken_at` + 시간(+ 연장) | 같음 |
| 카운트다운 | 10초 전부터 화면 표시 | 같음 |
| 마감 때 | 에이전트가 방 정보의 `deadlineAt`에 그때까지 인식한 글로 답변을 낸다(`endReason` `TIME_LIMIT`). 한마디도 안 했으면 내지 않는다. BE는 `deadline_at` + 5초까지 답변이 없으면 질문을 닫는다(`closed_at`) | BE가 마감에 임시 저장 글로 자동 제출한다(6.7). 비어 있으면 질문을 닫는다 |
| 연장 | 답변자가 10.8을 부른다. BE가 그룹 행을 잠그고 답변자 · `ANSWERING` · 남은 30초 이하 · 미연장을 확인한 뒤 `deadline_at` + 1분, `extended`, 방 정보 갱신 | 없음(409) |

- 기존 규칙 중 7초 침묵 자동 제출은 그룹 화상에도 그대로 쓴다. 60초 무응답 안내(`timedOut`)는 2분 마감이 대신하므로 보내지 않는다 **[제안]**
- 마감이 지난 답변: 화상 `answer.completed`는 질문이 닫히기 전(`deadline_at` + 5초)까지 받는다. 채팅 5.7은 `deadline_at`이 지나면 409 `QUESTION_CLOSED`(자동 제출이 이미 처리하므로)

### 6.7 채팅: 실시간 반응 · 작성 중인 글 · 최종 답변

**지금 개인 채팅 면접의 실시간 반응(확인함)** 화면이 입력이 0.8초 멈출 때마다 입력 칸의 글 전체를 RPC `interview.chatInput`(`questionSeq` · `seq` · `text` · `pauseMs`)으로 에이전트에 보낸다. 에이전트는 마지막 문장으로 Jev 리액션을 판단해 `reaction`을 보낸다. 이 글은 저장하지 않고, 가장 최근 입력의 판단만 적용한다(API 명세 면접방 메시지, AI 명세 6.3 · 6.4).

**그룹에서 재사용** **[제안]**

- 같은 RPC · 같은 판단 규칙을 그대로 쓴다. 리액션은 방의 모두에게 보내 면접관 모습이 같게 보이게 한다
- 바뀌는 점은 둘이다: 에이전트가 보낸 사람이 지금 답변자인지 확인하고(아니면 `false`), `questionSeq`를 보낸 사람 세션의 질문 순서로 읽는다. 지금 에이전트는 배정 정보의 세션 하나로 메시지를 검사하므로 이 부분이 계약 변경이다 **[미정]**(AI · FE)
- 리액션용 글(에이전트로)과 작성 중인 글 저장(BE로)은 따로 보낸다. 리액션 경로는 저장하지 않고, 저장 경로는 리액션에 쓰지 않는다

**작성 중인 글과 최종 답변의 구분** **[결정]**

| | 작성 중인 글 | 최종 답변 |
|---|---|---|
| 저장 | Redis `group-draft:{sessionId}:{questionId}` | DB `answers`(질문 하나에 하나) |
| 만드는 곳 | 10.9 임시 저장 | 5.7 직접 제출 또는 BE 마감 확정 |
| 바뀜 | 덮어쓴다 | 확정 뒤 바뀌지 않는다 |
| 쓰는 곳 | 마감 확정의 재료뿐 | 채점 · 결과 · 다시보기 · 꼬리질문 판단 |
| 지움 | 확정 · 질문 닫힘 · 세션 종료 때, 아니면 1시간 TTL | 지우지 않는다 |

**흐름**

1. 화면은 입력이 0.8초 멈출 때마다(최소 5초 간격, 임시 값) 그리고 창을 벗어날 때 10.9로 글 전체를 보낸다. 같은 글을 `sessionStorage`에도 둔다(새로고침 복구용) **[제안]**
2. BE는 그 질문이 지금 그 사람의 답변 중인 질문이고 마감 전일 때만 저장한다. 다른 질문 · 마감 뒤 · 이미 확정한 질문이면 409. 키가 질문마다 달라 다른 질문의 글이 섞이지 않는다
3. **직접 제출(5.7)** 그룹 행 → 세션 행 잠금 → 열린 질문 · 답변 없음 확인 → 최종 답변 저장 → 작성 중인 글 삭제 → `DECIDING`
4. **마감 확정** 마감 처리기가 같은 잠금을 잡고 답변이 없을 때만 작성 중인 글로 최종 답변을 저장한다(`input_type` TEXT). 글이 없거나 비면 답변 없이 질문을 닫는다
5. 3과 4는 같은 잠금 · 같은 확인을 거치므로 하나만 저장된다. 늦은 쪽은 5.7이면 409 `ANSWER_ALREADY_SUBMITTED`(화면은 기존처럼 성공으로 본다), 마감 확정이면 아무것도 하지 않는다
6. 최종 답변은 커밋 뒤 에이전트에 전달한다(6.14)

- 마감 확정은 마지막으로 저장된 글을 쓴다. 마지막 임시 저장 뒤 입력한 몇 초는 빠질 수 있다. 화면이 0초에 5.7을 먼저 부르면 그 글이 우선한다(3이 먼저 커밋)

### 6.8 음성 간섭

- 에이전트는 현재 답변자의 마이크 트랙만 구독해 STT에 넘긴다. 차례가 바뀌면 이전 구독을 끊고 새 답변자를 구독한다 **[결정]**
- 화면은 자기 차례가 아니면 "마이크를 꺼 주세요" 안내를 띄우고 한 번 눌러 끄게 한다. 서버는 강제로 끄지 않는다 **[결정]**
- 다른 참가자 목소리가 답변자 마이크로 새어 들어가 답변 글에 섞일 수 있다. 입장 전 · 대기실에서 이어폰 사용과 차례 외 음소거를 안내한다 **[결정]**. 녹화는 본인 답변 구간만 남기므로(6.12) 다른 사람 차례의 목소리는 다시보기에 들어가지 않는다
- `interview.stt` · `answer.state`는 답변자에게만, `question` · `reaction`은 모두에게 보낸다 **[제안]**. 인상 판단 사진은 답변자 것만 판단한다

### 6.9 이탈 · 재접속

**감지: LiveKit 웹훅 + 서버 API 확인** **[결정]**

- BE가 LiveKit 웹훅 `participant_joined` · `participant_left`를 받는다(`POST /api/v1/webhooks/livekit`, 회원 인증 대신 LiveKit 서명 확인). 방 이름이 `group-`으로 시작할 때만 처리하고, 개인 면접 방은 무시한다
- 웹훅은 전달을 보장하지 않으므로 15초(임시 값)마다 `ListParticipants`로 진행 중 그룹을 확인해 고친다(6.5)
- 같은 이벤트는 `livekit-webhook:{eventId}`로 한 번만 처리한다
- 웹훅을 쓰려면 LiveKit 서버 설정에 BE 주소를 넣어야 한다 **[미정]**(인프라). BE 설계 5.6의 "웹훅을 쓰지 않는다"는 녹화 종료 웹훅에 대한 것이고, 그룹 면접은 참가자 이벤트만 쓴다

**처리** (그룹 행 → 세션 행 잠금)

| 사건 | 처리 |
|---|---|
| 지원자 퇴장 | `absent_since` 기록. 그 사람이 답변 중이면 진행 중이던 답변은 버리고(에이전트도 기존처럼 버림), 그 질문 행은 닫지 않고 둔 채 다음 차례로 넘어간다. 그 사람 차례가 오면 건너뛴다 |
| 2분 안에 재입장 | 5.14로 입장 정보를 다시 받아 같은 참가자 이름으로 들어온다. `absent_since` 지움. 현재 차례가 끝나면 6.3 규칙 2로 밀린 질문부터 받는다. 답변 중 나갔던 질문은 같은 `seq`로 다시 묻는다(새 마감) |
| 2분 초과 | 마감 처리기가 그 세션을 끝낸다(`end_reason` `DISCONNECTED`, 6.10). 그 뒤 5.14는 409라 다시 들어올 수 없다 |
| 에이전트(`interviewer`) 퇴장 | AI 장애(6.11) |

- 짧은 네트워크 끊김은 브라우저 SDK가 다시 붙이며 LiveKit이 퇴장으로 보지 않는다

### 6.10 세션 종료 · 그룹 종료

**세션 종료 경로** **[제안]** 모두 같은 종료 처리를 탄다.

| 경로 | `end_reason` | 시선 비율 |
|---|---|---|
| 질문을 모두 마침(`done_at`) → 방 정보로 그 사람에게 완료 알림 → 화면이 5.8 | `ALL_ANSWERED` | 화면이 보냄. 60초(임시 값) 안에 5.8이 없으면 BE가 끝내고 null |
| [끝내기] → 5.8 | `USER_ENDED` | 화면이 보냄 |
| 이탈 2분 초과 | `DISCONNECTED` | null |
| AI 장애 | `AI_FAILURE` | null |
| 안전장치(6.11) | `CLEANUP` | null |

- 답변 저장이 BE에서 끝난 뒤에만 완료가 정해지므로, 화면은 개인 면접처럼 저장 반영을 기다릴 필요가 없다

**종료 처리(한 트랜잭션, 그룹 행 → 세션 행 잠금)**

1. 세션이 `IN_PROGRESS`가 아니면 아무것도 하지 않는다(5.8은 기존처럼 409). 중복 종료가 여기서 막힌다
2. 기존 5.8 처리: 답변 1개 이상이면 `ANALYZING` · 연습 기록 · EVALUATE 작업, 0개면 `ABORTED`. `end_reason` 저장. 그 세션의 임시 글은 지운다(저장하지 않음)
3. 현재 답변자였으면 다음 차례를 정한다(6.3)
4. 남은 `IN_PROGRESS` 세션이 있으면 커밋 뒤 LiveKit `RemoveParticipant`로 그 사람을 내보내고 방 정보를 갱신한다(에이전트는 방 정보의 참가자 상태로 안다)
5. 마지막 세션이면 그룹 `ENDED`, 화상이면 그룹 화상 세션 모두에 녹화 합치기 작업을 넣고, 커밋 뒤 방을 지운다

- **결과 생성과 녹화는 분리돼 있다**: EVALUATE는 세션이 끝나면 바로 시작하고 녹화를 기다리지 않는다. 결과(6.3)는 녹화 상태와 관계없이 조회된다

### 6.11 AI 장애 · 정체 · 안전장치

**마감 처리기** **[제안]** BE 스케줄러가 1초마다 `group:due`에서 기한이 지난 그룹을 꺼내 그룹 행을 잠그고 처리한다. 잠근 뒤 DB 값으로 다시 확인하므로 그 사이 진행된 그룹은 건드리지 않는다.

| 단계 · 상황 | 기한이 지나면 |
|---|---|
| `SPEAKING` | `question.spoken` 누락으로 보고 답변 시간을 시작한다(6.4). 장애가 아니다 |
| `ANSWERING` | 6.6 마감 처리(자동 제출 · 닫기) → `DECIDING`(답이 있으면) 또는 다음 차례 |
| `DECIDING` 7초 | 꼬리질문 없이 다음 차례. 장애가 아니다(꼬리질문은 필수가 아님). 측정은 `missing`(6.4) |
| `WAITING` · 이탈 2분 | 그 세션 `DISCONNECTED` 종료 |
| 완료 뒤 60초 5.8 없음 | 그 세션 `ALL_ANSWERED` 종료 |
| `ASKING` 20초 | 방 정보를 한 번 더 보내고 10초(임시 값) 더 기다린다. 그래도 `question.started`가 없으면 **AI 정체**. 그룹에 질문 행이 하나도 없으면 시작 실패(`START_FAILED`), 있으면 AI 장애 |

**AI 장애 처리** **[결정]** 에이전트 퇴장(웹훅 · 서버 확인) 또는 AI 정체

1. 그룹 행 → 세션 행 잠금. 남은 `IN_PROGRESS` 세션을 모두 끝낸다(`AI_FAILURE`). 저장된 답변이 1개 이상이면 `ANALYZING`(부분 결과), 0개면 `ABORTED`. 채점은 에이전트가 아니라 AI 분석 작업자가 하므로 에이전트가 멈춰도 저장된 답변으로 채점한다(6.14)
2. 진행 중이던 답변(아직 BE에 오지 않은 것)은 저장하지 않는다. 채팅 임시 글은 자동 제출하지 않는다(시간이 다 되지 않은 글이므로)
3. 그룹 `ENDED`, 녹화 합치기 작업, 방 삭제. 이미 끝난 답변 · 녹화 원본은 그대로 둔다
4. 에이전트 자동 재시작 · 이어 하기는 하지 않는다 **[결정]**
5. 화면은 방 정보(`groupStatus: ENDED`, 참가자 `endReason`)로 알고, "면접관 연결이 끊겨 면접을 마쳤습니다"를 안내한 뒤 결과 대기로 보낸다

**부분 결과** **[결정]** `end_reason`이 `AI_FAILURE`인 세션의 결과다

- 6.3 응답에 `partial: true`를 더해 화면이 "면접이 중간에 끝나 일부 답변으로 만든 결과"로 표시한다. 다른 경우는 `false`
- 스트릭 · 연습 기록 · 성장 리뷰 · 통계는 **지금 규칙 그대로 반영한다**: 답변 1개 이상으로 끝난 면접은 연습 면접이다. 개인 면접에서 중간에 [끝내기]를 눌러도 이미 같은 규칙이므로, 사용자 잘못이 아닌 AI 장애로 연습 인정을 빼지 않는다. 집계 코드는 바뀌지 않는다

**안전장치** **[결정]** 화상 60분 · 채팅 100분(임시 값)

- 그룹 `started_at`부터 이 시간이 지났고 **동시에** 마지막 진행(`progressed_at`) 뒤 5분(임시 값) 동안 변화가 없을 때만 남은 세션을 `CLEANUP`으로 끝낸다
- 정상 면접은 질문마다 단계가 바뀌어 `progressed_at`이 계속 갱신되므로 이 조건에 걸리지 않는다. 최대 길이(아래)가 상한에 가까워도 강제 종료되지 않는다
- 예상 최대 길이(3명, 기본 4 + 꼬리 2, 모두 시간을 다 씀): 화상 18질문 × 3분 ≈ 54분 + 질문 음성 · 전환 ≈ 60분, 채팅 18질문 × 5분 ≈ 90분 + 전환 ≈ 95분. 상한은 이 값보다 짧아지지 않게 둔다

### 6.12 녹화 · 다시보기 (화상)

- **녹화 위치** 방을 만들 때 트랙 자동 녹화 경로를 `recordings/raw/group-{groupId}/{publisher_identity}-{track_type}`로 둔다 **[제안]**. 참가자별로 `candidate-{sessionId}-video-…` · `candidate-{sessionId}-audio-…`, 면접관은 `interviewer-audio-…` 하나다
- **합치기 시점** 그룹이 끝난 뒤 그룹의 화상 세션마다 작업을 넣는다 **[결정]**. 면접관 음성 녹화가 방이 닫혀야 끝나기 때문이다
- **본인 답변 구간만** **[결정]** BE가 그 세션의 구간 목록 `segments`를 작업에 담는다. 구간은 질문마다 질문 시작(`question.started` 시각)부터 답변 끝(`answers.ended_at`, 답이 없으면 `closed_at`)까지다. AI는 내 영상 · 내 음성 · 면접관 음성을 합친 뒤 **구간만 잘라 이어 붙인 mp4**를 만든다. 다른 사람 차례는 파일에 남지 않는다. 자를 위치를 맞추려면 영상을 다시 인코딩해야 해 합치기 시간이 늘어난다 **[미정]**(AI)
- **섞이지 않는지 검증** 1) 합칠 때 다른 참가자 트랙(`candidate-{다른 id}-…`)을 쓰지 않는다. 2) 구간 밖은 파일에 없다. 3) 구간 안에서 내 마이크로 새어 들어온 목소리는 막을 수 없다(6.8 안내). 구현 시험에서 2명 이상 녹화로 1) · 2)를 확인한다
- **다시보기(6.4)** 그룹 세션은 잘라 붙인 영상의 위치로 응답한다. 질문 마커 · 타임라인 위치는 "구간 순서대로 이어 붙인 위치"로 BE가 계산한다(`segments[]`의 `videoStart`). 구간 밖 시각의 타임라인 점은 뺀다
- **녹화 처리 중** 합치기 전 · 중에는 기존처럼 `videoStatus: MERGING`이고 화면은 "녹화 처리 중"을 표시한다. "15분이 지나면 `FAILED`" 규칙은 그룹 세션이면 그룹 종료 시각부터 센다
- **다시 시도** `FAILED`면 6.5 녹화 다시 합치기(7.1)로 같은 작업을 다시 넣는다. 원본 트랙은 지우지 않으므로 다시 할 수 있다. 상태는 `MERGING`으로 돌아간다. 연속 실패 횟수 상한 3회(임시 값)
- 채팅 그룹은 녹화하지 않는다

### 6.14 답변 전달 · 채점 안정성

**원칙** **[결정]** 답변은 DB에 먼저 저장하고, 그 뒤에 AI로 보낸다. 전달이 실패해도 저장된 답변은 그대로다.

**채팅 최종 답변 → 에이전트(꼬리질문 판단용)** **[제안]**

1. 최종 답변을 저장한 트랜잭션이 커밋된 뒤 LiveKit `SendData`로 `group.answer`(`sessionId` · `seq` · `content` · `turnVersion`)를 에이전트에 보낸다
2. 보내기가 실패하면(LiveKit 호출 오류) 마감 처리기가 `DECIDING` 동안 1초 간격으로 다시 보낸다. 7초 제한 시간 안에서만 다시 보내고, 넘으면 꼬리질문 없이 넘어간다(6.4)
3. 에이전트는 `(sessionId, seq)`로 중복을 거른다. 같은 답변을 다시 받으면 새로 판단하지 않고 처음 결과를 다시 보낸다. BE도 `turnVersion` · 단계가 맞는 첫 `followup.decided`만 반영한다
4. 화상 답변은 에이전트가 만든 글이라 따로 전달하지 않는다. 에이전트는 방 정보 `DECIDING`(BE 저장 확인)을 본 뒤 판단한다

**에이전트 → BE(화상 답변 · 진행 메시지)** 기존 규칙을 그대로 쓴다: 결과 큐에 넣기 실패 시 1 · 2 · 4초 재시도, 그래도 실패하면 `submitFailed`와 [다시 시도], BE는 `answers.question_id` UNIQUE와 잠금 안 확인으로 중복을 버린다(AI 명세 6.5). 그룹은 큐 이름만 `ai:results:group`이다

**채점 · 결과** 지금 구조를 그대로 쓴다.

| 단계 | 처리 |
|---|---|
| 답변별 채점(SCORE_ANSWER) | 답변 저장과 같은 트랜잭션에서 Outbox로 작업을 넣는다(BE 설계 5.0). 큐 전송이 실패하면 5초마다 다시 보낸다. 실패해도 결과 생성(EVALUATE)이 마저 채점한다 |
| 결과 생성(EVALUATE) | 세션이 끝날 때(정상 · 이탈 · AI 장애 모두) Outbox로 넣는다. AI 분석 작업자가 처리하며 면접 에이전트와 다른 프로세스라, 에이전트가 멈춰도 저장된 답변으로 채점된다 |
| 실패 | 작업자가 GMS 호출을 재시도하고(AI 명세 5장), 그래도 실패하거나 10분이 지나면 `FAILED`. 화면은 기존 5.9로 다시 시도한다 |
| 중복 | 같은 작업이 두 번 와도 BE가 상태 · 마지막 `jobId`로 거른다(BE 설계 5.5) |

## 8. AI · LiveKit 계약 변경

### 8.1 에이전트 배정 정보 **[제안]**

`kind`가 없으면 지금 개인 면접 형식이다. 진행 순서 · 시간은 방 정보로 받으므로 배정 정보에는 질문만 담는다.

```json
{ "kind": "GROUP", "groupId": 12, "mode": "VIDEO", "persona": "COFFEE_CHAT",
  "commonQuestions": [ { "content": "1분 동안 자기소개해 주세요.", "criteria": "핵심 경험 · 지원 동기" },
                       { "content": "의견이 다른 동료와 문제를 해결한 경험은?", "criteria": "갈등 상황 · 본인 행동 · 결과" } ],
  "participants": [
    { "sessionId": 55, "identity": "candidate-55",
      "personalQuestions": [ { "content": "…", "criteria": "…" }, { "content": "…", "criteria": "…" } ] } ] }
```

- 형식이 틀리면 지금처럼 거절하고 `assignment.rejected`에 `groupId`를 담는다
- 에이전트 재배정은 하지 않는다(6.11)

### 8.2 방 정보(room metadata) **[제안]**

BE만 쓴다. 화면 · 에이전트는 읽기만 한다. JSON, LiveKit 방 정보 크기 상한 안(질문 글은 담지 않음).

```json
{ "turnVersion": 17, "serverTime": "2026-11-04T14:03:00.120+09:00",
  "groupStatus": "IN_PROGRESS", "round": 2, "phase": "ANSWERING",
  "turn": { "sessionId": 55, "seq": 3, "kind": "PERSONAL", "announce": "FULL",
            "deadlineAt": "2026-11-04T14:05:02.000+09:00", "extended": false, "followupsLeft": 2 },
  "participants": [ { "sessionId": 55, "turnOrder": 1, "state": "PRESENT" },
                    { "sessionId": 56, "turnOrder": 2, "state": "ABSENT", "absentUntil": "…" },
                    { "sessionId": 57, "turnOrder": 3, "state": "ENDED", "endReason": "ALL_ANSWERED" } ],
  "upcoming": [ 56, 57 ] }
```

- `phase`: `ASKING` · `SPEAKING` · `ANSWERING` · `DECIDING` · `WAITING`. `groupStatus`가 `ENDED`면 끝. `deadlineAt`은 `ANSWERING`에서만 값이 있고 그 밖에는 null(질문 음성이 끝나기 전에는 시간을 표시하지 않음)
- `participants[].state`: `PRESENT` · `ABSENT` · `DONE`(완료, 5.8 대기) · `ENDED`
- 질문 글은 지금처럼 에이전트의 `question` 메시지로 보낸다(본인 차례에 공개)

### 8.3 면접방 메시지 **[제안]**

| 메시지 | 방향 | 변경 |
|---|---|---|
| `question` | 에이전트 → 모두 | `sessionId`(누구 질문인지) 추가 |
| `reaction` | 에이전트 → 모두 | `sessionId` 추가 |
| `interview.stt` · `answer.state` | 에이전트 → 답변자 | 그대로. `timedOut`은 그룹에서 보내지 않음 |
| `answer.submit` | 답변자 → 에이전트 | 화상만. 답변자 · 현재 `seq`가 아니면 `false`. 그룹 채팅은 쓰지 않는다(답변 글은 BE가 보냄) |
| `chat.input` | 답변자 → 에이전트 | 리액션용으로 그대로 재사용. 지금 답변자만 받고 `questionSeq`를 보낸 사람 세션 기준으로 읽는다 **[미정]**(6.7) |
| `group.answer` (새) | BE → 에이전트(`SendData`, 대상 `interviewer`) | 채팅 최종 답변이 저장되면 `sessionId` · `seq` · `content` · `turnVersion`. 꼬리질문 판단용. 다시 보낼 수 있고 에이전트가 중복을 거른다(6.14) |

### 8.4 결과 메시지 **[제안]**

그룹 세션의 에이전트 결과는 `ai:results:group` 큐로 보낸다(6.5). 형식은 `ai:results`와 같다.

| `type` | 변경 | BE 처리 |
|---|---|---|
| `question.started` | `turnVersion` · `kind` · `speechMs`(예상 음성 길이) 추가. 그룹 `seq` 1~6 | 현재 차례와 `turnVersion` · 세션 · `seq`가 맞을 때만 질문 행 저장, `SPEAKING`. 안 맞으면 버림 |
| `question.spoken` (새) | `sessionId` · `seq` · `turnVersion` · `endedAt` · `speech`(`ENDED` · `FAILED`) | `SPEAKING`이고 버전이 맞을 때만 `spoken_at` · `deadline_at` 저장, `ANSWERING`. 늦으면 버림(6.4) |
| `answer.completed` | `turnVersion` · `answerEndedAt` 추가, `endReason`에 `TIME_LIMIT` | 질문이 열려 있고 답이 없을 때만 저장(`ended_at`), `DECIDING`. 닫혔거나 답이 있으면 버림 |
| `followup.decided` (새) | `sessionId` · `seq` · `turnVersion` · `needed` · `content` · `criteria` · `promptVersion` · `modelVersion` · `receivedAt` · `generationMs` | `DECIDING`이고 `turnVersion`이 맞을 때만 다음 차례 계산에 반영. 늦게 오면 버리되 응답 시간은 기록(6.4) |
| `assignment.rejected` | `groupId` 추가 | 5.1 표 |

- 그룹 세션의 `seq` 검사는 1~6, 개인 면접은 지금처럼 1~5다
- 에이전트는 방 정보의 `turnVersion`을 결과 메시지에 그대로 담는다. BE는 버전이 다르면 늦은 메시지로 보고 버린다

## 9. 동시성 · 멱등성

**잠금 순서** **[제안]**: 회원 행 → 그룹 행 → 세션 행(id 순서). 그룹 세션을 다루는 모든 곳(10.x, 그룹 세션의 5.7 · 5.8 · 10.9, `ai:results:group` 처리, 웹훅, 마감 처리기)이 지킨다. 개인 면접은 세션 행만 잠그므로 영향이 없다.

**원칙**: 진행 상태를 바꾸는 일은 모두 그룹 행을 잠근 한 트랜잭션이다. 잠근 뒤 DB 값으로 조건을 다시 확인하고, 맞지 않으면 아무것도 하지 않는다. 그래서 같은 사건이 두 번 와도, 늦게 와도 결과가 같다.

| 경쟁 | 처리 |
|---|---|
| 마지막 자리에 두 명이 동시에 참가 | 그룹 행 잠금 후 인원 확인. 늦은 쪽 409 `GROUP_FULL` |
| 한 회원이 두 그룹에 동시에 참가 | 회원 행 잠금 후 참가 중 그룹 확인 |
| 시작과 나가기 · 준비 취소 | 그룹 행 잠금. 먼저 커밋한 쪽 기준으로 늦은 쪽 409 |
| 시작을 두 번 | 멱등 키. 다른 키면 상태 확인으로 409. 외부 호출을 잠금 안에서 해 방이 둘 생기지 않는다(최대 15초, 멱등 대기 20초) |
| 채팅 직접 제출과 자동 제출 | 같은 잠금 · 같은 확인(6.7). 하나만 저장 |
| 임시 저장이 다른 질문에 들어감 | 키가 질문별이고, 지금 차례 질문만 받는다 |
| 화상 답변과 마감 닫기 | 둘 다 그룹 행 잠금. 먼저 처리된 쪽만 반영(답 저장이면 닫지 않음, 닫힘이면 답 버림) |
| 같은 답변 두 번 | `answers.question_id` UNIQUE + 잠금 안 확인 |
| 늦게 온 에이전트 메시지 | `turnVersion` 비교로 버림(`question.spoken` · `followup.decided` 포함) |
| `question.spoken` 누락 처리와 늦은 도착 | 둘 다 그룹 행 잠금. 먼저 `ANSWERING`으로 바꾼 쪽만 반영 |
| 채팅 답변 전달 중복 | `group.answer` 재전송은 에이전트가 `(sessionId, seq)`로 거르고, BE는 첫 판단만 반영 |
| 연장 두 번 | `extended` 확인으로 두 번째 409 |
| 웹훅 중복 · 순서 뒤바뀜 | 이벤트 id로 한 번만. 퇴장 뒤 입장이 먼저 오면 서버 확인(15초)이 바로잡는다 |
| 5.8 · 이탈 2분 · AI 장애 · 안전장치가 겹침 | 같은 종료 처리. 두 번째는 세션이 `IN_PROGRESS`가 아니라 무시(5.8은 409) |
| 마지막 두 세션이 동시에 끝남 | 그룹 행 잠금으로 하나씩. 뒤 쪽이 그룹을 끝낸다. 방 삭제 · 합치기는 한 번 |
| 마감 처리기가 여러 BE에서 돎 | 그룹 행 잠금 후 기한 재확인. 지금 BE는 한 대지만 늘어나도 안전하다 |
| 방 정보 순서 | `turnVersion`. 받는 쪽이 낮은 버전 무시 |

**멱등 키**: 10.1 · 10.3 · 10.7 필수(그룹 · 세션 · 방이 두 번 생기지 않게). 그 밖의 새 API는 상태 확인으로 같은 결과가 나온다.

## 10. 호환성 · 기술 검토

### 10.1 기존 개인 면접과의 호환성: 깨지지 않음

| 확인한 것 | 결과 |
|---|---|
| 5.1 ~ 5.9 · 5.13 ~ 5.15 | 그룹 규칙은 `group_id`가 있을 때만. 개인 면접 응답은 null · false 필드만 늘어난다 |
| 결과 · 다시보기 · 통계 · 성장 리뷰 | 계산 그대로. `partial: false` · `segments: null` · `groupId: null` 추가. 스트릭 · 연습 기준(답변 1개 이상) 그대로 |
| 질문 5개 규칙 | BE `InterviewPlan.QUESTION_COUNT`(플랜 검증 · `seq` 검사 · 5.5 · 5.7)와 AI `MAX_SEQ` · `QUESTION_COUNT`(배정 · RPC · 리액션 검사)가 5를 가정한다. 개인 면접 값은 그대로 두고 그룹 분기(플랜 2개, `seq` 1~6)만 더한다 |
| PLAN | `questionCount`가 없으면 5개. 개인 면접 작업 메시지는 바뀌지 않는다 |
| 결과 큐 | 개인 면접은 `ai:results` 그대로. 그룹만 `ai:results:group` |
| LiveKit | 방 이름 · 참가자 이름 · 녹화 경로가 접두어부터 달라 겹치지 않는다. 웹훅은 `group-` 방만 처리 |
| 녹화 합치기 | 새 필드가 없으면 지금 규칙 |
| DB | 새 컬럼 모두 null 허용, 백필 없음 |
| 회귀 시험 | 공통 코드(`AiResultService` · `AnswerService` · 에이전트)에 분기가 들어가므로 기존 개인 면접 시험 통과가 완료 조건이다 |

### 10.2 AI · LiveKit 연동: 가능함

- 한 방 여러 참가자: 참가자 이름만 다르면 된다(지금 `candidate` 고정이라 둘째 사람이 들어오면 첫 사람이 튕긴다)
- 현재 답변자 음성만: 에이전트 음성 수집(`RoomCapture`)이 이미 참가자 이름을 받아 만든다. 차례마다 다시 만든다
- 차례 진행: 진행 판단이 BE로 와서 에이전트는 "방 정보를 보고 그 질문을 말하고 듣는" 단순한 반복이 된다. 지금 진행기(`InterviewRunner`, 한 사람 · 5개 반복)는 그룹용으로 새로 만들지만 질문 말하기 · STT · 리액션 · 결과 전송 부품은 그대로 쓴다
- 차례 전환 지연: 에이전트 → 그룹 큐 → BE 커밋 → 방 정보 → 화면 · 에이전트. 평소 1초 미만으로 예상하며 구현 뒤 실측한다

### 10.3 재접속 · 자동 종료 · 동시성: 상태가 꼬이지 않음

- 진행 상태의 주인이 BE(DB) 하나라 AI가 멈춰도 상태를 잃지 않는다
- 모든 상태 변경이 그룹 행 잠금 · 재확인 · 버전 비교를 거친다
- 종료 경로 다섯 개가 한 처리로 모이고, 두 번째 시도는 상태 확인으로 무시된다
- 웹훅이 빠져도 15초 서버 확인으로, 방 정보가 빠져도 1초 재전송 · 10.4로 맞춘다
- 정상 면접은 진행 시각이 계속 갱신되어 안전장치에 걸리지 않는다

## 12. 위험 · 남은 일

| 위험 | 영향 | 대응 |
|---|---|---|
| AI 장애 | 그룹 전체가 중간에 끝난다(개인 면접보다 피해가 큼) | 부분 결과 · 녹화 보존(6.11). 재시작은 범위 밖 |
| 차례 전환 지연 | 결과 큐 · DB · LiveKit 호출을 한 번씩 거친다. DB 장애로 그룹 큐 처리가 재시도에 걸리면 진행이 멈춘다 | 그룹 전용 큐 · 스레드. 실측 후 필요하면 다음 단계에서 에이전트 → BE 경로를 바꾼다 |
| 웹훅 누락 · 지연 | 이탈 감지가 최대 15초 늦다 | 서버 확인(6.9). 2분 기준에는 영향이 작다 |

| 질문 재생 끝 이벤트 누락 | 답변 시작이 최대 5초 늦게 잡힌다 | 늦은 만큼 시간을 빼지 않는다(6.4) |
| 채팅 마감 확정 | 마지막 임시 저장 뒤 몇 초의 입력이 빠질 수 있다 | 화면이 0초에 5.7을 먼저 부르고, 임시 저장은 보조(6.7) |
| 목소리 새어 들어감 | 답변 글 · 채점이 틀어질 수 있다 | 안내(6.8). 녹화는 본인 구간만 |
| 녹화 다시 인코딩 | 합치기 시간 · CPU가 면접 길이에 비례해 는다. 그룹 종료 뒤 여러 세션이 한꺼번에 들어온다 | A7 · I2. 다시보기는 "녹화 처리 중"으로 기다리고 결과 조회는 막지 않는다 |
| 먼저 끝난 사람의 다시보기 지연 | 그룹이 끝날 때까지 영상이 없다 | 정책상 허용. 화면 안내 |
| 면접 길이 | 화상 최대 약 60분, 채팅 약 95분 | 정원 3명 · 꼬리 2개 상한. 실측 뒤 시간 조정 |
| 에이전트 부하 | 그룹 하나가 3명 분의 질문 합성 · 꼬리질문을 한다 | A9 성능 시험 |
| 공정성 | 공통 질문은 뒤 순서가 생각할 시간이 길다 | 정책상 허용(무작위 고정 순서) |
| 문항 은행 관리 | 자기소개 · 인성 문항을 누가 쓰고 고칠지 | 처음 문항은 BE가 마이그레이션으로 넣고 팀이 검토 |

## 13. 고도화

### 13.1 방장의 기본 질문 개수 선택 **[제안]**

MVP는 개인당 기본 질문 4개로 고정이다 **[결정]**. 나중에 방장이 그룹을 만들 때 기본 질문 개수를 고르게 한다.

| 선택 | 공통 | 개인 맞춤 | 라운드 | 예상 최대 길이(3명, 꼬리 2개, 시간을 다 씀) |
|---|---|---|---|---|
| 4개(MVP) | 2 | 2 | 4 | 화상 약 60분 · 채팅 약 95분 |
| 6개 | 3 | 3 | 6 | 화상 약 80분 · 채팅 약 125분 |
| 8개 | 4 | 4 | 8 | 화상 약 100분 · 채팅 약 155분 |
| 10개 | 5 | 5 | 10 | 화상 약 120분 · 채팅 약 185분 |

- 범위: 꼬리질문을 뺀 기본 질문 4~10개, 짝수, 공통 · 개인 반반. 꼬리질문(0~2)은 따로 센다
- 바뀌는 곳: `interview_groups.base_question_count`, PLAN `questionCount`(개인 맞춤 수), 공통 질문 문항 유형(자기소개 1 + 인성 n−1), 라운드 수, `seq` 상한(기본 + 2), 안전장치 시간(질문 수로 계산)
- 같이 볼 것: 길이가 화상 1시간 · 채팅 1.5시간을 크게 넘는다. 시간 선택(답변 시간 단축)이나 정원과의 조합 제한이 필요하다. PLAN 생성 비용은 개인 맞춤 질문 수에 비례해 는다(10개면 5개 생성, 지금 개인 면접과 같은 수준)

### 13.2 AI 면접관 여러 명 **[제안]**

- 에이전트는 하나로 두고 여러 면접관을 목소리 · 페르소나로 나눠 말한다. 면접관마다 에이전트를 두면 누가 말할지 에이전트끼리 맞춰야 한다
- 차례를 BE가 정하므로 방 정보 `turn`에 `speaker`(어느 면접관)를 더하면 된다. 배정 정보의 `persona`는 `interviewers[]`로 늘린다
- 녹화의 면접관 음성은 트랙 하나로 유지한다
