## 1. 목적

세 가지 질문에 숫자로 답한다.

| 질문 | 증거 | 담당 |
|---|---|---|
| ① 평가를 믿을 수 있나? | 골든셋에서 AI 판정과 사람 판정 비교(6장) | 팀 측정 |
| ② 쓰면 실력이 늘까? | 피드백 반영 실험(7.1), 테스터 대조 실험(7.2) | 팀 측정 |
| ③ 사용자가 가치를 느끼나? | 설문, 재방문 D1·D3·D7(8장) | 사용자 설문 |

①이 먼저다. 평가를 믿을 수 없으면 ②의 "점수가 올랐다"도 의미가 없기 때문이다.

## 2. 지표와 목표치

목표치는 모두 **[제안]**이며, 첫 측정 결과를 보고 확정한다.

| 구분 | 지표 | 계산 | 목표 |
|---|---|---|---|
| ① | 사람-AI 일치도 | 항목별로 AI 판정 단계와 사람 합의 단계의 가중 카파(QWK, 2차 가중치) | ≥ 0.6, 그리고 사람끼리 일치도의 80% 이상 |
| ① | 반복 일관성 | 같은 답변을 5번 채점했을 때 5번 모두 같은 단계가 나온 비율 | ≥ 90% |
| ① | 변별력 | 원본과 품질을 떨어뜨린 변형의 쌍에서, 변형이 겨냥한 항목이 원본보다 낮게 나온 비율 | ≥ 90% |
| ① | 강건성 | 의미와 무관한 변형에서 4항목 단계가 모두 원본과 같은 비율 | ≥ 90% |
| ① | 이유 근거성 | 판정 이유가 답변에 실제로 있는 내용을 근거로 든 비율(사람 확인) | ≥ 90% |
| ②-A | 피드백 반영 효과 | 피드백대로 고쳐 쓴 답변에서 고칠 점이 겨냥한 항목이 오른 비율 − 피드백 없이 고쳐 쓴 답변의 같은 비율 | > 0, 오른 비율 자체는 ≥ 70% |
| ②-B | 실제 사용자 효과 | 같은 질문 재답변 점수 상승폭의 차이(실험군 − 대조군) | > 0(방향 확인) |
| ③ | 사용자 가치 | 도움 됐다(4·5점) 비율, 추천 의향(NPS), 재방문 D1·D3·D7 | 참고 지표 |

- QWK는 3단계 순서를 반영한다(1↔3 불일치가 1↔2보다 크게 깎인다). 0.6 이상을 "상당한 일치"로 본다
- 사람끼리도 완벽히 일치하지 않으므로, AI가 사람끼리 일치하는 만큼 맞추면 사람 채점자 한 명을 대신할 수 있다고 본다. 그래서 절대 기준(0.6)과 사람 대비 기준을 함께 둔다
- ②-B는 테스터가 10~20명이라 통계적 유의성은 기대하지 않는다. 방향과 크기(평균 차이, 부트스트랩 95% 구간)만 보고한다

## 3. 측정 범위

**[결정]**

| 항목 | 범위 | 이유 |
|---|---|---|
| 면접 방식 | 채팅(`CHAT`)만 | 화상은 음성 토큰·말하기 지표가 있어야 해 글 답변만으로 골든셋을 만들 수 없다. 채팅도 4항목을 모두 판정한다(`DELIVERY`는 답변 글로) |
| 면접관 | `DEVIL`·`COFFEE_CHAT`·`DUCK`을 고르게 | 판정 지침은 면접관과 관계없이 같다(AI 명세 3장). 면접관만 바꿔 판정이 같은지를 강건성으로 확인한다 |
| `COVER_LETTER` | 결과 생성(EVALUATE)의 확정 판정으로 평가 | 답변 채점(SCORE_ANSWER)의 판정은 임시이고 결과 생성에서 확정한다(AI 명세 4장 `SCORING`) |
| 나머지 3항목 | 답변 채점(SCORE_ANSWER) 판정으로 평가 | 결과 생성은 이미 채점된 값을 그대로 쓴다 |
| 피드백 | 결과 생성의 `improvePoint` | ②-A의 입력이다 |

## 4. 골든셋

AI 판정을 비교할 정답지다. `ai/eval/golden/`에 둔다(S15P31A301-506).

### 4.1 규모 **[결정]**

| 구성 | 수 | 설명 |
|---|---|---|
| 질문 | 30개 | 면접관마다 10개 |
| 원본 답변 | 90개 | 질문마다 의도한 단계 1·2·3 하나씩 |
| 변별력 변형 | 약 30개 | 단계 3 원본에서 한 항목만 떨어뜨림 |
| 강건성 변형 | 약 30개 | 단계 2·3 원본에서 의미와 무관한 것만 바꿈 |

사람 2~3명이 하루 안에 라벨링할 수 있는 양이다.

### 4.2 만드는 방법

1. 가상 자기소개서 5개를 쓴다(직무 2~3개). 실제 회원 자기소개서나 개인정보는 쓰지 않는다
2. 실제 PLAN(AI 명세 2장)으로 자기소개서마다 면접관 3종의 질문을 만들고, 그중 30개를 고른다. 질문의 `criteria`·`claimId`도 그대로 쓴다
3. 질문마다 단계 1·2·3을 의도한 답변을 쓴다. LLM으로 초안을 만들어도 되지만 사람이 고친다
4. 변형을 만든다(4.4)
5. 사람이 블라인드로 라벨링한다(5장). **정답은 의도한 단계가 아니라 사람 합의 단계다**

### 4.3 형식

`ai/eval/golden/items.jsonl`에 한 줄에 답변 하나를 둔다. 필드 이름은 작업 메시지(AI 명세 2장·3장)와 같게 맞춰 그대로 채점에 넣을 수 있게 한다.

```json
{
  "id": "q01-a2",
  "coverLetterId": "cl1",
  "persona": "COFFEE_CHAT",
  "mode": "CHAT",
  "seq": 1,
  "question": "응답 시간을 40% 줄인 과정은?",
  "criteria": "원인 분석 · 수치 근거",
  "claimId": "c1",
  "content": "…",
  "intendedLevel": 2,
  "variantOf": null,
  "variantType": null,
  "targetCriterion": null
}
```

- 자기소개서는 `ai/eval/golden/cover_letters.json`에 `coverLetterId`별로 둔다(`companyName`·`jobTitle`·`coverLetterItems`·`companyCard`). 주장(`claims`)과 질문 후보는 실제 PLAN 결과를 버전과 함께 `plan_runs.json`에 둔다. `companyCard`는 PLAN·EVALUATE가 받는 회사 카드(AI 명세 8장)이고 없으면 생략한다. 질문을 만들 때와 피드백을 만들 때(7.1) 같은 카드를 써야 하므로 함께 고정한다
- `intendedLevel`: 원본과 강건성 변형은 의도한 단계, 변별력 변형은 null(겨냥한 항목만 낮추므로)
- `variantOf`: 변형이면 원본 `id`, 원본이면 null
- `variantType`: 4.4의 변형 종류
- `targetCriterion`: 변별력 변형이 떨어뜨리려는 항목(`JOB_FIT`·`COVER_LETTER`·`LOGIC`·`DELIVERY`). 강건성 변형은 null
- 사람 라벨은 채점자마다 따로 둔다: `ai/eval/golden/labels/rater-a.json` 형식은 `{ "q01-a2": { "JOB_FIT": 2, "COVER_LETTER": 2, "LOGIC": 3, "DELIVERY": 2 } }`. 사람끼리 일치도를 구하려면 합치기 전 값이 필요하다
- 합의 라벨은 `labels/consensus.json`에 같은 형식으로 둔다
- 골든셋을 고치면 `datasetVersion`(`golden-v1`, `golden-v2` …)을 올린다

### 4.4 변형 종류

| 용도 | `variantType` | 바꾸는 것 | 기대 |
|---|---|---|---|
| 변별력 | `NO_ACTION` | 본인 행동·방법을 빼고 결과만 남김 | `JOB_FIT` 하락 |
| 변별력 | `NO_RESULT` | 결과·확인 방법을 뺌 | `LOGIC` 하락 |
| 변별력 | `SHUFFLED` | 원인·조치·결과 순서를 뒤섞음 | `LOGIC` 하락 |
| 변별력 | `CONTRADICT_CL` | 자기소개서와 수치·역할이 어긋나게 바꿈 | `COVER_LETTER` 하락 |
| 변별력 | `VERBOSE` | 핵심을 뒤로 미루고 군더더기를 넣음 | `DELIVERY` 하락 |
| 강건성 | `PUNCTUATION` | 문장 부호를 빼거나 더함 | 변화 없음 |
| 강건성 | `HONORIFIC` | 존댓말 ↔ 평서문 | 변화 없음 |
| 강건성 | `TYPO` | 오타 1~2개 | 변화 없음 |
| 강건성 | `PERSONA` | 면접관만 바꿈(`content` 동일) | 변화 없음 |

- 변별력 변형은 `targetCriterion` 외 항목은 되도록 그대로 둔다. 다만 행동·결과를 빼거나 순서를 섞으면 다른 항목도 함께 떨어질 수 있으므로, 변별력은 겨냥한 항목만 보고 판정하고(2장) 다른 항목의 변화는 결과 문서에 따로 적는다
- `PERSONA`는 판정 입력에 면접관이 들어가지 않으므로(AI 명세 3장) 반복 일관성과 같은 값이 기대된다. 나중에 면접관이 판정에 섞여 들어오는 것을 막는 회귀 검사로 둔다

## 5. 라벨링 가이드

사람 채점자가 보는 기준이다. AI 판정 지침과 같은 잣대여야 비교가 공정하다.

### 5.1 항목별 단계

| 항목 | 3 좋아요 | 2 보통 | 1 아쉬워요 |
|---|---|---|---|
| `JOB_FIT` 직무 적합 | 질문이 확인하는 역량에 대해 본인이 한 구체적 행동·방법과 그 방법을 고른 이유를 들어 경험과 직무 요구를 연결한다 | 관련 경험과 본인 행동은 있지만 방법을 고른 이유나 직무 요구와의 연결이 빠졌다 | 결과·수치나 일반론만 있고 본인이 한 행동·방법이 없다 |
| `COVER_LETTER` 자소서 검증 | 자기소개서의 해당 주장과 어긋나지 않고, 과정·수치·본인 역할을 구체적으로 설명해 주장을 뒷받침한다 | 어긋나지는 않지만 뒷받침이 일부만 구체적이다 | 자기소개서와 어긋나거나 근거 없이 주장만 반복한다 |
| `LOGIC` 논리 | 원인(상황) → 조치 → 결과(확인 방법) 순서가 분명하다 | 셋 중 하나가 빠졌거나 서로 이어지지 않는다 | 셋 중 둘 이상이 빠졌거나 결과만 나열한다 |
| `DELIVERY` 전달 **[제안]** | 질문에 대한 답(핵심)이 앞에 나오고 군더더기 없이 읽힌다 | 핵심은 있지만 뒤에 나오거나 장황하다 | 무엇을 말하려는지 알기 어렵다 |

- `JOB_FIT`·`LOGIC`은 AI 명세 3장의 판정 지침, `COVER_LETTER`는 결과 생성 판정 지침(`evaluate-cover-letter-v1`)을 옮긴 것이다
- 가정 상황 질문은 원인을 문제 정의로, 조치를 적용할 방법과 이유로, 결과를 확인할 방법으로 읽는다(AI 명세 3장)
- `DELIVERY`는 AI 판정 지침에 단계 설명이 없어 이 문서가 정한 것이다. 그래서 `DELIVERY` 일치도는 따로 해석한다
- 항목마다 단계별 예시 답변 1개씩(12개)은 [라벨링 안내](../ai/eval/golden/labels/README.md)에 둔다. 예시를 본 답변의 라벨이 예시에 끌려가지 않도록 골든셋에 넣지 않은 질문으로 만든다

### 5.2 진행 규칙

- **블라인드**: AI 판정, 다른 채점자 라벨, `intendedLevel`·`variantType`을 보지 않는다. 라벨링 시트(`labels/sheet.csv`)는 자기소개서·질문·`criteria`·`content`만 남겨 순서를 섞고, `id` 대신 블라인드 번호를 쓴다. `id`에 의도 단계와 변형 종류가 드러나기 때문이다. 시트에는 원본과 변별력 변형(120개)만 넣는다. 강건성 변형은 의미가 원본과 같아 사람 라벨이 필요 없다
- **독립**: 다 끝날 때까지 채점자끼리 이야기하지 않는다
- **채점자**: 팀원 2명 + 가능하면 외부 1명. 답변을 쓴 사람은 자기가 쓴 질문을 라벨링하지 않는다 **[제안]**
- **합의**: 다수결. 채점자가 2명이고 다르거나 3명이 모두 다르면 토론해 정하고, 토론한 항목은 `labels/disputes.md`에 이유를 남긴다
- 합의 전에 사람끼리 일치도를 먼저 계산해 둔다

## 6. ① 평가 신뢰도 측정

`ai/eval/reliability.py`(S15P31A301-507)가 골든셋 전체를 실제 채점 경로로 돌려 2장 지표를 계산한다.

| 지표 | 대상 | 방법 |
|---|---|---|
| 사람-AI 일치도 | 원본 90개 | 항목별 QWK. 사람끼리 QWK(채점자 쌍마다)와 나란히 보고한다 |
| 반복 일관성 | 원본 90개 | 5번 채점해 항목별로 5번 모두 같은 비율 |
| 변별력 | 변별력 변형 쌍 | 원본·변형 각각 5번 채점의 다수결 단계로 비교 |
| 강건성 | 강건성 변형 쌍 | 같은 방식으로 4항목 모두 같은지 비교 |
| 이유 근거성 | 무작위 30개 × 4항목 | 사람이 판정 이유가 답변 내용을 근거로 했는지 예·아니오로 표시 |

- 실제 GMS를 호출한다. 호출 수는 약 (90 + 60) × 5 = 750번이고, 결과(판정·이유·버전)를 `ai/eval/runs/<날짜>-<promptVersion>.jsonl`에 남겨 다시 계산할 때 재호출하지 않는다
- 항목별 결과와 함께 면접관별·의도 단계별로 나눠 본다(CONTRIBUTING 6.3 Slice). 평균이 목표를 넘어도 한 묶음이 크게 낮으면 결과 문서에 적는다
- 불일치가 큰 답변 10개는 결과 문서에 판정 이유와 함께 싣는다

## 7. ② 개선 효과 실험

### 7.1 ②-A 피드백 반영 실험

사람 없이 "피드백이 실행 가능한가"를 본다. `ai/eval/feedback_uplift.py`(S15P31A301-508).

1. 대상: 원본 중 사람 합의 단계에 1·2가 있는 답변
2. 결과 생성(AI 명세 4장)으로 `improvePoint`를 만든다
3. LLM이 답변을 두 번 고쳐 쓴다
   - 실험: "아래 고칠 점만 반영해 고쳐 써라"
   - 비교: "더 좋은 답변으로 고쳐 써라"(피드백 없음)
   - 둘 다 "자기소개서와 원래 답변에 없는 사실을 지어내지 마라"를 넣는다. 지어낸 수치로 점수가 오르면 피드백 효과가 아니기 때문이다
4. 고친 답변을 다시 채점(5번 다수결)한다
5. 고칠 점이 겨냥한 항목(사람이 고칠 점을 읽고 항목을 표시)이 오른 비율을 실험·비교 각각 구해 차이를 낸다
6. 고친 답변 중 20개는 사람이 블라인드로 라벨링해, AI 점수만 오르고 실제로는 나아지지 않은 경우가 있는지 확인한다

### 7.2 ②-B 테스터 대조 실험

실제 사람이 피드백을 보고 나아지는지 본다. 데이터 추출은 S15P31A301-509.

- **테스터** 10~20명, 팀원 제외. 취업 준비 중인 지인·교육생 위주
- **배정** 가입 순서대로 실험군·대조군을 번갈아 배정한다
- **계정** `utility-test-01` 형식으로 만들어 실험 데이터만 따로 뽑을 수 있게 한다
- **진행**(같은 날, 채팅 면접, 각자 자기소개서 1개·면접관 1종 선택)

| 순서 | 실험군 | 대조군 |
|---|---|---|
| 1 | 1차 면접(질문 5개) | 1차 면접(질문 5개) |
| 2 | 결과 화면에서 피드백을 읽는다(5분 이상) | 결과를 보지 않는다 |
| 3 | 같은 지원서·같은 면접관으로 2차 면접 | 같은 지원서·같은 면접관으로 2차 면접 |
| 4 | 2차 결과 확인, 설문(8장) | 2차 결과 확인, 설문(8장) |

- 같은 지원서·같은 면접관으로 다시 면접을 만들면 보관함 질문으로 준비하므로(API 명세 5.1) 1차와 같은 질문을 받는다. 그래서 질문 난이도 차이 없이 비교할 수 있다
- 대조군도 같은 질문을 두 번 받으므로 "한 번 해 봐서 나아진 것"은 양쪽에 똑같이 들어간다. 차이(실험군 − 대조군)가 피드백 효과다
- 대조군은 1차를 끝낸 직후 2차를 시작한다. 1차가 분석 중이라 결과를 볼 수 없다
- **측정** 질문별 2차 점수 − 1차 점수(답변 점수, 항목 점수)의 평균을 군별로 내고 차이와 부트스트랩 95% 구간을 보고한다
- 끝난 뒤 대조군에게도 결과를 보여 준다

## 8. ③ 사용자 가치

### 8.1 설문 **[제안]**

기존 구글폼(`NEXT_PUBLIC_SURVEY_URL`)을 그대로 쓴다. 화면이 3·7·21일째에 띄우고(API 명세 7.1 S08-B), 주소에 `userId`·`streak`이 붙는다. 테스터(7.2)는 2차 면접 뒤 같은 폼에 응답한다.

| 문항 | 형식 |
|---|---|
| 피드백이 내 답변을 고치는 데 도움이 됐나요? | 1~5점 |
| 점수와 판정 이유가 납득됐나요? | 1~5점 |
| 실제 면접 준비에 도움이 될 것 같나요? | 1~5점 |
| 친구에게 추천할 의향은? | 0~10점(NPS) |
| 가장 도움이 된 것 / 아쉬운 것 | 자유 응답 |

- "납득됐나요?"는 ①을 사용자 쪽에서 본 값이다. 6장 결과와 함께 본다
- 4·5점 비율과 NPS(9~10점 비율 − 0~6점 비율)를 보고한다

### 8.2 재방문

관리자 메트릭(API 명세 8.15·8.16)의 재방문 D1·D3·D7을 측정 기간 동안 기록한다. 회원 수가 적어 참고 지표로만 쓴다.
