## 1. 공통 규약

- **기본 경로** `/api/v1`. Resource는 복수 명사·kebab-case, JSON 필드는 camelCase, enum은 UPPER_SNAKE_CASE
- **처리 서버** 모든 API는 BE가 처리한다. 화면이 BE 말고 직접 붙는 곳은 면접방(LiveKit) 하나뿐이고, BE가 발급한 입장 토큰(5.4·5.14)으로만 들어간다. AI 서버는 화면에 API를 열지 않는다. 면접 중 화면과 AI 에이전트는 면접방 안에서 메시지를 주고받는다([면접방 메시지](#면접방-메시지-livekit))
- **일시** ISO 8601 오프셋 포함(`2026-10-15T12:00:00+09:00`), **날짜** `YYYY-MM-DD`(한국 시간)
- **인증** `Authorization: Bearer {accessToken}`. 토큰 없이 호출하는 API는 1.1~1.4·1.6·1.7, 8.1(관리자 로그인), 9.1·9.3·9.4·9.5(문의. 비회원도 호출하며, 토큰을 보내면 회원 문의)뿐이다. 관리 API(`/admin/**`, 8.1 제외)는 회원 토큰이 아닌 관리자 토큰(8.1)으로 부른다([8장](#8-관리자--공지--유지권)). 회원은 토큰으로만 식별(본문·경로로 회원 id를 받지 않음). 액세스 토큰은 JWT(HS256)이고 `sub`(회원 id)·`nickname`·`iat`·`exp`를 담는다. 리프레시 토큰은 JWT가 아닌 불투명한 문자열
- 다른 회원의 리소스는 존재 여부를 숨기기 위해 **404**. 탈퇴한 회원의 데이터는 조회되지 않음
- **성공 응답** 래퍼 없이 리소스 그대로. 본문 없는 성공은 204. 페이지 목록은 `{ content, page: { size, number(0부터), totalElements, totalPages } }`. 5.13 연습 면접 목록은 페이지와 무관한 집계를 담는 `summary`를 추가한다
- **실패 응답** RFC 9457 ProblemDetail(`title`·`status`·`detail`·`instance`, `type`은 기본값 `about:blank`라 생략) + `code`. 화면 분기는 `code`로 한다. 400 `VALIDATION_FAILED`는 `errors[{ field, reason }]` 추가. Nginx가 직접 주는 502·504는 본문 형식을 보장하지 않아 상태 코드로 판단한다
- **모든 API 공통 오류** 401 `UNAUTHORIZED`(토큰 없음·위조·탈퇴) · 401 `TOKEN_EXPIRED`(만료 → 토큰 재발급 후 재요청) · 400 `VALIDATION_FAILED` · 500 `INTERNAL_ERROR`(문구 고정 "잠시 후 다시 시도해 주세요.")
- **멱등성** 면접 만들기·시작·답변 제출·끝내기(5.1, 5.4, 5.7, 5.8)는 `Idempotency-Key: {UUID}` 필수. 같은 키·같은 본문 = 처음 결과 반환, 같은 키·다른 본문 = 409 `IDEMPOTENCY_KEY_REUSED`, 헤더 없음 = 400
- **파일** 프로필 사진은 Presigned URL로 브라우저가 S3에 직접 올리고 받는다. 면접 녹화는 서버(LiveKit Egress)가 저장하고, 다시보기는 Presigned URL로 받는다. API로 파일을 보내지 않음
- **상태 확인** WebSocket을 쓰지 않는다. 서버 작업이 끝났는지는 화면이 **2초마다(임시 값, B-11)** API를 다시 불러 확인한다
  - 질문 준비(S05): 5.2. `planStatus`가 `READY` 또는 `FAILED`가 되면 멈춘다
  - 결과 분석(S06-1): 5.2. `status`가 `COMPLETED` 또는 `FAILED`가 되면 멈춘다
  - 면접 중 다음 질문은 AI 에이전트가 면접방 메시지(`question`)로 알리므로 다시 불러 확인하지 않는다
- **연습 면접** 답변 1개 이상으로 끝난 면접(`ANALYZING`·`COMPLETED`·`FAILED`, `ABORTED` 제외). 스트릭·면접 수·연습 시간은 모두 이 기준
- **MVP 제외(API 없음)**: 비밀번호 찾기, 업적, 연습 알림 메일(카카오톡 알림 2.8~2.11로 대신함), 개발자 콘솔

목 서버는 실제 로직 없이 예시 응답을 돌려준다. 인증·DB는 없고, 경로의 id가 `0`이면 해당 404를 돌려준다(화면 오류 처리 확인용). 회원가입(1.2)은 요청한 닉네임으로, 로그인(1.3)·재발급(1.4)은 예시 회원(id 1, 닉네임 "면접왕")으로 액세스 토큰을 만든다. 토큰을 검사하지는 않는다. 소셜 로그인(1.6)은 `code`로 결과를 고른다(`signup` 가입 필요 · `no-email` 400 · `duplicated` 409 · `invalid` 401 · 그 밖은 로그인). 소셜 회원가입(1.7)은 `signupToken`이 `expired`면 401이다. 소셜 계정 연결(2.12)도 `code`로 결과를 고른다(`invalid` 400 · `already` · `in-use` 409 · `unavailable` 503 · 그 밖은 연결).

### 1. 인증

#### 1.1 이메일 사용 가능 여부

**화면 — S01-1 회원가입 › 이메일 입력 즉시 검사**

탈퇴하지 않은 회원 중 같은 이메일이 없으면 사용 가능하다. 탈퇴한 회원이 쓰던 이메일은 다시 쓸 수 있다. 이메일은 대소문자를 구분하지 않는다(가입·로그인·1.1 모두 같음).

- **200**: 항상. 사용 중이면 `available: false`(오류 아님)

#### 1.2 회원가입

**화면 — S01-1 회원가입 › [가입하고 시작하기]**

회원을 만들고 필수 약관 3개 동의를 기록한 뒤 로그인 토큰을 준다. 화면은 S02-D(첫 방문 홈)로 간다.

필수 약관은 `TERMS`(이용약관) · `PRIVACY`(개인정보 수집·이용) · `RECORDING`(면접 녹화·음성 이용) 3개다. `agreements`에 3개를 모두 보내며, 버전은 화면에 보여 준 약관 버전이다.

- **201**: 가입 완료. 로그인 상태
- **400 / AGREEMENT_REQUIRED**: 약관 3개 중 하나라도 없음. 가입하지 않음
- **400 / VALIDATION_FAILED**: 이메일·비밀번호·닉네임 조건 불일치, `agreements`가 3개가 아님. 칸마다 `errors`
- **409 / EMAIL_DUPLICATED**: 사용 중인 이메일(1.1 이후 다른 사람이 먼저 가입한 경우 포함)

#### 1.3 로그인

**화면 — S01 로그인 › [로그인]** → S02 홈(하루 첫 진입이면 S02-1)

여러 기기의 동시 로그인을 허용하며, 새 로그인은 다른 기기의 리프레시 토큰을 폐기하지 않는다.

자동 로그인 유지(스트릭 유지 목적)를 위해 리프레시 토큰 유효 기간을 길게 둔다(값은 BE 결정). 비밀번호 찾기는 MVP 제외.

- **200**: 이메일·비밀번호 일치
- **401 / LOGIN_FAILED**: 이메일 없음·비밀번호 틀림·탈퇴 회원·소셜 회원(비밀번호 없음). 구분 없이 같은 문구

#### 1.4 토큰 재발급

**화면 — 공통. 액세스 토큰 만료 시**

새 액세스·리프레시 토큰을 준다. 쓴 리프레시 토큰만 폐기되며 다른 기기의 토큰은 유지된다.

- **200**: 유효한 리프레시 토큰
- **401 / REFRESH_TOKEN_INVALID**: 만료·재사용·로그아웃·탈퇴로 폐기됨. 화면은 S01로

#### 1.5 로그아웃

**화면 — C01 프로필 메뉴, S09-1 설정** → 확인 없이 S00

- **204**: 인증한 회원이 제출한 리프레시 토큰만 폐기한다. 다른 기기의 토큰은 유지한다. 이미 폐기된 토큰이어도 204. 발급된 액세스 토큰은 만료 전까지 유지된다.

#### 1.6 소셜 로그인

**화면 — S01 로그인 · S01-1 회원가입 › [카카오로 시작하기] · [구글로 시작하기]** → 제공자 로그인 → 화면의 콜백 주소

화면이 제공자 로그인 화면으로 보내고, 제공자가 콜백 주소(`redirectUri`)로 넘겨 준 인가 코드(`code`)를 이 API로 보낸다. `provider`는 `kakao` · `google`이다. 구글은 `openid email profile` 범위(scope)를 요청한다. 콜백 주소는 `/oauth/{provider}/callback`(예: `https://hangguet.co.kr/oauth/google/callback`)이고, 제공자 앱과 BE 설정(`*_REDIRECT_URIS`)에 등록한 주소와 글자까지 같아야 한다. 로그인 전에 여는 화면이다. 로그인 위조(CSRF)를 막는 `state` 값은 화면이 만들고 콜백에서 확인한다(BE는 받지 않음).

BE는 인가 코드로 제공자 회원 정보(회원 번호·이메일·닉네임)를 읽고, 제공자 회원 번호로 연결된 회원을 찾는다. 이메일 회원이 연결한 카카오 계정(2.12)도 여기서 찾으므로 이메일이 달라도 그 회원으로 로그인한다.

- 연결된 회원이 있으면 `signupRequired: false`와 로그인 토큰(`token`, 1.3과 같은 형식)을 준다. 화면은 S02로 간다
- 처음 온 사람이면 `signupRequired: true`와 가입 정보(`signup`: 가입 토큰·이메일·닉네임·유효 시간)를 준다. 화면은 약관 동의를 받아 1.7로 가입한다. 인가 코드는 한 번만 쓸 수 있어 가입 토큰으로 이어 간다(10분, 가입에 성공하면 지움)

이메일은 제공자가 확인한 것만 쓴다. 같은 이메일로 가입한 회원(이메일 회원·다른 소셜 회원)이 있으면 계정을 합치지 않고 409로 막는다. 이메일 회원은 로그인한 뒤 2.12로 직접 연결한다. 소셜 회원은 비밀번호가 없어 1.3 로그인·2.3 비밀번호 변경을 쓸 수 없다. 닉네임은 제공자 닉네임(50자까지)이고 없으면 "면접러"다. 가입 뒤 2.2로 바꾼다.

- **200**: 로그인(`token`) 또는 가입 필요(`signup`)
- **400 / SOCIAL_EMAIL_REQUIRED**: 처음 온 사람이 확인된 이메일 제공에 동의하지 않음
- **400 / VALIDATION_FAILED**: 지원하지 않는 `provider`, 등록하지 않은 `redirectUri`
- **401 / SOCIAL_LOGIN_FAILED**: 쓸 수 없는 인가 코드(잘못됨·만료·이미 씀·`redirectUri` 불일치). 화면은 처음부터 다시 로그인
- **409 / SOCIAL_EMAIL_DUPLICATED**: 같은 이메일로 가입한 회원이 있음. 처음 가입한 방법으로 로그인하라고 안내
- **503 / SOCIAL_LOGIN_UNAVAILABLE**: 제공자 서버 오류·시간 초과(5초), 서버의 제공자 키 설정 오류

#### 1.7 소셜 회원가입

**화면 — S01-1 회원가입 › 소셜 로그인 뒤 약관 동의 › [가입하고 시작하기]** → S02-D

1.6에서 받은 가입 토큰과 필수 약관 3개 동의(1.2와 같음)로 비밀번호 없는 회원을 만들고 로그인 토큰을 준다. 가입에 성공하면 가입 토큰은 지운다. 가입하지 못했으면(400·409·500) 가입 토큰이 남아 있어 같은 토큰으로 다시 보낼 수 있다. 같은 소셜 계정이 그 사이 먼저 가입했으면(같은 토큰을 겹쳐 보낸 경우 포함) 회원을 새로 만들지 않고 그 회원으로 로그인한다.

- **201**: 가입 완료. 로그인 상태
- **400 / AGREEMENT_REQUIRED**: 약관 3개 중 하나라도 없음
- **401 / SIGNUP_TOKEN_INVALID**: 가입 토큰이 없거나 만료됐거나 가입에 이미 씀. 화면은 1.6부터 다시(이미 가입했으면 1.6이 바로 로그인한다)
- **409 / SOCIAL_EMAIL_DUPLICATED**: 그 사이 같은 이메일로 가입한 회원이 생김

### 2. 회원

#### 2.1 내 정보

**화면 — C01 헤더, S09 상단, S09-1 계정**

`socialProvider`는 소셜 회원이면 가입한 제공자(`KAKAO` · `GOOGLE`), 이메일 회원이면 `null`이다. 소셜 회원이면 S09-1에서 비밀번호 변경을 숨기고 탈퇴 때 비밀번호를 묻지 않는다.

`linkedProvider`는 이메일 회원이 연결한 소셜 계정(2.12, 지금은 `KAKAO`만)이고, 연결하지 않았거나 소셜 회원이면 `null`이다. 이메일 회원은 이 값으로 S09-1의 [카카오 연결하기] · [연결 해제]를 고른다.

- **200**: 항상

#### 2.2 닉네임 변경

**화면 — S09-1 설정 › 닉네임**

액세스 토큰의 `nickname`이 바뀐 값이 되도록 새 액세스 토큰을 함께 준다. 화면은 받은 `accessToken`으로 저장된 액세스 토큰을 바꾸고, 리프레시 토큰은 그대로 쓴다. 다른 기기의 액세스 토큰은 만료 전까지 예전 닉네임을 담고 있다가, 다음 재발급(1.4) 때 바뀐 값이 된다.

- **200**: 변경(같은 값이어도 200). 응답은 2.1에 `accessToken`·`expiresIn`(1.3과 같은 형식)을 더한 것

#### 2.3 비밀번호 변경

**화면 — S09-1 설정 › 비밀번호 변경**

이 기기는 로그인을 유지하고 다른 기기는 모두 로그아웃한다. 변경 기록을 남기고 그 회원의 리프레시 토큰을 모두 폐기한 뒤, 이 기기에 새 액세스·리프레시 토큰을 준다(1.4 응답과 같은 형식). 바꾸기 전에 받은 리프레시 토큰은 이 기기 것도 쓸 수 없으므로 화면은 응답의 토큰으로 바꿔 저장한다. 다른 기기에 이미 발급된 액세스 토큰은 1.5와 같이 만료 전까지 유지된다.

- **200**: 변경. `accessToken`·`refreshToken`·`expiresIn`
- **400 / PASSWORD_MISMATCH**: 현재 비밀번호 틀림
- **409 / PASSWORD_NOT_SET**: 비밀번호가 없는 소셜 회원

#### 2.4 프로필 사진 업로드 주소

**화면 — S09-1 설정 › [사진 변경]** → 받은 주소로 `PUT` 후 2.5

- **200**: 발급
- **400 / VALIDATION_FAILED**: JPG·PNG가 아니거나 5MB 초과

#### 2.5 프로필 사진 등록

**화면 — S09-1 설정 › 업로드 완료 직후**

- **200**: 등록. 응답은 2.1과 같음
- **400 / VALIDATION_FAILED**: 본인에게 발급된 키가 아님
- **404 / FILE_NOT_FOUND**: S3에 파일 없음

#### 2.6 프로필 사진 삭제

**화면 — S09-1 설정 › [삭제]**

- **204**: 삭제(이미 없어도 204)

#### 2.7 회원 탈퇴

**화면 — S09-1 설정 › 회원 탈퇴 › 확인 모달**

탈퇴 처리하고 모든 토큰을 폐기한다. 되돌릴 수 없고, 이메일·소셜 계정은 재가입에 쓸 수 있다. 이메일 회원은 `password`가 필수이고, 소셜 회원은 보내지 않는다(2.1 `socialProvider`). 탈퇴는 soft delete로, 회원 정보와 지원서·면접 기록·파일은 지우지 않고 남기되 조회되지 않는다. 연습 알림(2.8)은 저장한 카카오 토큰과 함께 바로 지운다. 최종 파기 시점은 B-6.

- **204**: 탈퇴
- **400 / PASSWORD_MISMATCH**: 비밀번호 틀림
- **400 / VALIDATION_FAILED**: 이메일 회원이 `password`를 보내지 않음

#### 2.8 연습 알림 설정

**화면 — S09-1 설정 › 알림**

카카오톡 연습 알림. 켜 두면 고른 시각(한국 시간, 분 단위)에 그날 연습하지 않았을 때 카카오톡 "나와의 채팅"으로 알린다. 카카오 계정이 연결된 회원(카카오로 가입했거나 2.12로 연결한 이메일 회원)만 받을 수 있다(`available`). 그 밖의 회원은 `available: false`이며, 이메일 회원에게는 2.12 연결을 안내한다.

- **200**: `{ available, enabled, time }`. `time`은 `HH:mm`이고 고르지 않았으면 `21:00`

#### 2.9 연습 알림 켜기

**화면 — S09-1 설정 › 알림 켜기** → 카카오 동의 화면 → 카카오 콜백 주소

화면이 카카오 인가 요청에 `scope=talk_message`를 붙여 "카카오톡 메시지 전송" 동의를 받고, 콜백 주소(1.6과 같은 `/oauth/kakao/callback`)로 받은 인가 코드(`code`)를 이 API로 보낸다. 로그인 콜백과 구분하는 값은 화면이 `state`에 담는다(BE는 받지 않음). BE는 연결된 카카오 계정과 같은지, 메시지 전송에 동의했는지 확인한 뒤 카카오 토큰을 암호화해 저장한다. 이미 켜져 있으면 새 토큰으로 바꾼다.

- **200**: 켜짐. 응답은 2.8과 같음
- **400 / KAKAO_CONSENT_FAILED**: 쓸 수 없는 인가 코드(이미 썼거나 만료, `redirectUri` 불일치)
- **400 / KAKAO_ACCOUNT_MISMATCH**: 연결된 카카오 계정과 다른 계정으로 동의함
- **400 / KAKAO_MESSAGE_CONSENT_REQUIRED**: 메시지 전송에 동의하지 않음
- **400 / VALIDATION_FAILED**: 등록되지 않은 `redirectUri`
- **409 / PRACTICE_ALARM_UNAVAILABLE**: 카카오 계정이 연결되지 않음
- **503 / KAKAO_UNAVAILABLE**: 카카오 키가 없거나 카카오 서버 오류 · 시간 초과

#### 2.10 연습 알림 시각 변경

**화면 — S09-1 설정 › 알림 시간**

`time`은 `HH:mm`(00:00~23:59). 꺼져 있어도 저장해 두고 켤 때 쓴다. 다시 동의하지 않아도 된다. 오늘 알림을 아직 받지 않았으면 오늘부터 바꾼 시각에 보낸다. 방금 지난 시각(10분 안)으로 바꾸면 곧 보낸다.

- **200**: 변경. 응답은 2.8과 같음
- **409 / PRACTICE_ALARM_UNAVAILABLE**: 카카오 계정이 연결되지 않음

#### 2.11 연습 알림 끄기

**화면 — S09-1 설정 › 알림 끄기**

저장한 카카오 토큰을 지운다. 알림 시각은 남는다. 카카오 쪽 동의는 그대로이며 회원이 카카오 계정 설정에서 철회할 수 있다.

- **204**: 꺼짐(이미 꺼져 있어도 204)

#### 2.12 소셜 계정 연결

**화면 — S09-1 설정 › [카카오 연결하기]** → 카카오 로그인 → 카카오 콜백 주소

이메일 회원이 카카오 계정을 연결한다. `provider`는 `kakao`만 받는다. 화면이 카카오 로그인(1.6)과 같은 인가 요청으로 받은 `code`와 `redirectUri`를 보낸다. 로그인 콜백과 구분하는 값은 화면이 `state`에 담는다(BE는 받지 않음). 이메일이 달라도 연결한다(로그인한 본인이 카카오 로그인까지 했으므로). 연결하면 1.6으로도 같은 회원에 들어가고, 연습 알림(2.9)을 켤 수 있다. 회원마다 소셜 계정은 하나만 연결한다.

- **200**: 연결. 응답은 2.1과 같음(`linkedProvider: "KAKAO"`)
- **400 / SOCIAL_LINK_FAILED**: 쓸 수 없는 인가 코드(이미 썼거나 만료, `redirectUri` 불일치)
- **400 / VALIDATION_FAILED**: `kakao`가 아닌 `provider`, 등록되지 않은 `redirectUri`
- **409 / SOCIAL_ALREADY_LINKED**: 소셜 회원이거나 이미 연결함. 카카오를 부르기 전에 확인한다
- **409 / SOCIAL_ACCOUNT_IN_USE**: 그 카카오 계정을 다른 회원이 쓰고 있음(카카오로 가입했거나 연결함)
- **503 / SOCIAL_LOGIN_UNAVAILABLE**: 카카오 키가 없거나 카카오 서버 오류 · 시간 초과

#### 2.13 소셜 계정 연결 해제

**화면 — S09-1 설정 › [연결 해제]**

연결을 지운다. 이후 그 카카오 계정으로는 로그인할 수 없고(1.6은 가입 안내), 켜져 있던 연습 알림은 꺼진다(시각은 남음). 카카오 쪽 앱 연결은 그대로이며 회원이 카카오 계정 설정에서 끊을 수 있다.

- **204**: 해제(연결하지 않았어도 204)
- **400 / VALIDATION_FAILED**: `kakao`가 아닌 `provider`
- **409 / PASSWORD_NOT_SET**: 소셜 회원(끊으면 로그인할 방법이 없음)

### 3. 홈 · 스트릭

**스트릭 규칙**: 연습 면접 = 답변 1개 이상으로 끝난 면접(`ANALYZING`·`COMPLETED`·`FAILED`, `ABORTED` 제외). 연습한 날 = 연습 면접의 한국 시간 시작 날짜. 자정을 넘겨 끝나도 시작한 날에만 인정하며, 종료 전에는 인정하지 않는다. 스트릭 = 오늘(또는 어제)까지 빠짐없이 이어진 연습일 수, 하루라도 빠지면 0. 스트릭은 연습 면접을 끝낸 순간(5.8) 오른다. 뱃지 구간 0 / 1–2 / 3–5 / 6–7 / 8–13 / 14+일(1·3·6·8·14일째에 다음 구간으로 레벨업).

#### 3.1 홈

**화면 — S02 · S02-B · S02-C · S02-D, S02-1 인트로**

홈 한 장에 필요한 값을 한 번에 준다. 오늘 횟수·시간·성장과 연습 날짜는 한국 시간 시작일 기준이다. 어떤 홈을 그릴지는 `homeState`로 정한다. 자정까지 남은 시간, 인트로 하루 1회 노출은 화면이 처리한다.

- **200**: 항상. 기록이 없으면 `FIRST_VISIT`, 숫자 0, 배열 빈 배열

#### 3.2 통계

**화면 — S09 마이페이지 › 통계 타일, 이름 아래 직무**

연습일·기간별 횟수·시간은 한국 시간 면접 시작일로 집계한다. 자정을 넘긴 면접의 전체 시간은 시작 날짜에 포함한다.

- **200**: 항상. 기록이 없으면 0·null

#### 3.3 연습 달력

**화면 — S09 마이페이지 › 스트릭 달력, 연습 기록(`/records`) › 날짜 탐색 달력**. S09 날짜 클릭은 7.1, 연습 기록의 날짜 선택은 5.13을 조회한다.

`month`는 필수(`YYYY-MM`)다. 마이페이지 달력·스트릭·연습 기록·홈 통계·성장 리뷰의 날짜를 모두 한국 시간 면접 시작일로 통일한다. 같은 시작 날짜로 묶어 하루당 1건을 반환한다. 답변 1개 이상인 면접을 끝낸 뒤 시작 날짜에 연습을 인정한다. 날짜 기준을 고르는 쿼리는 제공하지 않는다.

"이번 달 10일 연습"은 `content` 개수, "지금 7일 연속"은 3.2 `currentStreak`, 연속일 띠는 날짜가 이어지는지로 화면이 그린다.

- **200**: 항상. 없으면 빈 배열
- **400 / VALIDATION_FAILED**: `month` 형식 오류

### 4. 지원서

지원서 수정 API는 없다. 고칠 내용이 있으면 새 지원서를 쓴다.

#### 4.1 지원서 작성

**화면 — 지원서 쓰기 › [저장하기](지원 관리 [+ 지원서 쓰기] · S03 [+ 추가하기]로 들어온다)**

지원서를 저장해 두고 여러 면접에 다시 쓴다(S03에서 저장된 지원서 중 고른다). 자기소개서는 문항 단위(`coverLetterItems`)로 받으며 질문 생성과 "자소서 검증" 평가에 쓴다.

- 문항은 1~5개, 문항 질문 1~255자, 답변 1~20,000자다. 보낸 순서가 문항 순서(`itemOrder`, 1부터)다
- 저장하기 전에 AI가 자기소개서로 면접 질문을 만들 수 있는지 판단한다(AI 명세 2.1). 의미 없는 글이거나 질문을 만들 만큼 내용이 없으면 저장하지 않는다. 면접방에 들어간 뒤 질문 생성이 실패하지 않게 하기 위해서다. 판단에 몇 초 걸릴 수 있다

- **201**: 저장
- **400 / VALIDATION_FAILED**: 종류별 `errors[].field`는 아래와 같다
  - 문항 수: `coverLetterItems`("1~5개입니다.". 빠졌거나 `null`이면 "필수 값입니다.")
  - 문항 원소가 `null`: `coverLetterItems[i]`(i는 0부터)
  - 문항 칸(빠짐 · 빈 값 · 길이): `coverLetterItems[i].question` · `coverLetterItems[i].answer`
  - 질문을 만들기 어려운 자기소개서: `coverLetterItems`(판단 문구). 화면은 자기소개서 아래에 문구를 보여 주고 저장하지 않는다
- **503 / COVER_LETTER_CHECK_UNAVAILABLE**: 판단하지 못함(AI·Jev 장애, 시간 초과). 저장하지 않으며 화면은 다시 시도하게 안내한다

#### 4.2 지원서 조회

**화면 — 지원 관리 상세, S04·S05-1 상단 "○○전자 · 백엔드 개발자"**

자기소개서 문항을 `itemOrder` 순으로 준다.

- **200**: 본인 지원서
- **404 / APPLICATION_NOT_FOUND**: 없거나 남의 지원서 · 지운 지원서

#### 4.3 지원서 목록

**화면 — 지원 관리 목록, S03 저장된 지원서 고르기**

최근 작성 순. 목록에는 자기소개서 문항을 넣지 않는다(상세는 4.2). 쿼리는 `page`(0부터, 기본 0) · `size`(1~20, 기본 10)이다.

- **200**: 항상. 없으면 빈 `content`. 범위를 넘는 페이지도 빈 `content`와 실제 전체 건수

#### 4.5 지원서 삭제

**화면 — 지원 관리 상세 › [삭제] › 삭제 확인**

지원서를 지운다. 행과 문항 원문은 남긴다(soft delete, 파기 시점 B-6). 면접에 쓴 지원서도 지울 수 있고, 그 지원서로 본 면접 기록 · 결과 · 다시보기(5.13 · 6.3 · 6.4)는 남는다. 지운 지원서는 4.2 · 4.3 · 4.6 · 5.1에서 없는 지원서로 다룬다.

- **204**: 삭제
- **404 / APPLICATION_NOT_FOUND**: 없거나 남의 지원서 · 이미 지운 지원서

#### 4.6 지원서의 연습 면접 목록

**화면 — 지원 관리 상세 › 면접 기록**

이 지원서로 본 연습 면접을 시작 시각·id 내림차순으로 준다. 5.13과 같이 본인의 답변 1개 이상인 `ANALYZING`·`COMPLETED`·`FAILED`만 포함하고, 항목 모양도 5.13과 같다. 쿼리는 `page`(0부터, 기본 0) · `size`(1~20, 기본 10)이고 응답은 4.3과 같은 페이지 형식이다.

- **200**: 항상. 면접이 없으면 빈 `content`. 범위를 넘는 페이지도 빈 `content`와 실제 전체 건수
- **400 / VALIDATION_FAILED**: 음수 페이지·`size` 범위 오류
- **404 / APPLICATION_NOT_FOUND**: 없거나 남의 지원서 · 지운 지원서
- **500 / INTERNAL_ERROR**: 5.13과 같다. 완료 상태인데 기준별 평가 4개가 모두 저장되지 않은 경우. 불완전한 결과를 정상 평가로 표시하지 않는다

### 5. 면접 진행

**면접 상태** `READY` → (시작) `IN_PROGRESS` → (끝내기, 답변 ≥1) `ANALYZING` → `COMPLETED` / `FAILED`(결과 재생성으로 `ANALYZING`). 답변 0개로 끝내면 `ABORTED`. 시작 뒤 에이전트가 배정을 거절하면(동시 면접 상한 초과·배정 정보 형식 오류) `START_FAILED`이고, 다시 시작(5.4)하면 같은 질문으로 `IN_PROGRESS`가 된다. `START_FAILED`는 연습 면접이 아니다(스트릭·목록·달력에 들어가지 않음).

**면접 플랜 상태** `planStatus`: `GENERATING` · `READY` · `FAILED`. **분석 단계** `analysisStep`: `ORGANIZING_ANSWERS` → `SCORING` → `WRITING_FEEDBACK`.

#### 5.1 면접 만들기

**화면 — S05-1 면접 방식 › [다음: 장치 점검](화상) · [면접 시작](채팅)**

면접을 만들고 면접 플랜(질문·평가 기준) 생성을 시작한다(사용자에게 비노출). 완료는 5.2를 2초마다(임시 값) 불러 `planStatus`로 확인한다(1장 상태 확인).

- **201**: 생성(`status: READY`, `planStatus: GENERATING`)
- **404 / APPLICATION_NOT_FOUND**: 없거나 남의 지원서 · 지운 지원서
- **409 / IDEMPOTENCY_KEY_REUSED**: 같은 키로 다른 본문

#### 5.2 면접 조회

**화면 — S05 [면접 시작] 활성화, S06·S06-B 상단, S06-F 재연결 복구, S06-1 진행**

질문 준비(`planStatus`·`planProgress`)와 결과 분석(`status`·`analysisStep`)이 끝났는지 이 API를 2초마다(임시 값) 불러 확인한다(1장 상태 확인). 새로고침·재연결 때도 이 응답으로 화면을 다시 그린다. "질문 3 / 5"의 전체 질문 수는 5개로 고정이다. `leveledUp`은 5.8 응답에만 값이 있고, 이 API에서는 항상 null이다.

- **200**: 본인 면접
- **404 / SESSION_NOT_FOUND**: 없거나 남의 면접

#### 5.3 면접 플랜 재생성

**화면 — S05 장치 점검 › 생성 실패 › [다시 시도]**

- **202**: 재생성 시작. 5.2 형식(`planStatus: GENERATING`)
- **404 / SESSION_NOT_FOUND**
- **409 / PLAN_NOT_FAILED**: `planStatus`가 `FAILED`가 아님

#### 5.4 면접 시작

**화면 — S05 [면접 시작](화상), S05-1 [면접 시작](채팅)**

면접을 시작하고 면접방(LiveKit)을 연다. BE는 이 요청을 처리하며 다음을 한다.

- 면접방 입장 정보(`room`: 주소·토큰·만료 시각, 5.14와 같은 형식)를 응답에 담는다. 화면은 이 값으로 면접방에 접속한다
- AI 에이전트를 면접방에 배정한다. 미리 만든 질문 5개와 채점 기준을 배정 정보로 넘긴다. 2·4·5번은 직전 답변으로 생성한 꼬리질문으로 대체될 수 있다([AI 명세](AI-명세.md) 2.2)
- 화상이면 서버 녹화(LiveKit Egress)를 시작한다. 채팅은 녹화하지 않는다
- 질문은 AI 에이전트가 면접방에서 말하고, 글은 면접방 메시지 `question`으로 보낸다. 화면은 질문 음성을 따로 받지 않는다

채팅은 장치 점검 없이 5.1 직후 S06-B로 바로 넘어간다. 면접관을 띄워 둔 채 5.2에서 `planStatus: READY`를 받으면 화면이 이 API를 자동으로 부른다. 별도 대기 화면은 없다. 채팅도 면접방에 들어가며, 마이크·카메라 없이 면접관 음성만 받는다.

- **200**: 시작. 5.2 형식(`status: IN_PROGRESS`) + `room`. `currentQuestion`은 null이다. 질문은 에이전트가 말할 때 생기고 면접방 메시지 `question`으로 온다 **[결정]**
- **404 / SESSION_NOT_FOUND**
- **409 / PLAN_NOT_READY**: 플랜 생성 중이거나 실패
- **409 / INVALID_SESSION_STATE**: `READY`·`START_FAILED`가 아님
- **503 / ROOM_UNAVAILABLE**: 면접방 만들기·에이전트 배정·녹화 설정이 실패함. 면접은 이전 상태(`READY`·`START_FAILED`) 그대로라 화면은 다시 시도한다 **[결정]**
- 배정 요청은 에이전트가 수락하기 전에 성공하므로, 에이전트의 배정 거절(동시 면접 상한 초과·배정 정보 형식 오류)은 5.4 응답으로 알 수 없다. 거절하면 BE가 면접방을 닫고 면접을 `START_FAILED`로 변경한다([AI 명세](AI-명세.md) 1.4). 화면은 면접방 연결이 끊기면 5.2로 상태를 확인하고, `START_FAILED`면 면접관을 연결하지 못했다고 안내한 뒤 5.4로 다시 시작한다

#### 5.5 지금 질문

**화면 — S06·S06-B 새로고침·재접속 후 질문 말풍선 복구**

지금 답할 질문을 준다. 면접 중 다음 질문은 AI 에이전트가 면접방 메시지 `question`으로 알리므로, 이 API는 새로고침·재접속으로 화면을 다시 그릴 때만 부른다.

- **200**: 답할 질문 있음
- **202 / QUESTION_GENERATING**: 아직 질문이 없음(에이전트가 다음 질문을 말하기 전, 시작 직후 포함). 질문 행은 에이전트가 질문을 말하기 시작할 때 생기므로 꼬리질문을 생성하는 동안에도 "아직 내지 않음"이다 **[결정]**
- **404 / SESSION_NOT_FOUND**
- **409 / INVALID_SESSION_STATE**: `IN_PROGRESS`가 아니거나 5개 질문에 모두 답함(더 낼 질문이 없다)

#### 5.7 답변 제출(채팅)

**화면 — S06-B [보내기]**

채팅 면접의 답변 글을 낸다. 질문 하나에 답변 하나만 낼 수 있다. 화면은 202 또는 409 `ANSWER_ALREADY_SUBMITTED`를 받으면 면접방 메시지 `answer.submit`을 전송하고, 다음 질문은 AI 에이전트가 면접방 메시지 `question`으로 알린다. 답변별 채점은 제출 직후 시작하고, 결과(6.3)는 면접 종료 후 확정된다.

**화상 답변은 이 API를 쓰지 않는다.** AI 에이전트가 면접방에서 음성을 듣고 답변 끝을 판단해([면접방 메시지](#면접방-메시지-livekit)), 인식한 글·말한 시각을 Redis 결과 큐로 BE에 보낸다. BE는 이 API와 같은 규칙(질문 하나에 답변 하나)으로 저장한다. 메시지 형식은 [AI 명세](AI-명세.md) **[제안]**.

- **202**: 접수
- **400 / VALIDATION_FAILED**: `content` 비었거나 1,000자 초과, `inputType`이 `TEXT`가 아님(화상 면접에서 부름)
- **404 / SESSION_NOT_FOUND** · **QUESTION_NOT_FOUND**(질문이 경로의 면접에 속하지 않거나 아직 내지 않은 질문)
- **409 / ANSWER_ALREADY_SUBMITTED**: 이미 답변함(다른 키로 재전송)
- **409 / INVALID_SESSION_STATE**: `IN_PROGRESS`가 아님

#### 5.8 면접 끝내기

**화면 — 마지막 답변 후 자동, S06-E [끝내기], S06-F [면접 끝내기]**

본문은 선택이다. 답변 1개 이상이면 결과 생성을 시작하고 그날 연습으로 인정한다. 0개면 결과·연습 인정 없이 끝난다.

**시선 비율** 화상 면접이면 화면이 면접 내내 브라우저에서 잰 시선 비율을 본문 `gazeRatio`(면접 동안 면접관을 바라본 시간 비율, %, 0~100)로 보낸다. 재지 못했거나 채팅이면 보내지 않는다. BE는 결과가 나오는 화상 면접(답변 ≥1)일 때만 소수 둘째 자리로 맞춰 6.3 `speechMetrics.gazeRatio`로 남기고, 그 밖에는 버린다. 같은 멱등 키로 다시 보낼 때는 처음과 같은 값을 보낸다(본문이 다르면 409 `IDEMPOTENCY_KEY_REUSED`).

```json
{ "gazeRatio": 72.5 }
```

BE는 면접방을 닫아 AI 에이전트를 내보내고, 화상이면 녹화를 멈춘 뒤 녹화 합치기 작업을 큐에 넣는다. 진행 중이던(아직 끝나지 않은) 답변은 저장하지 않는다.

**직전 답변 저장 확인** 화상 답변은 에이전트 → Redis 결과 큐 → BE 순서로 저장되므로, 면접방 메시지 `answer.state`(`submitted`)를 수신한 시점에는 BE에 아직 저장되지 않았을 수 있다. 저장 전에 5.8을 호출하면 그 답변은 답변 수에서 제외되고 폐기된다. 화면은 `submitted`를 수신한 뒤 5.2를 2초마다(임시 값, B-11) 호출해 `answeredCount`가 그 답변의 `seq` 이상이 되면 5.8을 호출한다. 기다리는 동안 답변을 저장하는 중임을 안내한다. 10초(임시 값)가 지나도 반영되지 않으면 결과 큐 전송 실패 등으로 보고 그대로 5.8을 호출한다. 5번 답변 후 자동 종료와 [끝내기]에 같이 적용한다. 채팅은 5.7 응답으로 저장을 확인하므로 기다리지 않는다.

**레벨업** `leveledUp`: 이번 면접으로 스트릭이 올라 뱃지 구간이 바뀌었으면 true다. 그날 첫 연습 면접이고 스트릭이 1·3·6·8·14일이 된 경우다. 같은 날 두 번째 면접, 답변 0개로 끝낸 면접은 false. 면접 끝내기는 면접마다 한 번만 호출되므로 레벨업도 한 번만 온다. 화면은 이 값을 기억해 뒀다가 결과 분석이 끝난 뒤 S08에서 레벨업(S02-L)을 띄운다.

- **202**: 답변 ≥1. 5.2 형식(`status: ANALYZING`). 완료는 5.2를 2초마다(임시 값) 불러 확인
- **200**: 답변 0. 5.2 형식(`status: ABORTED`). 화면은 홈으로
- **400 / VALIDATION_FAILED**: `gazeRatio`가 0~100이 아님
- **404 / SESSION_NOT_FOUND**
- **409 / INVALID_SESSION_STATE**: `IN_PROGRESS`가 아님

#### 5.9 결과 재생성

**화면 — S06-1 › 실패 › [다시 시도]**

- **202**: 재생성 시작. 5.2 형식(`status: ANALYZING`)
- **404 / SESSION_NOT_FOUND**
- **409 / INVALID_SESSION_STATE**: `FAILED`가 아님

#### 5.13 연습 면접 목록

**화면 — 연습 기록(`/records`) › 달력 날짜 선택 › 면접별 카드**

쿼리 `practiceDate`는 필수(`YYYY-MM-DD`). 한국 시간의 면접 **시작일**로 조회한다. `page`는 0부터(기본 0), `size`는 1~20(기본 5)이다. 본인의 답변 1개 이상인 연습 면접(`ANALYZING`·`COMPLETED`·`FAILED`)만 포함하고 `startedAt` 내림차순, 같은 시각이면 `id` 내림차순으로 준다. `READY`·`IN_PROGRESS`·`ABORTED`는 포함하지 않는다. 21일 23:50 시작·22일 00:10 종료 면접은 21일 목록에만 들어간다.

- `content`: 면접별 `id`, 회사·직무, 면접관(`persona`), 방식(`mode`), 상태(`status`), 시작·종료 시각, 답변 수(`answeredCount`), 한 줄 총평(`summary`), 기준별 등급(`criterionGrades[{ criterion, grade }]`). 질문별 답변·상세 피드백·말하기 지표·영상 주소는 넣지 않는다
- `content[].summary`: 6.3 결과의 한 줄 총평(30자 이내)과 같다. `COMPLETED`라도 총평이 없으면 null이고, 화면은 그 문장 영역을 숨긴다
- `criterionGrades`: `COMPLETED` 면접의 6.3 `sessionScores`에서 기준·등급만 가져온다. 화면은 점수 대신 좋아요·보통·아쉬워요로 표시한다. `ANALYZING`·`FAILED`는 총평 null·등급 빈 배열이며 상태 안내만 표시한다
- `page.totalElements`: 선택 날짜의 전체 연습 면접 수. 페이지를 바꿔도 같다
- 최상위 `summary.totalInterviewCount`: 날짜 필터와 무관한 본인의 전체 연습 면접 수. 상단 보관함 건수에 쓴다
- 최상위 `summary.practiceMinutes`: 선택 날짜 **전체** 연습 시간(분). Σ(`endedAt − startedAt`)의 초 합을 60으로 나눠 소수점 아래를 버린다. 연결이 끊겨 멈춘 시간도 포함하며, 5.2의 `elapsedSeconds`와 의미가 다르다. 페이지를 바꿔도 같다

화면 연결 시 한국 시간 오늘을 선택하고 5.15 월별 횟수 달력·5.13 목록을 조회한다. 카드별로 6.3을 미리 호출하지 않는다. [상세 피드백]은 `id`로 6.3, [다시보기]는 6.4를 조회하는 화면으로 연결한다. 성장 리뷰(7.1)도 동일한 시작일 기준이다. 분석 중·실패 기록만 있고 완료 결과가 없는 시작 날짜는 성장 리뷰가 없을 수 있다(7.1의 404).

- **200**: 항상. 기록 없는 날짜는 빈 `content`, `page.totalElements: 0`, `page.totalPages: 0`, `summary.practiceMinutes: 0`. 전체 보관함 건수는 유지한다. 범위를 넘는 페이지도 빈 `content`와 실제 전체 건수·집계를 준다
- **400 / VALIDATION_FAILED**: 날짜 누락·잘못된 날짜(0001-01-01~9999-12-31 밖 포함)·음수 페이지·`size` 범위 오류
- **500 / INTERNAL_ERROR**: 완료 상태인데 기준별 평가 4개가 모두 저장되지 않은 경우. 불완전한 결과를 정상 평가로 표시하지 않는다

목 서버는 `2026-10-21`에 자정을 넘겨 종료한 완료 면접·분석 중 예시, `2026-10-20`에 실패·총평 없는 완료 예시를 준다. 그 외 날짜는 빈 목록이며, 전체 보관함 건수는 4다. 3.3도 시작일 기준으로 20·21일만 표시한다.

#### 5.15 월별 연습 면접 횟수

`GET /api/v1/interview-sessions/calendar?month=2026-10`

`month`는 필수이며 `YYYY-MM` 형식(0001-01~9999-12)이다. 로그인한 본인의 연습 면접을 한국 시간 **시작일**로 집계한다. 5.13과 동일하게 답변 1개 이상인 `ANALYZING`·`COMPLETED`·`FAILED`만 포함한다. 면접 방식은 화상·채팅 모두 포함한다.

- **200**: `{ "month": "2026-10", "content": [{ "practiceDate": "2026-10-01", "interviewCount": 0 }, ...] }`
- `content`에는 해당 월 1일부터 말일까지 모든 날짜를 오름차순으로 담는다. 기록이 없는 날짜도 `interviewCount: 0`으로 포함한다. 빈 달도 빈 배열 대신 28~31개 날짜를 반환한다. 페이지 구분은 없다.
- 한 면접은 답변 수와 무관하게 1회다. 자정을 넘기거나 다음 달에 종료해도 시작 날짜에만 집계한다. `interviewCount`는 동일 날짜 5.13의 `page.totalElements`와 같다.
- **400 / VALIDATION_FAILED**: 월 누락·잘못된 월 형식·월 범위 오류
- **401 / UNAUTHORIZED**: 로그인하지 않음

달력은 월 진입·월 이동 때 이 API를 한 번 호출한다. 날짜·페이지 선택 때는 5.13만 조회한다. 기존 3.3 스트릭 달력 계약은 유지한다. 목 서버의 `2026-10`은 20일 2회·21일 2회, 나머지 날짜 0회다.

#### 면접방 메시지 (LiveKit)

API 번호가 없는, 면접 중 화면과 AI 에이전트가 면접방 안에서 주고받는 메시지다. BE를 거치지 않는다. STT 표시는 LiveKit 텍스트 스트림, 카메라 사진은 LiveKit 바이트 스트림, 나머지 메시지는 LiveKit RPC를 사용한다. 형식은 [AI 명세](AI-명세.md#63-면접방-메시지-형식-제안)를 따른다.

| 메시지 | 방향 | 내용 |
|---|---|---|
| `interview.stt` (텍스트 스트림) | 에이전트 → 화면 | `streamId`, `revision`, `confirmedText`, `interimText`, `state`(`listening`·`failed`). 인식 텍스트 전체를 교체 |
| `question` | 에이전트 → 화면 | 질문 순서(`seq`)·글, 질문 음성 상태(`started`·`ended`·`failed`), 입 모양용 글자별 발음 시각 |
| `reaction` | 에이전트 → 화면 | 면접관 리액션(아래 리액션 값), 말 끊기 |
| `answer.state` | 에이전트 → 화면 | 답변 상태: 자동 제출, 60초 무응답, 음성 인식 재연결·실패, 제출됨, 제출 실패(결과 큐 전송이 재시도 후에도 실패) |
| `answer.submit` | 화면 → 에이전트 | 화상 [답변 완료]. 채팅은 5.7 응답이 202 또는 409(`ANSWER_ALREADY_SUBMITTED`)일 때 다음 질문으로 진행하라는 신호로 질문 순서(`seq`), 5.7로 제출한 답변 글(`content`, 꼬리질문 생성용)과 함께 전송한다 |
| `chat.input` | 화면 → 에이전트 | 채팅 입력이 0.8초(임시 값) 멈출 때마다 입력 칸의 글 전체(리액션용, 저장하지 않음) |
| `interview.frame` (바이트 스트림) | 화면 → 에이전트 | 화상 면접 동안 1초마다 눈을 가장 크게 뜬 카메라 사진(JPEG) 1장과 속성 `ageMs`. 에이전트는 답변 중에만 인상을 판단한다([AI 명세](AI-명세.md) 6.3·6.6) **[제안]** |

- 질문은 `questionId` 대신 `seq`로 가리킨다 **[제안]**. 에이전트가 질문을 말하는 순간에는 BE가 질문 행을 아직 만들지 않았기 때문이다
- 화상 면접 화면에 확정 글과 미확정 글을 함께 표시한다. 미확정 글은 최신 결과로 교체하고, 토큰별 시각은 에이전트에 보존한다. 현재 표시는 질문별 답변 저장과 연결되지 않는다
- 질문 음성이 실패하면(`failed`) 화면은 질문 글로 진행한다
- 화면은 `question`의 `started`부터 `ended`·`failed`까지 답변 시작을 잠근다

**화상 답변 끝 판단(에이전트)** 지원자가 답변하다가 7초(임시 값) 동안 아무 말이 없으면, [답변 완료]를 누른 것처럼 에이전트가 답변을 낸다.

- 7초는 마지막 말소리가 인식된 때부터 센다. 그 안에 다시 말하면 처음부터 센다
- 면접관이 말 끊기 안내를 말하는 동안에는 7초 계산을 멈추고, 안내가 끝난 시점부터 다시 계산한다([AI 명세](AI-명세.md) 6.2)
- 아직 한마디도 하지 않았으면 자동으로 내지 않는다. 빈 답변은 낼 수 없다
- 말을 시작하지 않은 채 60초(임시 값)가 지나면 에이전트가 `answer.state`로 알리고 화면이 안내한다. 그 뒤에도 에이전트는 같은 질문에서 계속 듣고 다음 질문으로 진행하지 않는다. 지원자가 말을 시작하면 7초 규칙으로 끝나고, 면접을 중단하려면 끝내기(5.8)를 사용한다
- 음성 인식이 실패한 뒤(`sttFailed`)에도 발화가 있었으면 [답변 완료]로 그때까지 인식된 글을 제출할 수 있다. 발화가 없었으면 60초 규칙이 그대로 적용된다([AI 명세](AI-명세.md) 6.5)
- 답변 중 지원자가 면접방에서 퇴장했다가 재입장하면(새로고침 등) 그 답변을 처음부터 다시 진행한다. 퇴장 전에 인식한 글은 폐기된다. 질문 음성 재생 중에 퇴장했으면 에이전트가 질문을 다시 말한다. 화면은 5.5로 질문 말풍선을 복구한다([AI 명세](AI-명세.md) 6.5)
- 답변 제출이 실패하면(`submitFailed`) 에이전트는 다음 질문으로 진행하지 않는다. 화면은 [다시 시도]로 `answer.submit`을 전송해 같은 답변을 다시 제출하게 하고, 제출에 성공하면(`submitted`) 다음 질문이 온다. 면접을 중단하려면 끝내기(5.8)를 사용하며, 이때 그 답변은 저장되지 않는다. 실패 상태에서 재입장해도 `submitFailed`를 다시 수신하므로 화면은 [다시 시도]를 다시 표시한다([AI 명세](AI-명세.md) 6.5)
- 답변 글이 저장할 수 있는 범위를 넘으면 에이전트는 그 답변을 제출하지 않고 다음 질문으로 진행한다. 이때 `submitted`는 수신하지 않으며, 그 답변은 저장되지 않는다([AI 명세](AI-명세.md) 6.2·6.5)
- 내기 전에 알릴지, 어떻게 알릴지는 화면에서 정한다

**리액션 시점** 화상은 문장이 끝날 때마다, 채팅은 `chat.input`을 받을 때마다 에이전트가 판단한다. 채팅은 말 끊기가 없다.

- 문장 끝: 음성 인식의 끝 감지(`<end>`)가 왔을 때, 그때까지 확정된 글이 종결어미(-다·-요·-까·-죠)로 끝나면 문장 끝이다. 글 끝의 마침표·물음표·느낌표·말줄임표와 공백은 빼고 보며, 쉼표로 끝나면 문장 끝이 아니다. 끝 감지가 온 응답에 미확정 토큰이 남아 있어도 문장 끝이 아니다. 문장 끝이 아니면 다음 끝 감지까지 이어 붙인다
- 말하기 지표의 문장 경계([AI 명세](AI-명세.md) 3장)는 이 중 종결어미 · 문장부호 규칙만 쓴다
- 에이전트가 리액션을 정하지 못하면(Jev 시간 초과·실패) `reaction: null`로 보내고, 화면은 리액션 없이 진행한다
- 화상에서 말하다 잠깐 쉴 때의 끄덕임은 화면이 직접 처리한다(메시지 없음)

**리액션 값** 면접관 방식에 따라 화면이 값을 쓰는 방법이 다르고, 에이전트는 면접관 방식을 몰라도 된다(B-8).

| 값 | 코드로 변형 (후보 2개) | 표정별 이미지 (후보 1개) |
|---|---|---|
| `state`: `idle` · `listening` · `thinking` · `speaking` | 자세·시선·입 움직임으로 표현 | 상태별 기본 이미지 |
| `expression`: `smile` · `frown` · `smirk` | `intensity`(세기)에 따라 연속 변형 | 표정별 이미지. `intensity` 무시 |
| `gesture`: `small_nod` · `nod` · `tilt` | 끄덕·갸웃 동작 | 무시 |
| `attitude`: `interest` · `trust` (0~1) | 리액션을 표시하는 `durationMs` 동안만 약하게 더하고, 지나면 기본 상태로 돌아감. 표정 리액션이면 표정은 리액션 값을 따름 | 무시 |
| `durationMs` | 순간 표정 유지 시간 | 이미지 표시 시간. 끝나면 `state` 이미지로 복귀 |

오리 면접관은 면접 자신감 향상이 목적이므로 `expression`은 `smile`, `gesture`는 `small_nod`·`nod`만 표시하고 `frown`·`smirk`·`tilt`는 표시하지 않는다. `attitude`도 부정적인 표정으로 반영하지 않는다.

오리 면접에서 화면은 답변 제출이 시작되면 호응 효과음을 한 번 재생한다. 채팅은 [답변 완료]로 5.7을 요청할 때, 화상 [답변 완료]는 `answer.submit` 응답이 `accepted: true`일 때, 화상 자동 제출은 `answer.state`(`autoSubmitted`)를 수신할 때다. [다시 시도]로 다시 제출할 때는 재생하지 않는다. 재생에 실패하면 효과음 없이 진행하고, 마지막 답변 뒤에는 효과음이 끝나기를 기다리지 않고 면접 끝내기(5.8)를 호출한다. 화면에서만 재생하므로 서버 녹화와 다시보기에 포함되지 않는다. 효과음은 CC BY-SA 4.0 녹음을 편집한 것이므로 화면의 출처 고지에 원본 출처를 표시한다.

리액션이 없을 때와 `durationMs`(2,400ms)가 지난 뒤 면접관은 기본 상태(듣는 중 `listening`, 무표정)다.

`state`를 에이전트가 보낼지 화면이 면접 단계로 정할지는 **[미정]**(B-8).

### 6. 녹화 · 결과 · 다시보기

**녹화** 화상 면접은 서버가 녹화한다. 녹화 동의는 가입 때 받는다(1.2 `RECORDING`). BE가 면접 시작(5.4) 때 LiveKit Egress로 트랙 녹화(지원자 영상·음성, 면접관 음성)를 시작하고 끝내기(5.8) 때 멈춘다. 면접이 끝나면 AI 분석 작업자가 트랙을 mp4 하나로 합친다. 화면은 카메라 영상을 H.264로 송출한다(합치기에서 영상을 다시 인코딩하지 않기 위해, AI 명세 7장). 화면은 녹화하거나 올리지 않는다(운영 배포 계획 4.3). 채팅 면접은 녹화하지 않는다.

#### 6.3 면접 결과

**화면 — S07 피드백 결과**

면접 1회 결과. 화면은 점수 대신 좋아요·보통·아쉬워요로 보여 준다. 반응 썸네일은 면접관별 고정 이미지라 API 필드가 없다. 채팅 면접은 같은 형식에 `mode: CHAT`, `speechMetrics: null`. 채팅도 기준 4개 점수가 모두 나온다. 전달력은 화상이면 답변 글과 말하기 지표로, 채팅이면 답변 글로 판단한다. 말하기 지표가 비어 있으면 그 지표는 빼고 판단한다. 시선 지표(`gazeRatio`)는 화면이 면접 내내 브라우저에서 잰 값을 면접 끝내기(5.8)로 받은 것이다. 받지 못했으면 null이다.

`grade`는 점수로 계산한다: 80 이상 `GOOD`, 60 이상 `NORMAL`, 그 외 `WEAK`. 6.4·7.1도 같다.

화면 표시: 기준 이름(`JOB_FIT` → 직무 적합성, `COVER_LETTER` → 자소서 검증, `LOGIC` → 논리성, `DELIVERY` → 전달력)과 `grade` 문구는 화면이 바꾼다. 질문별 피드백은 첫 번째 `WEAK`·`NORMAL` 질문만 펼친다.

- `summary`: 맨 위 한 줄 총평. 30자 이내이고, 없으면 null(화면은 그 줄을 그리지 않는다)

- **200**: `COMPLETED`
- **404 / SESSION_NOT_FOUND**
- **409 / RESULT_NOT_READY**: `ANALYZING` 또는 `FAILED`. 화면은 S06-1로
- **409 / NO_RESULT**: `ABORTED`
- **500 / INTERNAL_ERROR**: 완료 결과에 기준 4개 점수가 모두 있지 않음(저장이 불완전한 결과를 정상 평가로 내보내지 않음)

#### 6.4 다시보기

**화면 — S07-1 면접 다시보기**

화상은 녹화 영상과 질문별 시점(마커), 채팅은 같은 목록을 대화 기록으로 준다(`mode: CHAT`, `videoUrl: null`). 재생 중 자막은 재생 위치가 속한 질문(`questionCreatedAt` ≤ 위치 < 다음 질문)의 `answer`.

- `videoUrl`: 합친 mp4(`recordings/{면접 id}.mp4`)의 Presigned URL. 브라우저가 S3에서 바로 재생한다
- `questionCreatedAt`: 에이전트가 그 질문을 말하기 시작한 시각(녹화 시작 기준으로 마커 위치를 구한다)
- `videoStatus`: 녹화 영상 상태. `READY`(재생 가능) · `MERGING`(녹화 합치기 중) · `FAILED`(합치기 실패). 채팅이면 null이고, `READY`일 때만 `videoUrl`이 있다
- 화면은 `MERGING`이면 플레이어 자리에 녹화를 처리하는 중임을 안내하고 10초마다(임시 값) 6.4를 다시 조회한다. `FAILED`면 녹화를 불러오지 못했다고 안내한다. 두 경우 모두 질문 목록과 답변은 보여 준다
- 면접 종료 후 15분(임시 값)이 지나도 합치기 결과가 없으면 `FAILED`로 응답한다. 작업자 장애로 결과가 오지 않아도 `MERGING`에 계속 남지 않게 하기 위함이다
- `items[].timeline` **[제안]**: 다시보기 타임라인(화상만). 그 답변 동안의 면접 흐름 곡선과 평소보다 유난히 낮은 지점(체크포인트)이다. 계산은 [AI 명세](AI-명세.md) 4장 다시보기 타임라인. 채팅, 답하지 않은 질문, 타임라인을 만들지 못한 답변은 null
  - `points[]`: `at`(영상 위치, 초, 소수 셋째 자리) · `value`(그 면접 평균이 0인 표준화 값, 음수면 평소보다 아쉬움). 1초 간격
  - `checkpoints[]`: `at`(가장 낮은 지점) · `start` · `end`(이어진 낮은 구간, 영상 위치 초) · `value` · `reasons[]`(`metric`: `STABILITY`·`CONFIDENCE`·`EXPRESSION`·`EMOTION`·`LIKEABILITY`·`TRUST`·`TRAILING_OFF`·`FILLER`·`LONG_PAUSE`, `count`: 음성 이유의 횟수, 인상이면 null, `text`: 보완할 점)
  - 영상 위치 = (`answers.started_at` − 면접 `startedAt`) + 답변 기준 밀리초. 질문 마커(`questionCreatedAt`)와 같은 기준이다

- **200**: `COMPLETED`
- **404 / SESSION_NOT_FOUND**
- **409 / RESULT_NOT_READY** · **NO_RESULT**: 6.3과 같음

### 7. 성장 리뷰

저장하지 않고 조회 시 계산. 그날 = 면접의 한국 시간 시작 날짜. 그날 점수 = 그날 시작한 `COMPLETED` 면접들의 기준별 평균. 비교 대상 = 직전 연습일. `delta` = 그날 − 비교 대상(첫 연습일 null). 다음에 해볼 것(`nextActions`) = 그날 마지막으로 시작한 면접의 다음에 해볼 것 한 문장. 결과를 만들 때 그날 앞선 면접들의 내용까지 반영해 만든다(AI 명세 4장). 비었으면 그 앞 면접 것을 쓰고, 모두 비었으면 빈 배열이다.

#### 7.1 날짜별 성장 리뷰

**화면 — S08(오늘), S08-C(첫 면접), S09 달력 날짜, S02 최근 리뷰 [보기]**

화면 표시: S08 "오늘 나아진 점"은 `delta` > 0인 기준. 자소서 검증(`COVER_LETTER`)은 `delta` 없이 `comment`만(`grade`가 `GOOD`이면 "막힘 없이 통과"). S08-C는 `delta` 대신 `grade`로 기준점. 설문 유도(S08-B, 3·7·21일째)는 화면이 `streakOnDate`로 판단해 외부 구글폼을 연다.

- **200**: 그날 결과가 있음
- **400 / VALIDATION_FAILED**: 날짜 형식 오류 또는 0001-01-01~9999-12-31 밖
- **404 / GROWTH_REVIEW_NOT_FOUND**: 그날 연습 기록 또는 결과가 없음

#### 7.2 최근 성장 리뷰

**화면 — S02 홈 › 최근 성장 리뷰**(3.1에도 포함)

페이지 목록, 최근 날짜 순. 항목의 `criterion`·`delta`는 그날 가장 많이 오른 기준이다. 오른 기준이 없으면 `DELIVERY`·`0`("전달력 +0"), 첫 연습일이면 둘 다 null(화면은 배지를 숨긴다).

- **200**: 항상. 없으면 빈 배열

### 8. 관리자 · 공지 · 유지권

**관리자 인증** 관리 API(`/api/v1/admin/**`)는 회원 인증과 분리된 필터 체인이 맡는다. 8.1에서 받은 관리자 토큰(JWT HS256, 발급자 `a301-admin`, 회원 토큰과 같은 유효 시간)으로만 부르고, 회원 토큰(발급자 `a301`)은 받지 않는다(반대로 회원 API도 관리자 토큰을 받지 않는다). 삭제한 관리자의 토큰, 로그아웃(8.2)한 토큰은 401 `UNAUTHORIZED`, 만료는 401 `TOKEN_EXPIRED`. 재발급은 없어 만료되면 다시 로그인한다. 관리자 계정은 가입 API 없이 기동할 때 환경 변수(`ADMIN_LOGIN_ID`·`ADMIN_PASSWORD`·`ADMIN_NAME`)로 만든다. 8.8·8.9·8.13·8.14는 회원 API(회원 토큰)다.

관리 목록(8.3·8.10·8.12)은 `page` 0부터(기본 0), `size` 1~20(기본 10), 1장 페이지 목록 형식이다.

#### 8.1 관리자 로그인

**화면 — 관리 페이지 로그인**

- **200**: 로그인. `accessToken`·`expiresIn`(초)·`admin{ id, loginId, name }`
- **401 / ADMIN_LOGIN_FAILED**: 아이디 없음·비밀번호 틀림. 구분 없이 같은 문구

#### 8.2 관리자 로그아웃

- **204**: 이 토큰을 만료 시각까지 쓸 수 없게 한다

#### 8.3 공지 목록(관리)

삭제하지 않은 공지를 최근 작성 순으로 준다. 본문은 빼고 준다(8.5로 조회).

- **200**: 항상. 없으면 빈 목록

#### 8.4 공지 작성

`title`(최대 100자)·`content`·`startsAt` 필수, `endsAt`이 없으면 계속 보여 준다. 게시 시작 일시부터 사용자에게 보인다(8.8).

- **201**: 작성

#### 8.5 공지 조회

- **200**: 조회
- **404 / NOTICE_NOT_FOUND**: 없거나 삭제한 공지

#### 8.6 공지 수정

보낸 필드만 바꾼다. `endsAt`을 보내지 않으면 그대로, null로 보내면 게시 종료를 지워 계속 보여 준다. 제목·본문을 공백만으로 바꿀 수 없다.

- **200**: 수정. 응답은 8.5와 같음
- **404 / NOTICE_NOT_FOUND**: 없거나 삭제한 공지

#### 8.7 공지 삭제

soft delete. 관리 목록·8.8·8.9·8.15에서 빠진다.

- **204**: 삭제
- **404 / NOTICE_NOT_FOUND**: 없거나 이미 삭제한 공지

#### 8.8 공지 목록

게시 중인 공지(`startsAt` ≤ 지금 < `endsAt`, `endsAt`이 없으면 계속)를 최신순(게시 시작 일시 내림차순, 같으면 id 내림차순)으로 준다. 공지마다 이 회원의 확인(8.9) 여부 `read`를 함께 준다. 페이지 없이 `{ content }`.

- **200**: 항상. 없으면 빈 배열

#### 8.9 공지 확인

[확인]을 누른 공지를 기록한다. 8.8에서 그 공지는 `read: true`가 된다.

- **204**: 확인(이미 확인했어도 204)
- **404 / NOTICE_NOT_FOUND**: 없거나 삭제한 공지

#### 8.10 유지권 배포 목록

배포를 최근 등록 순으로 준다. `targetCount`는 지급한 배포면 실제로 받은 회원 수, 지급 전이면 지정 회원 수 또는 지금의 탈퇴하지 않은 회원 수.

- **200**: 항상. 없으면 빈 목록

#### 8.11 유지권 배포

배포 대상 `targetType`은 `ALL`(전체 회원) 또는 `USERS`(지정 회원, `userIds` 1명 이상). 지급 날짜(`grantDate`, 한국 시간)가 되면 매일 0시 작업이 그때의 대상 회원마다 유지권을 `quantity`개 만들고, 오늘이거나 지난 날짜면 등록하면서 바로 지급한다. 유지권은 `fillableDate` 하루만 연습한 날로 메울 수 있고, 지급 날짜 0시부터 2주 동안 쓸 수 있다. 전체 회원 배포는 지급할 때 공지를 함께 만든다(게시 기간 = 유효기간). 배포는 취소할 수 없다.

- **201**: 배포. 응답은 8.10 항목과 같음
- **400 / VALIDATION_FAILED**: `USERS`인데 `userIds` 없음, `ALL`인데 `userIds`를 보냄, `quantity` < 1 등
- **404 / USER_NOT_FOUND**: 없거나 탈퇴한 지정 회원

#### 8.12 회원 검색

지정 배포(8.11)·비밀번호 변경(9.10) 대상을 고를 때 쓴다. `keyword`(필수, 1~255자)가 이메일·닉네임에 들어간 탈퇴하지 않은 회원을 최근 가입 순으로 준다(대소문자 구분 없음).

- **200**: 항상. 없으면 빈 목록

#### 8.13 내 스트릭 유지권

**화면 — S09 마이페이지**

지금 쓸 수 있는 유지권(지급받았고 사용 전·만료 전)의 개수 `availableCount`와 유지권별 메울 수 있는 날짜·만료 일시를 만료가 빠른 순으로 준다.

- **200**: 항상. 없으면 `availableCount: 0`, 빈 배열

#### 8.14 유지권 사용

**화면 — S09 마이페이지**

고른 유지권(`freezeId`)의 메울 수 있는 날짜를 연습 기록에 넣어 연습한 날로 만든다. 스트릭(2.1·3.1·3.2)과 연습 달력(3.3)에 들어간다. 실패하면 유지권은 그대로 남는다.

- **200**: 메움. 메운 날짜 `practiceDate`, `freezeId`, 남은 `availableCount`, 메운 뒤의 `currentStreak`
- **404 / STREAK_FREEZE_NOT_FOUND**: 없거나 남의 유지권
- **409 / STREAK_FREEZE_NOT_AVAILABLE**: 이미 썼거나 기간이 지남
- **409 / STREAK_FREEZE_DATE_NOT_ALLOWED**: 그날 이미 연습 기록이 있음

#### 8.15 관리자 메트릭

관리 페이지 홈의 집계. 새 테이블 없이 기존 테이블을 조회 시 집계한다. 날짜는 한국 시간, 연습·면접은 면접 시작 날짜 기준이며 회원은 탈퇴하지 않은 회원만 센다(탈퇴 수·재방문 대상은 예외). 회원·연습(최근 7일, 재방문 D1·D3·D7)·면접(상태·방식·면접관별)·기준별 평균 점수·말하기 지표 평균·지원서·답변 대기 문의·유지권(지급·사용·만료)·게시 중인 공지별 확인 수를 준다.

- **200**: 항상

#### 8.16 관리자 일별 메트릭

매일 0시(한국 시간)에 남긴 전날 8.15 집계를 어제까지 최근 `days`일(1~365, 기본 30)만큼 날짜 오름차순으로 준다. 기록이 없는 날은 빠진다. 비율 대신 분자·분모를 준다.

- **200**: 항상
- **400 / VALIDATION_FAILED**: `days`가 1~365 밖

### 9. 문의

**문의 상태** `WAITING`(답변 대기) → 관리자 답변(9.8) `ANSWERED` → 이어서 쓰기(9.4) `WAITING`. 종료(9.5·9.9)하면 `CLOSED`이고 더 쓸 수 없다. 문의 id가 곧 문의번호다. 제목·본문은 암호화해 저장한다.

**회원 · 비회원** 9.1·9.3·9.4·9.5·9.11은 토큰 없이 부를 수 있다. 토큰을 보내면 회원 문의로 그 회원만 볼 수 있고, 보내지 않으면 비회원 문의로 `X-Inquiry-Password` 헤더(9.1에서 정한 조회 비밀번호)가 맞을 때만 볼 수 있다. 없는 문의·남의 문의·틀린 조회 비밀번호는 모두 404 `INQUIRY_NOT_FOUND`로 같게 답한다. 9.6~9.10은 관리자 토큰으로 부른다(8장).

목록(9.2·9.6)은 `page` 0부터(기본 0), `size` 1~20(기본 10), 최근 작성 순이며 메시지는 빼고 준다.

**사진** 질문(9.1·9.4)에 사진을 5장까지 붙인다. 9.11로 업로드 주소를 받아 S3에 올린 뒤 `attachmentKeys`에 `objectKey`를 보낸다. 첫 문의는 문의번호가 없고 비회원은 회원 id도 없어, 키를 누구에게 묶지 않는다. 대신 키는 받은 사람만 알고(추측할 수 없음) 1시간 안에 한 번만 쓸 수 있다. 메시지마다 `attachments`(붙인 순, 없으면 빈 목록)에 사진 id와 받는 주소(1시간)를 준다. 관리자 답변에는 사진을 붙이지 않는다.

#### 9.1 문의 작성

제목(최대 100자)과 첫 질문으로 문의를 남긴다(`WAITING`). 비회원은 `email`·`accessPassword`(4~20자)가 필수이고, 회원이 보낸 둘은 쓰지 않는다. 사진은 `attachmentKeys`(선택).

- **201**: 저장. 메시지는 첫 질문 하나
- **400 / VALIDATION_FAILED**: 비회원인데 `email`·`accessPassword` 없음, 형식·길이 오류
- **400 / VALIDATION_FAILED**(`attachmentKeys`): 발급되지 않았거나 이미 쓴 키, 같은 키를 두 번 보냄, 6장 이상
- **404 / FILE_NOT_FOUND**: 키는 맞지만 S3에 사진이 없음(키는 쓰지 않아 올린 뒤 다시 보낼 수 있다)

#### 9.2 내 문의 목록

회원만(토큰 필수).

- **200**: 항상. 없으면 빈 목록

#### 9.3 문의 조회

문의와 메시지(오래된 순)를 준다.

- **200**: 문의·메시지
- **404 / INQUIRY_NOT_FOUND**: 없는 문의, 남의 문의, 비회원 조회 비밀번호 틀림

#### 9.4 문의 이어서 쓰기

같은 문의에 질문을 하나 더 단다. 상태는 `WAITING`이 된다. 사진은 `attachmentKeys`(선택).

- **201**: 단 메시지
- **400 / VALIDATION_FAILED**(`attachmentKeys`): 발급되지 않았거나 이미 쓴 키, 같은 키를 두 번 보냄, 6장 이상
- **404 / INQUIRY_NOT_FOUND**: 9.3과 같음
- **404 / FILE_NOT_FOUND**: 키는 맞지만 S3에 사진이 없음(키는 쓰지 않아 올린 뒤 다시 보낼 수 있다)
- **409 / INQUIRY_CLOSED**: 종료한 문의(키는 쓰지 않는다)

#### 9.5 문의 종료

- **204**: 종료(이미 종료했어도 204)
- **404 / INQUIRY_NOT_FOUND**: 9.3과 같음

#### 9.6 문의 목록(관리)

회원·비회원 문의를 준다. `status`를 보내면 그 상태만 준다.

- **200**: 항상. 없으면 빈 목록

#### 9.7 문의 조회(관리)

문의와 메시지(오래된 순)를 준다. 비회원 문의면 `userId`·`nickname`이 null. 관리자 답변에는 `adminName`이 있다.

- **200**: 문의·메시지
- **404 / INQUIRY_NOT_FOUND**

#### 9.8 문의 답변

상태는 `ANSWERED`가 된다.

- **201**: 단 답변
- **404 / INQUIRY_NOT_FOUND**
- **409 / INQUIRY_CLOSED**: 종료한 문의

#### 9.9 문의 종료(관리)

- **204**: 종료(이미 종료했어도 204)
- **404 / INQUIRY_NOT_FOUND**

#### 9.10 회원 비밀번호 변경

관리자가 회원의 비밀번호를 바꾼다(문의로 요청받은 경우 등). 새 비밀번호 규칙은 2.3과 같다(8~64자, 영문·숫자 각 1자 이상). 변경 기록을 남기고 그 회원의 모든 리프레시 토큰을 폐기한다(모든 기기 로그아웃). `inquiryId`를 보내면 기록에 그 문의를 함께 남긴다. 회원 찾기는 8.12.

- **204**: 변경
- **400 / VALIDATION_FAILED**: 비밀번호 규칙 불일치
- **404 / USER_NOT_FOUND**: 없거나 탈퇴한 회원
- **404 / INQUIRY_NOT_FOUND**: 보낸 `inquiryId`의 문의가 없음
- **409 / PASSWORD_NOT_SET**: 비밀번호가 없는 소셜 회원(비밀번호 로그인 방법을 만들지 않는다)

#### 9.11 문의 사진 업로드 주소

토큰 없이 부를 수 있다. `files`에 사진마다 형식(JPG·PNG)과 크기(1바이트~5MB)를 1~5개 보내면 요청한 순서대로 `uploadUrl`·`objectKey`·`expiresAt`을 준다. 받은 `uploadUrl`로 말한 형식(Content-Type)과 크기의 파일을 PUT한다(`expiresAt`까지, 10분). `objectKey`는 1시간 안에 9.1·9.4에서 한 번만 쓸 수 있다.

- **200**: 사진마다 주소
- **400 / VALIDATION_FAILED**: 0장·6장 이상, 형식·크기 오류
